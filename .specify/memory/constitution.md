# Конституция проекта NOX

NOX — защищённый кросс-платформенный мессенджер (iOS, Android, Windows, Linux, macOS; Flutter) с end-to-end шифрованием; ориентир — Signal. Эта конституция фиксирует не подлежащие компромиссу принципы проекта. Она имеет приоритет над прочими практиками; работа над фичами (spec → plan → tasks → implement) проверяется на соответствие ей.

## Основные принципы

### I. Приватность и E2EE — без компромиссов

E2EE включено по умолчанию для всех сообщений и файлов; сервер не имеет доступа к содержимому, и это **нельзя отключить**. Метаданные на стороне сервера минимизируются. Идентичность анонимна — без телефона и e-mail; технический идентификатор и публичный label разделены. Клиентская аналитика, логи и крэш-репорты **никогда** не содержат PII, содержимого сообщений, идентификаторов пользователей или имён чатов; аналитика — строго opt-in (по умолчанию выключена). Logout полностью стирает идентификатор и локальные данные с устройства.

**Обоснование:** приватность — смысл продукта (Signal-like), а не фича; любое решение, ослабляющее её, отклоняется или выносится владельцу.

### II. Спецификации и дизайн-корпус — источник истины

Каждая фича проходит spec-driven цикл: spec → plan → tasks → implement. Авторитетная UI/UX-спека — `docs/design/spec/` (верхнеуровневый UI зафиксирован, экраны детализированы); продуктовые решения фиксируются там и в таблице решений, а не «на ходу». Реализация не должна расходиться со спекой; обнаруженное расхождение устраняется в том же change-set — либо код приводится к спеке, либо спека осознанно обновляется. Зафиксированный out-of-scope молча не расширяется.

**Обоснование:** проект ведётся документацией-вперёд; согласованность спеки и реализации — условие предсказуемости.

### III. Архитектурный блюпринт обязателен

`docs/blueprints/mobile/` — обязательный блюпринт для всего клиентского Flutter-кода (на всех пяти целевых платформах). В начале любой Flutter/клиентской задачи — сверяться с ним и строить по нему. Несущие инварианты: один Dart-пакет `nox_app`, Clean Architecture слоями-папками (`presentation → domain ← data`, `domain` ни от чего не зависит), BLoC = Freezed, единый injectable + get_it DI, `RepositoryResult<T>` повсюду, обязательный `LogRepository` (никаких сырых `print`), codegen-first, дизайн-токены вместо хардкода. Эти инварианты платформенно-нейтральны и применяются ко всем таргетам. Платформенно-специфичные части блюпринта (build/secrets, push, deep-links, secure storage) сейчас определены для iOS/Android; перед desktop-работой в такой подсистеме блюпринт расширяется на desktop либо для неё фиксируется явный документированный desktop-fallback. Дрейф реального кода от блюпринта чинится в том же change-set (правится код либо сам блюпринт).

**Обоснование:** единый источник истины по архитектуре держит код консистентным между сессиями и контрибьюторами.

### IV. Верность дизайн-системе

UI строится на Material Design 3, light + dark. Источник истины дизайн-токенов — `docs/design/system/nox-handoff/` (формат W3C DTCG); Dart-тема генерируется из них. В коде фич **нет** хардкод-цветов, отступов, типографики и overlay-стилей — только токены. Экраны следуют зафиксированным спекам и глобальным UI-конвенциям (уровни ошибок, форматы времени, иконки типов файлов, генерируемые аватары). Brand-fixed исключения (тёмный splash, светлая поверхность QR) соблюдаются вне зависимости от темы.

Ревизия владельца от 2026-07-26 (фича 020 / трекер-пункт F4): правило «превью содержимого файлов — только type-icon-чип» **больше не абсолютно**. Image-вложение с реальным локальным файлом рендерит инлайн-миниатюру с переходом в full-screen-просмотр; все прочие типы (и изображения без локального файла) остаются type-icon-чипом. Дальнейшее расширение превью на новые типы требует отдельного решения владельца.

**Обоснование:** единая токенизированная дизайн-система даёт консистентный UI и дешёвую темизацию.

### V. Языковая дисциплина

Документация и общение — **русский**; код, идентификаторы, имена файлов, shell-команды, сообщения коммитов, имена веток и заголовки PR — **английский**; UI-микрокопия — **английский**. Языки приложения — English + Українська (системный по умолчанию, fallback на English); русский в UI продукта не используется. Языки не смешиваются внутри одного артефакта.

**Обоснование:** русскоязычная команда ведёт прозу, но кодовая база и продукт остаются англоязычными и переносимыми.

### VI. Паритет платформ mobile ↔ desktop

NOX — ОДНО приложение для мобильных и десктопных таргетов, поэтому каждая UI/экранная задача проектируется и верифицируется для **обеих** платформенных семей; mobile-only-реализация не принимается. Responsive-экран выбирает ветку по ширине (`Constants.railBreakpoint`): narrow-ветка строится по `docs/design/system/nox-mobile-screens/`, wide-ветка — по `docs/design/system/nox-desktop-screens/`; каждый корпус авторитетен для своей ширины. Задача **не считается закрытой**, пока wide-ветка не сверена с desktop-корпусом и не залочена desktop-голденом — совпадения с мобильным дизайном недостаточно. Фича или действие, доступное в одной платформенной семье и отсутствующее в другой, — дефект паритета: он либо закрывается, либо расхождение фиксируется в спеке как намеренное с обоснованием.

**Обоснование:** ширина — единственный переключатель между двумя очень разными раскладками, и мобильная поверхность физически не может отрендерить desktop-ветку. Без явной нормы desktop-раскладка тихо деградирует (уже случалось: растянутая мобильная карточка вместо desktop-Login; исчезнувший разделитель rail↔list).

### VII. Контракт провода — закон (client-сервер)

Go-реализация client-сервера в `client_backend/` — управляемый компонент проекта наравне с Flutter-приложением. Контракт `docs/client-backend/protocol/contract-draft.md` — единственный источник истины для провода: каждая команда, событие, имя поля, код ошибки и правило берутся из него дословно; изменение, нужное на проводе, — **сначала правка контракта, затем код** (обе стороны — Go-сервер и клиент — в одном change-set'е с контрактом). Этапность обязательна: **этап 1 реализуется без аутентификации** — запрещено преждевременно добавлять проверки подписи, таблицы токенов и криптографию (этап 2 — по одобренному `docs/client-backend/architecture/authentication.md`). Инварианты `client_backend/CLAUDE.md` (единственный писатель БД, транзакционный outbox, глобальный `seq`, subscribe → replay → live, порядок shutdown) — норма: нарушение — дефект, даже если тесты зелёные. Скиллы `go-style`, `ws-rest-patterns`, `add-command`, `migrations` — обязательные референсы соответствующих работ; блюпринт — `docs/blueprints/client-backend/`.

**Обоснование:** протокол существует в двух реализациях (Go-сервер + Rust-ядро клиента) — без единого писаного контракта они разъедутся молча; а дисциплина этапов защищает от «дочинивания» безопасности до того, как решены блокирующие вопросы реестра (Q1, Q11).

## Технологический контекст и ограничения

- Стек — по блюпринту `docs/blueprints/mobile/`: Flutter, запиненный через FVM (`3.44.1`), Dart `>=3.12.0 <4.0.0`, длина строки 140, стоковый `flutter_lints`; freezed + json_serializable + injectable + flutter_gen за один прогон `build_runner`.
- Платформы — iOS, Android, Windows, Linux, macOS (две мобильные + три десктопные). Web — вне scope. Платформенно-специфичные нативные части (сборка/секреты, push, deep-links, secure storage) сейчас покрыты блюпринтом для iOS/Android; для desktop они либо расширяются в блюпринте, либо получают явный документированный fallback (см. Принцип III).
- **Рабочий режим текущей фазы (нормативно, обновлён 2026-08-28).** Бэкенд-решения приняты: сервер — **Go + встроенная SQLite** одним статическим бинарником (`client_backend/`), клиентское криптоядро — **Rust** (диктуется iOS-расширением уведомлений), транспорт — **wss на 443 с пиннингом ключа**, контракт — **v0** (`docs/client-backend/protocol/contract-draft.md`, этап 1 без аутентификации). Открытыми остаются граница E2EE (Q1) и публичный id автора (Q11) — реестр `docs/client-backend/open-questions.md`. Этап 1 сервера (022–024) завершён и смёржен; идёт **клиентский трек** 025–028 (`docs/client-backend/roadmap-client-track.md`): переходные требования §9 выполняются ДО DI-флипа 016, поэтому приложение по-прежнему работает на mock-репозиториях поверх РЕАЛЬНОЙ локальной Sembast-БД (cache-first по блюпринту `04`), а его data-слой уже приведён к контракту (`seq`, курсорная история, коды ошибок §2.1, персистентный курсор `since`). Транспорт подключается в 027, подмена источников — в 028.
- **Сетевой слой локализован в seam'е.** Репозитории зависят от per-feature `*RemoteDataSource`-интерфейсов, а не от конкретных реализаций; выбор mock↔real — это `Environment`-scoped регистрация в DI, а не переписывание репозитория. Обмен идёт через конверт `ResponseEntity<T>` + `EntityConverter`; авторизация и адрес API вынесены в `AppConfig.apiUrl` + auth-интерсептор с правилом `401 → forced logout`. Seam **подготовлен, но инертен** (`apiUrl == null`) — он оживает в 027/028. Подключение сервера обязано менять только регистрацию data source'ов; контракт репозитория, БД, мапперы и UI остаются.
- Любой план или код, касающийся сети, авторизации, формата конверта или эндпоинтов, **сверяется с контрактом v0** (`docs/client-backend/protocol/contract-draft.md`); чего в контракте нет — сначала вносится туда (Принцип VII), а заблокированное его §8 не реализуется вовсе.
- Состояние кодовой базы: в `develop` смёржены фичи 001–024 (клиент 001–021 плюс этап 1 сервера 022–024) и серия ад-хок-веток трекеров; продукт целиком работает на моках поверх реальной локальной БД. Verification-only остаётся только слайс `Item` (network-only) вместе с несмонтированными `AppShell`/`ItemListPage` из Feature-001.

## Рабочий процесс и гейты качества

- **Ветки:** `master` — только релизные коммиты; `develop` — рабочая ветка, от неё стартуют фиче-ветки. Рутинная работа идёт в `develop`.
- **Коммиты и мержи:** imperative-subject, атомарные, на английском. Коммиты и `--no-ff` мержи фиче-веток в `develop` выполняются **автономно**, как часть рабочего ритма задачи. **Push в удалённый репозиторий и merge pull request'ов на GitHub — только по явному запросу владельца**; автономно они не выполняются никогда.
- **Гейт кода (по блюпринту):** перед завершением задачи — codegen (один прогон) → форматирование только изменённых файлов (`-l 140`) → `flutter analyze` без ошибок → затронутые тесты. Сгенерированные файлы руками не правятся.
- **Локальный гейт обязателен, пока автозапуск CI на паузе.** GitHub Actions переведены в `workflow_dispatch`-only ради экономии минут, поэтому перед каждым коммитом, затрагивающим Dart-код или ассеты, локально запускаются `make gate` **и** `make golden-verify` — это единственное место, где ловится регрессия. Change-set из одной прозы/тулинга гейта не требует. Возврат к автоматическому CI снимает это требование.
- **Голдены — три категории.** (1) widget-голден на `App*Widget`; (2) page-mobile — на каждую страницу; (3) page-desktop — на каждую **продуктовую** страницу, на широкой поверхности. Продуктовая страница владеет **парой** baseline'ов (mobile + desktop): именно desktop-вариант закрывает `_wide`/master-detail/оконную ветку, недостижимую на мобильной поверхности (см. Принцип VI). Исключения из desktop-варианта: dev-only-страницы и brand-fixed splash. Голдены рендерятся и верифицируются локально (Apple Silicon / macOS) и исключены из CI по тегу.
- **Гейт Go-кода (client_backend/):** перед каждым коммитом, затрагивающим Go-код, — `gofmt -l .` (пустой вывод) → `go vet ./...` → `go test -race ./...`; `-race` обязателен, не опционален. Линтеры (`staticcheck` / `golangci-lint` v2) добавляются в гейт по мере подключения через `tool`-директивы.
- **Гейт фичи (spec-kit):** spec → (опц.) clarify → plan → tasks → (опц.) analyze/checklist → implement; на этапе plan выполняется Constitution Check против принципов I–VII.

## Управление

Эта конституция имеет приоритет над прочими практиками проекта. Поправки требуют документированного изменения, обновления версии по семантике (ниже) и явного одобрения владельца. Все планы и PR проверяются на соответствие принципам (Constitution Check — гейт этапа plan); отклонения фиксируются и обосновываются в разделе Complexity Tracking плана либо устраняются. Усложнение требует обоснования — проще лучше.

Версионирование конституции: **MAJOR** — несовместимое изменение, удаление или переопределение принципов; **MINOR** — добавление принципа/раздела или существенное расширение; **PATCH** — уточнения и формулировки без смены смысла.

Руководства времени разработки: `CLAUDE.md` (корневые правила репозитория), `docs/blueprints/mobile/` (архитектура Flutter-клиента), `client_backend/CLAUDE.md` + `docs/blueprints/client-backend/` (Go-сервер), `docs/client-backend/` (контракт, архитектура бэкенда, реестр вопросов), `docs/design/spec/` и `docs/design/system/` (UI и дизайн-система).
