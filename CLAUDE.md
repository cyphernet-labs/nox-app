## Project Overview

**NOX** — secure cross-platform messenger for iOS, Android, Windows, Linux and macOS (web out of scope), built in Flutter (Dart). Design anchor: **Signal**-like — end-to-end encrypted text and file exchange. Product name in UI, wordmarks and prose is `NOX` (all caps); the GitHub repo is `cyphernet-labs/nox-app` (lowercase, technically derived). Russian working name in materials: «Секюрный Мессенджер».

**Status — a complete, self-contained client product running entirely on mock repositories over a real local Sembast DB.** Spec Kit features **001–021** are implemented and merged to `develop` (001–011 via PR #1–#12; 012–021 as local `--no-ff` merges), plus ~20 ad-hoc tracker branches (`p1`–`p14`, `d4`/`d5`/`e1`/`e2`/`n5`/`f3`, `feat-edit-chat-name`, `design-visual-audit`). All 17 screens exist with real reactive business logic: watch-based chats list and thread, unread counters, optimistic send with an offline queue, a real cross-platform file picker, inline image thumbnails + full-screen viewer, real file Save, l10n EN+UK with live switching, persisted settings/session/identity. Goldens are locked in all three categories. Gate on `develop` after the 043 merge: `make gate` = 1622 tests green, `make golden-verify` = 324 goldens green, `go test -race ./...` = 8/8 packages; on `040-tor-app`, `make tor-test` = 29 cargo + 5 Dart tests green (041–043 change nothing Tor); on `045-tor-service-addresses`, `make gate` = 1787 tests green.

**The backend phase is under way (2026-08): server stage 1 is merged, the client track is running.** Server language **Go** + embedded **SQLite** (client crypto core will be **Rust** — dictated by the iOS notification extension), transport **`wss` for commands and `https` for file bytes over TLS 1.3, with the Eidolon check against the server key the pairing link carries on every connection** — the whole channel lives in the app's Rust module (feature 044; the port comes from the link, not from a fixed 443) — over **two paths**: directly at home, and away from home through the **Tor client built into the app** to the server's onion service (feature 040, Arti in a local Rust package `packages/nox_tor`; since 045 only when the person turns `Use Tor` on, on all five platforms, Linux included — the onion service itself is published by a tor that runs as a SEPARATE OS service on the server machine, and the server only stores its addresses), wire **contract v0** fixed and implemented end to end by the server (`docs/client-backend/protocol/contract-draft.md`, staged: stage 1 has no auth), the security model is the tracker `docs/client-backend/roadmap-security.md` (topics 1–4 implemented feature by feature, 044–049, in branch `security-rework`). Still open: E2EE boundary (Q1) and — **blocking since 2026-09-10** — the client-server↔relay protocol (Q13); see the register `docs/client-backend/open-questions.md`. **Q11 (public author id) closed 2026-09-02** by feature 030: `author_id` carries a server-minted `u_` id and the device is named by `device_key` (the `login_ref` derivation it originally used is gone since 032, replaced by the device key itself).

The Go server lives in `client_backend/` (own CLAUDE.md + `/go-style`, `/ws-rest-patterns`, `/add-command`, `/migrations` skills). The network seam is fully prepared but **inert**: per-feature `*RemoteDataSource` interfaces, an `Environment`-scoped mock↔real DI flip, `ResponseEntity` + `EntityConverter` wire DTOs, `AppConfig.apiUrl` + auth interceptor + `401 → forced logout`. Flutter `3.44.1` is FVM-pinned; one Dart package `nox_app` under `lib/`. The app boots into the real product flow (`AppRoot` → `Splash` → `Login`/`QR` → `Set username` → `TabBarShell`); the `Item` slice plus the Feature-001 `AppShell`/`ItemListPage` remain verification-only and **not mounted**.

⚠️ **Model revision (owner, 2026-09-10, feature 037): the client server is ONE person's machine.** Q4 was reopened and re-decided "one server per user", reversing the 2026-08-17 "server per circle". Feature **034 (person invite) is cancelled**, Q15 and Q17 are struck, Q13 is blocking, and Q18–Q23 are new. Read the product-model section below before reasoning about any screen or wire shape.

## Language Conventions

The team's working/documentation language is **Russian**; only the code sphere stays **English**. Split:

| Surface | Language |
|---|---|
| Chat with the user | Russian |
| Documentation prose in `docs/` | Russian |
| Spec Kit feature artifacts in `specs/` (`spec.md`, `plan.md`, `tasks.md`, `research.md`, `data-model.md`, `quickstart.md`, `contracts/`, `checklists/`) | Russian |
| Project `README.md` and other repo-root prose docs | Russian |
| Code: identifiers, file/dir names, **code comments**, shell commands | English |
| Git: **commit messages, PR titles & descriptions, branch names** | English (repo artifacts; branch names ASCII — Cyrillic breaks tooling/CI) |
| Spec Kit tool internals (`.specify/templates`, `.claude/skills/speckit-*`) and this `CLAUDE.md` | English (tooling / agent-instruction files) |
| **In-product UI microcopy** (labels, buttons, errors — even quoted inside Russian docs) | **English** |

Do not mix languages within one artifact: code, commit messages and PR text stay English even when referencing Russian docs; docs and specs stay Russian even when quoting English APIs / identifiers. UI nuance: the app's user-facing languages are **English + Ukrainian** (system default, fallback to English); **Russian is never a UI language** — only the language of internal docs, specs and chat. So UI strings stay English even inside otherwise-Russian design docs.

**Chat is always Russian — including command output.** Every assistant chat reply is Russian prose, including Spec Kit command reports (`/speckit-analyze` findings, headings and tables; `/speckit-plan|tasks|implement` completion summaries; coverage/severity tables; "next steps") and interactive-tool prompts (`AskUserQuestion` question text/options/headers). A skill or template that presents English headings does **not** make the reply English — the template language never sets the chat language. Only code identifiers, file paths, shell commands, severity tokens (CRITICAL/HIGH/…) and canonical UI microcopy (`Sign in`, `Your ID`, screen IDs like `5.1`) stay English inline. Known recurring drift: after editing English code/specs the chat silently continues in English — re-check every message is Russian before sending.

## NOX product model — facts that span the design spec

NOX-specific decisions to know before reasoning about any screen or data model; each is synthesized from `docs/design/spec/overview.md` (+ `screens/`):

- **One person's own space, not an open shared one and not Signal 1:1 (owner revision, 2026-09-10, feature 037).** The client server belongs to ONE person and serves only the devices they own; servers of different people never talk to each other. All of that person's chats are visible on all of their devices and nowhere else. Everything between different people goes through a **relay whose protocol does not exist yet** (Q13, now blocking) and is out of scope. No permissions — there is nobody to tell apart; there is no "join" flow — there is nobody to join; chats are never deleted. Signal mechanics tied to a fixed 1:1 audience (delivered/read receipts, membership, per-chat subscriptions) are deliberately dropped. **The earlier "open shared space, all chats visible to everyone" model is REVOKED** — anyone reasoning from it will build the wrong product. Its single visible seam is a **permanently disabled** `Invite a person` action in the thread header (5.2) and in the new `People` section of the chat card (5.4), captioned `Available in a future version`.
- **Two-layer identity.** A technical anonymous **identifier** (shown as `Your ID`, a long key-like string entered by paste or QR — no phone/email) plus a public **label** (display name). Server assigns `User<random>` at first login (a name always exists); label is ≤32 chars, charset `[A-Za-z0-9._-]`. Label uniqueness is **not checked and no longer meaningful** (owner, 2026-09-02; reinforced by 037): the server neither checks nor reports it, nothing in the app asks, and on a one-person server there is nobody to collide with — naming people across servers is a relay question (Q18). Do not add a client-side uniqueness check for a person's name. One identity per device; switching = Logout (full local wipe) + re-login.
- **Message status is local-only:** `sent` (accepted by server) + `pending`/`error`; **no delivered/read** — there is nobody to deliver to: the message is accepted by the person's OWN server, not by another party. The question returns with the relay.
- **Shell:** 3-item bottom bar — `Chats` tab, central docked **`+`** FAB (create chat, visible on both tabs), `Settings` tab. **No profile screen** — profile-like items live in Settings.
- **Theming:** Material Design 3, light + dark via `ColorScheme` (default system), seed = teal extracted from the logo. Two brand-fixed exceptions independent of theme: splash background always dark, QR surface always light.
- **Chat name:** unique **within this server** (a chat is created locally and there is no shared namespace), ≤64 chars, unrestricted charset; the server is the authority on availability. Since 041 a chat is made on the device first and the server's word on the name comes when the outbox creates it there: a name taken by then marks the chat for a rename, done on the device. Chat avatars are generated (initials + hash-picked color from a fixed palette).
- Explicitly **out of scope** this iteration: calls, reactions/stickers, voice messages, stories, mentions/threads, profile screen, moderation/permissions/owners, multi-account, delivered/read, per-chat mute/pin, Support section, **and everything between different people** — a real chat roster, joining, leaving, invitations (all of it waits on the relay, Q13). The `People` section in 5.4 is a VIEW of the one person on this server, deliberately not a roster. **File previews are partly IN scope since 2026-07-26** (owner revision, feature 020 / tracker item F4): image attachments with a real local file render an inline thumbnail + tap-to-full-screen. ⚠️ **Widened again 2026-09-20 (owner):** an image whose bytes have NOT arrived is no longer a chip — it takes the thumbnail's box with a picture glyph and a spinner, because the prefetch was already running and said nothing, so people tapped and started a SECOND download of the same bytes. Two predicates keep the states apart — `AppImageAttachmentWidget.wouldRender` (this WILL be a thumbnail once the bytes land) and `canRender` (the file is on disk); a format that never becomes a thumbnail stays a chip in both. **Video plays in-app on 5.3**, and 5.3 now also SHOWS an image instead of describing it with a glyph. The player reads a LOCAL FILE only: a native player uses its own HTTP stack, so streaming would reach the server around the module's channel — around the Eidolon check — and the server answers nothing before that check anyway. ⚠️ **Playback is iOS/Android/macOS only** (`VideoPlaybackCapability`, same predicate as `QrScannerCapability`): `video_player` has no Windows or Linux implementation, and `media_kit` would add libmpv binaries plus exactly the two platforms nobody here can verify. On those two, 5.3 is what it always was. Every other type keeps the type-icon chip. `overview.md` still carries the un-revised "type-icon chips only" sentence in its out-of-scope list; the revision wins.

## Flutter architecture blueprint (`docs/blueprints/mobile/`) — unified & adopted

The adopted architecture for NOX's Flutter app (package `nox_app`, single app id `com.cyphernetlabs.noxapp` on all five targets — per-flavor native ids/signing are deferred, the flavor is a Dart-define only). Load-bearing decisions: **one Dart package**, Clean Architecture layers as folders (`presentation → domain ← data`, `domain` imports nothing); **BLoC = Freezed** (`@freezed` State/Event, thin `BaseBloc`, computed logic in extension getters or class-body getters, no `*.g.dart` on BLoC types); single **injectable + get_it** DI (`configureDependencies(env)`); `RepositoryResult<T>` (success XOR error) everywhere; mandatory `LogRepository` (no raw `print`); **Sembast** cache-first reactive repositories; `infinite_scroll_pagination` v5 (`PagingState`-in-bloc); design-token-only UI; FVM-pinned Flutter `3.44.1`, line length 140, stock `flutter_lints`; codegen-first (freezed + json_serializable + injectable + flutter_gen, one `build_runner` run).

> **Rule: at the start of any Flutter/client task, consult the relevant blueprint doc(s) (`README.md` index → layer docs `00`–`17`) and build to them.** If real code drifts from the blueprint, bring the blueprint back to a correct state in the same change-set. **Caveat:** the blueprints were reconciled with contract v0 in feature 025 (pagination, envelope, error codes, the file chain), but the parts that depend on **stage-2 authentication**, push delivery and deep links in `13`/`14`/`15` are still explicit placeholders — those questions are genuinely open.

### Implementation notes — data layer & DI (real `lib/`, beyond the blueprint prose)

- **File chain (028).** `FileRemoteDataSource` splits the two transports the contract splits: `file.uploadBegin`/`file.downloadBegin` go over the socket, the BYTES over HTTP through `ApiClient` — the first real consumer of Dio in the project (`initBase()` had never been called from app code before). `FileRepositoryImpl` returns the server's `fileId` **only after the bytes are confirmed**, spends one automatic second chance on a rejected pass itself (a pass is one-shot and 10-minute-lived, and the contract calls a refusal routine), and caches downloads under `getApplicationCacheDirectory()/nox_attachments/<fileId>.<ext>`. Its failure classification is deliberately NOT the drain's: a `404` on `/files/<token>` means "get a new pass", while the general Dio mapper would make it `notFound` → terminal → a message killed for good. `OutboxEntity.fileId` is the restart guard; `AttachmentPrefetchService` fetches received IMAGES only (the design corpus draws a thumbnail only for an image with a local path) and keys an `_inFlight` set so writing the path cannot re-trigger the watch that led there. `ChatThreadBloc` calls it on every load AND every live refresh and again when the channel comes back - a picture that arrived while the thread was open used to stay a spinning placeholder, because only a load called it. Those calls only QUEUE: one worker fetches one picture at a time (a walker per call grew to nine downloads at once through Tor), a picture the automation gave up on waits for `retryNow` (the channel's return) rather than the next refresh, and `FileRepositoryImpl.download` runs ONE transfer per file id - the prefetch and the file view (5.3) used to share one `.part` file, and the first could rename the second's still-growing file into place. **Bytes in transit are one in-memory map, `AttachmentTransferService`** (domain service, data impl): the queue reports an `upload` under the `client_message_id` for the WHOLE send (until the server accepts the message, not just the last byte), the prefetch a `download` under the stored message id; the thread projects THIS chat's entries into `Initialized.transfers`, by `AttachmentTransfer.chatId` and not by the messages on screen (the whole map redrew the open thread for every percent of any chat's transfer, and a filter by on-screen ids missed a send begun before the thread opened - there is no progress tick before the first byte) and the bubble draws a ring on a contrasting `inverseSurface` disc over a picture being sent, `Sending… 45%` over a bar in a chip, and a filling ring in a received picture's placeholder. It publishes only when the whole percent changes, because every Dio callback would otherwise redraw the thread. `FileViewPage` owns a `FileViewBloc` since this phase — blueprint 05 ends the BLoC-less carve-out with the client track by name.
- **Resumable files (043).** A transfer goes on from where it stopped, both ways, and only silence ends one - through Tor 100 MiB take tens of minutes, and the old 15-minute server deadline cut everything slower than ~0.93 Mbit/s. **Upload:** `file.uploadBegin` takes an optional `file_id` (continue) and answers `received` - the bytes the server holds safely, whose PRESENCE is the feature flag (an older server skips the field and the whole file goes); `PUT` carries the remainder from `received`, an empty one completes. The handle `UnfinishedUpload {fileId, sourceSize, sourceModifiedAt}` rides on the outbox record (`noteUpload`, written BEFORE the first byte so a restart continues); the source fingerprint is checked before AND after every `PUT` and compared as an INSTANT to the millisecond (the record keeps ms UTC; `DateTime ==` also compares the zone and anything below a millisecond); a server that lost the upload (`not_found`) gets a new one without an error; a terminal failure forgets the handle, an exhausted ladder keeps it. **The queue uploads from its OWN COPY** (owner, after the review): `OutboxRepository.enqueue` copies the picked file into `<Application Support>/nox_outbox/<client_message_id>/<original name>` (`OutboxCopies`; the name is kept because the upload declares the name of the file it reads) and the entry names the copy - the macOS sandbox lets the app read a picked file only while the process that picked it lives, the iOS picker's copy sits in a tmp dir the system may empty, and originals get moved or changed. Before `message.send`, `OutboxRepository.keepCopy` moves the copy to `FileRepository.cachePathFor(fileId)` (where a download would land) and the message is stored naming it; `remove`/`removeForChat`/`clean` take the copies with them. ONLY a folder named by the entry's own key is ever moved or deleted - an entry from an older build names the person's own file; the copy's path is re-rooted on every run (`find`/`pending`) because iOS moves the app container on every update. A copy that cannot be made leaves the entry naming the picked file. A source that exists but will not OPEN is `notFound` before anything is declared (the fingerprint includes an open probe - the sandbox still lets its size be read), and `putBytes` reports a read that fails mid-body as `sourceUnreadable` (→ `notFound`). Uploads now spend the same 10-refusal cap as `message.send` (`RetryLadder`, one ladder for the app) - without it an endpoint refusing every upload held the whole queue; a 5xx, a status §7 does not name and a `200` without a size are `FileTransferFailure.serverError` → `internal`, COUNTED (only `408`/`409` are a broken link). **Discarding** a message mid-upload goes through `OutboxService.discard` (the thread bloc's only discard path): the record goes first, then its upload is cancelled (`TransferCancellation`, threaded through `FileRepository.upload` → `putBytes`), the pass moves straight on, and a flush is asked for so a paused head stops holding the rest. **Download:** the part lives in `<cache>.part` with the server's `Last-Modified` in `.part.tag` (written BEFORE the first byte of a `200`); the next attempt sends `Range` + `If-Range`; `416` and a misplaced range drop the part; complete only at the size the message names. `AttachmentDownloadService` (domain; impl in `data/sync`) owns the retries - one download per file, joined with the last share at once, woken when the channel comes back, records the path itself (a store that refuses the write is logged, never fails the download) so a download begun on 5.3 survives the screen, which only detaches its listener on close (`stopListening`). Before every cache wipe (logout, world change) the prefetch is reset FIRST (its worker would otherwise start the old world's next picture), then `reset()` - bounded at 5 s, refusing `fetch()` while it runs - then the cache wipe in its OWN `try`; `FileRepositoryImpl._epoch` (raised by `cancelTransfers()`/`clean()`) stops a download caught between two steps from writing after a reset. The part is written with `RandomAccessFile`, each chunk awaited, and any disk error `abandon()`s the transfer (an un-abandoned one held its connection and transfer token). **Time:** the client's stall watch is 45 s (Dio's `sendTimeout` bounds the WHOLE body, and its download clock starts only at the first body chunk - so our watch is armed with the headers); after the last byte is handed over a PUT waits up to 3 min for the answer, because the buffers along a slow path still hold the tail; and a transfer through the onion service gets the socket's 45 s connect budget (`WebSocketChannelFactory.onionConnectTimeout`), not Dio's 30 s - a fresh onion stream sometimes refetches the descriptor, and the live probe caught 30 s cutting transfers the socket would have let through. `ApiClient` keeps a registry of transfers (`beginTransfer`/`endTransfer`/`cancelTransfers`) and `initBase` with a NEW address raises `pathGeneration`, then ends every transfer on the old path; a transfer that ends under another generation than it began with is `FileTransferFailure.pathChanged`, and the repository continues it AT ONCE within the same attempt (≤5 in a row, no pause, nothing counted) - as a plain break it reached the queue after the `live` edge that lifts pauses, and waited up to ~36 s on a healthy path. Server side: `<id>.synced` beside the part (durable length; fsync first, record second), one writer per file (`writers.go`, the fourth infrastructure lock; `stallReader`'s own mutex is per request and shares nothing), per-read/per-write deadlines of 60 s. **Known boundary:** a COMPLETED upload never bound to a message is still swept after a day at a server restart, and `message.send` naming it answers `invalid_request` (terminal) - telling that apart needs a new code on `message.send`.
- **Live-path truth (031).** Three decisions that used to be taken locally now come from where they belong. **Onboarding** is decided by the server: the greeting carries `identity.created`, and sign-in stores the identifier, greets, takes the outcome, then moves navigation — in that order, because storing first is what makes the greeting state a person rather than going out anonymously. A handshake that does not answer **rolls the session back**; a stored identifier with no settled outcome would strand the next launch in onboarding. The local flag is **monotonic**: a greeting may declare onboarding done and may never send someone back to it, which is what saves a device left on the naming screen while the same person named themselves elsewhere. `LiveIdentityHandshake` owns the wait and its own timer — an outer `.timeout()` does not cancel its source, so the `finally` never runs and sign-in wedges for the process. It also captures `NoxSocketClient.greetingGeneration` BEFORE restarting and accepts only an answer above it: `phase` is a `BehaviorSubject`, so a fresh listener is handed the CURRENT phase, and the app's own boot greeting is anonymous with `created: true` — reading that would route every returning person into onboarding. - **The secure channel (044).** Every connection — the `wss` socket and every `https` transfer — is opened by the Rust module (`packages/nox_tor`, `nox_chan_*`): TCP or an Arti stream → TLS 1.3 (rustls on ring; ANY certificate, the handshake signature checked; no SNI, no resumption, no early data) → the Eidolon exchange over the RFC 9266 exporter (the device shows its Ed25519 key first, the server answers with its own, and the channel opens only if that is the key the pairing link named). - **Outgoing queue (027).** `OutboxDao` owns a Sembast store `outbox` whose **record key IS the `client_message_id`**, so re-enqueuing the same send cannot create a second row. Order comes from an `ordinal` assigned inside the enqueue transaction — never from `createdAt`, which goldens freeze. `OutboxService` (`lib/data/sync/outbox_service.dart`) is the **only** thing in the app that calls `sendMessage`: passes are serialised on a `Future _queue`, run strictly in `ordinal` order one at a time, and delete a record only **after** the repository persisted the message. Failures are classified — `connection`/`rateLimited`/`internal`/unrecognised retry with `min(30s, 1s × 2^(attempts−1))` ±20% jitter; everything else is terminal (`error`) and the pass continues past it. The record carries **two** counters: `attempts` (any failure, drives the pause) and `refusals` (the server actually answered, and only this one may spend the 10-retry cap — counting a dead channel would strand a healthy message on a flaky link). A manual retry resets both. The pause is keyed to the entry it is waiting out, so discarding or settling that entry releases the queue. `ChatThreadBloc.outgoing` is a **projection** of `watchQueue(chatId:)`, not state it owns; it re-reads the cache only on a tick where the queue SHRANK (the one tick where a message was just persisted). Wire DTOs (`lib/data/entity/chat/wire/`, explicit snake_case `@JsonKey`) are **distinct** from the Sembast storage entities (`ChatEntity`/`MessageEntity`); `*WireMapper` converts wire↔domain, `*Mapper` converts storage↔domain. Repositories unwrap through `BaseRepositoryHelper.unwrapEnvelope` (025): a typed `error {code, message}` becomes `RepositoryException.fromWireCode(code)` (unknown code → `internal`) and passes through `execute()` unchanged via its `on BaseRepositoryException` branch; a `data == null` success still throws `StateError` → `unknown`. `MessageAttachment.localPath` is persisted but deliberately absent from the wire DTO, so `sendMessage` re-attaches it onto the server echo before persisting.
- **Auth seam (019): the URL landed with the transport in 026; the token is still plumbing** (its writer arrives with stage-2 auth). Since 036 `initBase` takes a REQUIRED address and is called only by `LiveSessionStarter`, with the paired one — `main.dart` no longer calls it and `AppConfig.apiUrl` is no longer a source of a live address. Commands still travel the socket; Dio carries only blobs, over `ChannelHttpClient.transferClient`. `AuthInterceptor` adds `Authorization: Bearer <token>` from `AppConfigRepository.getUserAuthIdToken()` (secure key `auth_id_token`, **no writer exists yet**) and always re-propagates errors; since 044 a 401 is a failed transfer, NOT a logout — the forced logout has one owner: `unauthenticated` to `session.hello` and the `device.revoked` event.
- **Error semantics.** `BaseRepositoryHelper.execute` catches everything, always logs via `logRepository`, and has **four** branches: `BaseRepositoryException` is re-emitted unchanged (this is how wire codes survive, 025), `SocketUnavailableException` → `connection` (026 — without it a dead channel lands in the catch-all as `unknown` and every cache fallback guarded on `connection` is unreachable code), `DioException` is mapped (timeouts/`connectionError` → `connection`; 401 → `unauthenticated`; 403 → `authentication`; 404 → `notFound`; else `internal`), everything else → `RepositoryException.unknown`. The never-throws guarantee covers **only** methods wrapped in `execute` (those returning `RepositoryResult<T>`); `Future<void>` and `Stream` members bypass it and propagate raw — which is why `ChatRepositoryImpl.createChat` wraps `seedCreatedChat` in its own try/catch and `watchChats()` can surface a failed seed as a stream error. `execute` takes an untyped `Function`, so a wrong-typed return is a runtime `TypeError` silently downgraded to `unknown`.
- **Session/identity storage.** Identifier → `flutter_secure_storage` (`session.identifier`); `session.onboarding_complete` + `session.label` → `SharedPreferences`; nothing session-related in Sembast. The server key from the link is `session.server_key` (044; the old `session.server_fingerprint` is swept). The secure store also holds `session.server_addresses` (`ConnectionStorage`; JSON since 045: the server's `direct` list, `public` and `onion` address, the person's `manual_address`/`manual_onion`, `use_tor`, `last_good`, `via_tor`) — secure rather than prefs because an onion address lets anyone who has it ask the Tor network whether the server is online. No Tor access key exists any more: `sweepLegacyKeys` deletes `session.access_key` and `session.access_key_registered` that 040–044 builds wrote, each with the options it was written under. `clear()` removes all of them; `discardSignIn()` all but the device key (`session.device_secret`, it names the install); `saveServer()` starts by removing what an earlier server said about itself. `saveIdentifier` writes prefs **first** and the secure identifier **last**, because `readSession()` keys presence on the identifier.
- **Unified identity (015).** `resolveIdentity(SessionModel?)` (`lib/general/identity/identity_resolver.dart`) is the single pure resolver of own-id/label (fallbacks `IdentityMockData.fallbackOwnId` / `Constants.defaultUserLabel` = `User7421`); it feeds own-message authorship, the Settings account row and the chat thread. `SessionRepository.watchLabel()` returns a **fresh single-subscription stream per call** (an `async*` generator over an internal broadcast controller): it yields the cached label on listen, then each rename, then `null` on logout. Call it once per consumer — re-listening to the same instance throws. Two live subscribers since 037: `TabBarShell` (feeding both account avatars) and `ChatCardBloc` (the People row of 5.4). `MessageRepositoryImpl` **refuses to seed** a chat's mock history when `readSession()` errors, because seeded own-author rows are permanent for the life of the local DB.
- **Logout wipe.** `AuthRepositoryImpl.logout({forced})` gates on a successful `SessionRepository.clear()` (secure `deleteAll` + remove the two prefs keys), stops the live channel and then `TorService.wipe()` (Tor stopped, its state and cache directories deleted - FR-018), then wipes — **in this order** — the sync cursor (`SyncRepository.clear()`, first so a crash can never leave a stale high `since` over an emptied store), then the Sembast chats + messages stores, then the outbox, then re-derives app state. `LiveSessionStarter.stop()` and `OutboxService.stop()` both run BEFORE the wipe so nothing in flight repopulates a store being emptied. It does **not** delete the database file; settings prefs (`settings.theme_mode`, `settings.notifications_enabled`, `ui_language`) survive logout.
- **App state.** `AppStateRepositoryImpl` is an rxdart `BehaviorSubject` projection with no DAO; on a session **read** error it preserves the last emitted state (only a cold start falls back to `unauthorized`), so a transient keychain failure never logs a valid user out.
- **DI bootstrap order (enforced in `lib/main.dart`):** `configureDependencies(env)` → `getIt.allReady()` → `getIt<AppConfigRepository>().initialize(flavorType:)`. `RegisterModule` provides `FlutterSecureStorage` (macOS pinned to the legacy keychain via `MacOsOptions(usesDataProtectionKeychain: false)`), `@preResolve`d `SharedPreferences`, and an env-keyed `@Named('isTestEnvironment')` bool. Cross-cutting singletons are reached via top-level getters in `lib/di/global_aliases.dart` — `logRepository`, `itemRepository`, `settingsRepository`, `chatRepository`, `appStateRepository`, `authRepository`, `sessionRepository`, `cameraPermissionService`, `notificationPermissionService`, `qrImageDecodeService` — while BLoCs typically resolve their own dependencies with `getIt<X>()` field initializers. Neither path uses constructor injection. Two abstractions have a genuinely env-split binding: `AppDatabase` and `ConnectivityService` (real `connectivity_plus` for `[dev, prod]`, always-online mock for `[test]`, because the plugin needs a platform channel) — any new plugin-backed service must follow the same split or widget/BLoC tests break.
- **`AppClock.now()`** (`lib/general/app_clock.dart`) is the app-wide clock seam used by the mock generators and by repository writes; tests and goldens pin it with `AppClock.freeze()` / `reset()`.

### Implementation notes — presentation layer

- **No router.** `MaterialApp` sets only `home: const SplashPage()`; there is no route table, no `onGenerateRoute`, no router package. Every navigable page exposes `static Route<T> route()` returning a `MaterialPageRoute` with a named `RouteSettings`, and callers push the tear-off; 12 of 21 also expose a `routeDemo()` gallery variant. Adding a screen = adding its `route()` plus, for the gallery, a `_ScreenEntry` row in `ScreensGalleryPage`.
- **Navigation spine.** `AppRoot` swaps the **root** route from `AppRootState.appliedAppState.state`: `unauthorized` → `LoginPage`, `registrationPending` → `SetUsernamePage`, `authorized` → `TabBarShell`, `init` → stay on Splash. The **first** transition uses `pushReplacement`, every later one `pushAndRemoveUntil(route, (_) => false)` — no auth boundary is back-navigable. The first resolved state is deliberately **held**: `AppRootBloc._land` only records it, and `SplashPage` dispatches `ApplyAppState` once its reveal animation finishes and `isReady` is true. `AppRoot` also owns two app-wide transient notices (session-expired snackbar; settings-save-error snackbar driven by the `settingsSaveErrorTick` counter).
- **Responsive convention.** `LayoutBuilder` + `constraints.maxWidth >= Constants.railBreakpoint` (840) selecting `_narrow`/`_mobile` vs `_wide`/`_desktop`. A page hosted as a **shell tab** must instead honour `forceWide` (`widget.forceWide ?? (constraints.maxWidth >= railBreakpoint)`) — the rail narrows the body, so self-measuring lands on the wrong branch in the 840…rail band. Callback-side helpers that cannot use a `LayoutBuilder` (`showAdaptiveLightbox`, `showChatCard`, `ChatsListPage._onOpenCreated`) branch on `MediaQuery` width against the same constant.
- **Desktop replaces push with selection.** 5.1 dispatches `ChatsListEvent.chatSelected(id)` when wide (mobile pushes `ChatThreadPage.route`); 7.1's menu pane sets `_selected` via `setState` (mobile pushes the leaf `*Page.route()`). `AppListDetailWidget` is the shared two-pane container and never touches the Navigator. Overlays follow the same rule: chat card → right side-sheet vs push; file view / image viewer → `showAdaptiveLightbox` (Dialog vs push); create chat → `CreateChatPage.showAsDialog` vs `route()`.
- **The live shell is `TabBarShell`** (`lib/presentation/widgets/shell/tab_bar_shell_widget.dart`). Narrow: `AppBottomBarWidget` + center-docked `AppCreateFabWidget`. Wide: `AppWindowTitlebarWidget` (subtitle tracks the active tab) over `AppNavigationRailWidget` — a **hand-built 80dp rail, explicitly NOT Material's `NavigationRail`**: painted right hairline, two `Semantics(button, selected)` destination cells that FILL when selected (no pill around the glyph), `Spacer()`, then `_NavRailAccountAvatar`. **No create FAB** — since 2026-09-20 the `+` is an icon button in the Chats pane header, so the wide branch has no create affordance while Settings is open. Both tabs stay mounted in a `Stack` of `IgnorePointer` + `AnimatedOpacity` so tab state survives switching. The shell holds a live `sessionRepository.watchLabel()` subscription feeding **both** account avatars (desktop rail + the mobile Chats app-bar action), and owns three `ValueNotifier` signals into the tabs: `_chatsScrollToTop`, `_settingsJumpToAccount`, `_chatsOpenCreated`.
- **Reactive data flow (014/015).** `ChatsListBloc` and `ChatThreadBloc` each hold a `watchChats()` / `watchMessages(chatId)` subscription with `.skip(1).debounceTime(100ms)`; the stream **value is ignored** — a tick dispatches a `refresh: true` load that re-reads through `getChats`/`getMessages`, so the repository query stays the single projection path and query/selection/scroll/optimistic `outgoing` survive. The re-read differs by path (025): the chats list walks pages 1..`loadedPageCount`; the thread does ONE tail read of `items.length + pageSize` (the cursor has no page numbers). Both also watch `ConnectionStatusService.watchStatus()` for the offline banner (since 040; the session phase before that); the thread additionally watches the session phase, which holds its sends until the channel is current again. `WatchChat` (`widgets/chat/watch_chat.dart`) is the single seam for live single-chat data (thread title, card title/header, desktop thread header, and since 041 the thread's creation notice) so a rename propagates everywhere without a reload. It builds a NEW stream on every build, so it must sit OUTSIDE a bloc's builder: the thread opens ONE watch above its `BlocConsumer` - inside it, every state tick (a transfer's every percent among them) re-subscribed the row.
- **Chats not on the server yet (041).** `AppChatItemWidget.creation`: waiting → `schedule` in place of the time (screen-reader name `Waiting to be created`, preview kept); `nameTaken` / `failed` → `error` glyph in place of the time and `Name already taken` / `Couldn't create` in place of the preview, in the error colour, the glyph excluded from semantics so the merged row reads the refusal once. `AppThreadViewWidget._banner` shows ONE notice: wrong server → name taken (`Rename` → `AppRenameChatDialogWidget.show`) → refused (`Try again` → `ChatThreadEvent.creationRetried`) → waiting, ONLY while `Initialized.isHeld` (the channel is not current), INSTEAD of `No connection` → offline. `isHeld` is apart from `isOffline` on purpose: the offline banner waits for a whole failed round, and with a current channel the creation is going out right now, so a waiting notice would only flash.
- **BLoC discipline.** Repository calls returning `RepositoryResult` never throw, so blocs `await` them bare and use `result.match(onData:, onError:)`. `BaseBloc.executeLogic` is reserved for handlers running raw async work (delays, pickers, multi-step loads) — **never call it without `onError`**: it catches everything and, with no callback, neither emits nor rethrows. Transformers in use: `bloc_concurrency` `sequential()` on paginated loads and on the thread's `ConnectivityChanged`, plus a project-local `debounceRestartable([300ms])` (`lib/presentation/base/bloc_transformers.dart`) on search and name-availability checks.

Paginated/loading screens use `@freezed sealed` unions (`Initializing`/`Initialized`/`Error`) with computed logic in an extension on the substate; form screens use a single-factory `@freezed abstract` value state with a private `const X._()` and computed getters in the class body.

- **Builds** wrap `mise`: `mise run build:<platform>:<stage|prod>` for android/ios/macos/windows/linux (all `--debug`). The `Makefile` wraps only `build-macos-stage|prod`, `build-windows-stage`, `build-linux-stage`. mise resolves Flutter through `.fvm/flutter_sdk/bin/flutter`, and `.fvm/` is gitignored — **`fvm use 3.44.1` must have run first on a fresh clone**.

**Flavors** are a compile-time Dart define: `--dart-define-from-file=config/<flavor>.json`, each file holding `{"app.flavor": "stage"|"prod"}`, read via `String.fromEnvironment('app.flavor')`. `AppFlavor.getFlavor()` maps empty/unknown → **prod** (safe default), and `main.dart` then picks `Environment.prod` for prod, `Environment.dev` otherwise — so a build with **no** define lands on `Environment.prod`. No native `--flavor`; no per-flavor app id.

**Golden tests** are plain-Flutter `matchesGoldenFile`, tagged `@Tags(['golden'])` (declared in `dart_test.yaml`), rendered/verified **locally only on Apple Silicon/macOS** and **excluded from `make test` and CI**. Verify with `make golden-verify`, regenerate with `make golden-update` (both accept `FILE=`). See *Testing*.

**CI** (`.github/workflows/`): `ci.yml` (`gate` job, macOS) mirrors `make gate` minus goldens — `pub get` → `build_runner` → `dart format -l 140 --set-exit-if-changed $(git ls-files lib test | grep '\.dart$')` → `analyze` → `flutter test --exclude-tags golden`. Because the format step enumerates via `git ls-files`, gitignored generated code can never trip it. `compile-check.yml` runs five per-platform `--debug` smoke builds against `config/stage.json` (the Linux job apt-installs `ninja-build libgtk-3-dev libsecret-1-dev libjsoncpp-dev`). **CI uses bare `flutter`/`dart` (subosito action), not `fvm`** — locally always use `fvm`.

**l10n:** `flutter: generate: true` + `l10n.yaml` (`arb-dir: lib/l10n`, template `app_en.arb`, class `AppLocalizations`, `nullable-getter: false`). UI strings resolve through `context.l10n` with live EN+UK switching (`LocaleController` → `MaterialApp.locale`); supported locales are exactly `en` and `uk`. `app_en.arb` and `app_uk.arb` each hold **200 keys with identical key sets** — a new string must land in **both**. `lib/general/text_constants.dart` no longer exists. `integration_test/` holds two MANUAL Tor checks (`tor_pairing_test.dart`, `tor_relaunch_test.dart`) run on a simulator or emulator against a live `noxd` whose onion service a separate tor publishes (`test/live/tor_live_probe.dart` leaves both and a fresh invite behind) - part of no gate; see `specs/045-tor-service-addresses/quickstart.md`.

**pubspec gotchas:**
- **Do not swap `file_selector` for `file_picker`** — `file_picker` pins `win32 ^5.x`, conflicting with `package_info_plus ^10.1.0` (`win32 ^6`). `file_selector` sits behind the `FilePickerService` seam and never reads file bytes.
- **`mockito` is declared `^5.6.4` and locked at 5.6.4**; 5.6.5+ pulls analyzer ^13 and conflicts with `injectable_generator`. The caret range does not block that — do not `pub upgrade` mockito.
- **`packages/nox_tor` is a workspace member with a native build hook** (`workspace: [packages/nox_tor]`, `nox_tor: {path: packages/nox_tor}`). The hook compiles the Rust crate with `native_toolchain_rust` on every build AND on `flutter test` (the package's tests load the host library), so **Rust is a build prerequisite** on every platform, Linux included (the channel lives in the module since 044, and Tor runs on Linux too since 045): `rustup` with the toolchain pinned in `packages/nox_tor/rust/rust-toolchain.toml` (1.93.1, all targets); Android also needs NDK `28.2.13676358`. On a fresh machine run `rustup show active-toolchain` in that directory once - two first hook runs collide while downloading. `make tor-test` runs `cargo test` + the package's `dart test`. `.gitignore` excludes `packages/nox_tor/rust/target/`.
- **`flutter_launcher_icons` MUST NOT be run** — it would overwrite the hand-crafted per-platform icon set and does not cover Linux.
- **`video_player` covers three of the five targets** (`video_player_android`, `video_player_avfoundation` for iOS+macOS, plus an unused `video_player_web`). There is no Windows or Linux implementation, so `VideoPlaybackCapability` gates every playback surface — a controller built there throws at `initialize()` rather than degrading. Do not swap it for `media_kit` without an explicit owner decision: it covers all five but ships libmpv natively in every bundle.
- `zxing2` powers pure-Dart QR **decode from a picked image** (Windows/Linux sign-in, gated by `QrImageSignInCapability`), while `mobile_scanner` (`QrScannerCapability`) is camera-only on iOS/Android/macOS. `permission_handler` backs **both** camera and notification permissions.
- `app_links`, `cached_network_image` and `skeletonizer` are declared but have **zero imports** in `lib/` — deep links (blueprint 13) are not implemented.
- Native capability declarations already ship on all five targets (macOS entitlements: camera + user-selected file read/write; iOS+macOS `NSCameraUsageDescription`; Android `CAMERA` with `required="false"` + `POST_NOTIFICATIONS`). Minimums: iOS 13.0, macOS 10.15. Windows/Linux branding lives outside `pubspec.yaml` (`windows/runner/Runner.rc`, `linux/CMakeLists.txt`).

## Testing

Tests deep-mirror `lib/` under `test/` (not flat); BLoC tests live in the page's `bloc/` sub-folder. The team's test-generation conventions are the slash-command skills **`/bloc-test`, `/golden-test`, `/widget-test`**, sourced from **`.claude/commands/*.md`** (note: under `.claude/commands/`, **not** `.claude/skills/`, which holds `speckit-*`, `prepare-preview` and the Go-backend skills `go-style`/`ws-rest-patterns`/`add-command`/`migrations`). Read the relevant one before writing or updating a test.

- **Global bootstrap: `test/flutter_test_config.dart`** is auto-loaded by `flutter test` for the whole suite and installs in-memory mock backends for `SharedPreferences` and `FlutterSecureStorage`. Without it every test that calls `configureDependencies` fails, because the generated `$initGetIt` `@preResolve`s `SharedPreferences` over a platform channel. It does **not** build the DI container — tests do that themselves.
- **`pumpApp(tester, child, {themeMode, settle, textScale})`** is the mandatory canvas: `ScreenUtilInit(Constants.designSize, fontSizeResolver: AppTextStyleTokens.fontSizeResolver)` + `AppTheme.light()/dark()` + a textScaler clamp + a pinned `locale: Locale('en')` with the `AppLocalizations` delegates. Skip it and the spacing/text tokens fail to resolve and localized copy renders non-deterministically.
- **UI copy is asserted through a file-level `final l10nEn = AppLocalizationsEn();`** (`package:nox_app/l10n/app_localizations_en.dart`) — never raw literals, never the deleted `TextConstants`.
- **Golden harness (`test/utils/golden.dart`).** `goldenTest(name, build, {settle})` renders light+dark on the mobile design surface; `goldenTestDesktop(name, build, {settle, size})` does the same pinned to `kDesktopGoldenSize` (1280×800, dpr 2). Both **freeze `AppClock` at `kGoldenClock` = 2026-06-15 21:30** (with a reset tearDown), pin the surface by assigning `tester.view.devicePixelRatio` + `physicalSize` (**not** `setSurfaceSize`, which does not reach the MediaQuery ScreenUtil reads and would scale every token ~1.5×), load real Roboto via `loadNoxFonts`, and precache the brand logo inside `tester.runAsync` on settled screens (`pumpAndSettle` does not await async PNG decode, so a logo screen can otherwise snapshot blank). Use `settle: false` for animated content.
- **Reactive pages need a bespoke harness.** `chat_thread_page`, `chat_card_page` and `tab_bar_shell` cannot use the shared helpers: `watchMessages`/`watchChats` plus mock seed delays keep timers in flight, so `pumpAndSettle` hangs while `settle: false` snapshots the spinner. They mirror `golden.dart` but settle with bounded pumps (`14 × tester.pump(150ms)`) and do `SharedPreferences.setMockInitialValues({})` → `configureDependencies(Environment.test)` → `await getIt<AppDatabase>().clearEntireDatabase()` in `setUp` (the test DB is in-memory but **persists across tests in the same isolate**).
- **Three golden categories (project rule).** (1) **widget** goldens per `App*Widget`; (2) **page — mobile** for every `*Page` via `goldenTest`; (3) **page — desktop** for every *product* `*Page` via `goldenTestDesktop` → `goldens/<name>_desktop_<mode>.png`. Category 3 is **required for every product page** — it locks the desktop `_wide`/master-detail/window-titlebar branch the mobile surface cannot reach. Desktop-exempt today: the dev-only pages (`home_page`, `ui_kit_page`, `screens_gallery_page`), the brand-fixed `splash_page`, and the `theme_showcase` fixture. The desktop variant is **not** page-only — `app_message_bubble_widget_narrow_pane` and `tab_bar_shell_settings` are desktop baselines too. See `.claude/commands/golden-test.md`.
- **Baselines live beside their test** as `test/<mirrored path>/goldens/<name>_<mode>.png` (there is no repo-root `goldens/`); mismatch diffs go to a sibling `failures/` dir, gitignored via `**/failures/`. Current counts: **285 test files, 74 of them `*_golden_test.dart`, 362 committed baseline PNGs (122 of them `_desktop_`)**.
- **Golden coverage of functional states uses production test seams, not mocks:** pages accept `@visibleForTesting initialScenario` (`ChatsListScenario` / `ChatThreadScenario` / `ChatCardScenario`, plus `initialViewMode` / `initialSendText`) which seeds the debug scenario — `ChatCardPage` pins it at construction (`ChatCardBloc(initialScenario:)`, no re-init race), while `ChatsListPage` and `AppThreadViewWidget` queue a `SetScenario` event *after* the initial `Initialize`. That is how the `*_empty` / `*_offline` / `*_inline_error` / `*_fatal` / send-error baselines are produced.
- **A `SetScenario` debug switch empties the chat's queue** (`removeForChat`), so a golden that needs a queued message seeds the store inside `tester.runAsync` and swaps `ConnectivityService` for a no-network fake instead of using the offline scenario (`chat_thread_page_creation_*`). Rows whose ORDER matters are seeded with fixed ids and distinct times: created through `createChat` under the frozen golden clock they tie, and the tie is broken by a random id (`chats_list_page_creation`).
- **Naming / tagging:** golden files are `*_golden_test.dart` and **must** carry `@Tags(['golden'])`; widget/unit tests are `*_test.dart` and **must not** (tagging silently drops them from CI). Test names are descriptive sentences, not `test_should…_when…`. Tagging is currently 100% consistent — keep it that way.
- **Widget tests pick the layout branch with `tester.binding.setSurfaceSize`** (narrow ~420×900, wide ~1200×900) + a tearDown reset — the golden helpers' `tester.view` pinning is not reused there.
- **Mocking: `mockito` only — `mocktail` is forbidden** (it exists solely as a transitive lock entry). Prefer the test-env DI (`configureDependencies(Environment.test)`, which serves mock data); use `mockito` only to force a path via `@GenerateMocks` + `getIt.allowReassignment = true` + `registerSingleton`, with `tearDown(getIt.reset)`. A stub whose return type is a generic `RepositoryResult<T>` needs `provideDummy<RepositoryResult<...>>(...)` in `setUp` before any `when(...)`. Hand-written fakes are an accepted alternative — `test/utils/fake_session_repository.dart` provides `kTestIdentifier`, `kTestSession` and `registerFakeSession()` (it implements only `readSession` + the 015 label channel; every other member throws).
- **BLoC tests** use `bloc_test`. Sealed-union blocs assert **bare** substate names (`isA<Initialized>()`/`Error`, never page-prefixed); single-class-state blocs assert with `predicate<XState>((s) => …)` on fields. Only assert an `Error` emission where the handler passed `onError` to `BaseBloc.executeLogic` (otherwise errors are swallowed by design). Product BLoC tests reset with the three-step `setMockInitialValues` → `configureDependencies(Environment.test)` → `clearEntireDatabase()` sequence.
- **Accessibility (FR-016)** is covered by two files: `test/presentation/widgets/accessibility_test.dart` (cross-widget) and `test/presentation/pages/m1_settings_accessibility_test.dart` (screen-level); both exercise `pumpApp(..., textScale: 2.0)` and assert ≥48×48 tap targets plus tooltips on icon-only actions.
