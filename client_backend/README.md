# NOX client server (noxd)

Собственный сервер мессенджера NOX для **одного человека и его устройств**: один WebSocket-канал команд (JSON-конверт, глобальный журнал событий `seq`, догон по курсору `since`), байты вложений по HTTPS, встроенный SQLite. База и вложения на диске зашифрованы, и после каждого запуска сервер заперт, пока не введён пароль владельца (фаза 047). Один статический бинарник без CGO; других процессов сервер не запускает.

Контракт провода — `docs/client-backend/protocol/contract-draft.md` (v0); правила кода — `CLAUDE.md` рядом.

**Кто подключается, решает канал** (контракт §1). Каждое соединение — и сокет команд, и каждая передача файла — проходит TLS 1.3 на техническом сертификате, который сервер выпускает в памяти при каждом старте, а сразу за ним — проверку Eidolon: устройство показывает свой ключ Ed25519, сервер — свой, и обе подписи стоят над отпечатком именно этого TLS-соединения. Флагов «без TLS» и «без проверки» нет. Сервер принимает любой ключ, доказавший себя, а права даёт по нему: спаренному устройству — всё, незнакомому ключу — только `pair` и `pair.cancel`.

**Устройство добавляется двумя путями** (контракт §8A):

- **ссылкой с машины сервера** — её выдают служебная страница и команда `noxd link`; живёт 10 минут, живая всегда одна (новая гасит прежнюю) и спаривает сразу: человека на сервере нет — создаёт его, есть — присоединяет к нему новое устройство со всей перепиской. Так спаривают первое устройство, возвращаются после выхода с последнего и после потери всех;
- **приглашением со спаренного устройства** (`device.invite`, 10 минут) — новое устройство ждёт, пока выдавшее приглашение устройство ответит `Allow` или `Deny`; без ответа запрос истекает вместе с приглашением, а новое устройство может отменить ожидание само.

Ни ссылка, ни токен не попадают в журнал сервера, как и onion-адрес: строка запуска говорит, где взять ссылку, но не саму ссылку, а каждая строка журнала проходит через один обработчик, который заменяет onion-адреса и ссылки метками `[onion]` и `[link]`, откуда бы ни пришёл текст.

## Требования

- Go 1.27+ (`go version`)
- tor 0.4.9 или новее — только для пути через onion-сервис, отдельной службой на той же машине (раздел «Tor»)

## Сборка и запуск

```bash
cd client_backend
go build -o noxd .
./noxd -addr 127.0.0.1:8080 -db /tmp/nox-smoke.db
./noxd unlock      # в другом терминале: первый раз — пароль и повтор, после каждого перезапуска — пароль
```

**Сервер стартует запертым** (фаза 047): база и вложения на диске зашифрованы ключом данных, который запирает пароль владельца, и пароль нигде не хранится. До ввода пароля слушает только служебная страница (`http://127.0.0.1:8081`, поле пароля — ни ссылки, ни адресов), основной порт закрыт. Пароль — не короче 12 знаков; забытый пароль — потерянные данные. Без терминала команды читают пароль из стандартного ввода, по строке на пароль: `printf '%s\n%s\n' "$PW" "$PW" | ./noxd unlock`.

После пароля сервер открывает базу, применяет миграции (журнал — slog JSON в stderr), пишет свой открытый ключ (`server_key` в строке `listening`) и начинает слушать. Пока ни одного устройства нет, журнал говорит, где взять ссылку для первого, — саму ссылку он не пишет никогда.

Проверка живости — на служебном слушателе, открытым HTTP: основной порт до проверки канала не отвечает ничем, а пока сервер заперт, не занят вовсе.

```bash
curl -s http://127.0.0.1:8081/health
# → {"status":"locked"} до пароля, {"status":"ok"} после
```

Пароль, бэкап и восстановление:

```bash
./noxd password                          # текущий, новый, повтор; ключ данных перезапирается, данные не трогаются
./noxd backup /backups/nox-2026-10-10.tar   # один зашифрованный файл; пишет работающий сервер, поверх файла — никогда
./noxd restore /backups/nox-2026-10-10.tar -db /srv/nox/nox.db   # на пустое место, без сервера, тем же паролем
```

Восстановленный сервер — та же машина с тем же ключом: устройства подключаются без спаривания и перечитывают переписку, потому что имя журнала новое. Устройство, отозванное после бэкапа, восстановленный сервер снова принимает — `noxd restore` называет устройства, которые он примет, и такое отзывают заново. Ключ onion-сервиса в бэкап не входит: он в папке службы tor, и на новой машине без неё у сервиса будет новый адрес.

Остановка — `Ctrl+C` или SIGTERM: сервер закрывает основной и служебный HTTP-серверы (до 5 с каждый), шлёт соединениям close-код going away и ждёт их до 15 с — закрывающее рукопожатие через Tor бывает долгим. Верхняя граница — около 25 с. Запертый сервер останавливается сразу.

### Флаги и переменные окружения

| Флаг | Env | По умолчанию | Назначение |
|---|---|---|---|
| `-addr` | `NOX_ADDR` | `127.0.0.1:8080` | Где сервер принимает приложения (`host:port`): WebSocket `/ws` и байты `/files/{token}` за TLS 1.3 и проверкой канала. Порт занимается только после пароля. Служба tor ведёт onion-сервис на `127.0.0.1:<порт>`, поэтому с tor сервер слушает все адреса (`0.0.0.0`) или loopback |
| `-status-addr` | `NOX_STATUS_ADDR` | `127.0.0.1:8081` | Служебная страница (открытый HTTP): пароль; у открытого сервера — ссылка с машины и QR-код, состояние машины, адреса, смена пароля; там же `GET /health` и `/control/*` для `noxd link`, `noxd unlock`, `noxd password`, `noxd backup`. Адрес обязан быть loopback и не может быть пустым, а занятый порт останавливает старт: пароль вводится только здесь |
| `-db` | `NOX_DB` | `nox.db` | Путь к файлу базы SQLite, зашифрованной по страницам. В нём же лежат ключ сервера и его адреса; рядом — `<db>.key`, запертый паролем ключ данных. Бэкап — только `noxd backup` |
| `-files` | `NOX_FILES` | `<db>-files` | Каталог байтов вложений |
| `-public-addr` | `NOX_PUBLIC_ADDR` | — | Публичный адрес машины `host:port` (IP или DNS-имя), если сервер виден из интернета: проброс порта, DNS-имя. Пишется в базу, только когда параметр появился или изменился с прошлого применённого значения |
| `-onion-addr` | `NOX_ONION_ADDR` | — | Onion-адрес, который публикует отдельная служба tor (`<56 знаков>.onion`, допускается `:443`). Пишется в базу по тому же правилу |

Приоритет: флаг → переменная окружения → значение по умолчанию. Настроек в конфигурационном файле нет.

Публичный и onion-адрес хранятся в базе и действуют сразу, без перезапуска: новые ссылки несут их, подключённые устройства получают их тут же (событие `server.addresses`). Параметр запуска записывает адрес, только когда сам появился или изменился, поэтому адрес, заданный на служебной странице кнопкой `Set`, переживает перезапуск с прежним параметром в unit-файле. Испорченный параметр не применяется и старт не останавливает: прежний адрес остаётся, в журнале — ошибка, а на странице — предупреждение, называющее параметр. Пустой параметр ничего не меняет — удаляют адрес на странице, пустым полем и `Set`. Адрес проверяется до записи: onion — версия 3, 56 знаков base32, контрольная сумма; публичный — `host:port`, хост — IP или DNS-имя, порт 1–65535.

Флаги `-tor`, `-tor-bin` и `-tor-dir` сервер отвергает с подсказкой: tor работает отдельной службой (раздел «Tor»).

### `noxd link` — ссылка из терминала

```bash
./noxd link [-status-addr 127.0.0.1:8081] [-qr]
```

Подкоманда того же бинарника — для машины без экрана, на которой не открыть служебную страницу. Она просит у **работающего и открытого паролем** сервера новую ссылку с машины через его служебный адрес (`POST /control/link`) и печатает её и срок (`Expires in 10 minutes`); с `-qr` — ещё и QR-кодом в терминале. Прежняя живая ссылка — на странице или от прошлого `noxd link` — перестаёт работать. Базу команда не открывает: её открывает только сервер. Адрес служебной страницы ищется так же, как у сервера: флаг → `NOX_STATUS_ADDR` → `127.0.0.1:8081`. Если все адреса ссылки — loopback этой машины, QR-кода нет: такую ссылку откроет только приложение на этой же машине.

Сервер отвечает на `POST /control/link` только запросу с локальным `Host`, заголовком `X-Nox-Control: 1` и без `Origin` — такой запрос сторонний сайт из браузера отправить не может. Тот же порядок — у `noxd unlock`, `noxd password` и `noxd backup`. Запертый сервер ссылок не выдаёт: `noxd link` говорит, что сначала нужен `noxd unlock`.

### Служебная страница

`http://127.0.0.1:8081` — только с этой машины, открытым HTTP. Пока сервер заперт, на странице только поле пароля — на свежем сервере пароль и повтор с предупреждением, что забытый пароль не восстановить, — и больше ничего: ни ссылки, ни адресов, ни цифр. Когда пароль введён и ни одного устройства нет, страница сразу показывает ссылку с машины: QR-код, ссылку текстом с кнопкой `Copy link` и срок. Когда устройства есть — кнопку `Add a device` и состояние машины: версия, аптайм, схема, счётчики, размер базы. Истёкшая ссылка сменяется `Link expired` и кнопкой `New link`; сама она не перевыпускается. Ниже — адреса: найденные в сетях машины (только чтение) и поля публичного и onion-адреса с кнопками `Set`; пустое поле и `Set` удаляют адрес; в самом низу — смена пароля (текущий, новый, повтор). Формы страницы (`Add a device`, `New link`, `Set`, формы пароля) принимаются только из самой страницы: проверяются `Host`, `Origin` и токен формы.

Отзыва устройств на странице нет: потерянное устройство отзывают с устройства, которое у человека в руках, — в том числе с только что добавленного ссылкой с машины. Выход или отзыв последнего устройства возвращает страницу к ссылке сразу; человек и переписка остаются, и устройство по ней присоединяется к тому же человеку.

### Кто сможет подключиться — решает `-addr`

- `127.0.0.1` (по умолчанию) — напрямую только приложения на этой же машине; телефону остаются публичный адрес и onion-сервис (ниже). Без них страница не рисует QR-кода: ссылку вставляют в приложение на этой машине.
- `0.0.0.0` — все адреса машины: подключаются и устройства в той же локальной сети. Так запускает `scripts/demo-stand.sh`; в ссылку попадает адрес машины в сети.
- Из-за пределов сети (мобильный интернет, чужой Wi-Fi) — по публичному адресу (`-public-addr`: проброшенный порт, публичный IP или DNS-имя) или через onion-сервис (раздел «Tor»). Через onion приложение идёт, только если у человека включено `Use Tor`, а напрямую до сервера не достучаться.

В ссылку спаривания записываются, в этом порядке, публичный адрес (если задан), один прямой адрес машины и onion-адрес (если задан). Остальное устройство узнаёт после подключения: найденные в сетях машины адреса, публичный и onion-адрес сервер сообщает в ответе на приветствие, а когда они меняются — событием `server.addresses`; приложение пробует их само. Для дома надёжнее постоянный адрес (резерв DHCP, статический IP) или DNS-имя.

### Tor

Onion-сервис публикует отдельная служба tor на той же машине и ведёт его на основной порт сервера; сервер её не запускает, ею не управляет и знает о ней только onion-адрес — строку в базе. Ставят и настраивают её вручную или скриптом установки. Ключ onion-сервиса живёт в папке службы tor, в базе сервера его нет. Дочерних процессов у сервера нет: служба tor живёт и останавливается сама по себе.

Нужен tor 0.4.9 или новее. Linux — пакет дистрибутива, если он не старее 0.4.9, иначе репозиторий Tor Project. macOS — tor из Tor Expert Bundle или `brew install tor`; бинарь из комплекта не подписан, и Apple Silicon убивает его при запуске — для разработки хватит `codesign --force -s - tor` и того же для `libevent-*.dylib` рядом. Windows — `tor.exe` из Tor Expert Bundle.

Пример `torrc` для сервера, запущенного с `-addr 0.0.0.0:8443`:

```
SocksPort 0
DataDirectory /var/lib/nox-tor
HiddenServiceDir /var/lib/nox-tor/hs
HiddenServicePort 443 127.0.0.1:8443
HiddenServicePoWDefensesEnabled 1
HiddenServiceMaxStreams 16
HiddenServiceMaxStreamsCloseCircuit 1
```

- `SocksPort 0` — прокси для программ на машине не нужен: tor только держит onion-сервис.
- `HiddenServicePort 443 127.0.0.1:<порт сервера>` — виртуальный порт сервиса всегда 443 (контракт §1), цель — порт `noxd` на loopback. Сервер для этого слушает все адреса (`-addr 0.0.0.0:8443`) или только loopback (`-addr 127.0.0.1:8443`: тогда до него доходят только tor и программы этой машины). Сервер, привязанный к одному адресу сети, на loopback не отвечает — целью тогда служит этот адрес; соединение от tor приходит с него же, и сервер узнаёт в нём эту машину так же, как loopback.
- `HiddenServicePoWDefensesEnabled 1` — защита PoW от наплыва: под нагрузкой сервис просит клиентов решить задачу, и встроенный в приложение Tor решает её сам.
- `HiddenServiceMaxStreams 16` и `HiddenServiceMaxStreamsCloseCircuit 1` — не больше 16 потоков разом на цепочку, а цепочка, попросившая больше, закрывается целиком. PoW делает дорогими только новые цепочки, а не потоки на уже построенной; без этих строк одна цепочка открывает сколько угодно соединений с сервером. Приложению на цепочку хватает сокета и нескольких передач файлов.
- `DataDirectory` и `HiddenServiceDir` доступны только пользователю, под которым работает tor (права 700). В `HiddenServiceDir` лежит ключ onion-сервиса: без него сервис получит новый адрес.

Onion-адрес tor пишет в `<HiddenServiceDir>/hostname`. Его передают серверу параметром `-onion-addr` (или `NOX_ONION_ADDR`) либо вписывают на служебной странице кнопкой `Set`; с этого момента он попадает в новые ссылки и в ответ на приветствие.

**Один порт на оба пути.** Прямые соединения и соединения от tor приходят на один порт и проходят одни и те же слои — TLS 1.3, проверку канала, HTTP; пришло ли соединение через Tor, сервер не знает, поэтому сроки медленного пути через Tor действуют для всех соединений: проверка канала — 30 с от приёма, запись кадра и ожидание pong — 30 с, заголовки запроса — 30 с. Ключей доступа Tor нет: onion-адрес открыт любому, кто его знает, — дальше пускают только проверка канала и права ключа устройства. Спариваться через onion можно и первому устройству, и следующим — и ссылкой с машины, и приглашением.

**Пределы.** На входе — до проверки — сервер держит не больше 256 соединений, от одного источника (адрес IPv4 или сеть IPv6 /64) не больше 8, с этой машины — то есть от tor, со всеми, кто пришёл через onion, — не больше 64; новое соединение никогда не отвергается, вместо этого обрывается самое старое из своего источника или со всего входа. Соединение не с этой машины, не приславшее ни байта за 5 с, обрывается. После проверки незнакомому ключу соединение служит один запрос: любой ответ, кроме перехода на WebSocket, закрывает соединение. Тело, которое сервер не читает, он ждёт не дольше 30 с после заголовков, чей бы ни был ключ. Соединение с незнакомым ключом на `/ws` держится не дольше 2 минут, если не спарилось, и таких соединений не больше 32 — для 33-го закрывается самое старое. Соединение, на котором приглашение ждёт `Allow`, от обоих пределов свободно, пока запрос ждёт, — до 10 минут; такое соединение у запроса одно — последнее, на котором его предъявили, а прежнее сервер закрывает. Закрылся запрос без спаривания — 2 минуты отсчитываются заново. Соединение спаренного устройства между двумя запросами HTTP ждёт не дольше 2 минут. Обрывы на входе и закрытия неспаренных соединений попадают в лог предупреждением не чаще раза в минуту — одни счётчики, без адресов и ключей; рост `evicted_local` значит, что напор идёт через onion.

## Проверка вживую — `cmd/smoke`

```bash
cd client_backend
go run ./cmd/smoke '<ссылка с машины>'
```

Ссылку дают служебная страница и `noxd link`. Смоук говорит с сервером так же, как приложение: TLS 1.3, проверка канала с ключом сервера из ссылки, затем сокет. Он спаривает первое устройство по ссылке (на свежем сервере оно создаёт человека, на сервере с человеком — присоединяется к нему), второе — по приглашению с `Allow` на первом, третьему отказывает (`Deny`), четвёртое отзывает свой запрос само (`pair.cancel`) — и проверяет, что ни то, ни другое не спарено, — и обменивается сообщением между двумя устройствами. Каждый шаг печатается; смоук падает на первом несошедшемся. Ссылку он тратит, а его устройства остаются спаренными на этом сервере. Прямые адреса ссылки пробуются по порядку; onion-адрес смоук называет, но не пробует — Tor в нём нет.

```bash
go run ./cmd/smoke -check 127.0.0.1:8080 '<ключ сервера, base64>'
```

открывает один канал и говорит, та ли машина отвечает по этому адресу; так `scripts/demo-stand.sh` убеждается, что порт держит именно его сервер. Ничего не спаривается.

Ни `websocat`, ни `curl` с основным портом не поговорят: до первого байта HTTP соединение проходит проверку канала, которую умеют только приложение и `cmd/smoke`.

```
← {"srv":{"schema_max":1}}
→ {"id":1,"cmd":"session.hello","data":{"schema":1,"since":1041}}
← {"id":1,"ok":true,"data":{"schema":1,"cursor":1042,"journal_id":"j_…","limits":{…},"identity":{"id":"u_…","label":"Anna"},"addresses":{…}}}
```

- **Подписка → replay → live.** После ответа сервер досылает все события с `seq > since` по возрастанию и переходит к живому потоку. Устройство догнано, когда обработало событие с `seq ≥ cursor`; дубликаты на стыке допустимы (дедупликация по `seq`), потеря — нет. Без `since` досылки нет, только живой поток.
- **Своё сообщение — на всех устройствах человека.** `message.send` на первом устройстве: эхо приходит ответом, `message.new` — обоим устройствам, и оба кадра несут `client_message_id`: собственное — это личность, а не устройство (контракт §5). Повтор с тем же `client_message_id` возвращает прежнее эхо, и второе событие не приходит.
- **Медленный получатель.** Переполнил очередь соединения (64 кадра) — соединение закрывается кодом policy violation; переподключение с `since` досылает пропущенное.
- **Перезапуск.** Тот же `-db` — после пароля ничего не потеряно и мир не сброшен; устройство продолжает с прежним `since`, а пока сервер заперт, видит то же, что при выключенном. Восстановление из бэкапа — новое имя журнала: устройство стирает локальный мир и перечитывает переписку, не спариваясь заново. Новая база — новый ключ сервера: прежние устройства не узнают сервер на проверке канала и спариваются заново.

Чаты и история (`chats.list`, `chat.get`, `chat.create`, `chat.rename`, `chat.nameAvailable`, `messages.list`) — контракт §4–§5; файлы (`file.uploadBegin` → `PUT /files/{token}` от `received` → `message.send {attachment}`, `file.downloadBegin` → `GET` с `Range`) — §7; спаривание и устройства — §8A. Поведение каждой команды закреплено тестами `internal/server/*_test.go`.
