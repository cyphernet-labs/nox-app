# NOX client server (noxd)

Собственный сервер мессенджера NOX для **одного человека и его устройств** (ревизия 2026-09-10; прежняя формулировка «малый круг ~10 человек» отменена): один WebSocket-канал команд (JSON-конверт, глобальный лог событий `seq`, догон по курсору `since`), REST-поверхность для байтов вложений (`PUT`/`GET /files/{token}`), встроенный SQLite. Один статический бинарник без CGO; других процессов сервер не запускает.

Контракт провода — `docs/client-backend/protocol/contract-draft.md` (v0).

**Сервер проверяет, кто подключается** (фазы 032 и 044). Каждое соединение — TCP, затем TLS 1.3 на техническом сертификате, который никто не сверяет, затем проверка Eidolon над экспортёром TLS 1.3: устройство доказывает свой ключ Ed25519, сервер — свой, и устройство сверяет ключ сервера с ключом из ссылки спаривания `nox://pair/` версии 3. Ни `session.hello`, ни `pair` ключа и подписи не несут: сервер знает ключ по соединению. Незнакомому ключу доступна только `pair` — единственная команда до приветствия; `session.hello` с таким ключом получает `unauthenticated`. Человек и устройство появляются только через `pair`.

**Канал закрыт.** Флагов «без TLS» и «без проверки» нет; основной порт до проверки не отвечает ничем, даже 404, а `/health` живёт на служебном loopback-слушателе.

## Требования

- Go 1.27+ (`go version`)
- Для пути через Tor — tor 0.4.9 или новее, отдельной службой на той же машине (см. «Tor — отдельная служба»)

> ⚠️ **`websocat` и `curl` до сервера не доходят.** После TLS 1.3 сервер ждёт проверку Eidolon и до неё не отвечает ничем, а эти инструменты её не умеют. Сборка `websocat` из homebrew вдобавок линкуется с Security.framework и до TLS 1.3 не поднимается: `-k wss://…` умирает с `WebSocket SSL error: bad protocol version`.
>
> **Живой смоук один, и он настоящий:** `go run ./cmd/smoke '<claim-ссылка>'` — ссылку берут со служебной страницы свежего сервера. Он открывает канал — TLS 1.3 и проверку Eidolon — по прямым адресам ссылки в её порядке (публичный первым, если он задан), **сверяет ключ сервера** с ключом из ссылки, спаривает два устройства одного человека, обменивается сообщением и печатает каждый шаг. Onion-адрес из ссылки он не пробует: Tor в нём нет. `go run ./cmd/smoke -check <host:port> <ключ сервера, base64>` открывает один канал и говорит, та ли машина отвечает по адресу. Стенд одной командой — `../scripts/demo-stand.sh`.

## Сборка и запуск

```bash
cd client_backend
go build -o noxd .
./noxd -addr 127.0.0.1:8080 -db /tmp/nox-smoke.db
```

При старте сервер применяет миграции (лог slog JSON в stderr) и начинает слушать. Пока ни одно устройство не может войти (сервер ничей или у владельца не осталось устройств), claim-ссылку и QR показывает служебная страница (`http://127.0.0.1:8081`); строка запуска говорит, где страница, но не саму ссылку. Проверка живости — на служебном слушателе, рядом со страницей:

```bash
curl -s http://127.0.0.1:8081/health
# → {"status":"ok"}
```

### Флаги и переменные окружения

| Флаг | Env | По умолчанию | Назначение |
|---|---|---|---|
| `-addr` | `NOX_ADDR` | `127.0.0.1:8080` | Где сервер принимает приложения (`host:port`): WebSocket `/ws` и байты `/files/{token}` за TLS 1.3 и проверкой Eidolon. Служба tor ведёт onion-сервис на `127.0.0.1:<порт>`, поэтому с tor сервер слушает все адреса (`0.0.0.0`) или loopback |
| `-status-addr` | `NOX_STATUS_ADDR` | `127.0.0.1:8081` | Служебная страница (HTTP): claim-ссылка и QR, адреса с кнопкой `Set`, `GET /health`. Адрес обязан быть loopback — иначе сервер не стартует; пустое значение выключает и страницу, и `/health` |
| `-db` | `NOX_DB` | `nox.db` | Путь к файлу базы SQLite. В нём же лежат ключ сервера и его адреса — бэкапить только целиком |
| `-files` | `NOX_FILES` | `<db>-files` | Каталог байтов вложений |
| `-public-addr` | `NOX_PUBLIC_ADDR` | — | Публичный адрес `host:port` (IP или DNS-имя), если сервер виден из интернета. Пишется в базу, только когда параметр появился или изменился с прошлого применённого значения |
| `-onion-addr` | `NOX_ONION_ADDR` | — | Onion-адрес, который публикует служба tor (`<56 знаков>.onion`, допускается `:443`). Пишется в базу по тому же правилу |

Приоритет: флаг → переменная окружения → значение по умолчанию. Настроек в конфигурационном файле нет. Флаги `-tor`, `-tor-bin` и `-tor-dir` убраны: с любым из них сервер не стартует и подсказывает, что tor — отдельная служба.

**Адреса живут в базе.** Публичный и onion-адрес задаются параметрами запуска или кнопкой `Set` на служебной странице и действуют сразу, без перезапуска: новые ссылки несут их, подключённые устройства получают их тут же (событие `server.addresses`). Параметр перезаписывает базу, только когда сам появился или изменился с прошлого применённого значения, поэтому правка со страницы переживает перезапуск с прежним параметром в юните. Испорченный параметр не применяется и старт не останавливает: сервер работает с прежним адресом из базы, пишет ошибку в журнал и показывает на странице предупреждение, называющее параметр. Пустой параметр ничего не меняет — удалить адрес можно только на странице (пустое поле и `Set`). Адрес проверяется до записи: onion — версия 3, 56 знаков base32, контрольная сумма; публичный — `host:port`, хост — IP или DNS-имя, порт 1–65535.

**Кто сможет подключиться — решает `-addr` и адреса.**

- `127.0.0.1` (по умолчанию) — только приложения на этой же машине. Телефон не подключится.
- `0.0.0.0` — «все адреса машины сразу»: подключаются и устройства в той же локальной сети. Так запускает `scripts/demo-stand.sh`; QR на служебной странице сам подставляет адрес машины в сети.
- Из-за пределов сети (мобильный интернет, чужой Wi-Fi) — по публичному адресу (`-public-addr`: проброшенный порт, публичный IP или DNS-имя) или через onion-сервис службы tor (`-onion-addr`). Через onion приложение идёт, только если у человека включено `Use Tor`, а напрямую до сервера не достучаться.

Ссылка спаривания несёт адреса в порядке: публичный (если задан) → прямой → onion (если задан). Все свои адреса — найденные в локальной сети, публичный и onion — сервер сообщает устройствам после подключения, и приложение пробует их само. Для дома надёжнее постоянный адрес (резерв DHCP, статический IP) или DNS-имя.

### Tor — отдельная служба

Сервер tor не запускает и ничего о нём не знает, кроме onion-адреса — строки в базе. Onion-сервис публикует служба tor на той же машине и ведёт его на основной порт сервера; ставит и настраивает её владелец или скрипт установки. Ключ onion-сервиса живёт в папке службы tor, в базе сервера его нет.

Нужен tor 0.4.9 или новее. Linux — пакет дистрибутива, если он не старее 0.4.9, иначе репозиторий Tor Project. macOS — tor из Tor Expert Bundle или `brew install tor`; бинарь из комплекта не подписан, и Apple Silicon убивает его при запуске — для разработки хватит `codesign --force -s - tor` и того же для `libevent-*.dylib` рядом. Windows — `tor.exe` из Tor Expert Bundle.

Пример `torrc` для сервера, запущенного с `-addr 0.0.0.0:8443`:

```
SocksPort 0
DataDirectory /var/lib/nox-tor
HiddenServiceDir /var/lib/nox-tor/hs
HiddenServicePort 443 127.0.0.1:8443
HiddenServicePoWDefensesEnabled 1
HiddenServiceMaxStreams 16
HiddenServiceMaxStreamsCloseCircuit 1
```

- `SocksPort 0` — прокси для программ на машине не нужен: tor только держит onion-сервис.
- `HiddenServicePort 443 127.0.0.1:<порт сервера>` — виртуальный порт сервиса всегда 443 (контракт §1), цель — порт `noxd` на loopback. Сервер для этого слушает все адреса (`-addr 0.0.0.0:8443`) или только loopback (`-addr 127.0.0.1:8443`: тогда до него доходят только tor и программы этой машины). Сервер, привязанный к одному адресу сети, на loopback не отвечает — целью тогда служит этот адрес; соединение от tor приходит с него же, и сервер узнаёт в нём эту машину так же, как loopback.
- `HiddenServicePoWDefensesEnabled 1` — защита PoW от наплыва: под нагрузкой сервис просит клиентов решить задачу, и встроенный в приложение Tor решает её сам.
- `HiddenServiceMaxStreams 16` и `HiddenServiceMaxStreamsCloseCircuit 1` — не больше 16 потоков разом на цепочку, а цепочка, попросившая больше, закрывается целиком. PoW делает дорогими только новые цепочки, а не потоки на уже построенной; без этих строк одна цепочка открывает сколько угодно соединений с сервером. Приложению на цепочку хватает сокета и нескольких передач файлов.
- `DataDirectory` и `HiddenServiceDir` доступны только пользователю, под которым работает tor (права 700). В `HiddenServiceDir` лежит ключ onion-сервиса: без него сервис получит новый адрес.

Onion-адрес tor пишет в `<HiddenServiceDir>/hostname`. Его передают серверу параметром `-onion-addr` (или `NOX_ONION_ADDR`) либо вписывают на служебной странице кнопкой `Set`.

**Один порт на оба пути.** Прямые соединения и соединения от tor приходят на один порт и проходят одни и те же слои — TLS 1.3, проверку Eidolon, HTTP; пришло ли соединение через Tor, сервер не знает, поэтому сроки медленного пути через Tor действуют для всех соединений: проверка канала — 30 с от приёма, запись кадра и ожидание pong — 30 с, заголовки запроса — 30 с. Ключей доступа Tor нет: onion-адрес открыт любому, кто его знает, — дальше пускает только проверка Eidolon и права ключа устройства. Поэтому в лог сервера не попадают ни onion-адреса, ни ссылки спаривания (ссылка несёт ключ onion-сервиса в упакованном виде): один обработчик журнала заменяет их метками `[onion]` и `[link]`, откуда бы ни пришёл текст.

**Пределы.** На входе — до проверки — сервер держит не больше 256 соединений, от одного источника (адрес IPv4 или сеть IPv6 /64) не больше 8, с этой машины — то есть от tor, со всеми, кто пришёл через onion, — не больше 64; новое соединение никогда не отвергается, вместо этого обрывается самое старое из своего источника или со всего входа. Соединение не с этой машины, не приславшее ни байта за 5 с, обрывается. После проверки соединение с незнакомым ключом на `/ws` держится не дольше 2 минут, если не спарилось, и таких соединений не больше 32 — для 33-го закрывается самое старое; соединение между двумя запросами HTTP ждёт не дольше 2 минут. Обрывы на входе и закрытия неспаренных соединений попадают в лог предупреждением не чаще раза в минуту — одни счётчики, без адресов и ключей; рост `evicted_local` значит, что напор идёт через onion.

**Служебная страница** показывает найденные адреса (только чтение), публичный и onion-адрес — каждый в своём поле с кнопкой `Set`; пустое поле и `Set` удаляют адрес. Запись принимается только из формы самой страницы: проверяются `Host`, `Origin` и токен формы.

Остановка — `Ctrl+C` (graceful shutdown: клиенты получают close-код going away; обычно секунды, верхняя граница — около 25 с, см. смоук ниже). Дочерних процессов у сервера нет: служба tor живёт и останавливается сама по себе.

## Смоук A — обмен вживую

> ⚠️ **Не запускается как напечатано** (см. «Требования»): `websocat` не проходит проверку Eidolon, а без неё основной порт не отвечает ничем. Раздел оставлен как описание протокола; живая проверка — `go run ./cmd/smoke '<claim-ссылка>'`.

Терминал 1:

```bash
websocat -k wss://127.0.0.1:8080/ws
# ← {"srv":{"schema_max":1,"challenge":"..."}}
{"id":1,"cmd":"session.hello","data":{"schema":1,"label":"Anna"}}
# ← {"id":1,"ok":true,"data":{"schema":1,"cursor":0,"limits":{...},"identity":{"id":"Anna","label":"Anna"}}}
{"id":2,"cmd":"chat.create","data":{"name":"smoke"}}
# ← {"id":2,"ok":true,"data":{"chat":{"chat_id":"<CID>",...}}}   <- скопировать CID
{"id":3,"cmd":"message.send","data":{"chat_id":"<CID>","client_message_id":"a1","body":{"type":"text","text":"hello"}}}
# ← эхо с message_id, seq и client_message_id
```

Терминал 2 (открыть **до** отправки следующего сообщения):

```bash
websocat -k wss://127.0.0.1:8080/ws
{"id":1,"cmd":"session.hello","data":{"schema":1,"label":"Bob"}}
```

Снова терминал 1:

```bash
{"id":4,"cmd":"message.send","data":{"chat_id":"<CID>","client_message_id":"a2","body":{"type":"text","text":"second"}}}
```

**Проверка:** в терминале 2 мгновенно (< 1 с) появляется `{"seq":N,"event":"message.new","data":{...}}` с полным сообщением.

Отправитель тоже получает event-кадры собственных сообщений (после эха). Кадр автора содержит `client_message_id`; кадры остальных получателей — нет (контракт §5).

**Идемпотентность:** повторить кадр `id:4` с тем же `client_message_id":"a2"` → эхо идентично первому, событие второй раз не приходит.

## Смоук B — обрыв и догон

> ⚠️ **Не запускается как напечатано** (см. «Требования»): `websocat` не проходит проверку Eidolon, а без неё основной порт не отвечает ничем. Раздел оставлен как описание протокола; живая проверка — `go run ./cmd/smoke '<claim-ссылка>'`.

1. В терминале 2 запомнить последний увиденный `seq` (= `S`), убить websocat (`Ctrl+C`).
2. Из терминала 1 отправить 2–3 сообщения (`a3`, `a4`, …).
3. Переподключить терминал 2 с курсором:

```bash
websocat -k wss://127.0.0.1:8080/ws
{"id":1,"cmd":"session.hello","data":{"schema":1,"label":"Bob","since":S}}
```

**Проверка:** в ответе — текущий `cursor`; следом досылаются **все** пропущенные события с `seq > S` по возрастанию. Клиент догнан, когда обработал событие с `seq ≥ cursor`; дальше поток live (проверить ещё одним сообщением из терминала 1). Дубликаты на границе реплея допустимы — клиент дедуплицирует по `seq`; потеря — нет. `since` без поля = без досылки (только live); `since` больше текущего `cursor` = пустая досылка.

## Смоук C — живучесть

> ⚠️ **Не запускается как напечатано** (см. «Требования»): `websocat` не проходит проверку Eidolon, а без неё основной порт не отвечает ничем. Раздел оставлен как описание протокола; живая проверка — `go run ./cmd/smoke '<claim-ссылка>'`.

- **Медленный клиент:** приостановить вывод в терминале 2 (`Ctrl+S`) и лить сообщения из терминала 1, пока не переполнится буфер соединения → соединение 2 закрывается кодом policy violation, терминал 1 продолжает получать эхо без задержки. `Ctrl+Q` возвращает вывод; переподключение с `since` досылает пропущенное.
- **Shutdown:** при живых соединениях нажать `Ctrl+C` в терминале сервера → клиенты получают close-код going away, процесс завершается. Обычно за секунды; верхняя граница — около 25 с: по 5 с на каждый из двух HTTP-серверов (основной и служебная страница) и до 15 с на прощание соединений (закрывающее рукопожатие через Tor бывает долгим).
- **Рестарт:** повторный запуск с той же `-db` стартует без ошибок, данные на месте (повторить смоук B с прежним `since`).

## Смоук Д — полный чат-сценарий (фаза 023)

> ⚠️ **Кадры, не команды.** Раздел описывает, ЧТО идёт по проводу; отправить это `websocat`-ом больше нельзя (см. «Требования»). Живая проверка — `go run ./cmd/smoke '<claim-ссылка>'`.

Подготовка: Anna создаёт два чата и пишет в первый (`Kitchen` → CID1, `Общий` → CID2, сообщение `a1` в CID1). Между шагами — пауза ~1 с: активность имеет секундную гранулярность, и у строк, попавших в одну секунду, порядок в списке определяет `chat_id`, а не последовательность действий.

### Список и поиск

```bash
{"id":10,"cmd":"chats.list","data":{"page":1,"page_size":10}}
# ← оба чата; Kitchen первым (последняя активность — сообщение), has_more:false
{"id":11,"cmd":"chats.list","data":{"page":1,"page_size":10,"query":"общ"}}
# ← только "Общий" (регистронезависимо, кириллица)
{"id":12,"cmd":"chat.get","data":{"chat_id":"<CID2>"}}
# ← полная карточка чата
```

Порядок списка — по последней активности (новые сверху); превью строки — свёрнутый текст последнего сообщения. Порция больше 100 строк молча ограничивается сотней (`page_size` меньше 1 — ошибка `invalid_request`).

### История чата

Anna шлёт в CID1 ещё 4–5 сообщений (`a2`…), затем:

```bash
{"id":20,"cmd":"messages.list","data":{"chat_id":"<CID1>","limit":3}}
# ← 3 самых свежих по возрастанию seq, has_more:true; запомнить минимальный seq (= S)
{"id":21,"cmd":"messages.list","data":{"chat_id":"<CID1>","before_seq":S,"limit":10}}
# ← все более старые, has_more:false; вместе — вся история без дублей и пропусков
```

`before_seq` не задан — сервер отдаёт хвост (самые свежие). В выдаче Anna её сообщения несут `client_message_id`; тот же запрос от Bob — без этого поля (правило §5: ключ идемпотентности виден только автору). Повтор `message.send` с использованным `client_message_id` строки не добавляет — история показывает сообщение один раз.

### Переименование вживую

Bob держит соединение открытым; Anna:

```bash
{"id":30,"cmd":"chat.nameAvailable","data":{"name":"Общий"}}                             # ← available:false
{"id":31,"cmd":"chat.nameAvailable","data":{"name":"Общий","exclude_chat_id":"<CID2>"}}  # ← available:true
{"id":32,"cmd":"chat.rename","data":{"chat_id":"<CID2>","name":"Новый общий"}}
# ← ok с полной карточкой; у Bob мгновенно (< 1 с) кадр {"seq":N,"event":"chat.updated",...}
{"id":33,"cmd":"chats.list","data":{"page":1,"page_size":10}}
# ← порядок НЕ изменился: переименование не считается активностью
```

Уникальность имени — глобальная, без учёта регистра (включая кириллицу), с исключением самого чата. Переименование в то же самое имя — успех без события. После обрыва `chat.updated` досылается реплеем с `since` в общем порядке журнала.

## Смоук Е — файлы (фаза 024)

> ⚠️ **Не запускается как напечатано** (см. «Требования»): `curl` не проходит проверку Eidolon, а без неё основной порт не отвечает ничем. Раздел оставлен как описание протокола файлов.

Байты живут в каталоге рядом с базой (`<db>-files`; флаг `-files` / `NOX_FILES`). Тестовый файл: `dd if=/dev/urandom of=/tmp/probe.bin bs=1m count=10`.

### Отправка вложения

Терминал Anna:

```bash
{"id":10,"cmd":"file.uploadBegin","data":{"name":"probe.bin","size":10485760,"mime":"application/octet-stream"}}
# ← {"file_id":"<FID>","upload_url":"/files/<UT>","upload_token":"<UT>","max_attachment_bytes":104857600}
```

Заливка байтов (обычный терминал):

```bash
curl -skS -X PUT --data-binary @/tmp/probe.bin https://127.0.0.1:8080/files/<UT> -o /dev/null -w '%{http_code}\n'   # → 204
```

Сообщение-вложение (текст необязателен, но хотя бы одно из двух — обязательно):

```bash
{"id":11,"cmd":"message.send","data":{"chat_id":"<CID>","client_message_id":"f1","attachment":{"file_id":"<FID>"}}}
# ← эхо с attachment{file_id,name,size,mime,expires_at}; у второго клиента — message.new с тем же объектом
{"id":12,"cmd":"chats.list","data":{"page":1,"page_size":10}}
# ← превью чата = "probe.bin" (нет текста → имя файла)
```

Токены одноразовые (10 минут): повторный `PUT` тем же токеном → 404. Заливка сверх заявленного размера → 413, меньше (обрыв) → 400 — в обоих случаях байты не сохраняются, цепочка начинается заново с `file.uploadBegin`.

### Скачивание с докачкой

Терминал Bob:

```bash
{"id":20,"cmd":"file.downloadBegin","data":{"file_id":"<FID>"}}
# ← {"download_url":"/files/<DT>","download_token":"<DT>"}
```

```bash
curl -skS https://127.0.0.1:8080/files/<DT> -o /tmp/got.bin && cmp /tmp/probe.bin /tmp/got.bin && echo identical
```

Докачка после обрыва: запросить новый токен (`<DT2>`) и передать Range со смещения — сервер отдаёт `206` и только остаток:

```bash
curl -skS -r 5242880- https://127.0.0.1:8080/files/<DT2> -o /tmp/tail.bin -w '%{http_code}\n'   # → 206
cmp <(tail -c 5242880 /tmp/probe.bin) /tmp/tail.bin && echo resumed
```

Использованный токен скачивания → 404. Файл с истёкшим сроком или физически пропавшими байтами → `attachment_gone` на `file.downloadBegin` (терминальное состояние экрана файла).

## Негативные проверки

На подключении, где `session.hello` уже выполнен:

```bash
{"id":9,"cmd":"nope","data":{}}                       # → ok:false, invalid_request
{"id":10,"cmd":"chat.create","data":{"name":"SMOKE"}} # → name_taken (имена уникальны без учёта регистра)
{"id":11,"cmd":"session.hello","data":{"schema":1}}   # повторный hello → invalid_request
```

На свежем подключении:

```bash
{"id":1,"cmd":"session.hello","data":{"schema":99}}   # → unsupported_schema
{"id":1,"cmd":"chat.create","data":{"name":"early"}}  # команда до hello → invalid_request
```

Команды фазы 023:

```bash
{"id":40,"cmd":"chats.list","data":{"page":0,"page_size":10}}               # → invalid_request
{"id":41,"cmd":"chat.get","data":{"chat_id":"c_missing"}}                   # → not_found
{"id":42,"cmd":"chat.rename","data":{"chat_id":"<CID2>","name":"KITCHEN"}}  # имя другого чата → name_taken
{"id":43,"cmd":"messages.list","data":{"chat_id":"<CID1>","limit":0}}       # → invalid_request
```

Команды фазы 024:
