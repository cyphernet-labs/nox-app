# Data Model: что уходит из схемы и что остаётся

Единственная миграция `001_init.sql` правится **на месте** — развёрнутых установок не существует. Локальные базы разработчиков несовместимы и удаляются перед прогоном.

## `pair_tokens` — худеет на пять колонок и индекс

| Объект | Судьба | Почему |
|---|---|---|
| `kind` — значение `'invite_user'` | **уходит из CHECK** | Приглашения человека не существует. Остаются `claim` и `invite_device`. |
| `request_id TEXT UNIQUE` | **удаляется** | Имя ожидающего запроса на проводе. Ждать больше нечего. |
| `awaiting_platform TEXT` | **удаляется** | Платформа, заявленная неаутентифицированным устройством, пока владелец думает. |
| `awaiting_until INTEGER` | **удаляется** | Дедлайн ответа человека — единственный «человеческий» таймаут протокола. |
| `outcome TEXT CHECK (...)` | **удаляется** | Записанный исход approved / declined / expired. |
| `idx_pair_tokens_pending` | **удаляется** | Обслуживал единственный запрос — свипер просроченных. |
| `user_id`, `paired_user_id` | **остаются** | Формально тавтологичны при одном человеке, но на них стоит реплей «тот же ключ получает тот же ответ», который к многолюдности отношения не имеет. Трогать их — риск без выгоды. |
| `created_person` | **остаётся** | Различает «claim завёл человека» и «переclaim нашёл существующего». Смысл сохраняется: это про первый запуск. |

## `users` — становится синглтоном по построению

Таблица **не удаляется**: на `user_id` стоит внешний ключ `messages.author_id` и индекс идемпотентности отправки. Вместо этого вторая строка делается непредставимой:

```sql
CREATE UNIQUE INDEX idx_users_singleton ON users ((1));
```

Уникальный индекс по константе допускает ровно одну строку. **Проверить при реализации**, что SQLite принимает индекс по выражению на `STRICT`-таблице; если нет — заменить на инвариант в комментарии плюс тест, доказывающий, что вторая личность не заводится ни одним путём.

## `server_identity` — не меняется

`owner_user_id` **сохраняется** как отметка «машина забрана» и остаётся автоматом состояний: `NULL` — сервер свободен и принимает только claim-токены. Решение фазы 033 («автомат живёт здесь, а не в `claimed_at`») не отменяется — см. [research.md](./research.md) §3.

Пара ключей машины (`public_key`, `private_key`) не трогается: это опора пиннинга и будущей фазы 036.

## `messages`, `chats`, `files`, `events`, `devices`, `journal` — не меняются

Ни одна колонка не уходит. `messages.author_id` по-прежнему ссылается на `users`; индекс `(author_id, client_message_id)` остаётся, хотя вторая половина его обоснования («чтобы двое не столкнулись») перестаёт быть актуальной — переписывать работающий индекс ради комментария не нужно.

## Сущности предметной области

| Сущность | Что изменилось |
|---|---|
| **Личность** | Была одной из многих — стала единственной. Признак владения перестаёт быть её полем. |
| **Устройство** | Не изменилось. Принадлежит единственной личности, авторизуется ключом, отзывается удалением строки. |
| **Чат** | Не изменился как данные. Приобретает **представление** о людях — вычисляемое, не хранимое (см. research.md §4). |
| **Ожидающий запрос** | **Исчезает как сущность.** |
