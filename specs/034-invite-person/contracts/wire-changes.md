# Правки контракта v0 — фаза 034

Выдержка того, что вносится в [contract-draft.md](../../../docs/client-backend/protocol/contract-draft.md) **до** кода (Принцип VII, FR-017). Здесь — итоговая форма кадров; обоснования — в [research.md](../research.md).

Форма ссылки не меняется (FR-018): тип токена в ней по-прежнему не передаётся.

---

## §2.1 — три новых кода

| Код | Когда | Реакция клиента |
|---|---|---|
| `not_owner` | команда доступна только владельцу сервера, а спрашивающий им не является | Показать, что дело не в ссылке и не в сети; не повторять |
| `pair_declined` | владелец отклонил это приглашение | Терминально: нужна новая ссылка, повтор бессмыслен |
| `pair_timeout` | владелец не ответил в отведённое время | Попросить владельца выпустить приглашение заново |

`pair_declined` и `pair_timeout` разделены потому, что ведут к разным действиям: «не настаивай» против «попроси ещё раз». Правило эволюции прежнее — неизвестный клиенту код трактуется как `internal`.

## §8A — `pair` со статусом

Ответ получает `status`. Существующая форма сохраняется целиком: при `paired` рядом со `status` едет тот же объект `identity`, что и сегодня.

**Подтверждённое спаривание** (claim, приглашение устройства, подтверждённое приглашение человека):

```json
{"id": 1, "ok": true, "data": {
  "status": "paired",
  "identity": {"id": "u_3f2a1c9d40b7e518", "label": "User7421", "created": true, "owner": true}
}}
```

**Приглашение человека, ждущее владельца**:

```json
{"id": 1, "ok": true, "data": {
  "status": "pending",
  "request_id": "r_9c41e0b7",
  "expires_at": 1788496380
}}
```

`status` присутствует **всегда**, без `omitempty`, по той же причине, по которой всегда присутствуют `created` и `owner`: пропавшее значение читается как «не заявлено», а не как значение по умолчанию.

`identity` при `status: "pending"` отсутствует — личности ещё нет. Клиент, увидевший `pending`, обязан **ждать событие**, а не считать спаривание неудавшимся.

`expires_at` — крайний срок ответа владельца. Едет, чтобы приложение показало обратный отсчёт и не сочиняло его само.

**Повтор предъявления тем же ключом** возвращает записанное:

| Состояние приглашения | Ответ |
|---|---|
| ждёт владельца | тот же `pending` с тем же `request_id` |
| подтверждено | `paired` с личностью |
| отклонено | ошибка `pair_declined` |
| ожидание просрочено | ошибка `pair_timeout` |

Чужим ключом — `invalid_token` во всех четырёх случаях: погашенный токен не рассказывает постороннему даже о том, что он существовал.

**`device_key`, уже принадлежащий другому человеку, отвергается на предъявлении** — до того, как владельца о чём-либо спросят. Правило фазы 032 не меняется, меняется только момент: будить владельца вопросом, ответ на который заведомо не сработает, нельзя.

## §8A — `person.invite`

```json
{"id": 6, "cmd": "person.invite", "data": {}}
```

```json
{"id": 6, "ok": true, "data": {"token": "<16 байт, base64url>", "link": "https://nox.app/p/#…", "expires_at": 1788582480}}
```

Выпускает приглашение **нового человека** — не нового устройства. Заводит новую личность, а не привязывает ключ к существующей.

Доступна **только владельцу сервера**; всем остальным — `not_owner`. Это решение Q15 (владелец, 2026-09-04): приглашение — решение оператора машины, а не право участников пространства.

Живёт **24 часа**, против 10 минут у `device.invite`: своё второе устройство человек держит в руках, а чужому надо дойти сообщение.

Адрес в ссылке собирается так же, как для `device.invite`.

## §8A — `person.list`

```json
{"id": 7, "cmd": "person.list", "data": {}}
```

```json
{"id": 7, "ok": true, "data": {"people": [
  {"id": "u_3f2a1c9d40b7e518", "label": "Anna", "owner": true},
  {"id": "u_71b0e4d2aa38c169", "label": "Boris", "owner": false}
]}}
```

Люди круга. Доступна любому спаренному устройству: имена не секрет — они едут в каждом сообщении как `author_label`.

**Устройств, их количества, публичных ключей и времени последнего появления команда не отдаёт.** Вопрос «кто здесь живёт» — не вопрос «у кого сколько техники».

Это и есть то место, куда лёг признак владения, отложенный из фазы 033: `device.list` возвращает устройства одного человека, поэтому признак был бы одинаков во всех строках. Здесь строки — разные люди, и он наконец различает.

## §8A — `person.confirm`

```json
{"id": 8, "cmd": "person.confirm", "data": {"request_id": "r_9c41e0b7", "approve": true}}
```

```json
{"id": 8, "ok": true, "data": {"outcome": "approved"}}
```

Решение владельца по конкретному запросу. Доступна **только владельцу** — `not_owner` остальным.

Отказы: `not_found` — такого запроса нет либо он уже решён; `pair_timeout` — решение опоздало, ожидание уже истекло.

Ответ с **любого** устройства владельца решает за все: вопрос про машину, а не про аппарат.

## §8A — событие `person.pairRequested`

```json
{"seq": 0, "event": "person.pairRequested", "data": {
  "request_id": "r_9c41e0b7", "invited_at": 1788496080, "expires_at": 1788496380
}}
```

Уходит **всем живым подключениям владельца**, когда кто-то предъявил приглашение человека. Также досылается каждому устройству владельца сразу после успешного приветствия — по одному кадру на каждый ожидающий запрос: устройство могло быть выключено, а сервер перезапущен.

**О приглашённом не сообщается ничего.** До входа он — предъявленный токен: ни имени, ни аватара у него нет, а `platform`, которую прислало неаутентифицированное устройство, — утверждение, а не факт, и показывать его владельцу как факт нельзя.

`invited_at` — когда владелец выпустил это приглашение. Это то, что сервер знает, и то, чем владелец узнаёт своё приглашение среди нескольких.

Токен приглашения в событии **не едет**: подтверждающий называет запрос, а не предъявляет право.

## §8A — событие `person.pairResolved`

```json
{"seq": 0, "event": "person.pairResolved", "data": {
  "request_id": "r_9c41e0b7",
  "outcome": "approved",
  "identity": {"id": "u_71b0e4d2aa38c169", "label": "User3140", "created": true, "owner": false}
}}
```

```json
{"seq": 0, "event": "person.pairResolved", "data": {"request_id": "r_9c41e0b7", "outcome": "declined"}}
```

Уходит **и ждущему соединению, и всем устройствам владельца**: первому — чтобы узнать исход, вторым — чтобы вопрос исчез со всех экранов, а не только с того, где на него ответили.

`outcome` — `approved` · `declined` · `expired`. `identity` присутствует только при `approved` и по форме совпадает с ответом `pair`: `created` там всегда `true` (приглашение человека заводит личность), `owner` — всегда `false` (владение записывается только claim'ом, фаза 033).

**Оба события несут `seq: 0` и в журнал не попадают** — как `device.revoked` и `identity.updated`. Журнал общий, а кто подключается к машине — не общий мир (инвариант 3 сервера).

## Сроки, сведённые в одном месте

| Что | Сколько | Почему |
|---|---|---|
| claim-токен | без срока | умирает от использования; истекающий оставил бы свежий сервер невостребуемым |
| `device.invite` | 10 минут | дойти с телефоном до второго устройства успеть можно, скриншот QR через сутки — нет |
| `person.invite` | **24 часа** | ссылка едет через мессенджер, и адресат откроет её не сразу |
| ожидание подтверждения | **5 минут** с предъявления | владельцу — заметить, взять телефон, прочитать; приглашённому — не сидеть перед экраном впустую |
