# Data Model: Приглашение нового человека в круг

**Фаза 1** для [plan.md](./plan.md). Решения и их обоснования — в [research.md](./research.md).

## Сервер — SQLite

### `pair_tokens` (изменяется)

Одноразовое право. До этой фазы у токена было два состояния — «свежий» и «потрачен», — и второе описывало сразу и факт траты, и её исход. Приглашение человека разводит их: токен тратится в момент предъявления, а исход появляется позже и записывается отдельно.

| Поле | Тип | Было | Стало |
|---|---|---|---|
| `token` | TEXT PK | ✓ | без изменений |
| `kind` | TEXT NOT NULL CHECK | `claim`, `invite_device` | **+ `invite_user`** |
| `user_id` | TEXT NULL → `users` | кого приглашает | для `invite_user` — **кто выпустил** (владелец на момент выпуска) |
| `created_at` | INTEGER NOT NULL | ✓ | без изменений; для `invite_user` — то, что видит владелец в запросе |
| `expires_at` | INTEGER NULL | ✓ | без изменений; `invite_user` — `created_at + 86400` |
| `used_at` / `used_by` | INTEGER / TEXT NULL | ✓ | без изменений: предъявление тратит токен **сразу**, даже пока исход неизвестен |
| `paired_user_id` | TEXT NULL → `users` | ✓ | заполняется на подтверждении |
| `created_person` | INTEGER NOT NULL DEFAULT 0 | ✓ | заполняется на подтверждении |
| `request_id` | TEXT NULL | — | **новое.** Имя ожидающего запроса на проводе. Уникально |
| `awaiting_platform` | TEXT NULL | — | **новое.** Платформа предъявившего, чтобы завести строку устройства на подтверждении |
| `awaiting_until` | INTEGER NULL | — | **новое.** Крайний срок ответа владельца |
| `outcome` | TEXT NULL CHECK | — | **новое.** `NULL` пока не решено; `approved` · `declined` · `expired` |

```sql
kind TEXT NOT NULL CHECK (kind IN ('claim', 'invite_device', 'invite_user')),
...
request_id TEXT UNIQUE,
awaiting_platform TEXT,
awaiting_until INTEGER,
outcome TEXT CHECK (outcome IS NULL OR outcome IN ('approved', 'declined', 'expired'))
```

**Правила**:

- `awaiting_device` отдельной колонкой **не заводится**: предъявившее устройство — это `used_by`, уже существующая колонка с ровно этим смыслом. Вторая запись того же факта разошлась бы с первой (урок `claimed_at`, фаза 033).
- «Ожидает подтверждения» = `kind = 'invite_user' AND used_at IS NOT NULL AND outcome IS NULL`. Отдельного флага нет: состояние выводится из тех же трёх колонок, которыми оно и создаётся.
- Индекс `idx_pair_tokens_pending` по `(outcome, awaiting_until)` — единственный запрос подметальщика ходит по нему.
- `request_id` уникален и **случаен**: он попадает в кадры, идущие владельцу, и не должен позволять угадать соседний запрос.
- Правка идёт в `001_init.sql` **на месте** (пре-релизное правило владельца 2026-08-27). Базы прошлой фазы становятся несовместимыми — их ловит отпечаток схемы на старте (фаза 033).

### Состояния приглашения человека

| Состояние | `used_at` | `outcome` | Что отвечает `pair` |
|---|---|---|---|
| Выпущено, не предъявлено | NULL | NULL | заводит ожидание, отвечает «ждём» |
| Ожидает подтверждения | ✓ | NULL | тому же ключу — «ждём» (повторно); чужому — `invalid_token` |
| Подтверждено | ✓ | `approved` | тому же ключу — личность (обычный путь повтора фазы 032) |
| Отклонено | ✓ | `declined` | тому же ключу — `pair_declined`; чужому — `invalid_token` |
| Просрочено ожидание | ✓ | `expired` | тому же ключу — `pair_timeout`; чужому — `invalid_token` |
| Ссылка старше суток | NULL | NULL | `token_expired` |

Переход из `approved`, `declined` и `expired` **отсутствует**: исход записывается один раз и не пересматривается. Именно это делает повтор безопасным.

### `users`, `devices`, `server_identity` (не изменяются)

Новая личность заводится тем же `insertUser`, что и при claim, и не получает владения: владение записано у машины и появляется только в ветке claim (фаза 033).

## Сервер — типы Go

### `store.PairResult` (новый)

`Pair` перестаёт возвращать личность: у неё теперь есть исход, при котором личности ещё нет.

| Поле | Роль |
|---|---|
| `Identity` | кто получился — пусто, пока не подтверждено |
| `Pending` | ожидание заведено (или продолжается), личности нет |
| `RequestID` | имя ожидания на проводе; пусто, если не ожидание |

Возвращать `(Identity, error)` с пустой личностью и сентинельной ошибкой было бы дешевле по diff'у и дороже по смыслу: «принято, ждём» — не ошибка, а нормальный исход, и вызывающему пришлось бы отличать его от настоящих отказов по типу ошибки.

### `store.PendingRequest` (новый)

`RequestID`, `InvitedAt`, `ExpiresAt`, `AwaitingDevice`. Что подметальщик и досылка при приветствии знают о висящем запросе. `AwaitingDevice` наружу не уезжает — по нему сервер находит ждущее соединение.

### `store.Person` (новый)

`UserID`, `Label`, `Owner`. Строка `person.list`. Устройств и ключей в ней нет намеренно ([research.md](./research.md) Р7).

### `store.ErrNotOwner`, `ErrPairDeclined`, `ErrPairTimeout` (новые)

Три сентинели ровно под три кода провода. Существующие `ErrTokenInvalid` и `ErrTokenExpired` не трогаются.

## Провод — контракт v0

- `pair` (§8A) получает `status` в ответе: `paired` (с `identity`, как сегодня) либо `pending` (с `request_id`).
- Три команды: `person.invite`, `person.list`, `person.confirm`.
- Два события с `seq: 0`: `person.pairRequested`, `person.pairResolved`.
- Три кода: `not_owner`, `pair_declined`, `pair_timeout`.

Точная форма — в [contracts/](./contracts/).

`device.list` не меняется (FR-018).

## Клиент — Dart

### `PairOutcome` (новый, домен)

Что вернуло предъявление ссылки: `paired(identity)` · `declined` · `timedOut` · `refused(expired)`. Sealed-union, потому что четыре исхода ведут к четырём разным экранам, а не к одному с разным текстом.

### `PersonModel` (новый, домен)

`id`, `label`, `isOwner`. Строка экрана `People`.

### `PairRequest` (новый, домен)

`requestId`, `invitedAt`. Всё, что известно о постучавшемся, — и по [research.md](./research.md) Р6 больше знать неоткуда.

### Хранение

**Ничего нового не сохраняется.** Ожидание живёт на сервере; приложение, убитое во время ожидания, после запуска возвращается к экрану спаривания и предъявляет ту же ссылку заново — она действительна сутки, а исход, если он уже записан, придёт ответом.

### Поток

```
гость: ссылка ──→ pair ──→ status=pending ──→ ждёт person.pairResolved (5 мин + запас)
                                                        ▲
владелец: person.pairRequested ──→ AppRoot ──→ диалог/страница ──→ person.confirm ──┘
```

Обе стороны ведут в **один** ответ сервера: подтверждение решает запрос, а не «впускает кого-нибудь». Второй путь означал бы второй способ разойтись.
