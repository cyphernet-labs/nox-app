# Research: приложение через Tor (фаза 040)

Решения плана и то, на чём они держатся. Измерено или проверено сборкой там, где сказано «замерено» или «проверено»; остальное — из исходников и документации на 2026-10-03.

## Решение 1. Мост Rust ↔ Dart — native assets, C ABI, `@Native`

**Decision**: Rust-модуль живёт в локальном пакете `packages/nox_tor/` — участнике workspace корневого `pubspec.yaml`. Внутри пакета:
- `rust/` — крейт с `crate-type = ["staticlib", "cdylib"]`.
- `hook/build.dart` — сборка крейта build-хуком (`native_toolchain_rust` 1.0.4+0, `hooks`, `code_assets`).
- `lib/` — Dart-обёртка над функциями `@Native` из `lib/src/nox_tor_bindings.dart`.

Flutter сам кладёт библиотеку в сборку:
- iOS и macOS — `nox_tor.framework`;
- Android — `lib/<abi>/libnox_tor.so`;
- Windows — DLL рядом с exe.

На Linux хук ничего не собирает: Tor на Linux — отдельный этап.

**Rationale**:
- Native assets стабильны и включены по умолчанию во Flutter 3.44.1. NOX уже запускает такой хук через `objective_c`, зависимость `path_provider_foundation`.
- Не нужно ни CocoaPods-фаз, ни Gradle- и CMake-обвязки.
- Проверено в пробных приложениях на шаблоне NOX (AGP 9.0.1, Gradle 9.1): `nox_ping()` вернул 42 на macOS, на симуляторе iOS 26.4 и на эмуляторе Android arm64. Настоящий `arti-client` 0.47.0 собрался для macOS, iOS и Android и загрузился на эмуляторе API 30.
- Зависимостей без конфликтов:
  - добавляются только `native_toolchain_rust` 1.0.4+0 и `toml` 0.18.0;
  - `analyzer` в них нет, поэтому пин `mockito` 5.6.4 не задет;
  - 1.0.4+0 закреплена, потому что 1.0.7 требует `code_assets ^2`, а это блокирует `objective_c` 9.4.1.

**Хук делает три вещи помимо сборки:**
1. Возвращается сразу на `OS.linux`.
2. На Android направляет `CC_*`, `CXX_*` и `CARGO_TARGET_*_LINKER` на `clang` под API устройства `code.android.targetNdkApi`. Сам `native_toolchain_rust` берёт API 35, а минимум NOX — API 24 (issue #113 этой библиотеки).
3. Перечисляет `Cargo.toml`, `Cargo.lock` и `rust-toolchain.toml` в `output.dependencies`. Без этого правка одного `Cargo.toml` оставляла старую библиотеку.

Для iOS хук выставляет `IPHONEOS_DEPLOYMENT_TARGET=13.0`. Без этого C-зависимости собирались под iOS 26.5, а Rust — под 10.0, и линковка падала.

**Цена**: `flutter test` запускает хуки для хоста, поэтому `make gate` теперь собирает крейт под macOS.

| Прогон | Время |
|---|---|
| Первый, со скачиванием целей | около 2,5 мин |
| Повторный | около 2 с |
| После правки Rust | около 25 с |

Rust становится условием гейта наравне с Xcode. Два первых запуска хука одновременно сталкиваются в `~/.rustup/downloads`, поэтому на свежей машине один раз выполняется `rustup show active-toolchain` в `packages/nox_tor/rust`.

**Alternatives considered**:
- **flutter_rust_bridge 2.x.** Установленный codegen 2.11.1 падает на Gradle 9.1 (`cargokit … Could not find method exec()`). 2.13.0 работает, но требует:
  - фазы podspec только под CocoaPods;
  - Gradle- и CMake-обвязку, которая уже ломалась;
  - точной тройной фиксации версий: codegen = Dart-пакет = крейт.

  Единственный плюс — `flutter test` не компилирует Rust.
- **Готовые бинарники в git.** Тяжёлые и непроверяемые — плохо для продукта о безопасности.

## Решение 2. Tor-клиент — Arti 0.47.0 на Rust 1.93.1

**Decision**:
- `arti-client = "=0.47.0"` (Arti 2.7.0, 2026-10-01) и прямые зависимости `tor-hscrypto`, `tor-llcrypto`, `tor-keymgr`, `tor-config` той же версии.
- `rust-toolchain.toml` закрепляет 1.93.1 с целями: Apple darwin, ios и ios-sim, три Android ABI, Windows MSVC. Linux не нужен.
- Возможности: `tokio`, `rustls` с `ring`, `onion-service-client`, `static-sqlite`, `compression`, `keymgr`, `experimental-api`, `ephemeral-keystore`.
- `Cargo.lock` держит `libc` на 0.2.189 или ниже. 0.2.190 (2026-10-02) сделал `mach_absolute_time` только macOS-функцией, и `rand_jitter` из `tor-llcrypto` перестал собираться под iOS.
- Профиль release: `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, `strip`, `panic = "abort"`.

**Rationale**:
- 0.47.0 требует Rust 1.92 — проверено: 1.90 отказывает.
- Последняя версия, которую собирает 1.90, — 0.43.0. В ней нет исправлений безопасности 2.5–2.7, включая одно высокой серьёзности.
- 1.93.1 уже установлен на машине со всеми целями. Пин тулчейна в репозитории — то же, что FVM для Flutter.
- rustls с ring обходится без OpenSSL на всех платформах и меньше aws-lc на 0,4–0,6 МБ. Начиная с Arti 2.3 провайдер rustls нужно установить самим, иначе паника.

**Alternatives considered**:
- `native-tls` — Security.framework на Apple устарел и не договаривался о TLS 1.3 (#2475), а на Android нужен вшитый OpenSSL.
- `aws-lc-rs` — больше и капризнее при кросс-сборке.
- C tor как библиотека — другой язык, своя сборка под четыре платформы и не решение владельца №9.

## Решение 3. Ключ доступа — в памяти Arti, не на диске

**Decision**:
- Основное хранилище ключей Arti — эфемерное (`ArtiKeystoreKind::Ephemeral`).
- Ключ для onion-адреса кладётся через `TorClient::insert_service_discovery_key(KeystoreSelector::Primary, hsid, HsClientDescEncSecretKey)` и убирается через `remove_service_discovery_key`.
- Вставка не перезаписывает существующий ключ, поэтому смена одноразового ключа на свой — это снять, потом вставить.
- Закрытая часть приходит из защищённого хранилища приложения при каждом запуске Tor и на диск Arti не попадает.

**Rationale**:
- Arti ищет ключ при каждом `connect()`, поэтому ключ меняется без перезапуска клиента. Проверено сквозным тестом через живую сеть:
  - без ключа соединение отказывает за 4–9 с с `OnionServiceMissingClientAuth`;
  - с ключом соединяется;
  - после снятия ключа снова отказывает.
- Ключ, которого нет в списке сервиса, даёт `OnionServiceWrongClientAuth` — это сигнал «ключ не зарегистрирован или устройство отозвано».

**Alternatives considered**:
- Файлы `.auth_private` в C-tor-хранилище (`storage.keystore.ctor.clients`). Стабильный API, но закрытый ключ ложится на диск открытым текстом.
- Хранилище Arti по умолчанию пишет ключ на диск незашифрованным.

`experimental-api` не обещает semver — отсюда точный пин версии.

## Решение 4. Мост байтов — локальный порт с секретом

**Decision**:
- Пока путь идёт через Tor, модуль слушает `127.0.0.1:0`.
- Каждое принятое соединение сначала должно прислать 32-байтовый секрет этой сессии Tor; сравнение — за постоянное время.
- Затем модуль открывает `TorClient::connect((onion, 443))` с таймаутом и гоняет байты через `copy_bidirectional`.
- Подключиться можно только к onion-адресу, заданному приложением (FR-008).

На стороне Dart `PinnedHttpClient._connect` для хоста `.onion`:
1. Открывает `Socket.connect(127.0.0.1, port)`.
2. Пишет секрет.
3. Делает `SecureSocket.secure(socket, host: onion, supportedProtocols: ['http/1.1'])`.
4. Проверяет листовой сертификат по отпечатку — проверка та же, что на прямом пути.

WebSocket и байты файлов идут через этот клиент, поэтому оба транспорта получают Tor-путь без отдельной ветки (FR-009).

**Rationale**:
- Отпечаток проверяет Dart, как и сегодня; Tor ничего не удостоверяет.
- Секрет закрывает порт от других приложений устройства: на Android любое приложение может подключиться к чужому `127.0.0.1`.
- SNI и заголовок `Host` остаются onion-именем, как и ждёт сервер.

**Alternatives considered**:
- Поток байтов через FFI — сложно и медленно.
- SOCKS5 с паролем — та же защита, но больше кода с обеих сторон.

## Решение 5. Цена соединения через Tor и таймауты

**Замерено** (macOS, домашняя сеть):

| Шаг | Время |
|---|---|
| Холодный старт | 5,6 с |
| Тёплый старт | 0,55 с |
| Первое соединение с onion-сервисом | 11–13 с |

Каждое соединение **с ключом доступа** заново скачивает описание сервиса, 3–6 с: Arti сравнивает наборы ключей по указателю, и цепочка не переиспользуется. Иногда соединение виснет (#2166, #2482): 2 из 6 ждали до таймаута 120 с.

**Decision**:
- **Подъём**: бюджет 90 с на старт и первую готовность. Затем соединение с onion — 45 с на попытку, с повтором через лестницу переподключения.
- **Ответ на команду**: как сейчас, 10 с. Пока путь поднимается, команды ждут в очереди (FR-023).
- **Соединения**: одно долгое — WebSocket; HTTP-соединения для файлов переиспользуются в пределах простоя `HttpClient`.
- **Нынешний разрыв**: у `IOWebSocketChannel.connect` сейчас нет `connectTimeout`. Его ставит фаза: 45 с для onion, 10 с для прямого адреса.

**Rationale**: сеть Tor медленнее, и висящее соединение не должно держать приложение дольше бюджета. Своя реализация `HsClientConnector` с кэшем ключей могла бы убрать повторное скачивание, но она не проверена и экспериментальна — не в этой фазе.

## Решение 6. Устаревший клиент — перехватить выход Arti

Arti сверяет свои протоколы с консенсусом:
- **Нет рекомендованного протокола** — только запись `info!`.
- **Нет обязательного протокола на старте** — запуск отказывает с `ErrorKind::SoftwareDeprecated`.
- **Нет обязательного протокола во время работы** — `arti-client/src/client.rs`:
  1. запись `error!` с целью `arti_client::protostatus`;
  2. сообщение в stderr;
  3. 5 с асинхронного сна на runtime клиента;
  4. `std::process::exit(1)` — смерть приложения (#1932 открыт, отключить нельзя с 2.4.0).

**Decision**:
- Модуль ставит свой слой `tracing`. Событие с целью `arti_client::protostatus` уровня WARN и выше переводит состояние в `obsolete`.
- Управляющий поток модуля сворачивает tokio-runtime клиента (`shutdown_background`). Задача с `exit(1)` снимается на своём `sleep`, прежде чем дойдёт до выхода.
- Приложение запоминает «устарел» вместе с номером своей сборки. Tor в этой сборке больше не запускается, а человек видит просьбу обновиться (FR-026).
- `SoftwareDeprecated` на старте даёт то же состояние.

**Rationale**: runtime — наш, поэтому его остановка отменяет задачу Arti до выхода. Это прочитано в исходниках 0.47.0, а не замерено на живой сети, где такой консенсус не воспроизвести. Слой покрывается модульным тестом синтетическим событием. Риск записан: если Arti перенесёт выход в синхронный код, защита перестанет работать, и это ловится обновлением пина.

## Решение 7. Фон и сон

**Decision**:
- **Уход приложения в фон на iOS и Android**: Tor-клиент переводится в `DormantMode::Soft` — фоновая работа и паддинг останавливаются. Сокет живёт, пока его не заморозит ОС.
- **Возврат**:
  - `Normal`;
  - если сокет не на связи — немедленный выбор пути без ожидания лестницы;
  - если Tor-клиент не готов к трафику за 10 с — он пересоздаётся из тех же каталогов: тёплый старт около 0,5 с.
- **Desktop** в фоне не спит (FR-025 — только мобильные).

**Rationale**:
- У Arti нет более глубокого сна (#71, #90), обработка засыпания открыта (#2705).
- Возможное застревание менеджера каталогов с просроченным каталогом (#2740) лечится пересозданием клиента.
- Как Arti переживает приостановку iOS, нигде не опубликовано. Проверка — на устройстве, за владельцем.

## Решение 8. Выбор пути — до каждого набора сокета

**Decision**: решает `ConnectionPathSelector` в data-слое. `NoxSocketClient` спрашивает у него цель перед каждой попыткой: `_openOnce` и так перечитывает адрес на каждой попытке.

1. **Прямые кандидаты**, по порядку:
   - последний работавший адрес;
   - прямые адреса из списка сервера;
   - адрес из ссылки спаривания;
   - без повторов.

   Каждый проверяется TLS-рукопожатием с проверкой отпечатка и `GET /health`. Первый запускается сразу, остальные через 300 мс параллельно. Первый ответивший правильным ключом побеждает. Общий бюджет — 5 с (FR-002).
2. **Чужой ключ на прямом адресе** — «не дома»: кандидат отпадает (FR-005). В «чужой сервер» он не переводит.
3. **Если прямых нет**, Tor доступен (платформа, onion-адрес известен, ключ зарегистрирован, клиент не устарел), — поднять Tor с целью «свой onion» и своим ключом и отдать `wss://<onion>:443/ws`. Отказ отпечатка на этом пути — `serverMismatch` (FR-030).
4. **Иначе** — «пути нет», и сокет уходит в лестницу ожидания.

**Возврат на прямой**:
- **Пока путь — Tor**: при смене сети и раз в 2 минуты кандидаты проверяются заново. Ответил — сокет переключается на прямой адрес, Tor останавливается, когда новое соединение на связи (FR-003, SC-002).
- **Пока путь прямой**: смена сети проверяет текущий адрес. Если он не отвечает, сокет переподключается через выбор пути.

**Без потерь** (FR-004): новый путь проверен до того, как старый закрыт. Сообщения не теряются и не задваиваются по устройству протокола:
- пропущенное докатывается с `since`;
- дубли отбрасываются по `seq`;
- повтор отправки идемпотентен по `client_message_id`.

**Проверки — своим клиентом.** Сокет сейчас узнаёт об отказе пина по счётчику всего процесса. Проверка, идущая параллельно с набором сокета, приписала бы свой отказ сокету, поэтому проверки работают через отдельный экземпляр `PinnedHttpClient`.

**Alternatives considered**:
- Держать два сокета одновременно — сокет-клиент один на процесс, а протокол и так даёт отсутствие потерь.
- Пробовать Tor параллельно с прямым путём — противоречит решению владельца №1 и тратит батарею.

## Решение 9. Список адресов, эпоха и миграция

**Decision**:
- **Хранение**: список адресов лежит в защищённом хранилище одной записью JSON `session.server_addresses`: `direct`, `onion`, `last_good`. Обновляется из `addresses` в ответе на приветствие и из события `server.addresses` (seq 0, рядом с `device.revoked` и `identity.updated` в `SyncService`). Адрес из ссылки (`session.server_address`) остаётся отдельно как исходный.
- **Эпоха** — `fp:<отпечаток>` вместо `live:<адрес>`.
- **Миграция**: если сохранённая эпоха начинается с `live:`, она переписывается на `fp:<отпечаток>` без стирания (FR-012). Сервер за этим адресом уже проверен по отпечатку с фазы 036, так что это тот же мир.

**Rationale**:
- Без миграции смена ключа эпохи один раз стёрла бы чаты у всех обновившихся.
- Onion-адрес даёт узнать, в сети ли сервер, поэтому он не лежит в обычных настройках и не попадает в логи (FR-013).

## Решение 10. Ключ доступа устройства

**Decision**:
- **Создание и хранение**: X25519 из уже подключённого `cryptography` 2.9.0 (`X25519()`). Закрытая часть — в защищённом хранилище `session.access_key`, без синхронизации: на iOS `synchronizable` по умолчанию выключен, а ключ Android Keystore не переносится резервной копией.
- **Регистрация**: при первом приветствии с `addresses` после спаривания или обновления приложение один раз шлёт `device.setAccessKey`, а при успехе ставит `session.access_key_registered`. Повтор того же ключа сервер принимает без последствий. Так закрываются и сервер, обновлённый после спаривания, и устройство, спаренное до 039.
- **Отказы**:
  - `invalid_request` — новый ключ и повтор, не больше 3 раз за сессию (FR-017);
  - `unauthenticated` — нынешний путь отзыва.
- **В спаривании** `access_key` уходит всегда: безопасно для любого сервера (§2.1).

## Решение 11. Ссылка версии 2 и приглашение с onion

**Decision**:
- **Разбор ссылки**: `PairingLink` принимает версию 2 с полями `onion_pub` (32), `onion_port` (2) и `one_time_priv` (32). Onion-адрес из `onion_pub` выводит модуль Rust — функция `nox_tor_onion_from_pubkey`, SHA3-256 по rend-spec-v3. В Dart SHA3 нет, а тестовый вектор уже есть в 039.
- **На Linux** поля onion читаются, но не используются.
- **Спаривание по v2**:
  1. Сохраняются адрес, отпечаток, onion-адрес и одноразовый ключ — временно, `session.invite_access_key`.
  2. Выбор пути пробует прямой адрес ссылки, затем Tor с одноразовым ключом.
  3. Спаривание передаёт свой `access_key`.
  4. После ответа — удачного или нет — одноразовый ключ стирается (FR-021), а ключ Tor-клиента меняется на свой.
- **Приглашение**: `DeviceRepository.inviteDevice` всегда просит `{"onion": true}` и возвращает ссылку вместе с флагом `onion`. Если флаг `false`, карточка приглашения говорит, что ссылка работает только в домашней сети (FR-019).
- **Ссылка v1 без связи** — сообщение «Couldn't reach your server. Pairing works on your home network.» (FR-022).

## Решение 12. Состояние связи для интерфейса

**Decision**: новая доменная служба `ConnectionStatusService` отдаёт `ConnectionStatus`:
- `state` — `connecting`, `catchingUp`, `online`, `offline`, `serverMismatch` или `unsupported`;
- `path` — `direct`, `tor` или «нет»;
- `torObsolete`.

Разведение по окружениям:
- `dev`: живая реализация — фаза сокета плюс события выбора пути;
- `prod` и `test`: выводится из нынешней `SessionPhaseService`.

**Сглаживание**: `offline` наступает после первого неудачного полного раунда выбора пути и держится на повторных попытках до первого успеха. Так баннер «No connection» не мигает на каждом повторе.

**Потребители**:
- три блока с баннерами (`ChatsListBloc`, `ChatThreadBloc`, `ChatCardBloc`) берут `isOffline` и `isServerMismatch` у новой службы. Сегодня `isOffline = !phase.isCurrent`, и баннер горит даже при подключении — это противоречит решению «в углу Connecting…»;
- новый виджет угла `AppConnectionIndicatorWidget` со своим блоком.

`SessionPhaseService` не меняется: её используют очередь отправки, предзагрузка, просмотр файла и устройства, и восемь частных фейков в тестах остаются целы.

**Нажатие на индикатор** открывает короткое пояснение: каким путём идёт связь и, на iOS и macOS, где включить доступ к локальной сети, если человек дома. Это закрывает подсказку FR-032 без ненадёжного распознавания запрета.

## Решение 13. Платформы, разрешения, обязательные мелочи

- **iOS и macOS**: `NSLocalNetworkUsageDescription` в `Info.plist`: «NOX connects to your server on your home network.».
- **macOS**: в Release-entitlements добавляется `com.apple.security.network.server` — локальный порт моста слушает внутри песочницы. В DebugProfile он уже есть.
- **Android**: INTERNET приходит в release только через слияние манифестов зависимостей. Фаза объявляет его в основном манифесте явно.
- **Linux**: `TorCapability` ложна, путь только прямой, Tor-состояний нет.
- **Windows**:
  - код тот же, что на macOS;
  - собрать отсюда нельзя — `cargo check` под MSVC падает на C-заголовках у ring и sqlite;
  - #2726 сообщает о зависании загрузки на Windows 11;
  - проверка — на Windows, за владельцем.
- **Жизненный цикл** — новая служба `AppLifecycleService` на `AppLifecycleListener`. Сегодня приложение жизненный цикл не слушает вовсе.
- **Смена сети** — `ConnectivityService` получает поток смен сети. Сегодня в живом окружении смену сети не слушает никто.

## Решение 14. Замер (FR-034) — первая работа реализации
