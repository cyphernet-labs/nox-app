## User Scenarios & Testing *(mandatory)*

### User Story 1 - Владелец запускает сервер локально и обменивается сообщениями (Priority: P1)

Владелец собирает сервер одной командой, запускает его на своей машине и из двух терминалов (websocat) проходит полный цикл: подключение, создание чата, отправка сообщения — второй подключённый клиент видит событие о новом сообщении вживую.

**Why this priority**: это и есть цель фазы — «пощупать» работающий канал руками; без этого сценария фича не демонстрируема.

**Independent Test**: полностью проверяется двумя websocat-сессиями против локально запущенного процесса; ценность — работающий обмен сообщениями end-to-end.

**Acceptance Scenarios**:

1. **Given** собранный бинарник и пустой каталог данных, **When** владелец запускает процесс с адресом и путём к БД, **Then** процесс стартует, применяет миграции с нуля и отвечает на `GET /health` признаком живости.
2. **Given** запущенный сервер, **When** клиент открывает WebSocket-соединение, **Then** первым кадром приходит приветствие сервера (`srv` с challenge), и до `session.hello` никакая другая команда не принимается.
3. **Given** два подключённых клиента, прошедших `session.hello`, **When** первый выполняет `chat.create` и `message.send`, **Then** первый получает ответы-эхо на свои `id`, а второй — события `chat.created` и `message.new` с монотонно растущими `seq` и полными данными сущностей.
4. **Given** сообщение отправлено повторно с тем же `client_message_id` (повтор после обрыва), **When** сервер получает дубль, **Then** он возвращает прежнее эхо и не создаёт вторую запись.

---

### User Story 2 - Клиент переподключается и догоняет пропущенное (Priority: P2)

Клиент обрывает соединение (закрыл терминал), в его отсутствие другие пишут сообщения; при переподключении он передаёт последний обработанный `seq` и получает всё пропущенное, затем живой поток — без потерь, с возможными дубликатами на стыке.

**Why this priority**: курсорная синхронизация — архитектурное сердце всего протокола (replay = наша гарантия доставки); bootstrap без неё — просто эхо-сервер.

**Independent Test**: kill второго терминала → N сообщений от первого → переподключение с `since` → пришли ровно пропущенные события в порядке `seq`, затем live.

**Acceptance Scenarios**:

1. **Given** клиент знает последний обработанный `seq` = S, **When** он подключается и передаёт `since = S` в `session.hello`, **Then** в ответе приходит текущий `cursor`, после чего досылаются все события с `seq > S` в порядке возрастания, и затем поток становится живым.
2. **Given** клиент подключается впервые (без `since`), **When** проходит `session.hello`, **Then** replay не выполняется, а клиент получает `cursor` как стартовую точку.
3. **Given** во время replay появляется новое живое событие, **Then** клиент получает и его; дубликат события на стыке допустим, и клиент отличает его по `seq`; потеря события недопустима.
4. **Given** ответ `session.hello` с `cursor = C`, **When** клиент обработал событие с `seq ≥ C`, **Then** клиент вправе считать себя догнанным.

---

### User Story 3 - Сервер корректно живёт под нагрузкой обрывов и остановки (Priority: P3)

Медленный или зависший клиент не влияет на остальных; остановка процесса (Ctrl+C) завершает всё аккуратно: соединения получают прощальный код закрытия, база закрывается целой, повторный запуск поднимает всё с того же места.

**Why this priority**: это свойства «инфраструктуры, которой можно доверять» — без них сценарии 1–2 работают только в идеальных условиях.

**Acceptance Scenarios**:

1. **Given** клиент перестал читать свои кадры, **When** его буфер исходящих на сервере переполняется, **Then** сервер разрывает только это соединение с кодом «policy violation», остальные клиенты продолжают получать события без задержки.
2. **Given** запущенный сервер с активными соединениями, **When** процесс получает сигнал остановки, **Then** REST-запросы дорабатывают, WebSocket-клиенты получают код «going away», процесс завершается за ограниченное время, и следующий запуск проходит миграции/чтение базы без ошибок.
3. **Given** пауза в обмене дольше типичного тайм-аута NAT, **When** соединение простаивает, **Then** периодический ping удерживает его живым, а неотвечающий клиент обнаруживается и отключается.

---

### Edge Cases

- Кадр не является JSON-объектом или не содержит ни `cmd`, ни ожидаемых полей → ответ `invalid_request` (для кадров с `id`) либо разрыв соединения при неразбираемом потоке; сервер не падает.
- Неизвестное имя команды → `invalid_request`; неизвестные поля внутри известных кадров игнорируются (эволюция v0).
- Команда до `session.hello` → отклоняется; повторный `session.hello` в том же соединении → отклоняется.
- `session.hello` с несовместимой версией схемы → `unsupported_schema`.
- Кадр больше объявленного лимита → соединение закрывается по превышению лимита чтения.
- `since` больше текущего `cursor` (клиент «из будущего» — база сервера откатилась) → определено детерминированное поведение: replay пуст, клиент получает актуальный `cursor`; расхождение фиксируется в логе.
- Два одновременных `chat.create` с одинаковым именем → ровно один успех, второй получает `name_taken` (правила имени — по контракту §4).
- Обрыв соединения посреди replay → при следующем подключении с тем же `since` клиент получает те же события заново (идемпотентность по `seq`).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сервер принимает WebSocket-соединения и ведёт обмен кадрами конверта v0 (приветствие `srv`, команда, ответ, событие) в точном соответствии с контрактом §2, включая правило «ровно один ответ на каждый `id`».
- **FR-002**: Первый кадр каждого соединения — приветствие сервера с challenge; поля подписи в `session.hello` принимаются и игнорируются (этап 1 без аутентификации; никакие проверки подписи/токенов не реализуются).
- **FR-003**: `session.hello` возвращает версию схемы, объявленные лимиты и identity-заглушку (label, назначаемый сервером на соединение) и запускает механизм подписки и replay по правилам контракта §3, включая семантику первого подключения и правило «догнан».
- **FR-004**: Реализованы команды `chat.create` и `message.send` c полной цепочкой «мутация + событие атомарно, доставка события всем подписчикам после фиксации»; `message.send` идемпотентен по `client_message_id`.
- **FR-005**: События `chat.created` и `message.new` несут полные данные сущности и глобально монотонный `seq`; события воспроизводимы по `since` сколько угодно раз с тем же результатом.
- **FR-006**: Данные переживают перезапуск процесса: чаты, сообщения и журнал событий хранятся во встроенной базе; схема создаётся миграциями с нуля при первом запуске.
- **FR-007**: Медленный клиент отключается по переполнению его буфера с кодом «policy violation», не влияя на остальных; простаивающие соединения поддерживаются периодическим ping.
- **FR-008**: `GET /health` отвечает признаком живости процесса.
- **FR-009**: Остановка по сигналу выполняет упорядоченное завершение: дорабатывает HTTP, закрывает WebSocket-соединения кодом «going away», останавливает рассылку, закрывает базу.
- **FR-010**: Ошибки отвечаются только кодами из контракта §2.1; неизвестные команды — `invalid_request`; несовместимая схема — `unsupported_schema`.
- **FR-011**: В корне `client_backend/` задокументированы (README): команды сборки, запуска, флаги/переменные конфигурации и **пошаговый websocat-сценарий** ручной проверки (сценарии историй 1–2), выполнимый владельцем без чтения кода.

### Key Entities

- **Chat** — чат открытого пространства: идентификатор, имя (правила — контракт §4), время создания, label создателя, время последней активности.
- **Message** — сообщение: идентификатор, `seq` своего события, чат, автор (identity-заглушка этапа 1), тело, время; ключ идемпотентности `client_message_id`.
- **Event** — запись журнала: глобальный `seq`, тип, полезная нагрузка события; единственный источник replay.
- **Session/Connection** — активное соединение: буфер исходящих, статус подписки, курсор клиента.

## Success Criteria *(mandatory)*

- **SC-001**: Владелец, следуя README, от чистого клона доходит до работающего локального сервера и успешного сценария истории 1 не более чем за 10 минут, не заглядывая в код.
- **SC-002**: Сообщение, отправленное одним клиентом, появляется у второго подключённого клиента менее чем за 1 секунду на локальной машине.
- **SC-003**: После обрыва и переподключения с `since` клиент получает 100% пропущенных событий (потерь нет) в правильном порядке; дубликаты возможны только на стыке replay/live.
- **SC-004**: Повторная отправка с тем же `client_message_id` никогда не создаёт дубликат сообщения (0 дублей на любой серии повторов).
- **SC-005**: Остановка сервера по сигналу завершается корректно (клиенты получают код закрытия, процесс выходит) в пределах 10 секунд; после 100 циклов «запуск → обмен → остановка» база остаётся целой.
- **SC-006**: Отказ одного клиента читать поток не увеличивает задержку доставки остальным (события продолжают приходить < 1 с).

## Assumptions

- Локальный запуск этапа 1 — без TLS (loopback); wss/пиннинг приходят с этапом 2/деплоем — на смоук-сценарий это не влияет.
- Identity-заглушка: сервер назначает соединению label вида `User<n>`; постоянных личностей на этапе 1 нет (появятся со спариванием).
- Из готового набора контракта в bootstrap входят только `chat.create` + `message.send` (+ `session.hello`); остальные команды §4–§5 — фаза 023, файловые — 024.
- Лимиты (`max_message_bytes` и др.) — константы конфигурации со значениями из примера контракта §3.
- Ручной сценарий владельца использует websocat (установлен); README приводит точные команды.

## Out of Scope

- Аутентификация, спаривание, токены, проверка подписи (этап 2; конституция Принцип VII).
- Команды `chats.list`, `chat.get`, `chat.rename`, `chat.nameAvailable`, `messages.list`, `chat.files`, событие `chat.updated` (фаза 023), файловая цепочка (фаза 024), push, `chat.markRead`.
- Интеграция Flutter-приложения (клиентский трек, после 022–023).
- TLS, туннель, страница спаривания, бэкапы `VACUUM INTO` (деплой-работы).
