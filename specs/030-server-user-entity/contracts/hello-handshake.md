# Контракт: приветствие после фазы 030

Готовые правки для `docs/client-backend/protocol/contract-draft.md` §3. **Применяются первыми, до кода** (Принцип VII). Здесь — целевое состояние; ниже каждой правки указан якорь в текущем файле.

## 1. Запрос `session.hello`

**Якорь:** блок JSON перед строкой 100.

```json
{"id": 1, "cmd": "session.hello", "data": {
  "schema": 1,
  "since": 1041,
  "label": "Anna",
  "login_ref": "ebd1cf0d547f0c4f025f2ab7a6dd2a01d6cd4c6c32c9a7c402a09d10e70752b5",
  "device_key": "<base64 Ed25519 pub>",
  "signature": "<base64: подпись challenge>"
}}
```

## 2. Ответ

**Якорь:** блок JSON на строках 102–108.

```json
{"id": 1, "ok": true, "data": {

  "cursor": 1042,
```

## 3. Правки пунктов

### 3.1. `identity` — снятие блокировки Q11 и уточнение обязанности клиента

**Текущий текст (строка 116):**

> **`identity`** — авторитет по собственной личности: `id` — собственный author-id клиента (им ключуется own/other-разметка сообщений; формат — за Q11), `label` — текущее имя. **Обязанность клиента:** персистить оба в сессию при каждом подключении и раскатывать по поверхностям (существующий канал `watchLabel`); префилл экрана выбора имени берётся отсюда, не из константы. Это же закрывает догоняющее обновление label, изменённого с другого устройства офлайн.

**Заменить на:**

> **`identity`** — авторитет по собственной личности: `id` — собственный author-id клиента (им ключуется own/other-разметка сообщений), `label` — текущее имя. **Формат `id`:** `u_` + 16 строчных шестнадцатеричных знаков; выдаётся сервером, непрозрачен для клиента, разбору не подлежит. Не совпадает ни с каким секретом входа (**Q11 закрыт 2026-09-02**). **Обязанность клиента:** персистить оба в сессию при каждом подключении **сессии, у которой есть вошедший человек**, и раскатывать по поверхностям (существующий канал `watchLabel`); подключение без входа личность **не усваивает** — иначе следующий вошедший унаследует чужое имя и чужой author-id. Префилл экрана выбора имени берётся отсюда, не из константы. Это же закрывает догоняющее обновление label, изменённого с другого устройства офлайн.

### 3.2. `label` — одноразовое заявление

**Текущий текст (строка 117):**

> **`label`** (необязательное; **поле этапа 1**) — желаемый label соединения; без него сервер назначает `User<n>`. Личности на этапе 1 не персистятся. На этапе 2 источником label становится сервер (спаривание), и поле уходит из контракта.

**Заменить на:**

> **`label`** (необязательное; **поле этапа 1**) — заявление «я только что переименовался», **а не** «вот моё имя». Клиент присылает его только после реального переименования (включая выбор имени при онбординге) и перестаёт, как только сервер подтвердил новое имя в ответе. **Приветствие без `label` имя не меняет.** Причина нормативна: устройство с устаревшим кэшем, присылающее имя при каждом подключении, возвращает старое имя поверх нового — переименования начинают пинг-понговать между устройствами одного человека. Без заявленного имени у новой личности сервер назначает `User<случайное четырёхзначное число>`. Сервер не проверяет длину, набор символов и уникальность и **не может отказать в приветствии из-за имени**. На этапе 2 источником label становится сервер (спаривание), и поле уходит из контракта.

### 3.3. `login_ref` — новый пункт

**Вставить после пункта `label`:**

> **`login_ref`** (необязательное; **поле этапа 1**) — односторонняя производная от идентификатора входа, по которой сервер узнаёт **человека**. Сам идентификатор входа устройство не отправляет никогда. Формула закреплена контрактом, потому что детерминированность между установками — свойство провода, а не деталь клиента: строчный hex от `SHA-256("nox/login-ref/v1:" ‖ идентификатор в UTF-8)`, ровно 64 знака. Контрольный вектор: идентификатор `abc` даёт `login_ref` = `ebd1cf0d547f0c4f025f2ab7a6dd2a01d6cd4c6c32c9a7c402a09d10e70752b5`. **Сервер эту производную не вычисляет и не проверяет** — только ищет по ней строку и хранит как непрозрачный ключ; сам идентификатор входа не хранится ни в каком виде. Поле присутствует **только** в `session.hello` — никогда в ответе, событии и модели на проводе. На этапе 2 уходит из контракта вместе со входом по идентификатору (§8.1).

### 3.4. `device_key`/`signature` — этап 1 больше не игнорирует ключ

**Текущий текст (строка 118):**

> **`device_key`/`signature`** — аутентификация подключением: подпись `challenge` из приветствия сервера (§2) ключом устройства. Входа по идентификатору-секрету в контракте **не существует** — устройство авторизуется спариванием, соединение — подписью. ⚠️ **На этапе 1 поля игнорируются** — это единственное отличие этапа 1 от контракта.

**Заменить на:**

> **`device_key`/`signature`** — аутентификация подключением: подпись `challenge` из приветствия сервера (§2) ключом устройства. Входа по идентификатору-секрету в контракте на этапе 2 **не существует** — устройство авторизуется спариванием, соединение — подписью. ⚠️ **Этап 1:** `device_key` несёт **непрозрачный идентификатор установки**, а не ключевой материал; сервер его записывает и связывает с личностью, но ничего им не доказывает. Сервер не проверяет его длину и формат и не может отказать в приветствии из-за него. `signature` игнорируется. На этапе 2 меняется только **значение** `device_key` (настоящий публичный ключ) и включается проверка `signature` — форма кадра и путь поиска не меняются.

### 3.5. `journal_id` — новый пункт

**Вставить после пункта `limits`:**

> **`journal_id`** — идентификатор **хранилища** сервера, выданный один раз при его создании. Клиент обязан хранить его рядом с локальным кэшем и при **любом** расхождении считать, что мир, который он кэшировал, исчез: полностью сбросить кэш переписки, отметку синхронизации и запомненный `identity.id`, затем подключиться заново. Правило существует потому, что по одному лишь курсору пересборку хранилища не распознать: пересобранное и уже обогнавшее прежнюю отметку хранилище от приветствия неотличимо, и клиент молча применил бы чужие события с совпавшими номерами. Проверка выполняется **до** применения первого кадра replay.

### 3.6. Датированная пометка о смене смысла

**Вставить в конце списка пунктов §3:**

> ⚠️ **Смена смысла 2026-09-02 (фаза 030).** До этой даты при `schema: 1` поля `identity.id` и `author_id` (§5) везли отображаемое имя; после — публичный `user_id`. Номер схемы намеренно не поднят: развёрнутых установок не было, а `unsupported_schema` отправил бы существующие сборки в фатальный экран. Кадры, снятые до этой даты, несовместимы по смыслу — записанные ранее фикстуры и базы подлежат пересозданию.

## 4. Правки §5 (сообщения)

### 4.1. `author_id`

**Текущий текст (строка 174):** `"author_id": "<см. §8.1 — Q11>", "author_label": "Anna",`

**Заменить на:** `"author_id": "u_3f2a1c9d40b7e518", "author_label": "Anna",`

Добавить пункт:

> **`author_id`/`author_label`** — `author_id` называет **личность** (формат — §3), `author_label` — вмороженная копия её имени **на момент отправки**: позднейшее переименование автора её не меняет, поэтому история показывает то имя, которое было тогда.

### 4.2. Правило `client_message_id`

Дополнить существующее правило §5:

> Собственное — это `author_id == identity.id`, то есть **личность, а не устройство**: второе устройство того же человека тоже получает `client_message_id` чужой отправки. Незнакомый ключ клиент обязан считать отсутствующим — сверка идёт по его собственной очереди исходящих.

## 6. Что MUST NOT меняться

- Четыре вида кадров (`srv`/`cmd`/`ok`+`error`/`event`) и правило игнорирования неизвестных полей.
- Форма `Message`, `Chat`, событий и их типов.
- Набор кодов ошибок §2.1: **новый код не вводится**. Все отказы фазы уже покрыты — неизвестный `login_ref` не отказ (создаётся личность), чужой след на известном устройстве не отказ (перепривязка), отсутствие обоих полей не отказ (FR-009), неподходящее имя не отказ (FR-020), сбой записи → `internal`.
- Правило порядка «подписка → replay → live» и семантика `since`/`cursor`.
- `schema` остаётся `1`.
