# Контракт: опознание личности

Внутренний контракт сервера — то, что обязано быть истинным независимо от реализации, и то, на что пишутся тесты. Форма провода — в [hello-handshake.md](./hello-handshake.md).

---

## 1. Вход и выход

**Вход:** `loginRef` (может быть пустым), `deviceKey` (может быть пустым), `label` (может быть пустым).

**Выход:** `Identity{UserID, Label}` — та личность, от имени которой соединение будет писать и по которой будет размечаться «своё/чужое».

Разрешение выполняется **один раз за соединение**, до регистрации в хабе, и результат далее не меняется: дубликат приветствия отвергается, поэтому кросс-горутинное чтение результата безопасно ровно по той же причине, которая уже записана для сегодняшнего поля имени.

---

## 2. Инварианты

| # | Инвариант | Почему |
|---|---|---|
| **I1** | Один и тот же непустой `loginRef` всегда даёт один и тот же `UserID` | US2: переустановка и вторая машина |
| **I2** | Один и тот же непустой `deviceKey` при пустом `loginRef` всегда даёт один и тот же `UserID` | US1: то же устройство узнаётся без ввода |
| **I3** | Непустой `loginRef` перевешивает `deviceKey`: при расхождении устройство перепривязывается | Иначе старое устройство удерживает чужую переписку |
| **I4** | Приветствие **никогда** не отклоняется из-за содержимого `loginRef`, `deviceKey` или `label` | FR-009, FR-020; отказ терминален на клиенте |
| **I5** | Пустые `loginRef` и `deviceKey` дают личность, **не записанную** в базу | Пробники и сканеры не оставляют мусорных строк |
| **I6** | Пустой `label` **не** меняет имя существующей личности | Иначе пинг-понг переименований между устройствами |
| **I7** | Разрешение не пишет строку в журнал событий | Создание личности на проводе не видно |
| **I8** | Всё разрешение — одна транзакция записи | Одновременные первые подключения не задваивают личность |
| **I9** | `created_at` устройства переживает перепривязку; `last_seen_at` двигается всегда | Момент появления устройства — факт, а не следствие последнего входа |

## 3. Алгоритм

```
BEGIN IMMEDIATE

  identity := nil

  IF loginRef != "":
      identity := SELECT users WHERE id_digest = loginRef
      IF identity == nil:
          identity := INSERT users (mintUserID(), mintLabel(label), loginRef, now)

  IF identity == nil AND deviceKey != "":
      d := SELECT devices WHERE device_key = deviceKey
      IF d != nil:
          identity := SELECT users WHERE user_id = d.user_id
      ELSE:
          identity := INSERT users (mintUserID(), mintLabel(label), NULL, now)

  IF identity == nil:                      -- I5: ни следа, ни устройства
      COMMIT
      RETURN Identity{mintUserID(), mintLabel(label)}   -- в памяти, не записана

  IF deviceKey != "":
      UPSERT devices SET user_id = identity.user_id, last_seen_at = now
             ON INSERT created_at = now                 -- I9

  IF label != "" AND label != identity.label:           -- I6
      UPDATE users SET label = label WHERE user_id = identity.user_id
      identity.label := label

COMMIT
RETURN identity
```

`mintLabel(label)` = `label`, если не пусто, иначе `User` + случайное четырёхзначное число из `crypto/rand`, с ограниченным числом попыток избежать уже занятого имени. Исчерпание попыток **не** отказ — выдаётся последнее сгенерированное (I4).

`mintUserID()` = `u_` + 16 строчных hex из `crypto/rand`.

---

## 4. Ленивая материализация

Личность, возвращённая по I5, существует только в памяти соединения. Она материализуется **при первой отправке сообщения** — единственном пути, которому нужна родительская строка из-за внешнего ключа `messages.author_id`.

```
handleMessageSend:
    IF identity не материализована:
        INSERT users (identity.UserID, identity.Label, NULL, now)
        пометить материализованной
    ... обычная отправка
```

Вставка идёт в **той же транзакции**, что и сообщение: наполовину созданная личность без сообщения не имеет смысла, а наполовину созданное сообщение без личности нарушает внешний ключ.

---

## 5. Где результат используется

Три места сравнения личности, все сегодня получающие отображаемое имя, переводятся на `identity.UserID`:

| Путь | Что решает | Последствие ошибки |
|---|---|---|
| выдача истории (`messages.list`) | срезать ли `client_message_id` у чужих | автор не получает собственный ключ отправки — вся его история |
| досылка пропущенного (replay) | полный или урезанный кадр | то же на догоняющей синхронизации |
| живая доставка | полный или урезанный кадр | то же в реальном времени |

Отправка сообщения передаёт `identity.UserID` как `author_id` и `identity.Label` как `author_label` — **два разных значения**, впервые за существование сервера.

## 6. Журналирование

Разрешение личности **не логирует** ни `loginRef`, ни `deviceKey`, ни `user_id`, ни `label` (Принцип I). Допустимы только безличные факты: «личность создана», «устройство перепривязано». Сбои логируются как ошибка без предъявленных значений.

---

## 7. Проверяемость

Каждый инвариант проверяется отдельным тестом:

| Инвариант | Тест |
|---|---|
| I1 | два приветствия с одним `loginRef` и **разными** `deviceKey` → один `identity.id`, две строки `devices` |
| I2 | два приветствия с одним `deviceKey` без `loginRef` → один `identity.id` |
| I3 | устройство известно, `loginRef` другого человека → `identity.id` второго, `devices.user_id` перепривязан, `created_at` не изменился |
| I4 | приветствия с пустыми, очень длинными и не-hex значениями → `ok`, ни одного `error` |
| I5 | приветствие без обоих полей → `ok`, `COUNT(*) FROM users` не вырос |
| I6 | приветствие без `label` после переименования → имя не откатилось |
| I7 | `MAX(seq) FROM events` не изменился после серии приветствий |
| I8 | `testing/synctest`: N одновременных первых приветствий с одним `loginRef` → одна строка `users` |
| I9 | перепривязка не меняет `created_at`, но двигает `last_seen_at` |
