# Feature Specification: Инициализация дизайн-системы в `lib/design` (всё, кроме виджетов)

**Feature Branch**: `002-design-system-init`

**Created**: 2026-06-14

**Status**: Draft

**Input**: Реализовать существующую дизайн-систему NOX (`docs/design/`) в коде по архитектурному блюпринту (`docs/blueprints/mobile/`), «натянув» её на `lib/design`. Интересует **абсолютно всё, кроме виджетов**.

> **Авторитет по «как»:** блюпринт `docs/blueprints/mobile/` (особенно `06-theming.md`, плюс `01-stack-and-tooling.md` и `10-code-templates.md`). **Источник истины дизайна:** `docs/design/spec/design-system.md` (UI/UX-спека, v0.2) и машинные токены `docs/design/system/nox-handoff/tokens/*.tokens.json` (W3C DTCG) → генерируемый Dart `docs/design/system/nox-handoff/flutter/nox_*.dart`. Каталог-дубликат `docs/design/system/nox-handoff-2/` авторитетным не считается. **Управляющий принцип:** конституция v1.1.0, Принцип IV (верность дизайн-системе). Эта спека фиксирует **что** и **границы объёма**; конкретные шаги реализации выводятся из блюпринта на этапах plan/tasks.

> **Природа фичи — инфраструктурная.** Это инициализация дизайн-слоя приложения, а не продуктовая фича. Технологические упоминания в требованиях (ColorScheme, ThemeData, токены, шрифты) — это зафиксированные ограничения конституции и блюпринта, а не «протёкшая» реализация. Критерии успеха намеренно сформулированы как наблюдаемые свойства (покрытие, верность токенам, отсутствие хардкода, зелёный gate), проверяемые без знания деталей кода.

> **Текущее состояние.** Дизайн-слой уже частично заскаффолжен в Feature-001: генерируемый слой `lib/design/theme/nox_*.dart` (ColorScheme, TextTheme, токен-классы, brand+avatar) и обёртки (`AppColors`-skeleton, `AppTheme`, `AppSpacingTokens`, `AppTextStyleTokens`, `AppOverlayStyleTokens`, `AppImagesTokens`, `flutter_gen`). Эта фича **доводит дизайн-систему до полноты** и приводит её в соответствие с авторитетным дизайн-корпусом и блюпринтом.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Канонический токенизированный фундамент темы (Priority: P1)

Разработчик строит любой экран и получает готовую тему NOX из кода: единый `ColorScheme` (light + dark, полный набор M3-ролей), типографическая шкала, токены формы/высоты/отступов/движения и бренд-палитра — все значения происходят из авторитетных токенов `nox-handoff`. Тема переключается light↔dark через `themeMode` без потери ролей и без хардкод-значений.

**Why this priority**: Без верного фундамента темы любой UI собирается на «глаз»; это минимально жизнеспособный дизайн-слой, от которого зависит всё остальное.

**Independent Test**: Собрать тему `AppTheme.light()`/`AppTheme.dark()`, проверить, что обе строятся, все роли `ColorScheme` заданы, значения совпадают с `nox-handoff`-токенами, переключение темы перерисовывает приложение.

**Acceptance Scenarios**:

1. **Given** чистый клон с зелёным gate, **When** приложение запускается в светлой системной теме, **Then** активна `noxLightScheme` с полным набором M3-ролей и токенизированной типографикой.
2. **Given** приложение в светлой теме, **When** система/настройка переключается на тёмную, **Then** активна `noxDarkScheme`, ни одна роль не «теряется», бренд-фиксированные исключения (тёмный splash, светлая QR-поверхность) сохраняются вне зависимости от темы.
3. **Given** любое значение токена в коде (цвет/радиус/высота/отступ/длительность), **When** его сверяют с соответствующим `*.tokens.json`, **Then** значения идентичны (нет дрейфа).

---

### User Story 2 — Семантические роли и component-сабтемы (вся темизация, кроме виджетов) (Priority: P2)

Разработчик получает не только примитивы, но и **полную тему уровня `ThemeData`**: расширенный набор семантических ролей (`AppColors` ThemeExtension, доведённый с skeleton до полного token-driven набора) и component-сабтемы (`CardTheme`, `FilledButtonTheme`, `AppBarTheme`, `SnackBarTheme`, `DialogTheme`, `NavigationBarTheme`/`NavigationRailTheme`, `SegmentedButtonTheme` и т.д.), сконфигурированные из токенов и component-токенов дизайн-системы (`design-system.md` §9). Будущие виджеты наследуют стиль NOX без хардкода — сами виджеты в этой фиче не пишутся.

**Why this priority**: Делает «темизацию» полной (в духе «всё, кроме виджетов»): когда виджеты появятся, им не нужно повторять дизайн-токены — стиль приходит из темы.

**Independent Test**: Проверить, что `ThemeData` несёт `AppColors`-extension с полным набором ролей и сконфигурированные component-сабтемы; рендер стоковых M3-компонентов под этой темой даёт NOX-стиль (форма/цвет/высота из токенов) без дополнительной стилизации.

**Acceptance Scenarios**:

1. **Given** собранная тема, **When** обращаются к `context.appColors`, **Then** доступен полный набор семантических ролей дизайн-системы (а не skeleton из двух полей), и значения происходят из токенов.
2. **Given** собранная тема, **When** на экран кладут стоковый M3-компонент (например, `Card`, `FilledButton`, `SnackBar`), **Then** он отображается в NOX-стиле (радиусы `NoxRadius`, высоты `NoxElevation`, роли `ColorScheme`) благодаря component-сабтемам, без локального хардкода.
3. **Given** бренд-фиксированные component-токены (`design-system.md` §9.9/§9.10 — маска QR-сканера, QR-поверхность), **When** их запрашивают, **Then** они доступны как именованные токены дизайн-слоя.

---

### User Story 3 — Сквозные non-widget-фундаменты (Priority: P3)

Разработчик получает остальные фундаменты дизайн-системы, лежащие вне `lib/design/theme`: подключённые шрифты (Sans + Mono), выбранный и подключённый набор иконок с реестром имён и картой «тип файла → иконка», форматтеры относительных дат/времени по двум NOX-лестницам, канон UI-microcopy (включая сетевые/offline-строки), верифицированный фундамент генерируемых аватаров (палитра/хеш/инициалы/fallback), реестр ассетов и канон применения system-overlay.

**Why this priority**: Без шрифтов типошкала не гарантирована кросс-платформенно; без иконок/форматтеров/microcopy дизайн-конвенции (`overview.md`) не реализуемы; это «абсолютно всё» из формулировки, что лежит вне `theme/`, но является дизайн-системой, а не виджетом.

**Independent Test**: Каждый фундамент присутствует и соответствует дизайн-корпусу: шрифты бандлятся и применяются; иконочный набор подключён, реестр и карта типов файлов покрывают `design-system.md` §8 / `overview.md`; форматтеры дат дают форматы из спеки; microcopy-строки заданы; аватар-логика воспроизводит правило хеша/инициалов.

**Acceptance Scenarios**:

1. **Given** любая платформа из пяти целевых, **When** рендерится текст, **Then** применяются заявленные семейства (Sans + Mono) без молчаливого fallback на системный шрифт.
2. **Given** известный тип файла, **When** запрашивают иконку через карту «тип → иконка», **Then** возвращается иконка из набора `design-system.md` §8 (с дефолтной для неизвестного типа).
3. **Given** временная метка, **When** её форматируют для списка чатов или разделителя дня, **Then** результат соответствует лестницам форматов из `overview.md`/`design-system.md`.
4. **Given** строка идентификатора чата/пользователя, **When** вычисляют аватар, **Then** индекс/цвет/инициалы детерминированы и совпадают с правилом `design-system.md` §2.5 (+`forum`-fallback).

---

### User Story 4 — Единый источник истины и гигиена дизайн-слоя (Priority: P4)

Дизайн-слой имеет один источник истины и не содержит расхождений: значения `lib/design/theme/nox_*.dart` происходят из `nox-handoff/tokens` (правило «генерируется из токенов, руками не правится» зафиксировано и соблюдено), задокументированные дубли устранены (единый канал spacing-токенов, единый канал ассетов), дрейфы токенов исправлены, типо-обёртки выровнены под каноническую M3-шкалу, а авторитетность `nox-handoff/` зафиксирована (с переносом уникальных non-widget-улучшений из `nox-handoff-2/`).

**Why this priority**: Гигиена не блокирует использование темы, но без неё дизайн-система быстро «расползётся»; делается последней, поверх готового фундамента.

**Independent Test**: Нет двух параллельных классов с одной ролью; значения токенов совпадают с `*.tokens.json`; в блюпринте/коде зафиксировано правило регенерации; авторитетный handoff — один.

**Acceptance Scenarios**:

1. **Given** любой токен дизайн-слоя, **When** сверяют код с `nox-handoff/tokens`, **Then** расхождений нет.
2. **Given** spacing- и asset-каналы, **When** их инспектируют, **Then** для каждой роли остаётся один канонический канал (без дублирующих параллельных классов).

---

### Edge Cases

- Что происходит, когда заявленный шрифт недоступен на платформе (Windows/Linux): должен ли быть детерминированный fallback, а не молчаливая подмена, ломающая типошкалу?
- Что происходит, когда реальный ассет (иллюстрация empty-state, лого-SVG) ещё не поставлен дизайном: реестр должен деградировать к Material-иконке-fallback, не падая.
- Как тема ведёт себя при смене `themeMode` в рантайме: ни одна роль не должна остаться неинициализированной.
- Как типошкала ведёт себя при системном масштабировании текста (screenutil/textScaler): токены должны оставаться консистентными.
- Что считается «неизвестным типом файла» в карте «тип → иконка» и какая иконка по умолчанию.
- Расхождение прозы `design-system.md` §2.3 с авторитетными токенами: источником истины считаются токены `nox-handoff`, а не устаревшая проза.

## Requirements *(mandatory)*

### Functional Requirements

**Фундамент темы (примитивы):**

- **FR-001**: Дизайн-слой MUST предоставлять полный функциональный `ColorScheme` для light и dark со всеми M3-ролями, со значениями из авторитетных токенов `nox-handoff` (без `ColorScheme.fromSeed`).
- **FR-002**: Дизайн-слой MUST предоставлять типографическую шкалу (M3-слоты) и явно заданные семейства Sans + Mono, соответствующие `design-system.md` §3.
- **FR-003**: Дизайн-слой MUST предоставлять токены формы (радиусы, включая асимметрию пузыря), высоты (M3 tonal), отступов/сетки (база 4dp) и движения (длительности + кривые) согласно `design-system.md` §4–§7.
- **FR-004**: Дизайн-слой MUST предоставлять бренд-палитру и бренд-фиксированные исключения (тёмный splash-фон, светлая QR-поверхность), не зависящие от темы.
- **FR-005**: Дизайн-слой MUST предоставлять стиль wordmark «NOX» (Title Large / Bold 700 / letter-spacing +0.12em) как токен типографики.

**Сборка темы и семантика (вся темизация, кроме виджетов):**

- **FR-006**: Дизайн-слой MUST собирать `AppTheme.light()`/`AppTheme.dark()` (`ThemeData`), связывая `ColorScheme` + типошкалу + семантическое расширение, с переключением через `themeMode`.
- **FR-007**: Семантическое расширение `AppColors` (ThemeExtension) MUST быть доведено со skeleton до полного token-driven набора ролей, требуемых дизайн-системой (а значения — из токенов, не из ad-hoc литералов).
- **FR-008**: Тема MUST включать component-сабтемы `ThemeData`, сконфигурированные из токенов и component-токенов (`design-system.md` §9), так чтобы стоковые M3-компоненты получали NOX-стиль без локальной стилизации. (Сами виджеты — вне объёма; см. ниже.)
- **FR-009**: Бренд-фиксированные component-токены, не сводящиеся к ролям `ColorScheme` (например, маска/визирь QR-сканера §9.9, QR-поверхность §9.10), MUST быть доступны как именованные токены дизайн-слоя.

**Сквозные non-widget-фундаменты:**

- **FR-010**: Sans MUST быть платформенно-нативным (Roboto/SF по ОС, §3) — без хардкода имени `Roboto`, чтобы исключить молчаливый fallback на Windows/Linux; mono-семейство `Roboto Mono` (отображение `Your ID`) MUST бандлиться (`assets/fonts/` + блок `fonts:` в `pubspec.yaml`) для детерминированного вида на всех пяти платформах.
- **FR-011**: Набор иконок MUST быть Material Symbols Rounded через пакет `material_symbols_icons` (оси FILL/weight/grade, по `design-system.md` §8 и icons.md из `nox-handoff-2`); MUST существовать реестр имён `NoxIcons` (навигация/действия/статус/типы файлов) и карта «тип файла → иконка» с дефолтом для неизвестного типа.
- **FR-012**: Форматтеры дат/времени MUST реализовывать NOX-лестницы относительного времени (список чатов) и разделителя дня (лента), соответствующие форматам `overview.md`/`design-system.md`.
- **FR-013**: Канон UI-microcopy MUST включать строки сетевых/offline-ошибок (включая исключение «pull to refresh» для списка чатов) на английском, без хардкод-копий в коде фич.
- **FR-014**: Фундамент генерируемых аватаров (палитра, детерминированный хеш-индекс, инициалы, `forum`-fallback) MUST соответствовать `design-system.md` §2.5 / `overview.md`.
- **FR-015**: Реестр ассетов MUST покрывать слоты дизайн-системы (лого, 3 иллюстрации empty-state) с деградацией к Material-иконке-fallback, когда реальный файл ещё не поставлен.
- **FR-016**: Канон применения system-overlay (стили статус-бара по brightness) MUST быть задан и применяться глобально.
- **FR-024**: Правила доступности (`design-system.md` §2.6: контраст WCAG AA, непрозрачность timestamp 70%) MUST быть зафиксированы как инварианты дизайн-слоя И покрыты автотестами контраста пар роль/фон `ColorScheme` (≥4.5:1 для body-текста, ≥3:1 для крупного текста/иконок).

**Источник истины, верность и гигиена:**

- **FR-017**: Все токенные значения дизайн-слоя MUST происходить из `docs/design/system/nox-handoff/tokens/*.tokens.json`; правило «генерируется из токенов, руками не правится» MUST быть зафиксировано; выявленные дрейфы MUST быть устранены в пользу авторитетного токена (примечание: «дрейф» dark `outlineVariant` — это устаревшая **проза** `design-system.md` §2.3 (#3F4948); Dart-код и токен уже совпадают (#4E5B58), поэтому правится проза, а не код).
- **FR-018**: Задокументированные дубли MUST быть устранены до одного канонического канала на роль: spacing-токены (фиксированные dp vs responsive) и канал ассетов (`flutter_gen` vs рукописный реестр).
- **FR-019**: Типо-обёртки (color-injecting фабрики) MUST быть выровнены под каноническую M3-шкалу (без рассинхрона размеров/весов с типошкалой).
- **FR-020**: Авторитетным источником MUST считаться `docs/design/system/nox-handoff/`; уникальные non-widget-улучшения из `nox-handoff-2/` (например, icons.md с FILL-осью) MUST быть перенесены до его удаления (само удаление дубликата может быть отдельным change-set).
- **FR-021**: При любом расхождении кода с дизайн-корпусом/блюпринтом расхождение MUST устраняться в том же change-set (правило docs-in-sync); если блюпринт `06`/`10` расходится с реализованным дизайн-слоем, блюпринт приводится в корректный вид.

**Границы (no widgets / no hardcode):**

- **FR-022**: В коде, не относящемся к дизайн-слою-фундаменту, MUST отсутствовать хардкод цветов, отступов, типографики, радиусов, длительностей и overlay-стилей — только токены/тема.
- **FR-023**: Фича MUST НЕ включать реализацию виджетов/компонентов (см. «Вне объёма»). Допускается тонкая verification-проверка (тест/golden) фундаментов, но не продуктовые виджеты.

### Вне объёма (виджеты и внешние ассеты)

Явно **не** входит в эту фичу (это и есть «кроме виджетов»):

- Любые реализации виджетов/компонентов из `design-system.md` §9: нижняя панель + docked FAB, message bubble, chat list item, identity card, поля/кнопки/контролы списка, прогресс-индикаторы, file-chip, composer, оверлей QR-сканера, QR bottom-sheet, SnackBar/MaterialBanner/Dialog/AppBar/экран ошибки 3.1, виджет аватара, виджеты иллюстраций empty-state.
- Любые переиспользуемые виджеты `lib/presentation/**` (включая `app_shell`, страницы, базовые страницы) и их стилизация на месте.
- Производство **реальных графических ассетов** (финальный лого-SVG, 3 иллюстрации empty-state, иконка приложения/launcher) — это внешние дизайн-поставки (`design-system.md` §11); в объёме только реестр/плумбинг и fallback.
- Настройка автоматизированного DTCG→Dart тулинга (Style Dictionary и т.п.) — в объёме принятие уже сгенерированного Dart из `nox-handoff` как практического источника + зафиксированное правило регенерации; автоматический генератор — вне объёма, если не попросят отдельно.
- Удаление каталога-дубликата `nox-handoff-2/` (после переноса уникального контента) — может быть отдельным change-set.

### Key Entities *(артефакты дизайн-системы)*

- **Функциональная цветовая схема**: полный набор M3-ролей для light и dark; источник — токены `color.{light,dark}.tokens.json`.
- **Типографическая шкала**: M3-слоты + семейства Sans/Mono + стиль wordmark.
- **Токен-классы**: форма (радиусы), высота, отступы/сетка, движение (длительности/кривые).
- **Бренд-палитра и бренд-фиксированные токены**: мульти-хью палитра, splash-фон, QR-поверхность/чернила, маска/визирь QR-сканера.
- **Семантические роли (`AppColors`)**: расширенный token-driven набор поверх `ColorScheme`.
- **Сборка темы (`AppTheme`/`ThemeData`)**: примитивы + семантика + component-сабтемы + `themeMode`.
- **Фундамент аватаров**: палитра + хеш-индекс + инициалы + fallback.
- **Иконочный фундамент**: набор + реестр имён + карта «тип файла → иконка».
- **Реестр ассетов**: канонический канал + слоты + fallback.
- **Форматтеры**: лестницы относительных дат/времени.
- **Канон microcopy**: UI-строки (включая сетевые/offline).
- **Канон overlay**: стили system UI по brightness.
- **Источник истины**: `nox-handoff/tokens` (DTCG) → генерируемый Dart.

## Assumptions

- **Источник истины** — `docs/design/system/nox-handoff/` (DTCG-токены + генерируемый Dart) и `docs/design/spec/design-system.md`; при расхождении прозы и токенов истиной считаются токены. `nox-handoff-2/` — дубликат (не авторитетный).
- **Охват — широкий (по решению владельца):** дизайн-система реализуется как **все non-widget-фундаменты, где бы они ни лежали** — `lib/design`, плюс конфиг шрифтов/иконок/ассетов в `pubspec.yaml`, форматтеры дат/времени и UI-microcopy в `lib/general`, глобальное применение overlay. Не ограничивается только каталогом `lib/design/`.
- **Темизация — полная (по решению владельца):** включаются component-сабтемы `ThemeData` (§9 как theme-конфиг), а не только примитивы; это переопределяет дефолт блюпринта 06 §3 («сабтемы приходят с первой фичей-виджетом») — блюпринт обновляется соответствующе.
- **Глубина — полная (по решению владельца):** `AppColors` доводится до полного token-driven набора (работа «US4»), дубли устраняются, дрейфы фиксируются, типошкала выравнивается.
- **Реальные графические ассеты** (лого-SVG, иллюстрации empty-state, иконка приложения) — внешние поставки, ещё не доставлены; в объёме реестр/плумбинг + Material-fallback, реальные файлы подключаются по мере поставки.
- **Регенерация из токенов** — принимается уже сгенерированный Dart из `nox-handoff` как практический источник; правило «руками не править, регенерировать» фиксируется; автоматизированный DTCG-генератор — вне объёма.
- **Виджеты целиком исключены**; платформы — пять целевых (iOS/Android/Windows/Linux/macOS), web вне scope; язык: проза/спека — русский, идентификаторы/UI-microcopy — английский.
