# Контракт: проверка соединения `POST /auth` → `POST /auth2`

Провод — как в теме 0 NOX Architecture (артефакт v41, раздел HTTP). Нормативный текст после фичи — §1 `docs/client-backend/protocol/contract-draft.md`.

## Место в соединении

```text
TCP или поток Tor → TLS 1.3 (технический сертификат, ALPN http/1.1)
  → POST /auth → POST /auth2          ← эта проверка, первые два запроса соединения
  → GET /ws (101) или PUT|GET /files/{token} — по этому же соединению
```

Проверка принадлежит соединению. Каждое новое соединение — сокет, передача файла, проба прямого адреса — проходит её заново. Токена или сессии поверх нет.

## `POST /auth`

Запрос:

```http
POST /auth HTTP/1.1
Host: 192.168.1.61:8443
Content-Type: application/json
Content-Length: 119

{"pk":"<base64url 32>","challenge":"<base64url 32>"}
```

Ответ `200`:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store
Content-Length: 224

{"pk":"<base64url 32>","challenge":"<base64url 32>","signature":"<base64url 64>"}
```

- `pk` — ключ сервера: приложение сверяет его с ключом из ссылки;
- `challenge` — челлендж сервера;
- `signature` — подпись сервера над челленджем устройства.

## `POST /auth2`

Запрос:

```http
POST /auth2 HTTP/1.1
Host: 192.168.1.61:8443
Content-Type: application/json
Content-Length: 107

{"signature":"<base64url 64>"}
```

`signature` — подпись устройства над челленджем сервера из ответа на `/auth`.

Ответ `200`:

```http
HTTP/1.1 200 OK
Content-Length: 0
```

## Отказы сервера

Каждый отказ — ответ без тела с `Connection: close`, затем разрыв.

| Код | Когда |
|---|---|
| `400` | тело не разбирается или больше 1 КиБ; поля не той длины; нет `Content-Length`; `Transfer-Encoding`; второй `/auth`; `/auth2` без `/auth`; второй `/auth2` |
| `401` | подпись в `/auth2` не сходится; любой другой путь до прохождения проверки (`/ws`, `/files/…`, `/health`, неизвестный) |
| `405` | метод не `POST` на `/auth` или `/auth2` |
| — (разрыв без ответа) | TLS и обе ступени не уложились в 30 с от приёма; ошибка RustSecureBox на сервере |

Порядок проверок сервера: путь и метод → ступень → тело → подпись.

## Правила

- Base64url без `=`, строгий: лишние символы, `=` и не та длина после декодирования — `400`.
- JSON — объект. Неизвестные поля не допускаются только в смысле длины тела; сервер их игнорирует.
- Сервер подписывает челлендж любого ключа. Чей ключ, решается после `/auth2`, по списку спаренных устройств: спаренному — всё, незнакомому — только `pair` и `pair.cancel` через `/ws` с пределами 045/046.
- Челлендж сервера и ключ устройства живут при соединении до `/auth2` и нигде не записываются.
- Приложение не шлёт `/auth2`, пока:
  - подпись сервера не проверена (иначе — неудачная попытка, `PROTOCOL`);
  - ключ сервера не совпал с ключом из ссылки (иначе — «не тот сервер», `WRONG_SERVER`).
- Приложение не шлёт ничего, кроме этих двух запросов, до ответа `200` на `/auth2`.
- Журналы обеих сторон пишут только вид исхода — никаких ключей, челленджей и подписей.
