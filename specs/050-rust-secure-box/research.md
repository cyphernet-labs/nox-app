# Research: RustSecureBox и проверка запросами /auth и /auth2

Все решения — для фичи 050. Источники решений владельца: трекер `docs/client-backend/roadmap-security.md`, тема 1 (2026-10-15), и раздел Clarifications спецификации. Помеченное «нашёл сам» найдено при планировании, владелец этого не говорил.

## R1. Чем Go выполняет RustSecureBox — переводом `wasm2go`

**Decision.** RustSecureBox собирается под `wasm32-unknown-unknown`. `wasm2go` v0.4.15 (`github.com/ncruces/wasm2go`) переводит его в исходник на Go: `client_backend/internal/securebox/boxwasm/box.go` плюс `box.dat` с данными сегмента (`-embed`). Сгенерированный код зависит только от стандартной библиотеки (`encoding/binary`, `math`, `math/bits`, `embed`). Он лежит в репозитории, поэтому сервер собирается как раньше: `CGO_ENABLED=0`, без Rust и без компилятора C. Генерирует его `packages/rust_secure_box/build-wasm.sh`. Скрипт запускает инструмент как `go run github.com/ncruces/wasm2go@v0.4.15`, поэтому `go.mod` сервера не меняется.

**Rationale.** Так сервер уже работает с SQLite: `ncruces/go-sqlite3` v0.35.6 тянет `go-sqlite3-wasm/v6`, а его `sqlite3.go` начинается со строки `// Code generated by wasm2go. DO NOT EDIT.` (нашёл сам: кэш модулей; `tools.sh`/`build.sh` того же модуля). Проба 2026-10-15 в scratchpad:

- заглушка собирается в wasm 23 КБ и переводится в Go 120 КБ;
- полный круг `generate → challenge → sign → check` проходит, испорченная подпись отклоняется;
- подпись — 3,1 мкс, новый экземпляр — 62 мкс (1 МиБ памяти; с меньшим стеком — меньше, R3);
- Ed25519 (`ed25519-compact` 2.x — его republish заказчик выпустил как `ec25519`) собирается в wasm 67 КБ и переводится; круг проходит, проверка подписи — 0,28 мс.

Значит, настоящий RustSecureBox на Ed25519 встанет тем же путём.

**Проверка подменой (T039, 2026-10-15).** В отдельной рабочей копии `src/stub.rs` заменён реализацией на `ed25519-compact`: четыре функции с теми же сигнатурами, плюс одна зависимость в `Cargo.toml`. Копия сервера пересобрана `build-wasm.sh`. Результат:
- проходят тесты интерфейса крейта (9 из 9), свойства Go-обёртки, `connauth` целиком, хранилище с перевыпуском и тесты сервера на спаривание и канал;
- ожидаемо падают только векторы заглушки, её распознавание (`IsStub` = `false`) и тест объявления заглушки на сервере;
- `git status` показывает только крейт и `boxwasm/`.

**Замена по README (ревью PR, 2026-10-16).** Ту же замену прошли по шагам README крейта, с векторами настоящей реализации. Найдено и исправлено:
- нулевой ключ в наборе векторов, на котором Ed25519 падает, заменён на `0x80…`;
- тест вытеснения на входе сервера берёт темп от скорости канала на этой машине.

После этого проходят все тесты крейта, сервера (`-race`) и Dart; `IsStub()` = `false`, строки о заглушке нет.

**Цена входа с настоящей библиотекой** (`ec25519`, `wasm2go`, M3 Max):
- `/auth` — около 1,07 мс процессора сервера: `GetChallenge` и `SignChallenge`, три умножения на базовую точку, потому что интерфейс не хранит состояние;
- `CheckSignature` в `/auth2` — 0,27 мс;
- рукопожатие TLS 1.3 — 0,37 мс.

Пределы входа ограничивают число одновременных рукопожатий, не их частоту (`client_backend/CLAUDE.md`, «Known deliberate omissions»). Под `-race` вызовы в десятки раз медленнее: тесты пакета сервера идут минуты.

**Alternatives considered.**
- *cgo и C ABI* — все три установщика собирают сервер с `CGO_ENABLED=0`; на машине владельца понадобились бы Rust и компилятор C, на Windows — MinGW (решение 11 трекера).
- *wazero как среда выполнения* — новая прямая зависимость (`client_backend/CLAUDE.md` разрешает их только с письменным обоснованием) и JIT/интерпретатор в процессе. Перевод даёт то же без зависимости.
- *Собирать wasm при каждой сборке сервера* — требует Rust на машине сервера.

## R2. Где и как устроен крейт RustSecureBox

**Decision.** `packages/rust_secure_box/` — отдельный крейт `rust_secure_box`, `crate-type = ["rlib"]`, edition 2021, на `std`. Файлы:
- `lib.rs` — интерфейс: функции, `Error`, константы размеров, документация интерфейса;
- `stub.rs` — заглушка; настоящая реализация встаёт на её место;
- `random.rs` — источник случайных байтов;
- `wasm.rs` — C ABI для WebAssembly, только `cfg(target_arch = "wasm32")`.

`nox_tor` зависит от крейта по пути `../../rust_secure_box` и зовёт Rust-функции напрямую. WebAssembly собирает `cargo rustc --release --target wasm32-unknown-unknown --crate-type cdylib` в каталоге крейта: профиль крейта (`panic = "abort"`, `opt-level = "z"`, `lto`) действует только там. Когда крейт собирается зависимостью, действует профиль `nox_tor`.

**Rationale.**
- Одна библиотека для двух сторон не принадлежит ни одной из них.
- `std`, а не `no_std`, ради разработчика заказчика: настоящую реализацию проще писать на `std`, а на `wasm32-unknown-unknown` `std` не даёт ни одного импорта.
- Обращений к системе в WebAssembly нет структурно. Проверяет это компилятор Go: интерфейс импортов `Xenv`, сгенерированный `wasm2go`, должен состоять ровно из `Xrsb_random`. Лишний импорт в настоящей реализации — ошибка сборки сервера, а не тихое расширение.
- `rlib` без `cdylib`: иначе cargo собирал бы библиотеку под каждую платформу приложения впустую.
- Хук `native_toolchain_rust` отслеживает `.rs`-файлы, о которых сообщает cargo, включая зависимости по пути. `Cargo.toml` крейта добавляется в зависимости хука, как это уже сделано для `Cargo.toml` модуля.

**Alternatives considered.** Крейт внутри `packages/nox_tor/rust/` — привязал бы библиотеку сервера к пакету приложения. `no_std` — строже, но связывает руки настоящей реализации: аллокатор, `panic_handler` на wasm.

## R3. C ABI для WebAssembly, память и потоки

**Decision.** Экспорты WebAssembly:

```text
rsb_io() -> *mut u8                                   // буфер обмена 256 байт
rsb_generate_keys(sk_out, pk_out) -> i32
rsb_get_challenge(sk, challenge_out, pk_out) -> i32
rsb_sign_challenge(sk, challenge, sig_out) -> i32
rsb_check_signature(pk, challenge, sig) -> i32         // 1 верна, 0 неверна, <0 ошибка
```

Импорт ровно один — `env.rsb_random(ptr, len) -> i32` (0 — успех).

Go пишет аргументы в буфер `rsb_io`, передаёт указатели внутри него и читает результаты оттуда же. Экземпляр модуля однопоточен, поэтому Go держит пул экземпляров (`sync.Pool`): каждый вызов берёт свой, и вызовы из разных горутин не мешают друг другу. Ловушка WebAssembly — panic в настоящем коде, `unreachable` — в переведённом коде становится паникой Go. Обёртка её перехватывает, возвращает ошибку RustSecureBox и выбрасывает этот экземпляр: его стек-указатель мог остаться посреди вызова. Стек wasm уменьшается до 64 КиБ (`-C link-arg=-zstack-size=65536`; флаги сборки целиком задаёт `build-wasm.sh`, вместе с `--remap-path-prefix` для путей `CARGO_HOME`, так что копия одинакова на любой машине), чтобы новый экземпляр не стоил мегабайт.

**Rationale.** Размеры всех аргументов фиксированы: 32/32/64 байта, один вызов — не больше 128 байт входа и выхода. Аллокатор на стороне wasm для этого не нужен, буфер проще и детерминированнее. Коды ошибок: `-1` — неверный аргумент, `-2` — нет случайных байтов, `-3` — внутренняя ошибка реализации.

**Alternatives considered.** Экспорт `rsb_alloc`/`rsb_free` — общее, но лишнее при фиксированных размерах. `--import-memory`, как у SQLite, — не нужно: память модуля Go получает через `Xmemory()`.

## R4. Заглушка

**Decision.**
- `generate_keys`: `sk` — 32 случайных байта; `pk = SHA-256("RustSecureBox stub public key v1" ‖ sk)`.
- `get_challenge(sk)`: 32 случайных байта и `pk(sk)`.
- `sign_challenge(sk, c)`: `SHA-512("RustSecureBox stub signature v1" ‖ pk(sk) ‖ c)` — 64 байта.
- `check_signature(pk, c, sig)`: та же величина для `pk` и `c`, сравнение за постоянное время.

Принимается любой 32-байтный закрытый ключ.

**Rationale.** Своя подпись проходит; подпись другим ключом или над другим челленджем — нет; испорченная — нет. Так все отказы проверяются уже с заглушкой. Подделать подпись может любой, кто знает `pk`, — это и есть «стороны по-настоящему не проверяются» из трекера, и об этом говорят комментарии заглушки и предупреждение сервера (R11). Открытые ключи заглушки не совпадают ни с Ed25519 Eidolon, ни с Ed25519 настоящего RustSecureBox — отсюда новое спаривание при каждом переходе (решение 13). `sha2` уже в графе `nox_tor`.

## R5. Как узнать заглушку

**Decision.** Пробный закрытый ключ — 32 байта `0x01`. Его открытый ключ у заглушки записан константой в `internal/securebox` и в векторах. `Box.IsStub()` сравнивает ответ RustSecureBox на пробный ключ с этой константой.

**Rationale.** Интерфейс не меняется. Пробный ключ — не нулевой (нашёл сам на пробе): `ed25519-compact` на нулевом семени паникует, а `ec25519` заказчика — тот же код, и `nox_tor` сегодня отсекает такое семя (`eidolon.rs`, «ec25519 panics on it»). Настоящий RustSecureBox на нулевом ключе мог бы упасть, а предупреждение должно исчезать само, а не превращаться в ошибку. Обёртка всё равно перехватывает ловушку (R3): любая ошибка на пробе значит «не заглушка».

## R6. Обмен в Rust-модуле приложения

**Decision.** `src/channel/auth.rs` заменяет `eidolon.rs`. Сразу после `tls::connect`:

1. `rust_secure_box::get_challenge(sk_device)` → `(c_a, pk_a)`.
2. Пишет:
   ```text
   POST /auth HTTP/1.1
   Host: <host:port как набран>
   Content-Type: application/json
   Content-Length: N
   ```
   и тело `{"pk":"…","challenge":"…"}` (base64url без `=`, `data-encoding`). Затем `flush`.
3. Читает ответ: заголовки — побайтно до `\r\n\r\n`, не больше 8 КиБ, разбор `httparse`. Статус должен быть 200, `Content-Length` обязателен; тело — ровно столько байт, не больше 1 КиБ. `Transfer-Encoding` — отказ.
4. Разбирает JSON (`serde_json::Value`): `pk`, `challenge`, `signature` — строки base64url ровно 32/32/64 байта.
5. `check_signature(pk_s, c_a, sig_s)`: неверна — `PROTOCOL`.
6. `pk_s` ≠ ключ из ссылки — `WRONG_SERVER`.
7. `sign_challenge(sk_device, c_s)` → `POST /auth2 {"signature":"…"}`.
8. Ответ `200` с `Content-Length: 0` — канал открыт. Байты после ответа не читаются: поток уходит в Dart как есть.

Отказы:

| Ситуация | Код |
|---|---|
| EOF и любой не-200 (`401` на `/auth2` тоже) | `PROTOCOL` |
| Ошибка TLS-записи (`InvalidData`) | `TLS` |
| Ошибка ввода-вывода | `NETWORK` |
| Ошибка RustSecureBox | `INTERNAL` |
| Время бюджета пути | `TIMEOUT` (как сегодня: один бюджет на транспорт, TLS и проверку) |

**Rationale.**
- Порядок «подпись, потом ключ» — FR-009. Чужой сервер NOX подписывает верно и даёт `WRONG_SERVER` (тихий пропуск по прямому адресу). Не-NOX машина отвечает не так и даёт `PROTOCOL` — неудачную попытку. Это различие 044 сохраняется.
- Побайтное чтение заголовков дешёво: rustls уже буферизует записи TLS. Зато модуль никогда не съедает байты, которые принадлежат Dart.
- `httparse` и `serde_json` уже в графе через Arti.

**Alternatives considered.** `hyper` — тяжёлая зависимость ради двух запросов. Ручной JSON — `serde_json` уже собран.

## R7. Обмен на сервере — во входном слушателе канала

**Decision.** `internal/connauth.Respond(ctx, conn, box, serverKey)` вызывается из `channelListener.verify` вместо `eidolon.Respond`. Возвращает ключ устройства и соединение, которое отдаётся `http.Server`. Порядок:

1. `bufio.Reader` (4 КиБ) над `io.LimitReader` в 16 КиБ на весь этап; `http.ReadRequest`.
2. Путь `/auth` или `/auth2` с методом не `POST` — `405`. Любой другой путь — `401`. Дальше проверяется ступень: `/auth` после `/auth`, `/auth2` без `/auth` и повторный `/auth2` — `400`.
3. Тело не больше 1 КиБ, только `Content-Length`, JSON с полями точной длины; иначе `400`.
4. На `/auth`:
   - `box.GetChallenge(serverKey)` → `(c_s, pk_s)`;
   - `box.SignChallenge(serverKey, c_a)`;
   - ответ `200`: `Content-Type: application/json`, `Cache-Control: no-store`, `Content-Length`.

   Челлендж `c_s` и ключ `pk_d` остаются в локальных переменных `Respond`, то есть при соединении.
5. На `/auth2`: `box.CheckSignature(pk_d, c_s, sig)`. Неверна — `401`. Верна — `200 Content-Length: 0`, и соединение с `pk_d` уходит дальше.

Каждый отказ: ответ с `Content-Length: 0` и `Connection: close`, затем закрытие. Бюджет: тот же контекст с дедлайном 30 с от приёма; не уложился — закрытие без ответа. Если клиент уже прислал байты после `/auth2`, их содержимое `bufio` отдаётся первым (`prefixConn`), ничего не теряется.

**Rationale.**
- На проводе это ровно два HTTP-запроса темы 0. Но в коде сервера проверка живёт там же, где жила Eidolon. Поэтому сохраняется несущее правило 044: ни один обработчик `http.Server` — даже 404 — не отвечает соединению, не доказавшему ключ.
- Пределы входа (на источник 8, этой машине 64, всего 256, первый байт 5 с) и единый бюджет охватывают всю проверку без нового кода.
- `channelPeer` в контексте запроса, `limitStrangers`, `unpaired.go`, `files.go` не меняются.
- Ответы пишутся вручную: два коротких ответа с фиксированными заголовками не стоят `http.ResponseWriter` вне сервера.

**Alternatives considered.** Обработчики `/auth` и `/auth2` в `ServeMux` с состоянием в `ConnContext`. Это пришлось бы отдать `http.Server` непроверенные соединения, повторить пределы входа на уровне запросов и закрыть всё остальное до проверки отдельным middleware — больше кода и больше мест для ошибки ради того же провода.

## R8. Ключ сервера и перевыпуск (FR-017, FR-021)

**Decision.** Схема `server_identity` не меняется: `public_key` и `private_key` — base64 std, по 32 байта. Хранилище получает интерфейс `KeySource` с двумя методами: `GenerateKeys()` и `PublicKey(sk)`; реализует его `securebox.Box`, `PublicKey` = открытый ключ из `GetChallenge`.

- `EnsureServerIdentity(ctx, keys)` создаёт пару через RustSecureBox. Запрет создавать ключ при существующих людях остаётся.
- `ServerKey(ctx, keys)` сравнивает `keys.PublicKey(sk)` с хранимым `public_key`. Не совпало — одна запись-транзакция `rekeyServerIdentity`: `DELETE FROM pair_requests` → `DELETE FROM pair_tokens` → `DELETE FROM devices` → `UPDATE server_identity SET public_key = ?`. Затем возвращается пара и признак «перевыпущен»; `Run` пишет предупреждение `server key was made by another RustSecureBox: every device pairs again`.

Удаляются все токены, включая потраченные: прав они не несут, а `pair_requests` ссылается на них внешним ключом. Люди, чаты, сообщения, файлы и журнал не трогаются; события журнала не пишутся (инвариант 3: спаривание — вне журнала).

**Rationale.**
- Сегодня несовпадение половин ключа останавливает старт («inconsistent»): иначе каждое устройство увидело бы ключ, который сервер не докажет. После 050 такое несовпадение означает смену реализации, и решение владельца — перевыпуск с сохранением переписки.
- Если удалить устройства, служебная страница сама покажет ссылку: её правило «нет устройств и нет непотраченной ссылки» уже есть (046).
- Ссылка с машины присоединяет к тому же человеку всю историю.

## R9. Ключ устройства в приложении

**Decision.**
- `DeviceKeys` больше не использует `package:cryptography`. `generate()` зовёт `RustSecureBox.generateKeys()` из `package:nox_tor/secure_box.dart`, `publicKeyOf(private)` — `getChallenge(private).publicKey`.
- `SessionRepository.deviceSecret()` уступает место `deviceKey()`: запись `session.device_key` = JSON `{"private": base64, "public": base64}` — одна запись, чтобы половины не разошлись. Создаётся при первом запросе, как сегодня (перед первым спариванием).
- `discardSignIn()` её сохраняет, `clear()` удаляет.
- `sweepLegacyKeys()` удаляет `session.device_secret`.

Отставка сессии. `AuthRepository.retireLegacySession()` к проверке «спарено до 044» добавляет проверку «ключ не этого RustSecureBox». Сессия есть, и при этом:
- записи `session.device_key` нет, или
- `publicKeyOf(private)` ≠ хранимого `public`.

Тогда `logout(forced: true)` — один раз, как сегодня. Ошибка чтения сейфа ничего не стирает.

Где используется открытый ключ:
- «это устройство» в списке — `DeviceRepositoryImpl`;
- самоотзыв при выходе — `AuthRepositoryImpl._revokeOwnKey`.

Оба берут хранимый `public`.

**Rationale.** FR-015, FR-016, FR-019, FR-020. Хранимый `public` — это и быстрый путь (без вызова RustSecureBox на каждый список), и признак, по которому видна смена реализации. При переходе 044 → 050 записи `session.device_key` ещё нет, и сессия уходит к спариванию. При переходе заглушка → настоящий RustSecureBox записи разойдутся, и сессия уйдёт так же.

## R10. Поверхность RustSecureBox для Dart

**Decision.** `nox_tor` экспортирует:

```text
nox_box_generate_keys(sk_out, pk_out)
nox_box_get_challenge(sk, challenge_out, pk_out)
nox_box_sign_challenge(sk, challenge, sig_out)
nox_box_check_signature(pk, challenge, sig)
```

Коды возврата — как у C ABI WebAssembly (R3), паника перехватывается (`catch_unwind`) в `-3`. Dart: `package:nox_tor/secure_box.dart` — `abstract interface class SecureBoxApi` и `NativeSecureBoxApi`; вызовы синхронные, это микросекунды. Ошибка — `SecureBoxException(code)`.

`nox_chan_open` принимает закрытый ключ устройства на месте семени — тот же размер, 32 байта. Параметр Dart `deviceSeed` переименовывается в `devicePrivateKey` по всей цепочке: `ChannelHttpClient.bind`, `ConnectionPathSelector.begin`, `DirectProber.probe`, `LiveSessionStarter`.

**Rationale.** Те же четыре функции, что в интерфейсе. Dart не получает своей криптографии (FR-014), а живые пробы и тесты могут вызвать любую функцию. Имена `nox_box_*` — в духе `nox_chan_*` и `nox_vault_*`.

## R11. Заглушка в журнале и на служебной странице (FR-022)

**Decision.** `Run` после открытия данных проверяет `box.IsStub()`:
- `true` — предупреждение уровня `Warn` при каждом старте: `RustSecureBox is a stub: devices are not really verified`;
- служебная страница открытого сервера показывает ту же строку с точкой (`status_page.go`), поле `Stub` в данных страницы.

Страница под замком не меняется: на ней только поле пароля (047). Приложение ничего не показывает.

## R12. Общие векторы и проверки интерфейса

**Decision.** `specs/050-rust-secure-box/contracts/rsb-vectors.json` создаёт тест крейта: `RSB_IMPLEMENTATION=<имя> cargo test --test vectors -- --ignored write_vectors` пишет файл и обе копии под именем реализации (`"implementation"`, у заглушки `stub-v1`; без переменной — под именем, которое уже стоит в копии крейта), обычный прогон сверяет с ним. Проверки, которые относятся только к заглушке, — ответ на пробный ключ, `IsStub()`, объявление в журнале и на странице — читают имя из векторов: с векторами другой реализации они требуют, что заглушкой её не назовут. Состав:
- `keys`: `{private_key, public_key}` — включая пробный ключ R5;
- `signatures`: `{private_key, challenge, signature}`;
- `checks`: `{public_key, challenge, signature, valid}` — верная, другой ключ, другой челлендж, испорченный байт.

Копии лежат в `packages/rust_secure_box/tests/data/` и `client_backend/internal/securebox/testdata/` и сверяются с файлом спецификации тестами крейта и сервера.

Проверки интерфейса, которые не зависят от реализации, есть и в Rust, и в Go:
- своя подпись проходит;
- чужая, над другим челленджем или испорченная — нет;
- `pk` из `get_challenge` равен `pk` из `generate_keys`;
- 1000 челленджей подряд не повторяются;
- параллельные вызовы из 16 потоков дают те же ответы.

## R13. Свежесть сгенерированного Go-кода

**Decision.** `make box-wasm` пересобирает wasm и перегенерирует `boxwasm/`. `make box-verify` делает то же во временный каталог и сравнивает с тем, что лежит в репозитории; его зовёт `make tor-test`, которому Rust уже нужен. В комментарии сгенерированного пакета записаны команда и версия `wasm2go`.

**Rationale.** Если правка крейта не дошла до копии сервера, это даст расхождение векторов, а не тихий сбой. `box-verify` ловит это раньше.
