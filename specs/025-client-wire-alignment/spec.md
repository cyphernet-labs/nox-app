# Feature Specification: client-wire-alignment

**Feature Branch**: `025-client-wire-alignment`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "client-wire-alignment — фаза 025 клиентского трека: данные Flutter-приложения переводятся на язык контракта v0 (переходные требования §9, пункты 1, 2, 4, 5, 7), оставаясь на моках; поведение UI заморожено голденами."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Сообщения в системе координат сервера (Priority: P1)

Участник листает тред как раньше, но под капотом каждое сообщение несёт глобальный номер журнала сервера (`seq`), история сортируется по нему, а «догрузить старше» работает так, как отдаёт сервер: порция «до номера» с признаком «есть ещё» — без страничной арифметики. Когда придёт живой сервер, тред не изменится ни на пиксель.

**Why this priority**: `seq` — ключ всей модели синхронизации (курсор, дедупликация, догон); пока сообщения сортируются по времени, а пагинация считает страницы, DI-флип невозможен без переписывания репозиториев и UI — ровно то, что §9 запрещает.

**Independent Test**: на моках — тред отображает историю в прежнем порядке, прокрутка вверх догружает старшие порции по `before_seq`/`has_more` без пропусков и дублей; голдены треда не изменились.

**Acceptance Scenarios**:

1. **Given** мок-чат с историей, **When** тред открыт, **Then** сообщения упорядочены по возрастанию `seq` и каждый несёт свой `seq` в локальной записи.
2. **Given** загружен хвост истории, **When** прокрутка достигает порога догрузки, **Then** запрашивается порция «старше минимального загруженного `seq`», склейка без пропусков и дублей, конец истории определяется признаком «есть ещё», а не подсчётом страниц.
3. **Given** два сообщения с одинаковым временем отправки, **Then** их порядок стабилен (по `seq`), а не зависит от сортировки по времени.

### User Story 2 — Провод говорит на языке контракта (Priority: P2)

Приложение сериализует и разбирает ровно те JSON-формы, которые отдаёт настоящий сервер: имена, типы и структура полей совпадают с контрактом дословно, а поля, которых на проводе не существует, из wire-слоя исчезают. Живой кадр сервера, снятый websocat'ом, разбирается без ошибок.

**Why this priority**: сегодняшние wire-DTO эпохи 018 расходятся с контрактом по именам (`id` → `message_id`), типам (время — ISO-строка вместо unix-секунд), структуре (плоский текст вместо объекта `body`) и несут несуществующие required-поля — первый же контрактный JSON уронит парсинг.

**Independent Test**: набор фикстур — живые кадры локального `noxd` (эхо, события, страницы списков, вложение) — разбирается в доменные модели и сериализуется обратно с точным совпадением полей.

**Acceptance Scenarios**:

1. **Given** живой кадр `message.new` c вложением, **When** он разбирается wire-слоем, **Then** получаются корректные доменные значения (unix-время → DateTime, объект `body` → текст, вложение с `{file_id, name, size, mime, expires_at}`).
2. **Given** доменное сообщение, **When** оно сериализуется для отправки, **Then** форма совпадает с контрактной (`chat_id`, `client_message_id`, объект `body`), без локальных полей.
3. **Given** кадр с неизвестным клиенту полем, **Then** разбор не падает (v0 эволюционирует).
4. **Given** локальные поля (`status`, счётчик непрочитанного, `localPath`), **Then** они живут только в домене/хранилище и не появляются в wire-слое.

### User Story 3 — Устройство помнит своё место и правила сервера (Priority: P3)

Приложение персистит позицию синхронизации (курсор `since`) и переживает рестарт, зная, с какого события догонять; вложения знают срок хранения своих байтов (кнопка Save гаснет заранее для просроченных); лимиты сервера доступны для предполётных проверок, а отказы провода различимы по кодам, а не схлопываются в одну «ошибку».

**Why this priority**: без курсора негде начать догон (§3), без `expires_at` клиент узнаёт о пропаже файла в момент открытия, без сохранённых `limits` и кодов провода композер не может валидировать до отправки. Всё это — швы данных, не UI.

**Independent Test**: курсор записывается при применении событий, читается после рестарта и сбрасывается логаутом; модель вложения несёт `expires_at`; коды провода доступны из `RepositoryException`.

**Acceptance Scenarios**:

1. **Given** применённые события с номерами журнала, **When** приложение перезапускается, **Then** сохранённый курсор равен максимальному применённому `seq`; **When** выполняется Logout, **Then** курсор сброшен вместе с локальной базой.
2. **Given** вложение с истёкшим сроком хранения, **Then** Save недоступна ещё до попытки скачивания; для действующего срока поведение прежнее (голдены не меняются — на этапе 1 срок далеко в будущем).
3. **Given** лимиты рукопожатия, сохранённые в data-слое, **Then** они доступны потребителям (шов для композера/пикера).
4. **Given** отказ провода (`payload_too_large`, `attachment_gone`, `name_taken`…), **Then** слой репозиториев различает его код, а не возвращает обобщённую ошибку.

---

### Edge Cases

- Дубликат события на стыке replay/live (тот же `seq` дважды) → применение идемпотентно, запись не задваивается.
- Кадр с неизвестным полем или неизвестным событием → разбор не падает; неизвестный код ошибки трактуется как `internal` (правило эволюции §2.1).
- Сообщение-вложение без текста → доменная модель корректна с пустым текстом; сообщение без вложения — без объекта вложения.
- Логаут → курсор и лимиты очищаются вместе с локальными данными; новая сессия начинает с `since = 0`.
- Локальная Sembast-база предыдущего формата (без `seq`/`expires_at`) → пересоздаётся мок-генераторами; миграция локальных данных не требуется (приложение не выпущено).
- Порция догрузки, вернувшая «есть ещё: нет» → дальнейшие запросы старших не выполняются (конец истории — терминальное состояние до перезагрузки треда).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Каждое сообщение MUST нести глобальный номер журнала (`seq`) во всех слоях данных (домен, локальное хранилище, мок-генераторы); порядок треда и пагинация MUST определяться `seq`, не временем отправки.
- **FR-002**: Догрузка истории MUST работать по модели контракта: порция «старше `before_seq`» с признаком «есть ещё»; страничная арифметика (`page/page_size/total`) из пути сообщений MUST быть удалена.
- **FR-003**: Wire-модели чата, сообщения и вложения MUST совпадать с контрактом 1:1 по именам, типам и структуре (unix-секунды, объект `body`, вложение `{file_id, name, size, mime, expires_at}`); поля, отсутствующие на проводе, MUST отсутствовать в wire-слое; неизвестные поля входящих кадров MUST игнорироваться.
- **FR-004**: Соответствие wire-слоя MUST быть закреплено фикстурами, снятыми с живого сервера этапа 1, и тестами «разбор → домен → сериализация» на них.
- **FR-005**: Курсор синхронизации (`since`) MUST персиститься на устройстве, обновляться по мере применения событий, переживать рестарт и сбрасываться логаутом вместе с локальными данными.
- **FR-006**: Модель вложения MUST нести срок хранения байтов (домен + локальное хранилище); доступность действия Save MUST учитывать срок (просрочено → действие недоступно).
- **FR-007**: Лимиты рукопожатия MUST сохраняться в data-слое и быть доступными потребителям через шов (реальное значение появится с транспортом 027; на моках — контрактные значения по умолчанию).
- **FR-008**: `RepositoryException` MUST различать коды отказов провода (§2.1), включая коды файловой цепочки; неизвестный код MUST трактоваться как `internal`.
- **FR-009**: Поведение UI MUST остаться неизменным: полный набор голденов проходит без перегенерации базовых снимков (исключая случаи, где изменение снимка — следствие детерминированного `seq` в мок-данных, а не видимого поведения).
- **FR-010**: Мок-датасорсы MUST отдавать данные в новых формах (seq, has_more, курсор), полностью имитируя контрактные ответы, чтобы флип 016 не менял репозитории и UI.

### Key Entities

- **Сообщение**: получает `seq` — глобальный разреженный внутри чата номер журнала; локальные поля (`status`, `localPath`) остаются устройство-локальными и в wire не выходят.
- **Вложение**: получает `expires_at` (unix-секунды) — срок хранения байтов на сервере.
- **Курсор устройства**: максимальный применённый `seq`; одно значение на устройство (журнал глобальный), живёт в локальном хранилище данных, гибнет с логаутом.
- **Лимиты сервера**: `max_message_bytes`, `max_attachment_bytes`, `max_frame_bytes` из рукопожатия; кэшируются в data-слое.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% фикстур живых кадров сервера (не менее 8: эхо, `message.new` c вложением и без, `chat.created`, `chat.updated`, страницы `chats.list`/`messages.list`/`chat.files`, ответ hello) разбираются и сериализуются с точным совпадением полей.
- **SC-002**: Полный набор голденов проходит без визуальных изменений; `make gate` зелёный.
- **SC-003**: Тред на моках догружает всю историю по `before_seq` без пропусков и дублей до признака «больше нет».
- **SC-004**: Курсор переживает рестарт приложения (значение равно максимальному применённому `seq`) и равен нулю после логаута.
- **SC-005**: Для каждого кода провода §2.1 существует различимое значение ошибки репозитория, покрытое тестом.

## Assumptions

- Приложение не выпущено: локальная Sembast-база пересоздаётся мок-генераторами при изменении формата — миграции локальных данных не требуются.
- Домен и хранилище сохраняют устройство-локальные поля (`status`, `localPath`, непрочитанное) — контракт §5/§6/§8.3 явно оставляет их клиенту; из провода они лишь исчезают.
- Курсор живёт в локальной базе данных (не в prefs): его жизненный цикл совпадает с локальными данными и он обязан гибнуть в том же акте логаута, что и сообщения.
- На этапе 1 `expires_at` — далеко в будущем, поэтому гейтинг Save не меняет ни одного текущего голдена; логика покрывается widget-тестом с просроченной фикстурой.
- Транспорта в этой фазе нет: лимиты и курсор питаются моками; живые значения приходят в фазе 027.
