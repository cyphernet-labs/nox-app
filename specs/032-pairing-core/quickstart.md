# Проверка: ядро спаривания

**Фаза 1** для [plan.md](./plan.md) · 2026-09-04

Как убедиться, что фича работает. Тесты закрывают механику; здесь — то, ответ на что принадлежит серверу и двум настоящим клиентам, а не нашему коду.

---

## 1. Гейт

```bash
make gate            # generate → format → analyze → test
make golden-verify   # эталоны, локально на Apple Silicon
cd client_backend && go test ./...
```

Ожидание: зелёные все три. Эталоны сдвинутся на затронутых экранах (вход, настройки, новый список устройств) — каждый сдвиг объясняется в сообщении коммита.

## 2. Живой сценарий на двух клиентах

### 2.1. Чистый старт

```bash
pkill -f noxd
rm -rf /tmp/nox-032 && mkdir -p /tmp/nox-032
cd client_backend && go build -o /tmp/nox-032/noxd . && cd ..
cd /tmp/nox-032 && ./noxd -addr 127.0.0.1:8080 -db /tmp/nox-032/t.db
```

**Ожидается:** в выводе — ссылка спаривания, один раз, с пометкой, что сервером ещё никто не завладел.

### 2.2. Главный сценарий — человек забирает свой сервер (SC-001)

1. Скопировать ссылку из вывода, запустить клиент, вставить её на экране входа.
2. **Ожидается:** личность создана, впереди экран выбора имени — сервер сообщил, что завёл её этим ответом. Назваться `Anna`, отправить сообщение.
3. Перезапустить клиент.
4. **Ожидается:** ни экрана входа, ни выбора имени — устройство подписало challenge и было узнано **по ключу**.

```bash
sqlite3 /tmp/nox-032/t.db "SELECT platform, datetime(created_at,'unixepoch') FROM devices"
sqlite3 /tmp/nox-032/t.db "SELECT claimed_at IS NOT NULL AS claimed FROM server_identity"
```

Одна строка устройства; `claimed = 1`.

### 2.3. Claim не срабатывает дважды

Предъявить ту же ссылку со второго клиента.

**Ожидается:** отказ «токен недействителен». **Не ожидается:** ни присоединения к чужой личности, ни второй личности.

### 2.4. Второе устройство той же личности (SC-004)

1. С первого клиента выпустить приглашение, показать ссылку.
2. Предъявить её на втором клиенте.
3. **Ожидается:** выбора имени НЕ показывается — личность не заводилась. Видна та же история; сообщение из шага 2.2 показано **своим**.

```bash
sqlite3 /tmp/nox-032/t.db "SELECT COUNT(*) FROM devices"          # 2
sqlite3 /tmp/nox-032/t.db "SELECT COUNT(*) FROM users"            # 1
```

Две строки устройств на **одну** личность — это то, ради чего личность отделена от устройства.

### 2.5. Приглашение одноразово и живёт десять минут (SC-003, SC-007a)

- Предъявить использованное приглашение ещё раз → «токен недействителен».
- Выпустить приглашение, подождать больше десяти минут, предъявить → **«срок истёк»**, отдельным сообщением.
- Предъявить claim на невостребованном сервере через сутки → **срабатывает**: у claim срока нет.

### 2.6. Одновременное предъявление

Предъявить одно приглашение с двух клиентов так, чтобы попытки пересеклись.

**Ожидается:** ровно один успех; второй получает «токен недействителен». **Не ожидается** двух устройств от одного токена.

### 2.7. Отзыв (SC-005)

1. Со второго клиента отозвать первый.
2. **Ожидается:** сессия первого рвётся **не дожидаясь** его следующей попытки; сам он приходит в состояние «не спарен» и вычищает локальные данные.
3. Попытаться подключиться первым заново → отказ.

```bash
sqlite3 /tmp/nox-032/t.db "SELECT COUNT(*) FROM devices"          # 1
```

### 2.8. Отзыв последнего устройства (SC-006)

Отозвать оставшееся устройство (выход из аккаунта при живой связи).

```bash
sqlite3 /tmp/nox-032/t.db "SELECT COUNT(*) FROM devices"          # 0
sqlite3 /tmp/nox-032/t.db "SELECT COUNT(*) FROM users"            # 1
```

**Личность осталась.** Она переживает потерю всех устройств — иначе кейс восстановления не к чему будет прицепить.

### 2.9. Выход без связи

Остановить сервер, выйти из аккаунта на клиенте.

**Ожидается:** локальная очистка прошла **безусловно**. Ключ остался в разрешённых на сервере — принятая цена, отзывается с другого устройства.

### 2.10. Имя уезжает командой (FR-019a)

Переименоваться в настройках при живой связи, **не перезапуская** приложение; смотреть на второе устройство.

**Ожидается:** имя доехало без перезапуска сессии. Сегодня для этого требуется переподключение.

### 2.11. Подпись действительно проверяется (SC-002)

```bash
sqlite3 /tmp/nox-032/t.db "UPDATE devices SET device_key='A6EHv/POEL4dcN0Y50vAmWfk1jCbpQ1fHdyGZBJVMbg='"
```

Подменить ключ устройства на чужой и попытаться подключиться.

**Ожидается:** отказ. Если соединение проходит — проверка подписи не работает, чем бы ни были зелены тесты.

### 2.12. Идентификатора входа нет нигде (SC-007)

```bash
sqlite3 /tmp/nox-032/t.db ".schema users" | grep -c id_digest      # 0
grep -rc "login_ref" client_backend/internal/ lib/ | grep -v ":0"  # пусто
```

Плюс глазами по журналам обеих сторон: ни идентификатора, ни токена, ни приватного ключа.

## 3. Признаки, что что-то пошло не так

| Симптом | Куда смотреть |
|---|---|
| Спаривание проходит с любым токеном | сжигание токена не атомарно, либо `used_at` не проверяется |
| Второе устройство попадает на выбор имени | `created` в ответе `pair` считается от факта, а не от того, завели ли личность |
| После отзыва устройство продолжает работать | сессия не рвётся, отзыв применён только к следующей попытке |
| Отозванное устройство показывает старые чаты | локальная очистка не отработала на событии отзыва |
| Имя расходится между двумя устройствами | переименование всё ещё уезжает приветствием, а не командой |
| Ссылка не читается на Windows/Linux | не задействован путь разбора QR из файла; вставка текстом обязана работать всегда |
