# Модель данных: ядро спаривания

**Фаза 1** для [plan.md](./plan.md) · 2026-09-04

Две стороны, два хранилища. Сервер — SQLite (`client_backend/migrations/001_init.sql`, правится **на месте**: до релиза миграция одна). Клиент — защищённое хранилище ОС для секретов и Sembast для всего остального.

---

## Сервер

### `server_identity` (новая таблица)

Долговременная личность самой машины. Одна строка, как `journal`.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | INTEGER PK CHECK (id = 1) | одна строка по построению |
| `public_key` | TEXT NOT NULL | Ed25519 pub, base64; уезжает в ссылку |
| `private_key` | TEXT NOT NULL | Ed25519 seed, base64; не покидает машину |
| `claimed_at` | INTEGER | когда сервером завладели; `NULL` = ещё нет |

**Ключ лежит в базе, а не в файле рядом** — обоснование в [research.md §4](./research.md). Коротко: правило кейса 6 требует, чтобы ключ не забыли при бэкапе, и один артефакт делает это невозможным по построению.

**`claimed_at` — это и есть автомат состояний сервера.** `NULL` — принимаются только claim-токены; не `NULL` — claim мёртв навсегда. Отдельного поля состояния не нужно, и невозможно рассинхронизировать два.

### `pair_tokens` (новая таблица)

| Поле | Тип | Смысл |
|---|---|---|
| `token` | TEXT PK | значение, 16 байт в base64url |
| `kind` | TEXT NOT NULL CHECK (kind IN ('claim','invite_device')) | тип; предъявителю **не виден** |
| `user_id` | TEXT REFERENCES users (user_id) | к какой личности привязывает; `NULL` для claim |
| `created_at` | INTEGER NOT NULL | |
| `expires_at` | INTEGER | момент истечения; **`NULL` = не истекает** |
| `used_at` | INTEGER | момент сжигания; `NULL` = ещё живой |

Правила:

- **Одноразовость через `used_at`, а не через удаление строки.** Израсходованный и никогда не существовавший токен требуют **разных** сообщений человеку (`invalid_token` в обоих случаях, но сервер обязан различать их в журнале), а удалённая строка теряет это различие. Плюс сожжение — атомарный `UPDATE … WHERE used_at IS NULL`, который безопасен при гонке двух предъявлений: выиграет ровно одно.
- **`expires_at IS NULL` для claim — не забывчивость, а решение** (уточнение 2026-09-04): claim умирает от использования, видит его только тот, у кого доступ к машине, а истекающий claim оставил бы свежий сервер невостребуемым. Приглашение живёт 10 минут.
- Токен переживает перезапуск — иначе приглашение нельзя показать человеку в соседней комнате.

### `devices` (существующая, меняется)

| Поле | Было | Стало |
|---|---|---|
| `device_key` | непрозрачный идентификатор установки | **публичный ключ Ed25519**, base64 |
| `platform` | — | **новое:** семейство ОС, для узнавания в списке |
| `user_id`, `created_at`, `last_seen_at` | без изменений | без изменений |

Отзыв — **удаление строки**. Никакого `revoked_at`: третье состояние пришлось бы проверять в каждом месте поиска, а удаление даёт нужное свойство даром — отозванное устройство неотличимо от неизвестного, и клиент ведёт себя одинаково в обоих случаях, включая пересобранный с нуля сервер.

### `users` (существующая, меняется)

`id_digest` (та самая производная от идентификатора входа) **удаляется**. Личность находится по ключу устройства; идентификатора входа больше не существует.

## Клиент

### Защищённое хранилище

| Ключ | Значение | Судьба |
|---|---|---|
| `session.device_secret` | **новый:** 32-байтовое семя Ed25519, base64 | рождается при первом спаривании, стирается выходом |
| `session.server_address` | **новый:** адрес и порт из ссылки | без него устройство спарится с одним сервером, а сообщения пошлёт в другой |
| `session.server_key` | **новый:** публичный ключ сервера из ссылки | сверять пока не с чем; сохранённый сейчас, он избавит от пере-спаривания, когда придёт пиннинг |
| `session.identifier` | **удаляется** | входа по идентификатору больше нет |
| `session.device_id` | **удаляется** | его роль занял публичный ключ |

Адрес и ключ сервера живут **вместе с сессией**, а не в конфигурации сборки: они описывают, какому серверу принадлежит эта установка, и умирают вместе с ней. Выход стирает их тем же `deleteAll`, что и всё остальное, и это правильно — после выхода человек предъявляет новую ссылку, которая несёт свой адрес.

Хранится **семя**, а не расширенный приватный ключ: 32 байта вместо 64, пара выводится детерминированно. Ограничение записано честно в [research.md §3](./research.md): ключ лежит в защищённом хранилище ОС, но извлекаем — аппаратный анклав требует нативной работы на пяти платформах и в эту фазу не входит.

### Обычные настройки

| Ключ | Изменение |
|---|---|
| `session.label_dirty` | **удаляется** — имя теперь уезжает командой, а не приветствием после перезапуска |
| `session.author_id`, `session.label`, `session.onboarding_complete` | без изменений |

Исчезновение `label_dirty` — не уборка, а следствие. Флаг существовал ровно потому, что имя могло уехать только в приветствии; с приходом `identity.setLabel` он описывает несуществующий путь, а `LiveSessionStarter.restart()` при переименовании перестаёт быть нужен.

### Признак «того же мира»

`LiveSessionStarter` сегодня считает эпоху мира как `'live:$apiUrl'` — от адреса из сборки. С адресом, приходящим из ссылки, ключ обязан считаться от **сохранённого** адреса: иначе два разных сервера, поднятых на одном адресе конфигурации, окажутся для устройства одним миром, и оно унесёт в новый чужие строки со старыми `seq`.

Признак смены журнала (`journal_id`, фаза 030) остаётся вторым, независимым детектором и не отменяется.

### Доменные модели

- **`PairingLink`** — разобранная ссылка: версия, адрес, порт, публичный ключ сервера, токен. Адрес и ключ из неё **сохраняются** (см. выше) — ссылка предъявляется один раз, а соединяться по этому адресу придётся всегда. Чистое значение, разбор — чистая функция; отказ разбора отличим от отказа токена.
- **`DeviceModel`** — строка списка устройств: ключ, платформа, момент привязки, момент последней связи, признак «это текущее».

## Что ломается намеренно

`device_key` меняет **значение**, а не форму, поэтому старые строки не преобразуемы: из идентификатора установки публичный ключ не выводится. Перехода нет — есть чистый старт хранилища сервера (правило единственной миграции, до релиза).

Клиенты узнают о пересборке уже существующим механизмом: `journal_id` изменился → локальный мир сбрасывается сам (фаза 030). Спариться заново придётся каждому: старый ключ новому серверу неизвестен, а это, по правилу выше, ровно то же самое, что отзыв — и обрабатывается тем же кодом.
