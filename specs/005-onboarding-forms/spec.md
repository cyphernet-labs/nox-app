# Feature Specification: Экраны этапа M2 — Онбординг-формы

**Feature Branch**: `005-onboarding-forms`

**Created**: 2026-06-20

**Status**: Draft

**Input**: User description: "Запланировать работу из `docs/roadmap.md` — Этап M2 — Онбординг-формы ⟶ вводит онбординг-хром и поля-ввода"

## Контекст фичи

Фаза 1 проекта (см. `docs/roadmap.md`) — сборка визуального слоя приложения по одному экрану; **интеграция с бэкендом вне scope**. Каркас «Галереи экранов» (этап M0) и семь экранов этапа M1 (Splash, Error, Appearance, Language, Notifications, Terms, About) уже готовы: на главном экране есть кнопка `Open Screens` → `ScreensGalleryPage` со списком всех экранов карты, где каждая строка активируется по мере реализации экрана.

Эта фича закрывает **этап M2** — четыре экрана онбординга и форм ввода: **Login / вход по идентификатору (2.1)**, **Set username / установка имени (2.3)**, **Create chat / создание чата (6.1)** и **QR scan / сканирование QR (2.2)**. Этап вводит два переиспользуемых семейства строительных блоков:

- **Онбординг-хром** — центральная карточка `OnboardCard` (440 на десктопе: логотип + wordmark + брендовый hairline) + десктоп-оконный фрейм/`TitleBar` (reuse `AppWindowTitlebarWidget` из M1). Переиспользуется 2.1, 2.3 (и desktop-denied состоянием 2.2).
- **Семейство полей-ввода** — моно ID-поле (2.1); labeled `TextField` + встроенный counter + suffix-спиннер доступности + `errorText` (2.3, 6.1).

Каждый экран реализуется как самостоятельный, открываемый из Галереи экранов, мультиплатформенный (мобайл + десктоп), со всеми визуальными состояниями на заглушечных данных, в соответствии с зафиксированными спеками `docs/design/spec/screens/` (`login.md`, `set-username.md`, `create-chat.md`, `qr-scan.md`) и десктоп/мобайл-корпусами (`nox-desktop-screens/screens/{04-login,05-username,06-qr,07-create}.md`, `nox-mobile-screens/screens/{2-1-login,2-2-qr-scan,2-3-username,6-1-create}.md`).

Связывание экранов в продуктовый флоу, реальная авторизация, серверные проверки уникальности, реальная камера/QR-декод — отдельная (backend) фаза.

## Clarifications

### Session 2026-06-20

- Q: Сколько внутри-онбординговой навигации проводить (экраны в спеках связаны: QR→Login auto-submit, Login→Username)? → A: **Полностью standalone, как M1.** Никакой меж-экранной навигации не строится; все переходы — `Scan QR` (2.1), исход sign-in (2.1), успех скана QR (2.2), `Done`/`Skip` (2.3), успех `Create` (6.1) — ведут на лёгкие плейсхолдеры или управляются debug-переключателями. Каждый экран открывается из Галереи изолированно; 2.2 открывается из Галереи напрямую, а не через `Scan QR` экрана 2.1.
- Q: Чем заменить живое видео камеры в 2.2 (плагин `mobile_scanner` — Фаза 2)? → A: **Нейтральный тематический плейсхолдер** за реальным оверлеем «прицел + затемняющая маска», плюс debug-контролы для воспроизведения состояний Scanning / невалидный-QR / permission-denied. Без выбрасываемых ассетов; строится весь настоящий хром, фейковые только пиксели потока.
- Q: Как детерминированно демонстрировать серверо-зависимые состояния (доступность имени 2.3/6.1, исходы входа 2.1)? → A: **Оба механизма.** Фиксированный мок-набор «занятых» имён/зарезервированных ID ведёт happy/taken-путь real-time проверки доступности (реалистичный ввод воспроизводит свободно/занято), плюс локальный debug-переключатель покрывает пути ошибка / fatal / исход входа.
- Q: Клиентская валидация формата ID на 2.1 — спека говорит «только сервер», десктоп-корпус упоминает клиентскую проверку (roadmap open-вопрос Q2)? → A: **Только сервер (по locked-спеке `login.md`).** `Sign in` активен при любом непустом вводе; ошибки формата приходят как inline серверные (заглушка). Упоминание клиентской проверки в десктоп-корпусе трактуется как дрейф — `login.md` не меняется.
- Q: Десктоп-лейаут QR scan (2.2) — выровнять по корпусу `06-qr.md` или оставить mobile-style и отложить оконный десктоп-хром? → A: **Выровнять по корпусу `06-qr.md`.** Десктоп 2.2 = оконный `TitleBar` (`NOX · Scan QR`) + центрированный вьюфайндер ≈300dp (brand-fixed углы) поверх нейтрального плейсхолдера + helper `Point your webcam at a code, or enter the ID manually.` с встроенной manual-entry-ссылкой + заголовок `Scan a QR code` + permission-denied внутри `OnboardCard` (иконка `no_photography` + `Open settings`). Переиспользование `OnboardCard` расширяется на 2.2-desktop-denied (FR-009 / SC-003). Отложенный `TODO(design-desktop-qr)` касается способа захвата QR, не лейаута.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Вход по идентификатору (Login, 2.1) (Priority: P1)

Пользователь вводит (или вставляет) длинный технический идентификатор и нажимает `Sign in`. Это головной экран онбординга и точка, вводящая онбординг-хром (`OnboardCard`) и моно ID-поле.

**Why this priority**: Первый экран онбординга и опорный для всего этапа — на нём впервые появляются и онбординг-хром, и семейство полей-ввода, которые переиспользуют остальные экраны M2.

**Independent Test**: Открыть Login из Галереи на узком и широком окне; убедиться, что поле `Your ID` принимает любой ввод без клиентской валидации, `Sign in` включается при непустом вводе, `Paste` отражает наличие буфера, а debug-переключатель воспроизводит исходы Loading / inline-error (формат и сеть) / fatal.

**Acceptance Scenarios**:

1. **Given** экран Login открыт и поле пустое, **When** он показан, **Then** многострочное поле `Your ID` пустое с placeholder `Paste or enter your ID`, `Sign in` disabled, `Paste` disabled при пустом буфере; снизу — secondary `Scan QR`.
2. **Given** в поле есть произвольный текст (любой длины и формата), **When** пользователь его ввёл, **Then** `Sign in` enabled (клиентской валидации формата нет), поле растёт по высоте при переносе строк.
3. **Given** поле заполнено, **When** пользователь нажимает `Sign in` (или Enter/Go), **Then** показывается Loading (поле и обе кнопки disabled, индикатор внутри primary button), затем — исход по debug-переключателю: новый ID → плейсхолдер установки имени, зарегистрированный → плейсхолдер шелла, ошибка формата/сети → inline-error с `errorText`, fatal → блокирующий экран ошибки 3.1.
4. **Given** широкое окно (десктоп), **When** экран показан, **Then** контент выводится центральной карточкой `OnboardCard` (≈440: логотип + wordmark `NOX` + брендовый hairline + моно ID-поле + `Sign in` + `Scan QR`) с оконным `TitleBar` (`NOX · Sign in`); на узком окне — полноэкранно с M3 `AppBar` (wordmark `NOX` + hairline).
5. **Given** экран Login (standalone-превью), **When** пользователь нажимает `Scan QR`, **Then** срабатывает заглушенный переход (плейсхолдер / no-op, помечен как точка замены) — реальная связка с 2.2 в этой фазе не строится.

### User Story 2 — Сканирование QR (QR scan, 2.2) (Priority: P2)

Пользователь наводит камеру на QR-код для входа без ручного ввода. В UI-only фазе живое видео камеры заменено нейтральным плейсхолдером, а все состояния воспроизводятся debug-контролами.

**Why this priority**: Альтернативный способ ввода идентификатора; вводит QR-overlay (прицел + маска) и blocking permission-denied панель. Камера — заглушка (плагин — Фаза 2), поэтому риск средний при высокой ценности проверки хрома.

**Independent Test**: Открыть QR scan из Галереи; убедиться, что построены прицел (brand-fixed #FAFAFA), затемняющая маска (`#000000` @ 55%), верхняя инструкция, AppBar-actions (фонарик `Flashlight` / смена камеры `Switch camera`) и нижний `Enter manually`; debug-контролами воспроизвести Scanning / Permission-denied / inline-error (snackbar) / успех скана.

**Acceptance Scenarios**:

1. **Given** экран QR scan открыт в состоянии Scanning, **When** он показан, **Then** под сплошным AppBar (цвет адаптируется под тему; тултипы `Back` / `Flashlight` / `Switch camera`) выводится нейтральный плейсхолдер вместо видео, поверх — brand-fixed квадратный прицел (#FAFAFA, 3dp) в центре и затемнённая маска (`#000000` @ 55%) вокруг, сверху инструкция `Aim your camera at a QR code`, снизу `Enter manually`; иконки фонарика и смены камеры — no-op.
2. **Given** смоделировано «доступ к камере отклонён», **When** экран показан, **Then** показывается **непрозрачная** поверхность с заголовком `Camera access needed`, сообщением `To scan a QR code, allow camera access in system settings.` и кнопкой `Open settings` (на мобайле — на весь экран, на десктопе — внутри `OnboardCard`; само действие — заглушка).
3. **Given** смоделирован «распознан валидный QR, но содержимое не подходит», **When** событие происходит, **Then** снизу показывается snackbar `This QR code is invalid. Try another one.`, плейсхолдер-сканирование продолжается.
4. **Given** смоделирован успешный скан, **When** событие происходит, **Then** срабатывает single-shot closing-flow (тихо, без кастомного feedback, плейсхолдер останавливается) — в standalone-превью ведёт на debug-плейсхолдер (реальный auto-submit в 2.1 — Фаза 2).
5. **Given** широкое окно (десктоп), **When** экран показан, **Then** по корпусу `06-qr.md` выводится оконный фрейм с `TitleBar` (`NOX · Scan QR`), центрированный вьюфайндер ≈300dp, заголовок `Scan a QR code` и helper `Point your webcam at a code, or enter the ID manually.` с manual-entry-ссылкой; состояние denied — внутри `OnboardCard`.

### User Story 3 — Установка имени пользователя (Set username, 2.3) (Priority: P2)

Пользователь опционально меняет публичное имя (label), предзаполненное значением `User<random>`, с локальной charset-валидацией и real-time проверкой занятости; шаг можно пропустить.

**Why this priority**: Второй экран онбординга; переиспользует онбординг-хром и вводит labeled-поле со счётчиком 32 и suffix-спиннером доступности — паттерн, который наследует 6.1.

**Independent Test**: Открыть Set username из Галереи; поле предзаполнено `User<random>`; ввод недопустимого символа даёт charset-ошибку, ввод «занятого» имени из мок-набора (после debounce) — `This name is taken`, ввод свободного валидного — enabled `Done`; очистка поля → только `Skip`.

**Acceptance Scenarios**:

1. **Given** экран Set username, **When** он показан, **Then** однострочное поле `Name` предзаполнено текущим `User<random>` (валидно и уникально), виден counter `N/32` и постоянный helperText `Others see this name. You can change it now or later in Settings.`, `Done` enabled, доступен `Skip`.
2. **Given** пользователь вводит недопустимый символ, **When** ввод обработан, **Then** показывается `errorText` charset (`Contains invalid characters (allowed: letters, digits, - _ .)`), `Done` disabled (charset-валидация клиентская — по спеке 2.3).
3. **Given** пользователь ввёл локально валидное имя, **When** проходит debounce (~300 мс), **Then** показывается suffix-спиннер (Checking-availability), затем по мок-набору — либо `Filled-valid` (свободно, `Done` enabled), либо `Filled-invalid (taken)` с `errorText` `This name is taken` (`Done` disabled).
4. **Given** поле очищено, **When** оно пустое, **Then** виден placeholder `How others will see you`, `Done` disabled (имя не может быть пустым), но `Skip` доступен.
5. **Given** имя валидно, **When** пользователь нажимает `Done` (или Enter/Done), **Then** показывается Loading-submit (индикатор внутри primary button), затем по debug-переключателю — успех (плейсхолдер шелла) / Race-taken (inline-error, фокус в поле) / fatal → 3.1.
6. **Given** широкое окно (десктоп), **When** экран показан, **Then** используется тот же онбординг-хром (центральная карточка), что и у 2.1.

### User Story 4 — Создание чата (Create chat, 6.1) (Priority: P3)

Пользователь вводит имя нового чата с real-time проверкой уникальности (лимит 64, charset не ограничен) и нажимает `Create`.

**Why this priority**: Форма, переиспользующая семейство полей-ввода (labeled + counter 64 + спиннер); зависит от ленты чата 5.2 (этап M4, ещё не построена), поэтому успех `Create` ведёт на плейсхолдер.

**Independent Test**: Открыть Create chat из Галереи; ввести имя — после debounce «занятое» из мок-набора даёт `This name is taken`, свободное — enabled `Create`; debug-переключатель воспроизводит Loading-submit / network-error / fatal.

**Acceptance Scenarios**:

1. **Given** экран Create chat, **When** он показан, **Then** полноэкранный Scaffold с AppBar `New chat` + back-стрелка (не wordmark — pushed-экран), поле `Chat name` (placeholder `e.g. Random thoughts`, counter `N/64`), снизу primary `Create` (disabled при пустом поле).
2. **Given** пользователь ввёл имя, **When** проходит debounce (~300 мс), **Then** показывается suffix-спиннер, затем по мок-набору — `Filled-valid` (`Create` enabled) или `Filled-invalid (taken)` с `This name is taken` (charset-ошибки нет — charset не ограничен).
3. **Given** имя валидно, **When** пользователь нажимает `Create` (или Enter/Done), **Then** Loading-submit (индикатор в primary button), затем по debug-переключателю — успех (плейсхолдер ленты 5.2) / network-error (`Could not create chat. Check your connection and try again.`, `Create` снова enabled) / fatal → 3.1.
4. **Given** форма заполнена, **When** пользователь делает back/cancel, **Then** возврат без подтверждения, введённый текст теряется.
5. **Given** широкое окно (десктоп), **When** экран показан, **Then** форма выводится модальным `Dialog` (≈460) со scrim вместо полноэкранного push, с действиями `Cancel` + `Create`; `Cancel` / тап по scrim закрывают без подтверждения (десктоп-корпус `07-create.md`).

### Edge Cases

- **Login (2.1):** поле растёт многострочно при длинном вводе и переносе строк; при фокусе клавиатура поднимается, AppBar может сжиматься, primary action остаётся виден; `Paste` всегда отображается, но disabled при пустом буфере.
- **Login (2.1) — корневой экран:** в реальном флоу системный back сворачивает приложение (`SystemNavigator.pop`); в standalone-превью из Галереи системный back/жест возвращает в Галерею (реальная «свернуть приложение» семантика — точка замены).
- **QR scan (2.2):** фонарик и смена камеры — toggle-иконки без реального эффекта (камеры нет); permission-prompt — системный диалог, в UI-only заглушен; fatal (камера недоступна на уровне устройства) → 3.1.
- **QR scan (2.2) — десктоп:** лейаут по корпусу `06-qr.md` (оконный `TitleBar` + ≈300dp вьюфайндер + `OnboardCard`-denied); реальный захват/декод QR — отложенный вопрос (`TODO(design-desktop-qr)`), в UI-only десктоп рендерит нейтральный плейсхолдер за вьюфайндером.
- **Set username (2.3):** kill-приложения на этом экране безопасен — имя `User<random>` уже «назначено при логине», состояния «без имени» не существует; back трактуется как `Skip`.
- **Set username (2.3) / Create chat (6.1) — гонка:** ответ «занято» может прийти на submit (race между real-time и submit) → inline-error, фокус возвращается в поле.
- **Все экраны:** компоновка не должна ломаться при большом масштабе текста и при узком/широком окне; debug-контролы воспроизведения состояний доступны только в dev-превью и не являются частью продуктового UI.

## Requirements *(mandatory)*

### Functional Requirements — сквозные

- **FR-001**: Все четыре экрана M2 (Login 2.1, QR scan 2.2, Set username 2.3, Create chat 6.1) MUST быть реализованы как самостоятельные экраны, открываемые из «Галереи экранов»; соответствующая строка галереи MUST активироваться (перестаёт быть `Coming soon`).
- **FR-002**: Каждый экран MUST иметь две адаптивные раскладки — мобайл (узкое окно) и десктоп (широкое окно), выбираемые по ширине окна (брейкпоинт `Constants.railBreakpoint`), согласно мобильному и десктопному корпусам. Ключевые десктоп-отличия: 2.1 — центральная карточка `OnboardCard` (≈440) + `TitleBar`; 2.3 — тот же онбординг-хром; 6.1 — модальный `Dialog` (≈460) вместо полноэкранного push; 2.2 — оконный `TitleBar` + центрированный вьюфайндер (≈300dp) + `OnboardCard`-denied (корпус `06-qr.md`).
- **FR-003**: Каждый экран MUST корректно отображаться в светлой и тёмной теме и при переключении темы. В M2 есть **одно** brand-fixed исключение — **camera-overlay сканера 2.2** (затемняющая маска `#000000` @ 55%, рамка-прицел stroke `brand/white` #FAFAFA 3dp, overlay-инструкция текст #FAFAFA), которое **не** темизируется (источник: `design-system.md` §9.9). AppBar сканера 2.2 — сплошной `surface`, адаптируется под тему через `ColorScheme`; всё остальное в M2 темизируется (тёмный splash и светлая QR-поверхность относятся к 1.1 и 7.1 — вне M2).
- **FR-004**: Вся пользовательская микрокопия MUST быть на английском через `TextConstants`; строковых литералов в виджетах и русского текста в UI быть не должно.
- **FR-005**: Все визуальные состояния каждого экрана, определённые его спекой, MUST быть воспроизводимы на заглушечных данных без бэкенда — через сочетание фиксированного мок-набора (happy/taken-путь проверки доступности) и локального debug-переключателя (исходы входа, ошибка/fatal, состояния камеры/скана).
- **FR-006**: Любая бэкенд-зависимость (серверная валидация ID, проверка уникальности имени/чата, исход входа, создание чата, разрешения камеры, реальная маршрутизация по флоу) MUST быть заглушена (фейковый результат/no-op) и помечена точкой будущей замены `// TODO(backend):`.
- **FR-007**: Каждый экран MUST быть покрыт автотестами уровня widget и golden (светлая + тёмная темы), по правилам именования/тегов проекта, через харнес `pumpApp`.
- **FR-008**: Экраны MUST оставаться **полностью standalone** — никакой меж-экранной навигации не строится: `Scan QR` (2.1), исход sign-in (2.1), успех скана QR (2.2), `Done`/`Skip` (2.3) и успех `Create` (6.1) ведут на лёгкие плейсхолдеры или управляются debug-переключателем. 2.2 открывается из Галереи напрямую (а не через 2.1).
- **FR-009**: Этап MUST ввести и переиспользовать два семейства блоков: (а) **онбординг-хром** — `OnboardCard` (центральная карточка ≈440 на десктопе: логотип + wordmark `NOX` + брендовый hairline над контентом — reuse `AppWordmarkWidget` + `AppSplashHairlineWidget`) + десктоп-оконный фрейм/`TitleBar` (reuse `AppWindowTitlebarWidget`; заголовок per-screen: `NOX · Sign in` / `NOX · Set up` / `NOX · Scan QR`), переиспользуемый 2.1, 2.3 и desktop-denied состоянием 2.2; (б) **семейство полей-ввода** — моно ID-поле (2.1) и labeled `TextField` + встроенный counter + suffix-спиннер доступности + `errorText` (2.3, 6.1). Дивергенция (несколько несогласованных реализаций) не допускается.

### Functional Requirements — Login / вход по идентификатору (2.1)

- **FR-010**: Login MUST показывать многострочное поле `Your ID` (открытый текст, без маски, растёт по высоте при переносе строк) с placeholder `Paste or enter your ID` и suffix-действием `Paste`.
- **FR-011**: Поле ID MUST НЕ иметь клиентской валидации формата (только серверная, заглушка); `Sign in` MUST быть enabled при любом непустом вводе и disabled при пустом.
- **FR-012**: `Paste` MUST всегда отображаться и быть disabled при пустом буфере обмена; при тапе вставляет содержимое буфера в поле.
- **FR-013**: Login MUST предоставлять primary `Sign in` (FilledButton на всю ширину) и secondary `Scan QR` (TextButton); Enter/Go на клавиатуре эквивалентен `Sign in`; auto-submit при ручном вводе отсутствует.
- **FR-014**: Login MUST воспроизводить состояния Empty / Filled / Loading (индикатор внутри primary button, поле и кнопки disabled) / Inline-error (формат `Invalid identifier`; сеть `Could not sign in. Check your connection and try again.`) / Fatal → блокирующий экран ошибки 3.1; исход выбирается debug-переключателем (новый ID / зарегистрированный / inline-error / fatal).
- **FR-015**: На десктопе Login MUST выводиться центральной карточкой `OnboardCard` (≈440: логотип + wordmark + hairline + моно ID-поле + `Sign in` + `Scan QR`) с оконным `TitleBar` (`NOX · Sign in`); на мобайле — полноэкранно с M3 `AppBar` (wordmark `NOX` + брендовый hairline под ним, как у M1 standalone-экранов).
- **FR-016**: `Scan QR` в standalone MUST быть заглушенным переходом (плейсхолдер/no-op, помечен `// TODO(backend):`) — реальная связка с 2.2 в этой фазе не строится.

### Functional Requirements — QR scan / сканирование QR (2.2)

- **FR-020**: QR scan MUST выводить (на мобайле) полноэкранный Scaffold со сплошным M3 `AppBar` (цвет адаптируется под тему через `ColorScheme`), back-стрелкой и actions-иконками фонарика (toggle) и смены камеры (toggle); заголовок AppBar намеренно пустой. Тултипы — `Back` (back-стрелка), `Flashlight` (фонарик), `Switch camera` (смена камеры).
- **FR-021**: Вместо живого видео камеры экран MUST рендерить **нейтральный плейсхолдер** (камера — плагин Фазы 2); поверх него — реальный QR-overlay с **brand-fixed** значениями (не из `ColorScheme`; источник `design-system.md` §9.9): затемняющая маска `#000000` @ 55% вокруг прицела, квадратный прицел stroke `brand/white` #FAFAFA шириной 3dp с углами `shape/m` (≈70% ширины экрана), верхняя инструкция `Aim your camera at a QR code` текстом #FAFAFA.
- **FR-022**: QR scan MUST воспроизводить (debug-контролами) состояния Scanning / Permission-denied / Inline-error (snackbar `This QR code is invalid. Try another one.`, сканирование продолжается) / Fatal → 3.1. Permission-denied — **непрозрачная** поверхность `surface` (не полупрозрачный scrim над плейсхолдером) с заголовком `Camera access needed`, сообщением `To scan a QR code, allow camera access in system settings.` и кнопкой `Open settings` (`FilledButton`); на мобайле — на весь экран, на десктопе — внутри `OnboardCard` (FR-026). Состояние Permission-prompt (системный диалог ОС) намеренно не воспроизводится в UI-only (OS-owned, заглушено) — на него SC-002 не распространяется.
- **FR-023**: Успешный скан MUST быть **single-shot** (сканирование плейсхолдера останавливается на первом распознавании и не ре-триггерится — в отличие от inline-error по FR-022, где плейсхолдер продолжает сканировать) и запускать closing-flow тихо (без звука, вибрации и кастомного UI-feedback'а); в standalone-превью ведёт на debug-плейсхолдер (реальный auto-submit в 2.1 — Фаза 2).
- **FR-024**: Фонарик, смена камеры, запрос системного разрешения и переход в системные настройки MUST быть заглушены (no-op) и помечены `// TODO(backend):`.
- **FR-025**: MUST быть secondary действие возврата к ручному вводу — на мобайле кнопкой `Enter manually` снизу, на десктопе встроенной manual-entry-ссылкой в helper'е (FR-026); в реальном флоу — возврат в 2.1 без submit, в standalone — заглушенный переход.
- **FR-026**: На десктопе QR scan MUST следовать корпусу `06-qr.md`: оконный фрейм с `TitleBar` (`NOX · Scan QR`), центрированный вьюфайндер ≈300dp (brand-fixed углы) поверх нейтрального плейсхолдера, helper `Point your webcam at a code, or enter the ID manually.` со встроенной manual-entry-ссылкой и заголовок `Scan a QR code`; состояние Permission-denied — внутри `OnboardCard` (иконка `no_photography` из `NoxIcons` + `Open settings`). Реальный захват/декод QR на десктопе остаётся заглушкой (`TODO(design-desktop-qr)` касается способа захвата, не лейаута).

### Functional Requirements — Set username / установка имени (2.3)

- **FR-030**: Set username MUST показывать (на мобайле) M3 `AppBar` с wordmark `NOX` + брендовый hairline (онбординг-экран) и однострочное поле `Name`, **предзаполненное** текущим `User<random>` (заглушка значения, в реальном флоу — назначено сервером при логине), с `maxLength: 32`, встроенным counter и постоянным helperText `Others see this name. You can change it now or later in Settings.`; на десктопе — `OnboardCard` с оконным `TitleBar` (`NOX · Set up`).
- **FR-031**: Поле имени MUST иметь **клиентскую charset-валидацию** (латиница + цифры + `-`, `_`, `.`) с `errorText` `Contains invalid characters (allowed: letters, digits, - _ .)`; это правило относится к полю имени (2.3) и не противоречит решению «ID-поле 2.1 — только сервер» (разные поля, разные правила). Валидность имени гейтится **только** charset (клиент) и уникальностью (мок) — зарезервированных/запрещённых имён нет (по Q5 спеки 2.3).
- **FR-032**: При локально валидном вводе MUST запускаться debounced (~300 мс) проверка занятости против мок-набора с suffix-спиннером (Checking-availability); проверка **case-sensitive** (`Anna` ≠ `anna`, по Q4 спеки 2.3); результат — `Filled-valid` (свободно) либо `Filled-invalid (taken)` с `This name is taken`.
- **FR-033**: Set username MUST воспроизводить состояния Prefilled / Checking-availability / Filled-invalid (charset) / Filled-invalid (taken) / Empty (placeholder `How others will see you`, `Done` disabled, `Skip` доступен) / Filled-valid / Loading-submit / Race-taken (inline-error, фокус в поле) / Fatal → 3.1.
- **FR-034**: Set username MUST предоставлять primary `Done` (FilledButton) и secondary `Skip` (TextButton); Enter/Done эквивалентен `Done`; `Skip` / системный back трактуются как пропуск (имя остаётся `User<random>`) — в standalone ведёт на debug-плейсхолдер.
- **FR-035**: На десктопе Set username MUST переиспользовать онбординг-хром (центральную карточку), введённый для 2.1.

### Functional Requirements — Create chat / создание чата (6.1)

- **FR-040**: Create chat MUST выводить полноэкранный Scaffold с M3 `AppBar` (title `New chat` + back-стрелка с тултипом `Back` — не wordmark, т.к. это pushed-экран) и поле `Chat name` (placeholder `e.g. Random thoughts`, `maxLength: 64`, встроенный counter, `helperText`/`errorText`).
- **FR-041**: Имя чата MUST иметь **неограниченный charset** (состояния charset-ошибки нет); при вводе MUST запускаться debounced (~300 мс) проверка уникальности против мок-набора с suffix-спиннером.
- **FR-042**: Create chat MUST воспроизводить состояния Empty / Checking-availability / Filled-invalid (taken, `This name is taken`) / Filled-valid / Loading-submit / Inline-error (network, `Could not create chat. Check your connection and try again.`, `Create` снова enabled) / Fatal → 3.1.
- **FR-043**: Create chat MUST предоставлять primary `Create` (FilledButton на всю ширину); Enter/Done эквивалентен `Create`; back/cancel возвращает без подтверждения с потерей введённого текста.
- **FR-044**: Успех `Create` в standalone MUST вести на debug-плейсхолдер (реальная лента чата 5.2 — этап M4, не построена), помеченный `// TODO(backend):`.
- **FR-045**: На десктопе Create chat MUST выводиться модальным `Dialog` (≈460) со scrim поверх (deselected) окна чатов, вместо полноэкранного push (корпус `07-create.md`); в диалоге — заголовок `New chat`, поле `Chat name` и пара действий `Cancel` (`TextButton`) + `Create` (`FilledButton`). `Cancel` или тап по scrim закрывают без подтверждения (эквивалент мобильного back). `Cancel` — добавляемая микрокопия.

### Key Entities

- **Screen entry (Галерея экранов)**: запись Галереи — идентификатор (например `2.1`), раздел (`Онбординг` / `Чаты`), наличие двух раскладок, признак «реализован/заглушка».
- **Онбординг-хром (OnboardCard)**: центральная карточка (≈440 на десктопе: логотип + wordmark `NOX` + брендовый hairline + контент) + десктоп-оконный фрейм/`TitleBar` (per-screen заголовок); переиспользуется 2.1, 2.3 и desktop-denied состоянием 2.2.
- **Семейство полей-ввода**: моно ID-поле (2.1) и labeled `TextField` + counter + suffix-спиннер доступности + `errorText` (2.3, 6.1).
- **Identifier / ID**: длинный технический идентификатор, вводимый в 2.1 открытым текстом; в этой фазе не валидируется и не хранится (заглушка).
- **Label / username**: публичное имя, ≤32 символов, charset `[A-Za-z0-9._-]`, уникальное case-sensitive; значение по умолчанию `User<random>` (заглушка).
- **Chat name**: имя чата, ≤64 символов, charset не ограничен, уникальное.
- **Availability check (mock)**: статус Checking / Available / Taken на основе фиксированного мок-набора «занятых» имён/ID (для 2.3, 6.1).
- **Sign-in outcome (mock)**: новый ID / зарегистрированный / inline-error / fatal — выбирается debug-переключателем (для 2.1).
- **Permission state (mock, камера)**: prompt (OS-owned, не воспроизводится в UI-only) / granted (схлопывается в Scanning — отдельного визуала нет) / denied — заглушка для 2.2.
- **QR scan result (mock)**: success(identifier) / invalid — debug-контрол для 2.2.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Все 4 экрана M2 открываются из Галереи экранов и отображаются без ошибок рендеринга в обеих темах и в обеих раскладках (узкое и широкое окно).
- **SC-002**: Для каждого экрана 100% состояний, определённых его спекой, демонстрируемы на заглушечных данных (мок-набор + debug-переключатель) — за единственным исключением OS-owned Permission-prompt сканера 2.2 (системный диалог, не воспроизводится в UI-only).
- **SC-003**: Онбординг-хром (`OnboardCard` + десктоп-оконный фрейм) и семейство полей-ввода введены один раз и переиспользуются ≥2 экранами каждый (хром: 2.1, 2.3 и desktop-denied 2.2; поле-ввода: 2.1, 2.3, 6.1) — без дублирующих несогласованных реализаций.
- **SC-004**: На Login `Sign in` включается при любом непустом вводе ID и нет клиентской валидации формата (только inline серверная заглушка).
- **SC-005**: На 2.3 и 6.1 real-time проверка доступности детерминированно показывает `available`/`taken` на мок-наборе (на 2.3 — case-sensitive: `Anna` ≠ `anna`); на 2.3 charset-валидация показывает charset-ошибку, на 6.1 charset-ошибки нет.
- **SC-006**: На 2.2 весь реальный хром построен поверх нейтрального плейсхолдера, причём прицел и затемняющая маска используют brand-fixed значения (#FAFAFA / `#000000` @ 55%), а не `ColorScheme`; все состояния скана (кроме OS-owned Permission-prompt) воспроизводимы debug-контролами.
- **SC-007**: 100% пользовательской микрокопии — английская; 0 строк русского текста в UI.
- **SC-008**: Каждый экран покрыт widget- и golden-тестами (светлая + тёмная), и проектный гейт качества (`make gate`) проходит зелёным.

## Assumptions

- Бэкенд, транспорт и протокол не выбраны (Конституция, тех-контекст) — поэтому все серверные зависимости (валидация ID, проверка уникальности имени/чата, исход входа, создание чата, разрешения камеры, реальная маршрутизация) заглушены и помечены точками будущей замены.
- Экраны открываются через dev-«Галерею экранов» (этап M0), а не через продуктовый навигационный флоу; связывание экранов — отдельная задача backend-фазы (решено в Clarifications / FR-008).
- **Полностью standalone**: никакой меж-экранной навигации; `Scan QR`, исход sign-in, успех скана QR, `Done`/`Skip`, успех `Create` → плейсхолдеры/debug-переключатели; 2.2 открывается из Галереи напрямую (FR-008).
- Камера (`mobile_scanner`) — плагин Фазы 2; 2.2 рендерит нейтральный плейсхолдер за оверлеем прицел+маска; фонарик/смена камеры/permission/deep-link — no-op (FR-021, FR-024).
- Charset-валидация имени (2.3) — клиентская, по locked-спеке `set-username.md`; это НЕ противоречит решению «ID-поле 2.1 — только сервер» — разные поля с разными правилами (FR-031).
- ID-поле (2.1) — только серверная валидация (Clarifications / FR-011); упоминание клиентской проверки в десктоп-корпусе трактуется как дрейф, `login.md` не меняется.
- Имя по умолчанию `User<random>` в 2.3 — предзаданная заглушка (в реальном флоу назначается сервером при логине), состояния «без имени» нет.
- 6.1 зависит от ленты чата 5.2 (этап M4, не построена) — успех `Create` ведёт на debug-плейсхолдер (FR-044).
- Дизайн-система, UI-kit (`App*Widget`) и токены готовы (Feature-003) и используются как есть; новые блоки (`OnboardCard`, семейство полей-ввода, QR-overlay) вводятся в рамках этой фичи и переиспользуются; десктоп-оконный фрейм/`TitleBar` — reuse `AppWindowTitlebarWidget` (введён в M1, уже принимает per-screen `title`); голова `OnboardCard` — reuse `AppWordmarkWidget` + `AppSplashHairlineWidget`.
- QR-overlay сканера 2.2 — единственное brand-fixed исключение M2 (маска `#000000` @ 55%, прицел/инструкция #FAFAFA; источник `design-system.md` §9.9); permission-denied — непрозрачная `surface` (мобайл) / `OnboardCard` (десктоп). Иконка denied — `no_photography` из `NoxIcons`; если её нет — добавляется как новый SVG (как в M1 для wifi/cloud), без сторонних icon-пакетов.
- Десктоп-корпус присутствует для всех четырёх экранов (`04-login`, `05-username`, `06-qr`, `07-create`) и используется как авторитетный desktop-референс наряду с locked-спеками.
- Десктоп-лейаут QR (2.2) выровнен по корпусу `06-qr.md` (оконный `TitleBar` + ≈300dp вьюфайндер + helper-ссылка + `OnboardCard`-denied + десктоп-копия) — решено в Clarifications / FR-026. Отложенный `TODO(design-desktop-qr)` касается лишь способа захвата/декода QR на десктопе (вебкамера/файл), не лейаута; захват остаётся заглушкой над нейтральным плейсхолдером.
- Login (2.1) и Set username (2.3) — корневые/онбординг-экраны; в standalone-превью системный back возвращает в Галерею, а реальная семантика «свернуть приложение / пропуск» помечается точкой замены.

## Out of Scope

- Связывание экранов в продуктовый навигационный флоу (`1.1 → 2.1↔2.2 → 2.3 → 4.1`; центральная `+` → `6.1` → `5.2`) и реальный auto-submit QR → Login.
- Реальная авторизация, чтение/хранение/валидация идентификатора, серверная проверка уникальности имени/чата, реальное создание чата.
- Реальная камера и QR-декод, фонарик, смена камеры, системные разрешения ОС и deep-link в системные настройки.
- Слой локализации (l10n) и персистентность (выбор имени, настройки) между перезапусками.
- Экраны-назначения переходов (4.1 шелл, 5.2 лента чата) — заменены лёгкими плейсхолдерами; их реализация — этапы M3/M4.
- Любая backend-интеграция и экраны других этапов (M3, M4).
