# Спецификация фичи: App-state flow (spine приложения)

**Feature Branch**: `009-app-state-flow`

**Created**: 2026-06-25

**Status**: Draft

**Input**: Перенос проверенного подхода «глобального app-state-flow» из другого Flutter-приложения (см. `docs/app-state-flow-migration.md`) в NOX, адаптированный под продуктовую модель NOX. Цель — единый реактивный источник правды «где сейчас приложение», который управляет всей верхнеуровневой навигацией, заменяя текущий launcher-вход. Спецификация экрана входа — `docs/design/spec/screens/login.md` (2.1).

---

## Контекст и мотивация *(почему)*

Сейчас приложение стартует в launcher (`HomePage`) → UI-kit / screens-галерею, а все экраны онбординга и оболочки — это **standalone-превью**, связанные демо-навигацией через placeholder-заглушки и debug-селекторы (`SplashOutcome`, `LoginOutcome`). Реальной точки принятия решения «куда вести пользователя при запуске» нет: нет источника правды о сессии, нет гейтинга навигации, нет единого места, откуда login / logout / установка имени переключают верхнеуровневый экран.

Фича вводит **spine приложения** — один реактивный объект состояния жизненного цикла (`init → unauthorized → registrationPending → authorized`), который вычисляется из локально сохранённых сигналов сессии и через единый app-level контроллер превращается в замену верхнеуровневого навигационного стека. Это снимает отложенный архитектурный gap `auth/app-state-spine`, отмеченный в блюпринте, и делает существующие экраны (Splash 1.1, Login 2.1, Set username 2.3, Chats shell 4.1, Error 3.1) частью одного связного флоу вместо разрозненных превью.

**Адаптация под NOX (отличия от исходника):** нет гостевого режима (`authorizedGuest` удалён), нет выбора роли — вместо `selectProfileType` используется `registrationPending` (идентификатор принят, но публичное имя ещё не задано → экран `Set username`). Бэкенд/протокол NOX ещё не выбран, поэтому реальный сетевой sign-in и 401-перехватчик отложены; резолюция состояния выполняется **только из локального кэша, без сети**.

## Clarifications

### Session 2026-06-25

- Q: Как смоделировать cache-only сигнал сессии и чем отличать `registrationPending` от `authorized`? → A: Ввести минимальный `SessionModel { identifier, label?, onboardingComplete }` через `SessionRepository` (cache-only); дискриминатор — флаг `onboardingComplete` (ставится по завершению `Set username` 2.3); `AppStateModel` несёт `SessionModel` вместо исходного `user`.
- Q: Как застабленный `Sign in` взаимодействует с хранилищем сессии до бэкенда? → A: Стаб пишет введённый идентификатор через `SessionRepository` и помечает `onboardingComplete=false` → `registrationPending`; идентификаторы из mock-набора `OnboardingMockData.registeredIds` сидятся как `onboardingComplete=true` → сразу `authorized`. Restart-resume работает.
- Q: В каком объёме подключаем триггер выхода на этом этапе? → A: Реальное действие Logout в `Settings`-табе шелла → обычный logout (полный wipe → `unauthorized` → Login 2.1); `forceLogout` (принудительный) остаётся программным/dev до бэкенда.

## Пользовательские сценарии и тестирование *(обязательно)*

### User Story 1 — Cold-start приводит пользователя на правильный экран (Priority: P1)

При запуске приложение само определяет, в каком состоянии находится сессия, и показывает соответствующий верхнеуровневый экран — без launcher и без мелькания промежуточных экранов. Первая навигация удерживается за анимацией splash: пользователь видит брендовый запуск и затем оказывается ровно на нужном экране.

**Why this priority**: Это ядро всей фичи и минимально жизнеспособный продукт. Без единого резолвера и гейтинга навигации остальные сценарии (login/logout-переходы, session-expiry) не на чем строить. Один этот слайс уже даёт ценность: детерминированный, демонстрируемый запуск приложения на реальных экранах.

**Independent Test**: Запустить приложение при трёх предзаданных локальных состояниях сессии (нет идентификатора / идентификатор есть, имя не задано / идентификатор и имя есть) и убедиться, что после анимации splash открывается соответственно Login (2.1) / Set username (2.3) / Chats shell (4.1). Никакой launcher/галерея при обычном запуске не показывается.

**Acceptance Scenarios**:

1. **Given** локально не сохранён идентификатор, **When** приложение запускается, **Then** после завершения reveal-анимации splash открывается экран Login (2.1), и splash из стека удаляется (назад на splash вернуться нельзя).
2. **Given** сохранён идентификатор, но публичное имя ещё не задано, **When** приложение запускается, **Then** после splash открывается экран Set username (2.3).
3. **Given** сохранены идентификатор и публичное имя, **When** приложение запускается, **Then** после splash открывается Chats shell (4.1).
4. **Given** первый запуск, **When** состояние сессии резолвится быстрее, чем проигрывается анимация splash, **Then** навигация не происходит раньше завершения анимации (нет вспышки/мелькания целевого экрана поверх splash).
5. **Given** обычный запуск приложения, **When** приложение стартует, **Then** пользователь не видит launcher (`HomePage`) или UI-kit/screens-галерею как точку входа.

---

### User Story 2 — Изменения сессии немедленно переключают верхнеуровневый экран (Priority: P2)

Любое действие, меняющее состояние сессии (успешный вход, установка имени, выход), приводит к пересчёту состояния, и навигация реагирует **немедленно**, заменяя весь стек (без сохранения back-stack через границу авторизации).

**Why this priority**: Превращает spine из «однократного резолвера на старте» в живой контроллер. Делает существующие экраны связным флоу. Зависит от P1.

**Independent Test**: Из Login выполнить вход под новым идентификатором → проверить переход на Set username (2.3); задать имя → проверить переход на Chats (4.1); выполнить выход → проверить возврат на Login (2.1) с полностью обнулённым стеком. Кнопка/жест «назад» после каждого перехода не возвращает на предыдущий экран авторизационной границы.

**Acceptance Scenarios**:

1. **Given** пользователь на Login (2.1), **When** вход под ранее не зарегистрированным идентификатором успешен, **Then** состояние становится `registrationPending`, и открывается Set username (2.3); назад на Login вернуться нельзя.
2. **Given** пользователь на Login (2.1), **When** вход под уже зарегистрированным идентификатором успешен, **Then** состояние становится `authorized`, и открывается Chats shell (4.1).
3. **Given** пользователь на Set username (2.3), **When** имя успешно задано, **Then** состояние становится `authorized`, и открывается Chats shell (4.1).
4. **Given** пользователь авторизован (Chats shell), **When** выполняется выход (Logout), **Then** всё локальное состояние сессии очищается, состояние становится `unauthorized`, и открывается Login (2.1) с обнулённым стеком.
5. **Given** любое из перечисленных изменений сессии произошло, **When** состояние уже было разрешено ранее (не первый запуск), **Then** переход применяется сразу, без удержания за splash-анимацией.

---

### User Story 3 — Контракт принудительного выхода и сообщения об истёкшей сессии (Priority: P3)

Spine несёт одноразовый признак причины выхода (`sessionExpired`): принудительный выход (forced logout) очищает сессию и при возврате на Login один раз показывает сообщение об истёкшей сессии. Обычный (пользовательский) выход сообщение не показывает. Сам триггер принудительного выхода (например, 401 от сервера) на этом этапе не подключается — контракт закладывается, чтобы будущая интеграция бэкенда не переписывала spine.

**Why this priority**: Сохраняет проверенный контракт целиком, чтобы при появлении бэкенда добавить только триггер, а не менять модель состояния и навигацию. Само по себе пользовательской ценности на этом этапе почти не несёт (триггер отложен), поэтому P3.

**Independent Test**: Вызвать публичный путь принудительного выхода (`forceLogout`) программно/через dev-точку и убедиться, что: состояние стало `unauthorized`, открылся Login (2.1), и **один раз** показалось сообщение `Your session expired` поверх свежего Login. Повторного показа при последующих переходах нет.

**Acceptance Scenarios**:

1. **Given** установленная сессия, **When** срабатывает принудительный выход, **Then** локальное состояние очищается, состояние становится `unauthorized` с признаком `sessionExpired`, открывается Login (2.1), и один раз показывается сообщение об истёкшей сессии.
2. **Given** установленная сессия, **When** выполняется обычный пользовательский выход, **Then** открывается Login (2.1) **без** сообщения об истёкшей сессии.
3. **Given** сообщение об истёкшей сессии уже показано, **When** происходят последующие верхнеуровневые переходы, **Then** сообщение повторно не показывается (одноразовость).

---

### Edge Cases

- **Окно «состояние ещё не разрешено» (boot).** До первой резолюции состояние не определено (`currentState == null`). Этот момент трактуется как «сессия не установлена»: никакие деструктивные действия (например, принудительный выход) в этом окне не выполняются. `null` ≠ `unauthorized`.
- **Сбой/недоступность локального хранилища сессии.** Если чтение идентификатора из защищённого хранилища завершается ошибкой или backend хранилища недоступен на платформе, резолюция безопасно сходится к `unauthorized` (показываем Login), а не падает.
- **Холодный старт без сети.** Резолюция состояния не должна ждать сетевого вызова — выполняется только из локального кэша, чтобы запуск был быстрым и работал офлайн.
- **Системный «назад» на корневых экранах.** На корневых экранах (Login / Chats shell) системный back сворачивает приложение (стандарт корневого экрана), а не возвращает на предыдущую авторизационную границу.
- **Изменение состояния посреди собственного навигационного флоу.** Заложить точку расширения (предикат), позволяющую при необходимости вето на верхнеуровневую замену стека, пока активен флоу, владеющий своей навигацией. На текущем этапе у NOX таких флоу нет — предикат остаётся нейтральным (всегда разрешает), но точка зафиксирована.
- **Гонка splash-анимации и резолюции.** Если резолюция завершилась раньше анимации — навигация ждёт анимацию; если анимация завершилась раньше резолюции — навигация ждёт резолюцию. Первая навигация происходит не раньше, чем выполнены оба условия.
- **Fatal-ошибки старта.** Неожиданные/fatal-ошибки (вне классов «нет сети»/«неверный формат») ведут на Universal error (3.1) согласно текущим экранным контрактам; они не являются отдельным app-состоянием.

## Требования *(обязательно)*

### Функциональные требования

- **FR-001**: Система ДОЛЖНА поддерживать единый реактивный источник правды о состоянии жизненного цикла приложения с конечным набором состояний: `init`, `unauthorized`, `registrationPending`, `authorized`.
- **FR-002**: Система ДОЛЖНА вычислять текущее состояние из локально сохранённых сигналов сессии **только из кэша, без сетевых вызовов**.
- **FR-003**: Резолюция ДОЛЖНА следовать детерминированному порядку: нет сохранённого идентификатора → `unauthorized`; идентификатор есть и `onboardingComplete=false` → `registrationPending`; идентификатор есть и `onboardingComplete=true` → `authorized`. Состояние `init` — только до первой резолюции (boot).
- **FR-004**: Система ДОЛЖНА предоставлять состояние тремя способами: (а) реактивный поток, повторяющий последнее значение новым подписчикам и форвардящий все последующие; (б) императивный пересчёт по запросу; (в) синхронное чтение последнего значения (для будущего перехватчика; до первой резолюции возвращает «не определено»).
- **FR-005**: Система ДОЛЖНА управлять **всей** верхнеуровневой навигацией из одного app-level контроллера: каждое применённое состояние отображается на верхнеуровневый экран по контракту `init → Splash (1.1)`, `unauthorized → Login (2.1)`, `registrationPending → Set username (2.3)`, `authorized → Chats shell (4.1)`.
- **FR-006**: Самый первый переход (с экрана Splash) ДОЛЖЕН быть **удержан за анимацией splash**: состояние резолвится во время splash, но навигация применяется только после завершения reveal-анимации. Все последующие переходы применяются немедленно.
- **FR-007**: При первом переходе со Splash система ДОЛЖНА заменять splash (без сохранения его в стеке); при любом последующем авторизационном переходе — полностью обнулять навигационный стек (назад через авторизационную границу невозможно).
- **FR-008**: Любой код, изменяющий сигналы сессии (успешный вход, установка имени, выход), ДОЛЖЕН сначала записать источник правды через `SessionRepository` (идентификатор / `onboardingComplete` / `label`), затем инициировать пересчёт состояния — именно пересчёт продвигает навигацию.
- **FR-009**: Система ДОЛЖНА хранить идентификатор пользователя (security-чувствительный) в защищённом хранилище платформы (`flutter_secure_storage`); несекретные сигналы сессии (`onboardingComplete`, кэш публичного `label`) — в обычном хранилище настроек (`SharedPreferences`).
- **FR-010**: Выход (logout) ДОЛЖЕН полностью очищать локальные данные сессии (полный wipe идентичности — согласно продуктовой модели «одна идентичность на устройство, смена = Logout + повторный вход» и Принципу I конституции), после чего резолюция даёт `unauthorized`. Обычный выход инициируется действием Logout в `Settings`-табе (FR-020); принудительный — публичным `forceLogout()` (FR-012).
- **FR-011**: Система ДОЛЖНА нести одноразовый признак причины выхода `sessionExpired`: он устанавливается **только** на пути принудительного выхода и потребляется ровно один раз для показа сообщения `Your session expired` поверх свежего Login. Обычный выход признак не устанавливает.
- **FR-012**: Система ДОЛЖНА предоставлять единый публичный путь выхода, принимающий признак «принудительный», и быть единственным местом, устанавливающим `sessionExpired = true`.
- **FR-013**: Точкой входа приложения ДОЛЖЕН стать Splash (1.1) под управлением spine; launcher (`HomePage`) перестаёт быть точкой входа при обычном запуске.
- **FR-014**: UI-kit / screens-галерея ДОЛЖНА оставаться доступной как dev-вход (не как обычная точка входа); существующая preview-обвязка экранов (`demo:`-режимы, placeholder-навигация, debug-селекторы) не должна ломаться.
- **FR-015**: Резолюция и навигация ДОЛЖНЫ безопасно деградировать: ошибка чтения хранилища сессии трактуется как «нет сессии» (`unauthorized`), а не как падение.
- **FR-016**: Система ДОЛЖНА закладывать нейтральную точку расширения (предикат подавления верхнеуровневой навигации) для будущих флоу, владеющих своей навигацией; на текущем этапе предикат всегда разрешает переход.
- **FR-017** *(вне реализации этого этапа, зафиксировано как отложенное)*: Триггер принудительного выхода (синхронное чтение состояния перехватчиком сети на 401 и решение о выходе только для уже установленной сессии) НЕ реализуется сейчас — закладывается контракт и публичный путь; подключение триггера выполняется в фазе бэкенда.
- **FR-018**: Система ДОЛЖНА вводить минимальную доменную сессию `SessionModel { identifier, label?, onboardingComplete }`, читаемую cache-only через `SessionRepository`; это единственный источник входных сигналов резолвера, и `AppStateModel` несёт `SessionModel` (вместо исходного `user`).
- **FR-019**: Застабленный `Sign in` (до бэкенда) ДОЛЖЕН записывать введённый идентификатор через `SessionRepository` и помечать `onboardingComplete=false` → `registrationPending`; идентификаторы из mock-набора `OnboardingMockData.registeredIds` ДОЛЖНЫ сидаться как `onboardingComplete=true` → `authorized`. Успешное завершение `Set username` (2.3) ставит `onboardingComplete=true`.
- **FR-020**: Система ДОЛЖНА подключить действие Logout в `Settings`-табе шелла, инициирующее обычный (не принудительный) выход по контракту FR-010 / FR-008.

### Ключевые сущности *(модель состояния)*

- **Состояние жизненного цикла (`AppStateType`)**: перечисление `init` / `unauthorized` / `registrationPending` / `authorized`. Линейно-подобный жизненный цикл, единственный, который интересует верхнеуровневый навигатор. `init` — загрузочный sentinel.
- **Модель состояния (`AppStateModel`)**: оборачивает состояние вместе с разрешённой сессией (`SessionModel`, опционально) и одноразовым признаком `sessionExpired` (по умолчанию `false`). Не является источником правды — это **проекция** сигналов сессии, пересчитываемая на каждом холодном старте; нигде не персистится отдельно (никакого собственного DAO).
- **Сессия (`SessionModel`)**: минимальный cache-only value-объект `{ identifier, label?, onboardingComplete }`, отдаваемый `SessionRepository`. Единственный вход резолвера. `identifier` — security-чувствительный (`flutter_secure_storage`); `onboardingComplete` и кэш `label` — несекретные (`SharedPreferences`). Дискриминатор `registrationPending` ↔ `authorized` — флаг `onboardingComplete`. Заменяет исходный `user` из мигрируемого подхода (в NOX доменной `UserModel` пока нет).
- **Контракт spine (`AppStateRepository`)**: три члена — реактивный поток состояния, императивный пересчёт (с параметром `sessionExpired`), синхронное чтение последнего состояния. Живёт как app-wide singleton (его реактивный субъект должен переживать каждую страницу).
- **App-level контроллер навигации**: подписывается на поток состояния один раз; держит «последнее» и «применённое» состояние плюс флаг готовности, чтобы реализовать удержание первого перехода за splash (двухфазное применение) и немедленное применение последующих.

## Критерии успеха *(обязательно)*

### Измеримые результаты

- **SC-001**: При обычном запуске пользователь в 100% случаев попадает на экран, соответствующий сохранённому состоянию сессии (Login / Set username / Chats), без показа launcher или галереи.
- **SC-002**: Первая навигация после запуска ни в одном прогоне не происходит раньше завершения reveal-анимации splash (нет вспышки целевого экрана поверх splash) — при любой относительной скорости резолюции и анимации.
- **SC-003**: После успешного входа, установки имени или выхода верхнеуровневый экран обновляется немедленно (в пределах того же кадра применения), и навигационный стек обнулён: жест «назад» с нового экрана не возвращает на предыдущую авторизационную границу.
- **SC-004**: Состояние сессии переживает перезапуск приложения: при сохранённом идентификаторе с `onboardingComplete=true` повторный запуск открывает Chats, с `onboardingComplete=false` — Set username; после выхода повторный запуск открывает Login.
- **SC-005**: Выход полностью очищает локальные данные сессии — после выхода ни в защищённом, ни в обычном хранилище не остаётся идентификатора/имени, и последующий cold-start резолвится в `unauthorized`.
- **SC-006**: Сообщение об истёкшей сессии при принудительном выходе показывается ровно один раз и не повторяется при последующих переходах; при обычном выходе не показывается ни разу.
- **SC-007**: Резолюция состояния на холодном старте не выполняет ни одного сетевого вызова (проверяемо при полностью отключённой сети — запуск ведёт себя идентично).
- **SC-008**: Существующая preview-обвязка остаётся рабочей: каждый экран по-прежнему открывается из галереи в demo-режиме, и `make gate` (generate → format → analyze → test) проходит зелёным.
- **SC-009**: Вход под идентификатором из mock-набора `registeredIds` детерминированно ведёт в Chats (`authorized`), под любым другим — в Set username (`registrationPending`); поведение воспроизводимо и проверяемо тестом.

## Предположения

- **Бэкенд/протокол NOX ещё не выбран.** Реальный сетевой sign-in не реализуется в этой фиче: исход входа остаётся застабленным (mock-датасет / debug-селектор, как сейчас), а резолюция состояния читает локальные сигналы сессии. Контракты сети/перехватчика помечены TBD в блюпринте.
- **Источник «есть ли сессия?»** — `SessionModel` (cache-only через `SessionRepository`): наличие сохранённого идентификатора + флаг `onboardingComplete`, а не серверный токен. `identifier` — в `flutter_secure_storage`; `onboardingComplete` и кэш `label` — в `SharedPreferences`. Застабленный `Sign in` пишет эти сигналы (registered-set из `registeredIds` → `onboardingComplete=true`); обычный выход — действие Logout в `Settings`.
- **Защищённое хранилище**: соответствующий пакет уже объявлен в зависимостях проекта; «интеграция» сводится к нативной донастройке (где требуется — например, системные зависимости desktop) и repository-обёртке, а не к добавлению пакета. Платформенная донастройка/верификация secure-storage на всех пяти таргетах — часть этого этапа в объёме, необходимом для работы spine; полная desktop-полировка остаётся будущей работой по блюпринту.
- **Продуктовая модель NOX**: нет гостевого режима и нет выбора роли; единственный промежуточный гейт — `registrationPending` (первый вход под идентификатором без заданного публичного имени → Set username 2.3). Одна идентичность на устройство; смена идентичности = Logout (полный локальный wipe) + повторный вход.
- **Точка входа**: spine заменяет launcher как точку входа; UI-kit/screens-галерея сохраняется как dev-доступная (например, из Settings или debug-only), и preview-обвязка экранов не ломается.
- **Принудительный выход (триггер) отложен**: закладывается контракт `sessionExpired` + единый публичный путь выхода; подключение 401-перехватчика и синхронного гейта по состоянию — в фазе бэкенда.
- **Splash как гейт первой навигации сохраняется**: двухфазное применение (удержать первый переход за анимацией, применять последующие немедленно) — обязательная часть подхода.

## Вне scope

- Реальный сетевой sign-in, refresh/токен-модель, HMAC/подпись запросов и любой реальный серверный контракт авторизации.
- 401-перехватчик сети и автоматический триггер принудительного выхода (закладывается только контракт и публичный путь).
- Привязка QR-success-флоу к реальному сканеру (2.2) и любой реальный backend сканирования.
- Deep links и push-навигация как потребители app-state (точки расширения упоминаются, но не реализуются).
- Локализация строк (i18n) — UI-микрокопирайт остаётся английскими константами, как в текущем коде.
- Гостевой режим и выбор роли (отсутствуют в продуктовой модели NOX).
