# Feature Specification: Полная бизнес-логика на mock-репозиториях поверх реальной локальной БД

**Feature Branch**: `013-local-db-business-logic`
**Created**: 2026-07-18
**Status**: Draft
**Input**: Довести приложение до абсолютно полной UI-части и бизнес-логики на моках: репозитории chat/message/file переходят с network-only мок-обёрток на **реальную локальную БД (Sembast cache-first по блюпринту 04)** — мок пишет/читает настоящую базу (watch + пагинация из БД); все BLoC-события/состояния реализованы по-настоящему; бэкенд НЕ рассматривается (предполагаемый API, будущая интеграция).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Данные чата живут в реальной локальной БД (Priority: P1)

Пользователь создаёт чат, отправляет сообщения, открывает вложения — и всё это сохраняется в настоящей локальной базе, а не в эфемерном mock-списке: после перезапуска приложения созданные чаты и отправленные сообщения на месте.

**Why this priority**: Сердце рабочего режима — «моки должны реально работать с базами». Сейчас chat/message/file — network-only мок (эфемерно, ничего не персистится). Без реальной БД бизнес-логика неполна.

**Independent Test**: Создать чат → отправить сообщение → «перезапустить» приложение → чат и сообщение присутствуют (читаются из локальной БД).

**Acceptance Scenarios**:

1. **Given** пустой список чатов, **When** пользователь создаёт чат, **Then** чат появляется в списке и сохраняется в локальной БД (виден после перезапуска).
2. **Given** открытый чат, **When** пользователь отправляет сообщение, **Then** оно добавляется в ленту, персистится локально (`sent`), и видно после перезапуска.
3. **Given** чат с сообщениями, **When** пользователь открывает список файлов чата, **Then** он строится из локально сохранённых вложений.

---

### User Story 2 - Cache-first реактивные репозитории (Priority: P1)

Экраны реагируют на изменения локальной БД реактивно (watch), а списки пагинируются из БД — так же, как будет с реальным бэкендом, только источник сейчас локальный.

**Why this priority**: Блюпринт 04 канонизирует cache-first reactive репозитории; это архитектурный контракт, который переживёт появление бэкенда (подменяется только сетевой слой). Реализовать сейчас = получить правильную архитектуру на моках.

**Independent Test**: Изменить данные в БД (создать чат/сообщение) без ручного refresh → подписанный экран обновляется сам; пролистать список → следующая страница приходит из БД.

**Acceptance Scenarios**:

1. **Given** открытый список чатов, **When** создан новый чат, **Then** список обновляется без ручного refresh (reactive watch).
2. **Given** длинный список/лента, **When** пользователь листает, **Then** следующая страница подтягивается из локальной БД (пагинация), без дублей и пропусков.
3. **Given** нет данных, **When** экран открыт, **Then** показывается пустое состояние; при ошибке чтения — состояние ошибки.

---

### User Story 3 - Полная бизнес-логика UI (все события/состояния) (Priority: P1)

Каждый экран имеет реализованные до конца BLoC-события и состояния: загрузка, пагинация, пустые/офлайн-состояния, ошибки, оптимистичные мутации (создание чата, отправка сообщения, статусы `pending`/`sent`/`error`) — без заглушек-плейсхолдеров логики.

**Why this priority**: Цель фазы — «абсолютно полная бизнес-логика». Реальная БД без полной логики бесполезна; полная логика без БД эфемерна. Вместе дают готовый к бэкенду продукт.

**Independent Test**: Пройти по каждому экрану со всеми состояниями (loading/loaded/empty/error/offline) и мутациями (create/send/retry) — все ведут себя корректно и детерминированно на локальных данных.

**Acceptance Scenarios**:

1. **Given** отправка сообщения, **When** мок-транспорт «принимает», **Then** статус переходит `pending → sent`; при смоделированной ошибке — `error` с возможностью retry.
2. **Given** создание чата с занятым именем (мок-правило), **When** submit, **Then** показывается inline-ошибка, без создания дубликата.
3. **Given** офлайн (смоделировано), **When** экран открыт, **Then** показан офлайн-баннер, данные читаются из кэша.

---

### Edge Cases

- Первый запуск с пустой БД → сидирование детерминированного мок-набора (текущие `_mockChats`/`_mockMessages`) в локальную БД один раз, затем чтение из БД.
- Повреждённая/несовместимая версия схемы БД → безопасная миграция/пересоздание, без падения.
- Пагинация на границе (последняя страница) → `nextPage == null`, без лишних запросов.
- Detерминизм тестов/goldens сохраняется (реальное время через `AppClock`, посев БД под фиксированные данные).
- Парити mobile/desktop: списки/лента/детали одинаковы на `_narrow`/`_wide`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Репозитории chat/message/file MUST хранить и читать данные из реальной локальной БД (Sembast), а не из эфемерного in-memory мок-списка.
- **FR-002**: Список чатов и лента сообщений MUST быть **cache-first reactive** (watch локальной БД) — экраны обновляются без ручного refresh при изменении данных.
- **FR-003**: Списки (чаты, сообщения) MUST пагинироваться из локальной БД (offset/cursor per blueprint 07), без дублей/пропусков.
- **FR-004**: Создание чата MUST персистить чат локально и отражаться в реактивном списке.
- **FR-005**: Отправка сообщения MUST персистить сообщение локально с корректными статусами (`pending → sent`; смоделированная ошибка → `error` + retry).
- **FR-006**: Список файлов чата MUST строиться из локально сохранённых вложений.
- **FR-007**: Все затронутые BLoC MUST иметь реализованные события/состояния: loading, loaded, empty, error, offline, оптимистичные мутации — без плейсхолдер-логики.
- **FR-008**: При первом запуске приложение MUST один раз засеять детерминированный мок-набор в локальную БД, далее читать из БД.
- **FR-009**: Слой MUST следовать блюпринту 04/07 (доменный контракт, entity+mapper, Sembast DAO, `RepositoryResult`, cache-first watch, network-only carve-out заменяется local-DB источником), с DI.
- **FR-010**: Никакой реальной бэкенд/сетевой интеграции; контракты API/envelope остаются помеченными как пример/TBD (предполагаемый API).
- **FR-011**: Функциональность MUST работать одинаково на mobile (`_narrow`) и desktop (`_wide`).
- **FR-012**: `make gate` + `make golden-verify` MUST быть зелёными; детерминизм goldens сохранён.

### Key Entities *(include if feature involves data)*

- **ChatEntity / MessageEntity / (Attachment)** — data-слой entity (basic-типы, enum→`.name`, DateTime→ISO-8601), маппятся в доменные `ChatModel`/`MessageModel`/`MessageAttachment`.
- **Sembast stores**: `chats`, `messages` (ключи — id; индексация по времени/чату для пагинации).
- **Chat DAO / Message DAO** — cache-first reactive доступ (watch + upsert + paginated read).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Созданные чаты и отправленные сообщения сохраняются в 100% случаев и присутствуют после перезапуска.
- **SC-002**: Реактивные экраны обновляются без ручного refresh при изменении локальных данных.
- **SC-003**: Пагинация из БД корректна (без дублей/пропусков) на всех списках.
- **SC-004**: Все затронутые BLoC имеют полные состояния/события (нет плейсхолдер-логики).
- **SC-005**: Поведение идентично на mobile и desktop.
- **SC-006**: `make gate` + `make golden-verify` зелёные.

## Assumptions

- Локальная БД — **Sembast** (уже в pubspec; `AppDatabase` + per-env провайдер уже зарегистрированы, сейчас unused). Расширяем на chat/message/file.
- Текущие мок-источники (`GetChatsApi`/`GetMessagesApi`/`SendMessageApi`/`GetChatFilesApi`, `_mockChats`/`_mockMessages`) становятся **сид-данными** локальной БД (одноразовый посев), а не эфемерным источником.
- Пагинация — offset per blueprint 07 (курсор — документированная альтернатива); конкретный wire-контракт остаётся TBD (бэкенд не выбран).
- Детерминизм: реальное время через `AppClock` (фича T2); goldens сеются под фиксированный набор.
- Statuses local-only (`sent`/`pending`/`error`), без delivered/read (NOX open-space модель).
- Бэкенд/транспорт/крипто НЕ трогаются — остаются TBD-плейсхолдерами; эта фича заменяет network-only источник локальной БД, сохраняя контракт репозитория для будущей подмены на реальный транспорт.
