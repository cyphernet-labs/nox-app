# Feature Specification: Персистентность настроек и реальная навигация онбординга

**Feature Branch**: `012-settings-persistence-nav`
**Created**: 2026-07-18
**Status**: Draft
**Input**: Персистентность настроек (тема / язык / уведомления) на реальном локальном сторе + замена заглушек `RoutePlaceholderPage` реальными переходами онбординга. Всё на моках, без бэкенда.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Настройки переживают перезапуск (Priority: P1)

Пользователь меняет тему оформления, язык интерфейса и переключатель уведомлений в Settings и ожидает, что после полного перезапуска приложения его выбор сохранится, а не сбросится к значениям по умолчанию.

**Why this priority**: Сейчас тема — in-memory, язык и уведомления — session-local; после рестарта всё сбрасывается. Это базовое ожидание от настроек и предпосылка для остального (inline-error появляется только там, где есть реальное сохранение).

**Independent Test**: Изменить каждую из трёх настроек → «перезапустить» приложение (пересоздать корневой стейт) → убедиться, что применены ранее выбранные значения (тема, язык, положение переключателя).

**Acceptance Scenarios**:

1. **Given** тема = System, **When** пользователь выбирает Dark и перезапускает приложение, **Then** приложение стартует в Dark.
2. **Given** язык = System, **When** пользователь выбирает Українська и перезапускает приложение, **Then** UI стартует украинским.
3. **Given** уведомления включены, **When** пользователь выключает их и перезапускает приложение, **Then** переключатель остаётся выключенным.
4. **Given** пользователь ничего не менял, **When** первый запуск, **Then** применяются значения по умолчанию (тема System, язык System, уведомления включены).

---

### User Story 2 - Онбординг ведёт реальными переходами (Priority: P1)

Новый или возвращающийся пользователь проходит онбординг без «тупиковых» экранов-заглушек: с Login может уйти на сканирование QR и вернуться, ввести новый ID и попасть на ввод имени, а после успеха — в основное приложение.

**Why this priority**: Онбординг — единственный путь входа; сейчас переходы `2.1 ↔ 2.2 / 2.1 → 2.3 / 2.3 → 4.1` упираются в `RoutePlaceholderPage`. Без реальной навигации онбординг не проверяем как флоу.

**Independent Test**: С экрана Login: (а) открыть Scan QR и вернуться на Login с сохранённым вводом; (б) ввести новый ID → попасть на Set username; (в) на Set username завершить → попасть на Tab bar shell.

**Acceptance Scenarios**:

1. **Given** пользователь на Login (2.1), **When** нажимает Scan QR, **Then** открывается QR-скан (2.2); **When** возвращается назад, **Then** снова Login с сохранённым ранее вводом.
2. **Given** пользователь на QR-скане (2.2), **When** распознан валидный ID, **Then** ID передаётся в поток входа Login (2.1) (существующая 009/010-механика).
3. **Given** на Login введён новый (незарегистрированный) ID, **When** вход принят, **Then** пользователь попадает на Set username (2.3).
4. **Given** пользователь на Set username (2.3), **When** сохраняет имя (или Skip), **Then** попадает на Tab bar shell (4.1), и назад к онбордингу вернуться нельзя.

---

### User Story 3 - Ошибка сохранения настройки видима (Priority: P2)

Если сохранение настройки не удалось, пользователь видит понятное сообщение и может повторить, а не остаётся в неведении с «молча откатившимся» переключателем.

**Why this priority**: Отложенный DoD-хвост (inline-error `Could not save. Try again.`). Появляется только теперь, когда есть реальное сохранение, которое может упасть. Ниже US1/US2, т.к. это обработка редкого сбоя.

**Independent Test**: Сымитировать сбой локального сохранения при переключении настройки → убедиться, что показан snackbar `Could not save. Try again.` и состояние UI не остаётся рассинхронизированным с фактически сохранённым значением.

**Acceptance Scenarios**:

1. **Given** сохранение настройки завершится ошибкой, **When** пользователь меняет её, **Then** показывается snackbar `Could not save. Try again.`.
2. **Given** сохранение упало и UI откатил оптимистичное изменение, **When** пользователь смотрит на контрол, **Then** он отражает фактически сохранённое (предыдущее) значение.

---

### Edge Cases

- Повреждённое/невалидное сохранённое значение (например, неизвестный код языка) → откат к значению по умолчанию, приложение не падает.
- Первый запуск без сохранённых настроек → значения по умолчанию.
- Смена языка/темы применяется немедленно (live) и одновременно персистится (US1 не ломает live-переключение из l10n-фичи).
- Онбординг: возврат с QR-скана без результата не должен терять ранее введённый на Login ID.
- Desktop (`_wide`) и mobile (`_narrow`): настройки живут в общем Settings-теле (list-detail на десктопе, leaf-экраны на мобайле) — персистентность и inline-error одинаковы на обеих раскладках.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Приложение MUST сохранять выбор темы (System/Light/Dark) в локальном хранилище и применять его при старте.
- **FR-002**: Приложение MUST сохранять выбор языка (System/English/Українська) в локальном хранилище и применять его при старте (не ломая live-переключение).
- **FR-003**: Приложение MUST сохранять положение переключателя уведомлений в локальном хранилище и применять его при старте.
- **FR-004**: При отсутствии сохранённого значения приложение MUST использовать значения по умолчанию (тема System, язык System, уведомления включены).
- **FR-005**: Повреждённое/нераспознаваемое сохранённое значение MUST безопасно откатываться к значению по умолчанию без сбоя.
- **FR-006**: При ошибке сохранения любой настройки система MUST показать неблокирующее сообщение `Could not save. Try again.` и MUST не оставлять UI-контрол рассинхронизированным с фактически сохранённым значением.
- **FR-007**: С Login (2.1) действие Scan QR MUST открывать QR-скан (2.2) и MUST поддерживать возврат назад с сохранением ранее введённого на Login ID.
- **FR-008**: Ввод нового (незарегистрированного) ID и принятие входа MUST вести на Set username (2.3).
- **FR-009**: Завершение Set username (2.3) (сохранение имени или Skip) MUST вести на Tab bar shell (4.1) без возможности вернуться назад в онбординг.
- **FR-010**: Все три перехода MUST заменить существующие `RoutePlaceholderPage`-заглушки реальными экранами.
- **FR-011**: Функциональность MUST работать одинаково на mobile (`_narrow`) и desktop (`_wide`).
- **FR-012**: Всё MUST работать на существующих мок-репозиториях / предполагаемом API — без реальной сетевой/бэкенд-интеграции в этой фиче.

### Key Entities *(include if feature involves data)*

- **SettingsPreferences**: сохранённые пользовательские предпочтения — тема (System/Light/Dark), язык (System/English/Ukrainian), уведомления (on/off). Локально-приватные, не sensitive; отдельны от идентификатора сессии.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После перезапуска все три настройки восстанавливаются в 100% случаев для валидных сохранённых значений.
- **SC-002**: Пользователь проходит онбординг `Login → (QR|new id) → Set username → Shell` полностью без экранов-заглушек.
- **SC-003**: Возврат с QR-скана сохраняет ранее введённый ID в 100% случаев.
- **SC-004**: При сбое сохранения сообщение об ошибке показывается в 100% случаев, а контрол отражает фактически сохранённое значение.
- **SC-005**: Поведение идентично на mobile и desktop (проверяется на обеих раскладках).
- **SC-006**: `make gate` и `make golden-verify` зелёные после реализации.

## Assumptions

- Локальный стор — `shared_preferences` (уже в pubspec; storage-policy: полностью-открытые, не sensitive данные → SharedPreferences). Идентификатор остаётся в `flutter_secure_storage` (не в scope этой фичи).
- Существующие live-механики сохраняются: тема через `AppRootBloc`, язык через `LocaleController` — эта фича добавляет ПЕРСИСТЕНТНОСТЬ поверх них, не заменяя live-переключение.
- «Перезапуск приложения» в тестах моделируется пересозданием корневого стейта/бутстрапа (без реального kill процесса).
- Регистрация/уникальность ID остаются на моках (`OnboardingMockData`) — эта фича не вводит реальный серверный контракт.
- Inline-error применяется к любой из трёх настроек единообразно; конкретный экран/контрол — деталь плана.
- Bytewise-идентичность goldens ожидается там, где визуал не меняется; новые состояния (inline-error snackbar) при необходимости покрываются поведенческими тестами или goldens по правилам проекта.
