# Research: Данные на диске устройства

Опора — код `lib/data/local/app_database.dart` (Sembast в «Документах»), `lib/data/repository/file/file_repository_impl.dart` (кэш вложений, докачка 043), `lib/data/local/chat/outbox_copies.dart` (копии исходящих), `flutter_secure_storage` с нынешними опциями, Rust-модуль 044.

## R1. Ключ локальной базы и «только это устройство»

- **Decision:** 32 случайных байта, создаются при первом запуске, хранятся в `flutter_secure_storage` под `device.storage_key` с опциями «только это устройство»; те же опции — у ключа устройства и всех секретов сессии (FR-002, FR-003):
  - iOS — `KeychainAccessibility.first_unlock_this_device`;
  - Android — хранилище плагина на Android Keystore, `allowBackup="false"` и правила извлечения данных, исключающие всё;
  - macOS — `usesDataProtectionKeychain: true` с `first_unlock_this_device`; для этого macOS-сборка подписывается командой (`DEVELOPMENT_TEAM = W84KAPTJ9Y`, как iOS) и получает `keychain-access-groups`; сборки CI — с `CODE_SIGNING_ALLOWED=NO`;
  - Windows — DPAPI плагина (текущий пользователь), файл хранилища — в `%LOCALAPPDATA%`, не в перемещаемом профиле;
  - Linux — libsecret (локальная связка ключей).
- **Rationale:** решение 3, Принцип III 1.4.0 (без desktop-fallback). Нынешняя macOS-связка ключей (`usesDataProtectionKeychain: false`) попадает в Time Machine и переносится Migration Assistant — так нельзя.
- **Риск:** локальная сборка macOS требует профиля разработки команды; проверяется на этой машине (`flutter build macos` c автоматической подписью), Windows и Linux — владелец.

## R2. Шифрование — в Rust-модуле

- **Decision:** модуль получает «сейф»: `nox_vault_set_key(key32)` (ключ в обнуляемом буфере процесса), `nox_vault_clear()`, `nox_vault_seal(data)`/`nox_vault_open(data)` (ChaCha20-Poly1305 на `ring`, случайный nonce в начале результата) и `nox_vault_seal_chunk`/`nox_vault_open_chunk` (ключ файла `HKDF-SHA256(ключ, info = "nox/devfile/v1|" + имя)`, nonce — номер куска, AAD — номер ‖ признак последнего). Вызовы синхронные, только процессор.
- **Rationale:** трекер темы 4: шифр локальной базы — `ring` в Rust-модуле, та же библиотека, что под TLS; синхронные вызовы нужны кодеку Sembast.

## R3. База

- **Decision:** Sembast открывается с `SembastCodec(signature: 'nox-vault-1', codec: VaultCodec)`: каждая строка файла — `base64(nonce ‖ шифротекст ‖ тег)`; чужой ключ — отказ подписи кодека при открытии. Файл базы переезжает из «Документов» в папку данных приложения (R5). Тестовое окружение — `databaseFactoryMemory`, как сегодня.
- **Rationale:** FR-004; Sembast шифрует запись целиком, включая служебную строку.

## R4. Файлы

- **Decision:** формат файла как у сервера (047): заголовок `NOXF`, куски по 64 КиБ с тегом. Кэш вложений (`nox_attachments`) и `.part` докачки 043 — запечатанные куски; докачка продолжается с границы последнего целого куска (`Range` от него), `.part.tag` — как сегодня. Копии исходящих (`nox_outbox/<client_message_id>/<имя>`) — запечатаны; загрузка читает расшифровывающим потоком с `received`. Картинки — расшифровка в память (`Image.memory`), миниатюры — в памяти.
- **Rationale:** FR-005, FR-006; докачка из 043 сохраняется.

## R5. Где лежат данные и бэкапы

- **Decision:** корень данных — `getApplicationSupportDirectory()` на iOS, Android, macOS, Linux; на Windows — `%LOCALAPPDATA%\NOX`. Там база, `nox_attachments`, `nox_outbox`, состояние Tor. iOS и macOS — метка `NSURLIsExcludedFromBackupKey` на корне данных (короткий метод платформы в `AppDelegate`); Android — `allowBackup="false"`, `fullBackupContent="false"`, `dataExtractionRules` с исключением всего для `cloud-backup` и `device-transfer`. Кэш (`getApplicationCacheDirectory`) не используется для вложений.
- **Rationale:** FR-009, FR-010, решение 2.

## R6. Временные копии

- **Decision:** `<временная папка>/nox_open/`: копия видео — для плеера, стирается при его закрытии; копия для «Открыть в…» — стирается при следующем запуске или выходе; при каждом запуске папка очищается. «Сохранить» — расшифровка в выбранное место. Нет места — ошибка открытия `Couldn't open this file. Free up some space and try again.` (EN), `Не вдалося відкрити цей файл. Звільніть місце і спробуйте ще раз.` (UK).
- **Rationale:** FR-007, FR-008, FR-014, уточнение.

## R7. Ключ не прочитать, выход

- **Decision:** при запуске: ключа нет и базы нет — новый ключ; ключа нет, а база есть — принудительный выход (стирание) и спаривание; ошибка чтения сейфа — без стирания, повтор с паузой (заставка). Выход: остановить связь, стереть базу, файлы, временные копии, ключ локальной базы и ключ устройства, `nox_vault_clear()`.
- **Rationale:** FR-011, FR-012, уточнение.

## R8. Производительность

- **Decision:** замер открытия списка чатов и треда на 10 000 сообщений до и после (тест-бенч в `test/`), бюджет +20% (SC-003).

## R9. Проверка

- **Decision:** Dart — кодек (круг, чужой ключ), формат файлов (круг, подмена, усечение, диапазон, докачка с середины куска), временные копии (жизненный цикл, очистка при запуске), ключ (нет ключа + база — стирание; ошибка чтения — без стирания), SC-001 (поиск маркеров по папке данных); Rust — сейф (круг, обнуление); голдены ошибки открытия на 5.3 обеих ширин. Устройства: iOS-бэкап, Android-перенос, Time Machine — владелец и проверка на этой машине, где возможно.

## R10. Решения реализации там, где документы молчат

Выбран осторожный вариант; ниже — что и почему.

- **Заголовок файла по байтам** — `NOXF` ‖ версия (1 байт) ‖ 3 нуля ‖ размер куска (u32 BE) ‖ id (16) ‖ 4 нуля; таблица — в `data-model.md`. Любое другое значение в заголовке — не файл формата: так открытый файл человека (выбранный в композере, запись очереди старой сборки) читается как есть, без попытки расшифровки.
- **Последний кусок** — тот, чей конец равен размеру файла (полный кусок в конце тоже последний); пустой файл — один пустой последний кусок, чтобы файл, обрезанный до заголовка, не читался как пустой.
- **Докачка** проверяет последний целый кусок части: открывается как непоследний — продолжение с его конца; нет — кусок отбрасывается (разорван крахом или это последний кусок целого файла, который не успели переименовать) и запрашивается снова. Ответ целиком — новая часть под новым id: под старым id не запечатываются другие байты.
- **Сервис связки ключей** на iOS и macOS — `com.cyphernetlabs.noxapp`, не сервис плагина по умолчанию. На iOS запись старого класса доступности под тем же именем мешает записать новую (`errSecDuplicateItem`): записи сборок до 048 лежат под старым сервисом, и старт удаляет их одним `deleteAll` по старым опциям (iOS: класс по умолчанию; macOS: legacy keychain), не трогая новые. На Android, Windows и Linux опции не менялись — там этой чистки нет: тестовый мок сейфа опции не различает, поэтому ветка проверяется отдельным двойником. На Mac, где стояла сборка до 048 (подписанная иначе), удаление её записей из legacy-связки может один раз спросить разрешение связки ключей; отказ только оставляет их до следующего запуска.
- **Windows**: `path_provider` подменяется целиком (`LocalAppDataPathProvider`) — папка поддержки приложения становится `%LOCALAPPDATA%\NOX` для всех, включая файл сейфа: у плагина сейфа нет опции пути. `SharedPreferences` на Windows ходят в свою копию `PathProviderWindows` и остаются в перемещаемой папке плагина (`%APPDATA%\Cyphernet Labs\NOX`): там тема, язык, уведомления, а пока сессия жива — кэш имени и id автора; переписки и ключей там нет. Перенос потребовал бы поля плагина, помеченного «только для тестов», — оставлено владельцу как решение (см. проверки владельца).
- **Настройки внешнего вида, языка и уведомлений переживают выход** (прежнее решение): на Linux их файл `shared_preferences.json` лежит в папке данных приложения, поэтому после выхода (SC-005) в ней остаётся он — без переписки, ключей и имён: имя и id автора выход удаляет.
- **Порядок старта**: `runApp` идёт до старта, первое решение навигации ждёт его (`AppStateRepository.holdUntil`): заставка видна, пока сейф не ответил. Сам старт — `AppDataRoot.excludeFromBackup` → `sweepLegacy` → очистка временных копий → `openLocalData` → прежние шаги (отставка сессии до 044, канал, очередь).
- **Ключ есть, а база под ним не открывается** (другой ключ — `invalidCodec`, нечитаемый файл) — то же, что «ключа нет при базе»: стирание и спаривание. Ошибка ввода-вывода при открытии ничего не стирает.
- **Два окружения — одна папка и один ключ.** `stage` и `prod` различаются только Dart-define: id приложения, папка данных и сейф у них одни, а значит, общие ключ локальной базы и сессия; разные только файлы базы (`app_dev.db`, `app.db`). Поэтому «база есть» при запуске — любая из баз обоих окружений или файл сжатия Sembast `~<имя>` рядом с ней (без основного файла Sembast открывает его как базу), а стирание — при выходе и при отставке данных — удаляет их все (`AppDatabase.clearEntireDatabase`), свою базу последней: пока она лежит, чтение посреди стирания находит базу без ключа и ничего не открывает, а новую базу, заведённую после, уже ничто не удаляет. Оставленная база другого окружения читалась бы как данные без ключа при каждом запуске обоих окружений, и ни одна база на устройстве больше не открылась бы. Прочитать при этом нечего: без ключа ни одна из баз не открывается, а выход в любом окружении стирает и общую сессию. Отвергнуто: считать только базу своего окружения — база другого, запечатанная ушедшим ключом, при его следующем запуске не откроется новым ключом этого окружения, и отставка заберёт с собой этот ключ, общую сессию, вложения и копии исходящих, которые здесь ещё живы.
- **Тело загрузки** — открытые байты копии из потока расшифровки, `Stream<Uint8List>`. Источник данных принимает любой подтип `Stream<List<int>>` и привязывает к нему свой обработчик ошибок через `bind`: `body.transform(...)` сверяет аргумент с типом элементов потока во время выполнения и бросает `TypeError` до первого байта. Тест реального источника гоняет такие потоки — и из генератора, и из запечатанной копии.
- **Ошибка сейфа** — повтор с паузой 2, 4, 8, 16, 30, 30… с без предела: без ключа база не открывается, а стирать нельзя (FR-011). На Linux без службы ключей это значит заставку до её запуска — как в допущении спецификации.
- **Остатки сборок до 048**: на старте удаляются открытая база в «Документах» там, где «Документы» — папка самого приложения (iOS, Android; macOS — только если папка лежит в контейнере песочницы: сборка без песочницы получает «Документы» человека), открытый кэш вложений в папке кэша (везде), на Windows — файл сейфа, копии исходящих и состояние Tor в перемещаемой папке. На Windows и Linux «Документы» — папка человека, и `app.db` там удаляет владелец (см. проверки владельца). Файлы в папке данных, которые нечем открыть, удаляются, когда заводится новый ключ.
- **«Открыть в…»**: на 5.3 такого действия нет (5.3, Q6), а FR-014 не допускает новых элементов интерфейса. Правило жизни такой копии заложено в `LocalFilesService.openCopy`: копия, которую не отпускают, живёт до следующего запуска или выхода.
- **Мок-сервер** хранит присланные байты в памяти, а не путём к файлу: путь к запечатанной копии бесполезен, а открытая копия на диске нарушила бы FR-004 и в мок-мире.
- **Корпуса 5.3** (`nox-mobile-screens`, `nox-desktop-screens`) дописаны по-английски: эти файлы целиком английские, и смешивать языки в одном артефакте нельзя.

**Проверки владельца.** macOS: профиль подписи, затем `quickstart.md` §2 целиком и `tmutil isexcluded` на `~/Library/Containers/com.cyphernetlabs.noxapp/Data/Library/Application Support/com.cyphernetlabs.noxapp`. iOS: бэкап в iCloud и на компьютер без данных NOX, восстановление → спаривание. Android: облачный бэкап и перенос без данных NOX. Windows: данные в `%LOCALAPPDATA%\NOX`, файл сейфа там же; решение о `SharedPreferences` в перемещаемой папке; удаление старого `app.db` из «Документов». Linux: данные в `~/.local/share/<id приложения>`, удаление старого `app.db` из «Документов»; без службы ключей приложение ждёт на заставке.

## R12. Живые пробы после слияния 044–047

Ручные пробы `test/live/` (тег `live`, вне гейтов) после слияния 044–047 не проходили по трём причинам — все в самих пробах, продукт их не касается:

- **Сервер стартует запертым (047).** `LiveNoxd.start` ждал `listening`, а сервер до пароля открывает только служебную страницу и пишет `no password is set yet` (новая база) или `this server is locked` (своя база). Теперь обвязка ждёт эту строку, вводит пароль через `noxd unlock -status-addr …` — дважды на stdin, как `scripts/demo-stand.sh`: новый сервер читает пароль и повтор, запертый — первую строку, — проверяет код выхода и только потом ждёт `listening`; строка `ERROR` в журнале сервера — отказ сразу. Пароль у проб один (`LiveNoxd.probePassword`), им же открываются перезапуски над той же базой (второй и третий сервер `tor_live_probe`). В заголовках ручных проб — шаг `noxd unlock` до чтения ссылки; ссылку для проб с `link=` даёт первая строка `noxd link`.
- **Файлы на диске запечатаны (048).** Пробы сравнивали скачанный файл и сохранённую копию очереди с открытыми байтами. Старая `live_files_probe` против живого сервера падала на `Expected: <65536>, Actual: <65584>` (заголовок 32 байта + тег куска 16). Теперь `openSealed` проверяет, что файл запечатан, и читает открытые байты через `SealedReader`, как приложение; 100 МиБ `resumable_files_probe` сверяются потоком по мебибайту, у сохранённой копии сверяется открытая длина.
- **Приглашение спаривает только после `Allow` (046).** `tor_pairing_probe` и `integration_test/tor_pairing_test.dart` спаривались по приглашениям из `invites.txt`, которые некому одобрить: выдавшее их устройство уходит вместе с процессом `tor_live_probe`. Теперь выдавшее устройство приносит сама проба: оно спаривается дома по свежей ссылке с машины, выдаёт приглашение и отвечает `Allow`, а приложение «вне дома» спаривается по этому приглашению через onion-адрес. `tor_live_probe` оставляет сервер работать с введённым паролем, а адрес служебной страницы — в `<work>/page.txt` для `noxd link`. Устройство «по проводу» (`WireDevice`) у этих проб и `pairing_live_probe` теперь общее.

Попутно: оба интеграционных теста Tor создавали чат и сразу писали в него, а с 041 чат сначала уходит на сервер через очередь — теперь тесты ждут его там, как `tor_live_probe`.
