# Контракты Feature-001 (скелет `nox_app`)

> **Phase 1 — внутренние контракты каркаса.** Этот каталог фиксирует контракты (форма + правила), которые скелет `nox_app` устанавливает внутри процесса. Источник «как» — блюпринт `docs/blueprints/mobile/` (особенно `00`/`02`/`03`/`05`/`09`); эти файлы — проекция блюпринта на Feature-001 (скелет, FR-013: без реальных продуктовых фич).

## Зачем это, а не OpenAPI/protobuf

Скелет **не экспонирует ни одного внешнего/сетевого API**: бэкенд, протокол, конверт ответа, набор эндпоинтов, push- и file-upload-контракты, deep-link-схема и крипто-ядро **намеренно не выбраны** — это ограничение конституции (v1.1.0, §«Технологический контекст»). В блюпринте все такие специфики (`04`/`14`/`15`/`16`) помечены как **пример/TBD** и здесь **не определяются**. Поэтому контракты Feature-001 — это **внутренние** контракты каркаса (DI/bootstrap, тип результата репозитория, оболочка, флейворы сборки), а не внешний API-surface.

## Что НЕ определено здесь (пример/TBD)

Перечисленное ниже остаётся **примером/TBD** до выбора бэкенда NOX и вносится отдельными spec-циклами, а не в скелете:

- **Сетевой контракт / эндпоинты / конверт ответа** (`ResponseEntity{data, timestamp, trace_id, meta}` — пример, см. `04`/`14`).
- **Auth-модель** (HMAC-подпись, access/refresh, security-заголовки — пример, см. `14`).
- **Push-контракт** (`POST`/`DELETE /api/v1/user/push_notification/` — пример, см. `15`); на десктопе push = disabled/no-op.
- **File-upload-конвейер** (2-step upload→attach — пример, см. `16`).
- **Deep-link-схема** (`nox://` — нативная регистрация FUTURE; в скелете deep links = no-op, см. `13`).
- **Криптоядро / messaging** — отсутствует в скелете (FR-013).

Любое утверждение об этих подсистемах в файлах ниже помечено как **пример/TBD** и описывает только desktop-fallback (no-op / disabled / документированный бэкенд), а не сам контракт.
