# Feature Specification: client-backend-files

**Feature Branch**: `024-client-backend-files`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "client-backend-files — stage-1 phase 024 of the NOX Go client server: the file chain of wire contract v0 §7 (file.uploadBegin / PUT / file.downloadBegin / GET with Range, one-time tokens with TTL, attachment assembly into echo and message.new) plus chat.files (§4) and the attachment_gone code."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Отправка файла: цепочка вложения (Priority: P1)

Участник прикладывает файл к сообщению. Клиент объявляет загрузку (имя, размер, тип), получает адрес и одноразовый токен, заливает байты отдельным HTTP-запросом — не блокируя командный канал, — и отправляет сообщение со ссылкой на загруженный файл (текст при этом необязателен). Сервер собирает полное описание вложения из метаданных загрузки и включает его в эхо автору и в событие всем остальным; в списке чатов у сообщения-вложения без текста превью — имя файла.

**Why this priority**: цепочка отправки — ядро фазы; без неё нет ни скачивания, ни панели файлов. Активирует правило контракта «`body` необязателен при наличии `attachment`».

**Independent Test**: одним клиентом объявить загрузку, залить байты, отправить сообщение с вложением; убедиться, что эхо и событие несут полный объект вложения, а превью чата — имя файла.

**Acceptance Scenarios**:

1. **Given** подключённый клиент, **When** он объявляет загрузку (имя, размер в пределах лимита, тип), **Then** приходит идентификатор файла, адрес загрузки, одноразовый токен и действующий лимит размера.
2. **Given** выданный токен, **When** клиент заливает байты по адресу загрузки, **Then** сервер принимает ровно объявленный объём; повторная заливка тем же токеном отклоняется (токен одноразовый).
3. **Given** залитые байты, **When** клиент отправляет сообщение с вложением без текста, **Then** эхо и событие `message.new` несут полный объект вложения (имя, размер, тип, срок хранения), а превью чата равно имени файла.
4. **Given** сообщение с вложением и текстом, **Then** превью — свёрнутый текст (правило свёртки едино).
5. **Given** объявление загрузки с размером больше лимита, **Then** отказ «превышен лимит» ещё до передачи байтов.

### User Story 2 — Скачивание вторым участником с докачкой (Priority: P2)

Другой участник видит сообщение-вложение и скачивает файл: запрашивает у сервера одноразовую ссылку на скачивание и забирает байты HTTP-запросом. Оборвавшееся скачивание возобновляется с места обрыва (Range), а не с нуля. Если срок хранения байтов истёк, сервер отвечает терминальным «вложение недоступно».

**Why this priority**: замыкает ценность фазы — файл, отправленный одним, получен другим; докачка — заявленное преимущество выноса файлов из сокета.

**Independent Test**: два клиента; первый отправляет файл, второй скачивает его целиком байт-в-байт, затем повторяет скачивание с заголовком Range с середины и получает ровно остаток.

**Acceptance Scenarios**:

1. **Given** сообщение с вложением у второго клиента, **When** он запрашивает скачивание по идентификатору файла, **Then** получает адрес и одноразовый токен, а HTTP-запрос отдаёт байты, идентичные исходным.
2. **Given** оборванное на середине скачивание, **When** клиент запрашивает новую ссылку и передаёт Range с байта N, **Then** сервер отдаёт данные с байта N (частичный ответ), и склейка идентична исходному файлу.
3. **Given** файл, чей срок хранения истёк, **When** клиент запрашивает скачивание, **Then** отказ «вложение недоступно» (терминальное состояние экрана файла, без повтора).
4. **Given** использованный или протухший токен скачивания, **When** приходит HTTP-запрос с ним, **Then** отказ без выдачи байтов.

### User Story 3 — Панель файлов чата (Priority: P3)

Участник открывает панель «Файлы» чата и видит все вложения этого чата — независимо от того, какая глубина истории загружена локально, — порциями от новых к старым, с той же обратной пагинацией, что у истории сообщений.

**Why this priority**: питает экран 5.4 приложения; самостоятельная витрина, строящаяся поверх цепочки историй 1–2.

**Independent Test**: отправить в чат несколько сообщений с вложениями вперемешку с текстовыми, убедиться, что панель отдаёт только вложения, страницами, каждая запись — с привязкой к сообщению.

**Acceptance Scenarios**:

1. **Given** чат с 5 вложениями среди 20 сообщений, **When** клиент запрашивает файлы чата с лимитом 3, **Then** приходят 3 самых свежих записи (вложение + идентификатор сообщения + номер журнала) и признак «есть ещё»; следующая порция «до номера» отдаёт оставшиеся 2.
2. **Given** чат без вложений, **Then** пустая страница с признаком «больше нет».
3. **Given** несуществующий чат, **Then** отказ «не найдено».

### Edge Cases

- Заливка байтов больше объявленного размера или сверх лимита → отказ протокола HTTP «слишком велико», файл не сохраняется, токен погашен.
- Заливка с неверным, протухшим или уже использованным токеном → отказ без записи байтов.
- Отправка сообщения со ссылкой на файл, чьи байты не были залиты (или неизвестный идентификатор файла) → «некорректный запрос».
- Сообщение без текста **и** без вложения → «некорректный запрос» (хотя бы одно из двух обязательно).
- Повторная отправка с тем же ключом идемпотентности — прежнее эхо с тем же вложением, без нового события (правило 022 распространяется на вложения).
- Один файл принадлежит одному сообщению: повторная ссылка на уже использованный идентификатор файла → «некорректный запрос».
- Имя файла — только метаданные: байты хранятся под серверным идентификатором, имя не участвует в путях (никакого «../» на диске).
- Скачивание файла, объявленного, но не залитого → «вложение недоступно» не выдаётся, это «не найдено»/«некорректный запрос» — байтов ещё не существовало.
- Range за пределами размера файла → стандартный отказ HTTP «диапазон не удовлетворим».
- Рестарт сервера между заливкой и отправкой сообщения: залитый файл переживает рестарт и остаётся пригодным для отправки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать объявление загрузки (имя, размер, тип) по командному каналу и отвечать идентификатором файла, адресом загрузки, одноразовым токеном с ограниченным сроком действия и действующим лимитом размера; размер сверх лимита → отказ «превышен лимит» без выдачи токена.
- **FR-002**: Система MUST принимать байты отдельным HTTP-запросом по одноразовому токену: объём строго ограничен объявленным размером и лимитом (превышение → HTTP-отказ «слишком велико» без сохранения), токен гасится после первого использования, метаданные берутся из объявления, не из байтов.
- **FR-003**: Байты MUST храниться в каталоге данных сервера под серверным идентификатором (имя файла — только метаданные) и переживать рестарт процесса.
- **FR-004**: Отправка сообщения MUST принимать ссылку на залитый файл; текст при наличии вложения необязателен, но хотя бы одно из двух обязательно; ссылка на незалитый, неизвестный или уже использованный файл → «некорректный запрос». Эхо и событие несут полный объект вложения (имя, размер, тип, срок хранения); идемпотентность 022 сохраняется.
- **FR-005**: Превью чата для сообщения-вложения без текста MUST быть именем файла; с текстом — свёрнутым текстом (единая формула свёртки).
- **FR-006**: Система MUST выдавать одноразовую ссылку на скачивание по идентификатору файла и отдавать байты HTTP-запросом с поддержкой Range (частичные ответы для докачки); неизвестный идентификатор → «не найдено».
- **FR-007**: Байты MUST храниться ограниченный срок; срок отдаётся клиенту в объекте вложения при отправке. Запрос скачивания после истечения срока → «вложение недоступно» (терминальный код).
- **FR-008**: Панель файлов чата MUST отдавать все вложения чата обратной пагинацией (как история сообщений: «до номера», лимит под общим потолком, порция по возрастанию номера), каждая запись — вложение плюс идентификатор сообщения и номер журнала; несуществующий чат → «не найдено».
- **FR-009**: Токены загрузки и скачивания MUST быть одноразовыми, с ограниченным сроком действия, непредсказуемыми и непригодными для доступа к чужим путям; HTTP-запрос с неверным/протухшим/использованным токеном отклоняется без раскрытия причин.
- **FR-010**: Все командные отказы MUST использовать только коды контракта (включая «превышен лимит» и «вложение недоступно»); HTTP-поверхность использует стандартные статусы (запрет, слишком велико, диапазон не удовлетворим).
- **FR-011**: Документация запуска (README сервера и quickstart фичи) MUST быть дополнена файловым смоуком, выполнимым владельцем локально (websocat + curl), включая докачку Range.

### Key Entities

- **Файл (вложение)**: серверный идентификатор, метаданные из объявления (имя, размер, тип), срок хранения байтов, привязка к одному сообщению после отправки; байты — в каталоге данных под идентификатором.
- **Одноразовый токен**: право на одну HTTP-операцию (заливку или скачивание) конкретного файла в ограниченном окне времени; гасится первым использованием.
- **Запись панели файлов**: вложение + идентификатор сообщения + номер журнала — проекция сообщений с вложениями.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Файл в 10 МБ проходит полную цепочку (объявление → заливка → сообщение → скачивание вторым клиентом) с побайтово идентичным результатом.
- **SC-002**: Скачивание, оборванное на середине, возобновляется с места обрыва: повторно передаётся только остаток, склейка идентична исходнику.
- **SC-003**: Повторное использование любого токена (заливки или скачивания) отклоняется в 100% случаев.
- **SC-004**: Превышение лимита размера отклоняется на обоих рубежах: при объявлении (до передачи байтов) и при заливке (передача обрывается, ничего не сохраняется).
- **SC-005**: Сообщение-вложение без текста показывает имя файла в превью строки чата у обоих клиентов.
- **SC-006**: Панель файлов чата отдаёт все вложения чата без пропусков и дублей при постраничной выборке, независимо от числа текстовых сообщений между ними.
- **SC-007**: Владелец проходит файловый смоук (websocat + curl, включая докачку) за ≤10 минут от чистой сборки.

## Assumptions

- Значения, не названные контрактом (срок хранения байтов, срок действия токенов, каталог хранения, судьба протухших байтов и незавершённых загрузок), выносятся на решение владельца — см. Clarifications.
- Лимит размера вложения — существующий `max_attachment_bytes` из конфигурации (100 МиБ по умолчанию), уже отдаваемый в рукопожатии.
- Панель файлов использует общий потолок порции 100 и правила пагинации фазы 023.
- Идентичность этапа 1 (label-заглушка) и отсутствие аутентификации сохраняются; владение файлами не проверяется — пространство открытое, скачать вложение может любой участник.
- `body` остаётся непрозрачным для сервера; свёртка превью для вложения расширяется единственным правилом «нет текста → имя файла» (шов Q1 не углубляется).
