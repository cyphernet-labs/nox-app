# Contracts: срез фазы 024

Источник — контракт v0, §7 (файлы), §4 (`chat.files`), §5 (`attachment` в `message.send`/`Message`), §2.1 (коды). Решения Clarifications вносятся в контракт правкой в change-set реализации (Принцип VII).

## Команды по сокету

| Команда | `data` запроса | `data` ответа | Ошибки |
|---|---|---|---|
| `file.uploadBegin` | `{name, size, mime}` | `{file_id, upload_url, upload_token, max_attachment_bytes}` | `invalid_request` (пустое имя/mime; size < 1), `payload_too_large` (size > лимита), `internal` |
| `file.downloadBegin` | `{file_id}` | `{download_url, download_token}` | `invalid_request` (пустой id; байты ещё не залиты), `not_found` (id неизвестен), `attachment_gone` (срок истёк или байты физически отсутствуют), `internal` |
| `chat.files` | `{chat_id, before_seq?, limit}` | `{files: [{file_id, name, size, mime, expires_at, message_id, seq}], has_more}` | `invalid_request` (пустой chat_id; limit < 1), `not_found` (чат), `internal` |

Правила пагинации `chat.files` — фазы 023: потолок 100 с молчаливым клампингом, порция по возрастанию `seq`, `before_seq` не задан → хвост.

## `message.send` — расширение (§5)

- `attachment: {file_id}` принят; **хотя бы одно из `body`/`attachment` обязательно** (правило контракта активируется этой фазой).
- `file_id` обязан существовать, быть залитым и не привязанным к другому сообщению — иначе `invalid_request`.
- Эхо и `message.new` несут полный объект `attachment {file_id, name, size, mime, expires_at}`; payload события собирается при записи (replay самодостаточен).
- Идемпотентный повтор возвращает прежнее эхо с тем же вложением; события нет.
- Превью (§6): нет текста → имя файла; формула свёртки едина (≤120 рун, одна строка).

## HTTP-поверхность (§1)

| Endpoint | Поведение |
|---|---|
| `PUT /files/{upload_token}` | приём байтов строго объявленного размера; больше → `413`; меньше (обрыв) → `400`, байты не сохраняются; неверный/протухший/использованный токен → `404`; успех → `204` |
| `GET /files/{download_token}` | отдача байтов с `Content-Type` из метаданных; `Range` поддержан (`206`, `416` — стандартно); неверный/протухший/использованный токен → `404` |

- Токены **одноразовые**, TTL **10 минут** (Clarifications), непредсказуемые (32 случайных байта); первый запрос гасит токен независимо от исхода — после обрыва клиент запрашивает новый токен той же командой.
- `upload_url`/`download_url` — **относительные** пути `/files/<token>`: сервер своего публичного адреса не знает, клиент соединяет с известной ему базой.
- HTTP-отказы токена не различают причин (`404` для всех) — не раскрываем существование файлов по перебору.

## Хранение (Clarifications)

- Этап 1: байты бессрочно, `expires_at = created_at + 10 лет` (поле обязано присутствовать; клиентская логика гашения Save по сроку остаётся рабочей).
- `attachment_gone` — терминальный: срок истёк ИЛИ байты физически отсутствуют.
- Каталог: флаг `-files` / `NOX_FILES`, дефолт `<db>-files`; байты лежат под `file_id`, имя пользователя в путях не участвует.
- Зачистка на старте: строки `files` без `message_id` старше суток удаляются вместе с байтами и `.part`-остатками.
