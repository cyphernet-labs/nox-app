# Data model — фаза 031

Серверная схема **не меняется** ([research.md](./research.md) R2). Меняется одна клиентская запись и порядок её очистки.

---

## 1. Отметка последнего открытия

Появляется в записи чата:

```dart
required int? lastOpenedSeq,
```

| | |
|---|---|
| **Тип** | `int?` — `null` означает «чат никогда не открывали» |
| **`required`** | обязательно, и это несущее решение |
| **Смысл** | наибольший номер сообщения, который был на экране в момент последней загрузки треда |
| **Живёт** | ровно столько же, сколько кэш переписки, и исчезает вместе с ним |

**Почему `required` при допустимом `null`.** Прежний счётчик держался в живом состоянии компилятором: `required int unreadCount` не позволял забыть про поле в новом месте создания записи. Голый `int?` без `required` тихо принимает пропуск, и первое же новое место создания получит `null` — то есть «никогда не открывали», то есть **отсутствие бейджа там, где он должен быть**. Такую регрессию не поймает ни один тест, который её не ждёт. С `required` каждое место создания становится ошибкой компиляции, пока не решит, что делать с отметкой.

---

## 2. Что происходит с прежним счётчиком

Хранимое число `unreadCount` перестаёт быть **источником** и становится производной, вычисляемой при чтении чата.

Правило пересчёта:

```
бейдж(чат) = |{ сообщение ∈ кэш(чат) :
                  сообщение.seq > (чат.lastOpenedSeq ?? 0)
                  и сообщение.author ∉ множество-своих-id }|
```

**Множество своих id** — все идентификаторы, которыми это устройство могло когда-либо подписать сообщение: серверный author-id, идентификатор входа и запасное мок-значение, за вычетом пустых. Не один разрешённый id: резолвер личности умеет падать на идентификатор входа, когда серверного ещё нет, и в этом окне сравнение с одним значением молча перестаёт совпадать — подавление отказывает в сторону «считать своё чужим» ([research.md](./research.md) R10). Множество безопасно по построению: серверные id имеют форму `u_` + 16 hex и с идентификатором входа совпасть не могут.

**Граница честности.** Пересчёт правдив ровно в пределах кэша. Обрезки истории сегодня нет, поэтому данные всегда полны; формулировка требования спеки останется истинной и после её появления.

**Цена и её снятие.** Пересчёт стоит разрешения личности и прохода по хранилищу сообщений. Делать это на каждую загруженную страницу каждого тика недопустимо — личность разрешается и подсчёт выполняется **один раз на обновление**, а не на страницу ([research.md](./research.md) R7 в плане, T7).

## 3. Переходы отметки

```
никогда не открывали        lastOpenedSeq = null   → бейджа нет (правило спеки)
        │
        │ тред загрузился (ОНЛАЙН ИЛИ ОФЛАЙН — любая вернувшаяся загрузка)
        ▼
   отметка = max(seq) среди того, что было на экране
        │
        │ пришло чужое сообщение выше отметки
        ▼
   бейдж = число таких сообщений
        │
        │ тред открыт снова
        ▼
   отметка продвинулась, бейдж = 0
```

**Продвижение только вперёд.** Отметка монотонна: назад не откатывается никогда.

**Офлайновое открытие ставит отметку.** Проект утверждал обратное — что офлайновое открытие уходит в ветку ошибки и отметки не ставит. Это неверно: офлайновое открытие возвращает кэш и попадает в ветку успеха. Отметка продвигается на **любой** вернувшейся загрузке, до того максимума, который человек действительно видел. Открыть офлайн при пустом кэше → отметка 0, чат считается открывавшимся; последующая догоняющая синхронизация принесёт историю, и она будет посчитана как непрочитанная — что верно, человек её не видел.

---

## 4. Отравление отметки чужим пространством номеров

**Опасность.** Отладочный ввод сообщений минтит номера из часов — то есть значения на пятнадцать разрядов выше любого серверного. Одно такое сообщение в живой чат продвигает монотонную отметку в это пространство, и бейдж чата умирает **навсегда**: ни одно настоящее событие уже никогда не окажется выше отметки.

**Закрывается двумя дешёвыми правилами:**

1. Отладочный ввод получает номер от **головы кэша** (`max(seq) + 1`) — ровно то, что выдал бы сервер, — а не из часов.
2. Отметка не продвигается за неправдоподобную голову: продвижение ограничивается кэшированной головой чата.

---

## 5. Порядок очистки — несущий

Отметка описывает **тот же мир**, что курсор синхронизации, и обязана умирать не позже него.

**Выход из аккаунта:** очистка отметок идёт **непосредственно перед** очисткой курсора. Порядок самого курсора не трогается: он должен исчезнуть раньше опустошаемого хранилища, и записанная в коде причина этого верна.

**Смена мира сервера** (журнал хранилища изменился): отметки уходят вместе с кэшем. Порядок внутри стирания пересматривается так, чтобы **невосстановимое шло первым** — курсор и отметки прежде, чем best-effort удаления очереди и файлового кэша. Сегодня первым идёт незащищённое удаление очереди, и брошенное там исключение оставляет высокие отметки над пересобранным пространством номеров — то есть навсегда погашенные бейджи.

**Почему асимметрия «высокая отметка хуже устаревшего счётчика».** Устаревший счётчик исправляется следующим открытием чата. Устаревшая **высокая** отметка не исправляется ничем: она гасит бейджи молча и бессрочно.

---

## 6. Что НЕ меняется

- Серверная схема: ни таблиц, ни колонок, ни индексов.
- Правило спеки продукта «никогда не открытый чат бейджа не имеет» — оно теперь выполняется по построению, а не совпадением.
- Форма `unread` на проводе: его там нет с фазы 025 и не появляется.
- Записи сессии, кроме монотонности флага онбординга (это правило, а не поле).
