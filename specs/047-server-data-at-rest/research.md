# Research: Данные на диске сервера

Опора — код `client_backend/` (`internal/db`, `internal/blob`, `internal/server/files.go`), 043 (докачка), 044–046, и проверка на этой машине (2026-10-09).

## R1. Шифрование базы

- **Decision:** драйвер SQLite меняется с `modernc.org/sqlite` на `github.com/ncruces/go-sqlite3` (SQLite, собранный в Wasm и исполняемый `wazero`, — чистый Go, `CGO_ENABLED=0`) с VFS `adiantum`, которой отдаётся наш случайный ключ данных (`hexkey`). `PRAGMA temp_store=memory`; остальные прагмы и `_txlock=immediate` — как сегодня. Импорт `modernc.org/sqlite` есть только в `internal/db/db.go` — замена локальная.
- **Проверено** (spike в scratchpad, 2026-10-09): WAL работает с этой VFS; после 20 000 строк с маркером ни в `nox.db`, ни в `-wal`, ни в `-shm` маркера нет — ни открытой базе, ни закрытой; чужой ключ — `file is not a database`; верный ключ открывает.
- **Rationale:** FR-008, FR-012: страницы базы и её служебные файлы на диске зашифрованы, бинарник статический и без C-кода. Модель угроз темы 4 — кража диска и утечка копий; Adiantum детерминирован и без MAC страниц (видно, какие страницы менялись между снимками; подделка страниц не обнаруживается) — подделка требует доступа к машине, а он вне рамок.
- **Alternatives considered:** `modernc.org/sqlite` — шифрующей VFS нет; шифрование колонок в приложении — схема, индексы и страницы остаются открытыми (FR-008); SQLCipher — CGO (FR-012); VFS `xts` того же автора — равноценна, Adiantum выбрана как основная у пакета и быстрая без аппаратного AES (Raspberry Pi).

## R2. Ключ данных и пароль

- **Decision:** ключ данных — 32 случайных байта. Файл `<db>.key` (JSON): версия, `argon2id` с параметрами (память 64 МиБ, 3 прохода, 4 потока), соль (16 байт), nonce (24), запечатанный ключ — `XChaCha20-Poly1305(KEK, nonce, ключ данных, aad = "nox/datakey/v1")`, где `KEK = Argon2id(пароль, соль)`. Неверный пароль — отказ AEAD, на диске ничего не меняется. Пароль — не короче 12 знаков и не из одних пробелов. Смена пароля — новая соль и nonce, запись `<db>.key.tmp`, `fsync`, переименование поверх, `fsync` каталога: после сбоя открывается прежний или новый пароль.
- **Rationale:** FR-001, FR-004, FR-006, SC-002, SC-006; `golang.org/x/crypto` (`argon2`, `chacha20poly1305`, `hkdf`).

## R3. Запертый старт

- **Decision:** при старте служебный loopback-слушатель поднимается сразу; состояние: «задать пароль» (нет ни базы, ни `<db>.key`), «заперт» (есть оба), отказ старта (есть одно без другого — база до 047 или потерянный ключ; сообщение говорит, что делать). Основной порт не слушается, пока сервер заперт: устройства видят обычное «нет связи». Разблокировка — открыть базу ключом данных, миграции, затем остальной `Run`, как сегодня. `/health` — `200 {"status":"locked"}` до разблокировки, `{"status":"ok"}` после.
- **Rationale:** FR-002, FR-005, уточнения.

## R4. Ввод пароля и команды

- **Decision:** страница — формы `POST` с проверкой `Host`, `Origin` и токена формы (как `Set` в 045). Команды — подкоманды того же бинарника, говорят с работающим сервером через `/control/*` на служебном адресе (заголовок `X-Nox-Control: 1`, без `Origin`, локальный `Host` — как `noxd link` в 046): `noxd unlock` (задать при первом запуске — пароль и повтор; ввести после перезапуска), `noxd password` (текущий, новый, повтор), `noxd backup <файл>`. В терминале пароль спрашивается без эха (`golang.org/x/term`), иначе читается из стандартного ввода. `noxd restore <файл>` работает без сервера.
- **Rationale:** FR-003, FR-006, уточнения; базу открывает только сервер.

## R5. Вложения кусками

- **Decision:** формат файла в `internal/blob`: заголовок 32 байта (`NOXF`, версия 1, размер куска 65 536); куски — шифротекст до 64 КиБ открытых байтов плюс 16 байт тега. AEAD — ChaCha20-Poly1305 с ключом файла `HKDF-SHA256(ключ данных, info = "nox/file/v1|" + file_id)`; nonce — 4 нулевых байта ‖ номер куска (8 байт); AAD — номер куска ‖ признак последнего. Последний кусок известен по объявленному размеру (`file.uploadBegin`). Загрузка: целые куски запечатываются и дописываются в `.part` по мере прихода, хвост ждёт в памяти запроса; `.synced` считает только запечатанные куски — оборванная загрузка продолжается с начала незаконченного куска. Чтение диапазона — нужные куски расшифровываются, отдаются точные байты.
- **Rationale:** FR-009, FR-010, SC-004; докачка и `Range` из 043 сохраняются.

## R6. Бэкап

- **Decision:** `noxd backup <файл>` → сервер делает `VACUUM INTO` во временную базу той же VFS и тем же ключом (согласованный снимок без остановки), затем пишет `<файл>.partial` — tar (`archive/tar`): `nox.key`, `nox.db`, `files/<id>` (готовые вложения как есть, уже зашифрованные) и в конце `manifest` (размеры и `HMAC-SHA256` с ключом `HKDF(ключ данных, "nox/backup/v1")`); `fsync` и переименование в `<файл>`. Недописанный `.partial` бэкапом не считается.
- **Rationale:** FR-013; всё содержимое внутри уже зашифровано, имена — случайные id; MAC закрывает подмену файла бэкапа, раз Adiantum сам её не ловит.

## R7. Восстановление

- **Decision:** `noxd restore <файл> -db <путь>`: отказ, если база, `<db>.key` или непустой каталог файлов уже есть; пароль → ключ данных из `nox.key` бэкапа; проверка `manifest`; распаковка во временный каталог рядом; `PRAGMA quick_check`; новое `journal_id`; переименование на место. Неверный пароль или испорченный бэкап — ничего не меняется.
- **Rationale:** FR-014, FR-015, уточнение; ключ сервера остаётся тем же — устройства подключаются без спаривания и перечитывают переписку по новому имени журнала (правило контракта §3).

## R8. Контракт

- **Decision:** §1 — пока сервер заперт, основной порт не принимает соединений; §3 — после восстановления из бэкапа имя журнала новое (действующее правило о смене `journal_id`); служебная страница и `/health` — вне контракта, кроме ответа `/health`.
- **Rationale:** FR-019.

## R9. Зависимости

- **Decision:** прямые зависимости сервера: `github.com/coder/websocket`, `github.com/ncruces/go-sqlite3`, `golang.org/x/crypto`, `golang.org/x/sync`, `golang.org/x/term`, `rsc.io/qr`; `modernc.org/sqlite` и его `libc` уходят. Обоснование — в `client_backend/CLAUDE.md`: шифрующая VFS без CGO есть только у `ncruces/go-sqlite3`; `x/crypto` — Argon2id и AEAD; `x/term` — пароль без эха.

## R10. Проверка

- **Decision:** Go — шифрованная база (поиск маркеров по файлам остановленного сервера и бэкапа, SC-001), ключ данных (неверный пароль ничего не меняет — сравнение каталога до и после, SC-003; смена пароля, сбой между записью и переименованием), запертый старт (порт закрыт, `/health`), формы и `/control/*`, вложения кусками (обрыв посреди куска, диапазоны, SC-004), бэкап и восстановление (SC-005), время открытия и смены пароля (SC-002, SC-006). Сквозной прогон: стенд, `noxd unlock`, спаривание, переписка, `noxd backup`, `noxd restore` в другой каталог, `cmd/smoke`.

## R11. Решения реализации там, где документы молчат

Выбран осторожный вариант; каждое решение записано здесь.

- **Ключ базы — прагмой, не в URI.** Соединение открывается URI `file:<абсолютный путь>?vfs=adiantum` без ключа; первым делом хук соединения выполняет `PRAGMA hexkey`, затем прагмы в прежнем порядке и `temp_store=memory`. URI — строка, которая расходится по ошибкам и по видимому VFS имени файла; прагма тратится на соединение. Путь в URI абсолютный и экранированный: пробел, `%`, `?` и `#` в пути — часть имени, а не запрос.
- **`VACUUM INTO` знает ключ только из URI** — снимок открывает файл сам, прагма до него не дотягивается. URI передаётся параметром запроса, а сообщение SQLite об ошибке цитирует URI целиком (проверено: «unable to open database: file:…hexkey=…»), поэтому ключ вырезается из текста ошибки до того, как она уходит из `internal/db`.
- **Заголовок файла вложения** (32 байта): `NOXF` (4), версия `1` (1), три нулевых байта, размер куска `65536` uint32 big-endian (4), двадцать нулевых байтов. Любое отличие — файл, который эта сборка не читает (`ErrCorrupt`), а часть с таким заголовком считается пустой.
- **Сколько части «надёжно».** `received` — только целые куски; короткий последний кусок считается, только когда запись `.synced` называет ровно всё, что в части: тогда пришёл последний байт файла. Продолжение загрузки — с начала куска или с конца файла; любое другое смещение — `404` и новый запрос `received`.
- **Повторная запечатка куска тем же nonce** (`0⁴ ‖ i`, ключ файла по `file_id`). Кусок, отрезанный обрывом, откатом или сбоем, запечатывается заново под тем же номером. Пока байты те же — а приложение после 043 шлёт ровно те же байты своей копии файла и при смене файла начинает новую загрузку с новым `file_id`, — шифротекст совпадает и ничего не раскрывает. Иные байты под тем же номером может прислать только неисправное устройство самого человека, а увидеть оба шифротекста — только криминалистика стёртых блоков диска; это вне модели угроз темы 4. Формат кусков — по data-model, без случайных nonce.
- **Правило пароля** — не меньше 12 знаков (символов, не байтов) и не одни пробелы; пароль из пробелов получает код `short`. Пароль не обрезается и не нормализуется: открывает ровно то, что набрано. Разная нормализация Unicode на разных машинах — известное ограничение для паролей не на ASCII.
- **Границы параметров Argon2id в файле ключа**: память до 1 ГиБ, до 64 проходов, до 64 потоков. Параметры читаются до того, как пароль что-то скажет о файле, а файл ключа из бэкапа пришёл извне.
- **Запертый старт и порт страницы.** `-status-addr` не может быть пустым, а занятый порт страницы останавливает старт: пароль вводится только там. Состояние определяют только база и `<db>.key`; каталог файлов не смотрится. При задании первого пароля файл ключа пишется первым, база создаётся вторым: сбой между ними оставляет «ключ без базы», и отказ старта говорит, что делать.
- **Один владелец ключа.** Задание, ввод и смена пароля и бэкап выполняются по очереди одной горутиной («ворота»: горутина `Run`, пока сервер заперт, затем горутина-хранитель), поэтому две смены пароля не пишут ключ поверх друг друга, а бэкап не берёт файл ключа посреди смены. Мьютекса нет.
- **Ответ на ввод пароля приходит, когда основной порт уже слушает**, — или с отказом, если данные не открылись (`internal`); тогда процесс останавливается с причиной в журнале, как при любом сбое открытия базы.
- **`GET /control/state`** — `{"state":"setup"|"locked"|"open"}`: `noxd unlock` должен знать до ввода, спрашивать ли пароль дважды с предупреждением о забытом пароле или один раз. Защита — как у остальных `/control/*`.
- **Коды ответов `/control/*`**: `wrong` — `403`, `short`, `mismatch`, `path` — `400`, `state` — `409`, сбой — `500 {"error":"internal"}`. Для `path` и `internal` в ответе есть `message` с причиной словами (путь и слова сервера, никаких секретов). `path` — путь бэкапа, по которому сервер писать не будет: не абсолютный, каталога нет, файл уже есть.
- **Повтор пароля** проверяет страница и команда; `/control/password` повтора не несёт. Правила нового пароля команда проверяет у себя до отправки, сервер — ещё раз.
- **Страница в запертом состоянии**: заголовок, поле пароля, кнопка, сообщение об ошибке и строка о том, что страница доступна только с этой машины. Ни скрипта, ни ссылок, ни адресов, ни цифр. Токен формы один на процесс: форма, выданная запертой страницей, принимается и после открытия.
- **HKDF — из стандартной библиотеки** (`crypto/hkdf`, Go 1.24+), а не из `x/crypto`; Argon2id и AEAD — из `x/crypto`.
- **Бэкап.** Снимок пишется рядом с живой базой (`<db>.snapshot`, локальный диск по правилу сервера) и удаляется после записи; список вложений берётся из строк самого снимка, поэтому бэкап несёт ровно те файлы, которые называет его база, а незаконченные загрузки не несёт. Файл бэкапа не пишется поверх существующего; `.partial` создаётся только как новый файл. Манифест несёт ещё и `version: 1`. MAC — `HMAC-SHA256` с ключом `HKDF(ключ данных, "nox/backup/v1")` над потоком: `nox/backup/v1\n`, затем по каждой записи длина имени (2 байта), имя, размер (8 байтов) и содержимое, в конце `0xff`, `created_at` и число записей; так восстановление считает MAC на лету и узнаёт момент из манифеста в конце.
- **Восстановление.** `-db` обязателен и без запасного значения из окружения. Каталоги цели должны существовать. Распаковка идёт во временные `<db>.restore` и `<files>.restore` рядом с целью; на место — файлы, затем база, последним — ключ: с ключом и базой место становится запертым сервером. Неверный пароль, испорченный бэкап или непустое место — ничего не меняется. Ключ onion-сервиса в бэкапе не появляется: после 045 его нет в базе.
- **Тесты** запирают ключ дешёвыми параметрами Argon2id через внутренний вход `run(..., kdf)`; производственные параметры проверяет отдельный тест пакета `vault` вместе со временем открытия и смены.

## R12. Сквозной прогон (macOS, 2026-10-10)

Бинарник `noxd` этой ветки, стенд во временном каталоге, свои порты, роль приложения — `cmd/smoke` и одноразовый драйвер по проводу (спаривание, переписка, вложения, обрыв загрузки, диапазоны).

| Шаг | Итог |
|---|---|
| Свежий старт | `/health` — `locked`, основной порт закрыт, на диске ничего. `noxd unlock` с паролем дважды из stdin — `Unlocked.`; `/health` — `ok`, порт слушает; на диске `nox.db`, `-wal`, `-shm`, `-files` и `nox.db.key` (`0600`) |
| Спаривание и переписка | `cmd/smoke` — все шаги; драйвер: 30 сообщений, фото 200 КБ, видео 24 МиБ; загрузка, оборванная на 2 437 177 байте, продолжена с 2 424 832 (граница 37-го куска) и дошла целой; три диапазона видео — точные байты |
| Остановка и поиск (SC-001) | маркеров сообщений, имён чатов, имени человека, `CREATE TABLE`, `SQLite format 3`, открытого ключа сервера и семени устройства в каталоге стенда нет |
| Перезапуск | `/health` — `locked`; страница — только поле пароля; драйвер — «connection refused». Неверный пароль — `Wrong password.`, хэши и времена всех файлов не изменились (SC-003). Верный — открыт за 0,17 с (SC-002); устройство здоровается без спаривания, 32 сообщения, вложения совпадают |
| `noxd password` | 0,23 с (SC-006), файлы вложений не тронуты; несовпавший повтор отказан командой; после перезапуска прежний пароль — `Wrong password.`, новый открывает |
| `noxd backup` | один tar 36 МБ: `nox.key`, `nox.db`, три файла, `manifest`; открытого текста нет; повторный бэкап в тот же файл отказан; сервер всё время отвечал; в журнале — только счётчики |
| `noxd restore` | с прежним паролем — `Wrong password. Nothing was restored.`, место пустое; на место с базой — отказ; с паролем — восстановлен. Сервер на новом месте и других портах заперт, открывается тем же паролем, доказывает тот же ключ (`smoke -check`); устройство, спаренное до бэкапа, здоровается без спаривания, имя журнала новое (`j_ec9b…` → `j_6b2d…`), переписка и вложения на месте (SC-005) |
| Журналы | ни одной строки `ERROR`, ни одного пароля |
| `scripts/demo-stand.sh` | с `NOX_STAND_PASSWORD` на своём каталоге и портах: `noxd unlock`, `cmd/smoke` по ссылке со страницы — все шаги |

Проверки владельца — Linux и Windows: запуск, пароль, бэкап и восстановление между машинами.
