# Research: Защищённый канал — TLS 1.3 и проверка Eidolon

Все решения проверены по исходникам: `eidolon-auth` 0.3.1, `cyphergraphy` 0.3.1, `ec25519` 0.1.0, `rustls` 0.23.45, Dart SDK 3.12.1 (`dart:io`, `dart:_http`), Go 1.27 (`crypto/tls`, `crypto/ed25519`), код `packages/nox_tor`, `lib/`, `client_backend/`.

## R1. Формат и порядок Eidolon

- **Decision:** сообщение — 160 байт: открытый ключ Ed25519 (32) ‖ подпись над самим ключом (64) ‖ подпись над отпечатком соединения (64). Инициатор — приложение: шлёт первым. Отвечающий — сервер: проверяет длину, обе подписи и только потом отвечает своим сообщением. Приложение проверяет ответ и ключ сервера по списку из одного ключа — ключа из ссылки.
- **Rationale:** ровно так работает `EidolonState` в `eidolon-auth` (`serialize_creds`, `verify_input`): подпись над ключом — над его 32 сжатыми байтами, подпись над вызовом — над переданным в `init` значением. Подписи детерминированные: `cyphergraphy` подписывает `sign(msg, None)` — Ed25519 по RFC 8032 без добавки, поэтому общие векторы сравниваются побайтно. Go `crypto/ed25519` воспроизводит оба сообщения из тех же семян байт в байт (проверено, `contracts/eidolon-vectors.json`).
- **Ошибки:** `InvalidLen`, `InvalidCert` (подпись над ключом), `SigMismatch` (подпись над отпечатком — так проявляется посредник), `Unauthorized` (ключ не из списка — так проявляется чужой сервер). В приложении `Unauthorized` → «не тот сервер», остальное → неудачная попытка связи.
- **Alternatives considered:** сервер первым (отвергнуто владельцем: как в `netservices`, первым — открывший соединение); своя реализация в Rust (отвергнуто: библиотека заказчика).

## R2. Отпечаток соединения

- **Decision:** экспортёр TLS 1.3 по RFC 9266: метка `EXPORTER-Channel-Binding`, пустой контекст, 32 байта. Rust — `ConnectionCommon::export_keying_material(…, b"EXPORTER-Channel-Binding", Some(b""))`; Go — `ConnectionState().ExportKeyingMaterial("EXPORTER-Channel-Binding", nil, 32)`. В TLS 1.3 отсутствующий и пустой контекст дают одно значение (RFC 8446, §7.5).
- **Rationale:** стандартная привязка к каналу для TLS 1.3; есть в обеих библиотеках; посредник с двумя сессиями получает два разных значения.
- **Alternatives considered:** случайный вызов от сервера (пересылается посредником — отвергнуто).

## R3. TLS в модуле приложения

- **Decision:** `rustls` 0.23.45 на провайдере `ring`, только TLS 1.3, ALPN `http/1.1`. Своя проверка сертификата: любой сертификат принимается (`ServerCertVerified::assertion()`), подпись рукопожатия TLS 1.3 проверяется `rustls::crypto::verify_tls13_signature` по алгоритмам провайдера; TLS 1.2 — отказ. Клиентского сертификата нет (`with_no_client_auth`). SNI не отправляется (`enable_sni = false`): по имени ничего не решается, а постоянное имя в открытом ClientHello метило бы трафик NOX для любого наблюдателя сети. Возобновления сессий нет (`Resumption::disabled()`), раннего отправления данных тоже: при возобновлении TLS 1.3 сервер не подписывает рукопожатие, а FR-002 требует проверенной подписи на каждом соединении. Асинхронность — `tokio-rustls` поверх `tokio::net::TcpStream` или потока Arti (`DataStream` уже реализует `tokio::io::AsyncRead/AsyncWrite` — модуль копирует его через `copy_bidirectional`).
- **Rationale:** решения 2 и 9 темы 1; `ring` уже в графе через Arti; проверка подписи рукопожатия оставляет TLS внутренне корректным.
- **Alternatives considered:** `aws-lc-rs` (постквантовое — вне рамок).

## R4. Технический сертификат сервера

- **Decision:** сертификат собирается при каждом старте из одноразового ключа ECDSA P-256, в памяти; на диске ничего. Ключ сервера Ed25519 — отдельно, в базе. Билетов возобновления сервер не выдаёт (`SessionTicketsDisabled`) — пара к R3.
- **Rationale:** приложение сертификат не сверяет; хранить его незачем; P-256 — алгоритм, который понимают все реализации TLS.
- **Alternatives considered:** сертификат на ключе Ed25519 сервера (смешивает роли ключа; отвергнуто).

## R5. Где на сервере идёт Eidolon

- **Decision:** обёртка слушателя. Сервер сам принимает TCP-соединения; на каждое — в отдельной горутине — рукопожатие TLS 1.3 (`tls.Server(...).HandshakeContext` со сроком), экспортёр, обмен Eidolon со сроком; готовое соединение уходит в очередь, из которой `Accept` отдаёт его `http.Server`. Срок на TLS и проверку вместе — 10 с от приёма на основном входе и 30 с на onion-входе (как `onionTimeout` сегодня): сегодня у рукопожатия TLS на основном входе 5 с (`ReadHeaderTimeout`), а проверка добавляет один обмен. Итог — открытый ключ устройства — несёт обёртка соединения, `ConnContext` кладёт его в контекст запроса. Так проверку проходят и WebSocket, и `/files`.
- **Rationale:** проверка — до HTTP, на каждом соединении (FR-001, FR-007); медленный клиент не держит приём остальных; механизм контекста уже есть (`markOnionConn`).
- **Alternatives considered:** проверка после HTTP Upgrade внутри WebSocket (файлы шли бы мимо — отвергнуто).

## R6. Ключ сервера в базе

- **Decision:** `server_identity.private_key` — base64 семени Ed25519 (32 байта), `public_key` — base64 открытого ключа; ECDSA уходит. `onion_seed` остаётся до 045. Миграция `001_init.sql` правится на месте (правило «одна миграция до релиза»); база — новая.
- **Rationale:** FR-009, FR-025; правило проекта о единственной миграции.

## R7. Связь Dart и модуля

- **Decision:** C ABI без блокировок (контракт `contracts/ffi-channel.md`): `nox_chan_open` возвращает дескриптор сразу; дальше события приходят в Dart через `NativeCallable.listener` (безопасно с любого потока, исполняется в цикле событий изолята): «канал проверен», «данные», «можно писать», «закрыт», «отказ (вид)». Данные — буфер модуля, Dart копирует и освобождает. Поток данных управляется окнами: модуль держит не больше 1 МиБ неподтверждённых входящих байтов (`nox_chan_ack`), очередь исходящих сообщает «можно писать», когда опустилась ниже половины своего окна.
- **Rationale:** `NativeCallable.listener` — штатный способ Dart для обратных вызовов из чужих потоков (Dart SDK 3.12, `ffi.dart`); без окон большой файл раздул бы память на стороне, которая не успевает.
- **Alternatives considered:** петлевой порт (запрещён конституцией 1.4.0); опрос из Dart (лишняя задержка).

## R8. Свой Socket для WebSocket и Dio

- **Decision:** `ChannelSocket extends Stream<Uint8List> implements Socket`. `HttpClient.connectionFactory` возвращает `ConnectionTask<Socket>` с ним; `findProxy` — `DIRECT`. При прямом соединении `HttpClient` использует сокет фабрики как есть и TLS поверх не накладывает (`dart:_http/http_impl.dart`: обёртка TLS — только на пути через прокси), поэтому адреса остаются `wss://`/`https://`. Тело запроса `HttpClient` пишет через `socket.addStream` с паузой источника (`_HttpOutgoing.addStream`: `controller.onPause = sub.pause`) — `ChannelSocket.addStream` ставит источник на паузу, пока очередь модуля выше окна. `flush` ждёт опустошения очереди.
- **Rationale:** проверено по исходникам SDK 3.12.1; WebSocket и Dio не меняются.

## R9. Путь через Tor в 044

- **Decision:** модуль сам подключается к onion-адресу через Arti внутри `nox_chan_open` (логика «подстраховочного» второго подключения из `bridge.rs` сохраняется: второе подключение в новой группе изоляции через 15 с, общий срок 45 с), поверх — тот же TLS и Eidolon. Петлевой мост, его секрет, `nox_tor_bridge_secret` и право `network.server` на macOS уходят. Ключ доступа Tor к onion (039/040) пока остаётся: `nox_tor_set_target` регистрирует его в хранилище ключей Arti без моста, `nox_chan_open` ключа не принимает; убирается в 045. Исход подключения к onion модуль пишет в снимок состояния Tor, как писал мост, — на нём держится правило «ключ не зарегистрирован после 5 минут отказов».
- **Rationale:** FR-014 (без локальных портов); 045 убирает ключи доступа целиком.

## R10. Ссылка версии 3

- **Decision:** `nox://pair/` + base64url без `=` над байтами: версия `0x03` (1) ‖ ключ сервера (32) ‖ токен (16) ‖ адреса. Адрес — тип (1 байт) ‖ длина значения (1 байт) ‖ значение. Типы: `1` IPv4 — 4 байта адреса + 2 байта порта (big-endian); `2` IPv6 — 16 + 2; `3` имя — UTF-8 + 2 байта порта, имя 1–253 байта; `4` onion — открытый ключ сервиса (32), порт 443. Неизвестный тип пропускается по длине; неполный заголовок или длина за концом — испорченная ссылка; версия ≠ 3 — «обновите приложение», если версия больше 3, иначе — испорченная. Векторы — `contracts/link-vectors.json`.
- **Rationale:** тема 3, решение 10; 158 знаков с тремя адресами.

## R11. Где модуль берёт ключ устройства

- **Decision:** семя Ed25519 (32 байта) создаёт и хранит Dart — как сегодня, `session.device_secret` в системном сейфе; при каждом `nox_chan_open` семя передаётся в модуль, модуль держит его в обнуляемом буфере на время рукопожатия. Новое семя — при каждом спаривании; при выходе стирается.
- **Rationale:** хранилище ключей — забота Dart-слоя (`flutter_secure_storage`, пометка «только это устройство» — 048); модулю не нужно своё хранилище.
- **Alternatives considered:** семя внутри модуля (пришлось бы писать сейф на пяти платформах в Rust).

## R12. Приветствие и спаривание на проводе

- **Decision:** сервер шлёт `{"srv":{"schema_max":1}}` без `challenge`; `session.hello` — без `device_key` и `signature`; `pair` — без `device_key`. Сервер берёт ключ устройства из соединения. Незнакомый ключ: `session.hello` → `unauthenticated` (приложение — принудительный выход), `pair` — разрешён, любые другие команды до приветствия — `invalid_request`, как и сегодня.
- **Rationale:** FR-006, FR-013, FR-015.

## R13. Прямой путь и проба адреса

- **Decision:** проба прямого адреса — открыть канал с Eidolon и закрыть. Итог: «мой сервер», «другой ключ» (адрес не мой — молча дальше), «не ответил». `/health` и пин уходят из пробы.
- **Rationale:** FR-011; только проверка ключа говорит, свой ли сервер по адресу.

## R14. Вид отказов и принудительный выход

- **Decision:** модуль сообщает вид отказа: `network`, `tls`, `wrong_server`, `protocol` (длина или подписи), `timeout`, `tor_<вид>`. Приложение: `wrong_server` по onion — «onion-адрес ведёт к другому серверу», остановка попыток по нему до смены адреса или `Try again`; по прямому адресу — адрес пропускается. Принудительный выход — только по `unauthenticated` на `session.hello` (и `device.revoked`, который приходит спаренному устройству, когда его отзывают с другого); 401 от `/files` — больше не выход, а ошибка передачи.
- **Rationale:** FR-011–FR-013; один хозяин принудительного выхода.

## R15. `/health`

- **Decision:** переезжает на служебный локальный слушатель (страница состояния), основной порт до проверки не отвечает ничем.
- **Rationale:** допущение спецификации; основной порт не должен отвечать неспаренному.

## R16. Linux

- **Decision:** хук сборки больше не пропускает Linux; в `rust-toolchain.toml` добавляются `x86_64-unknown-linux-gnu` и `aarch64-unknown-linux-gnu`. Встроенный Tor на Linux в интерфейсе остаётся выключенным до 045 (`TorCapability`), но модуль канала нужен везде.
- **Rationale:** FR-014; Tor на Linux — решение 045.

## R17. Имя пакета

- **Decision:** пакет остаётся `packages/nox_tor` — канал добавляется в него модулем `channel`. Переименование — механика без пользы для фичи.

## R18. Проверка совместимости и сквозной прогон

- **Decision:** общие векторы Eidolon и ссылки — в `contracts/`, тесты Rust и Go проверяют их; тесты Dart — векторы ссылки. Сквозной прогон: `noxd` с новой базой локально и приложение (macOS, `stage`) — спаривание по вставленной ссылке, сообщение, файл; а также Dart-тест модуля против Go-сервера, поднятого из теста (`test/live/`, вручную, вне гейтов).

## R19. Приглашения до 045

- **Decision:** сервер выпускает приглашения только версии 3; `onion` в запросе `device.invite` больше ничего не меняет, ответ — `"onion": false`. Ссылка несёт прямой адрес и onion-адрес, если сервис опубликован: onion-адрес нужен устройству после спаривания. Одноразовые ключи доступа onion-приглашений (`issueOnionInvite`, `BuildPairingLinkV2`) уходят: в ссылке версии 3 им нет поля. Приложение показывает под приглашением `This link works only on your home network.` для любой ссылки и на экране входа отвечает «спаривание работает дома», если сервер по прямым адресам не ответил.
- **Rationale:** до 045 onion-сервис открывается только ключом доступа спаренного устройства; честное «только дома» лучше приглашения, которое не сработает снаружи (тот же довод, что в 039).
- **Alternatives considered:** одноразовый ключ доступа в ссылке версии 3 (работа на выброс: 045 убирает ключи доступа целиком).

## R20. Сроки подключения в приложении

- **Decision:** срок, который Dart передаёт в `nox_chan_open`, — бюджет пути: 30 с напрямую, 45 с через Tor (подключение Arti с подстраховкой укладывается в те же 45 с, как у моста). Внешние сроки остаются и обрывают открытие раньше через `ConnectionTask.cancel` → `nox_chan_close`: у WebSocket — 10 с напрямую и 45 с через Tor (`IOWebSocketChannel.connect(connectTimeout:)`), у Dio — `connectTimeout` передачи (30 с, через onion — 45 с, 043).
- **Rationale:** проверка не добавляет своих сроков сверх сегодняшних (FR-008); один срок в модуле страхует от зависшего открытия, если внешний срок не задан.
