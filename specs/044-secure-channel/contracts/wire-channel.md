# Контракт: канал под конвертом (дельта контракта v0)

Правится первым в `docs/client-backend/protocol/contract-draft.md` (Принцип VII). Ниже — что меняется в §1, §2, §3, §8A и в кодах ошибок.

## §1. Транспорт → слои соединения

Каждое соединение — для команд (`wss`) и для байтов файлов (`https`) — собирается так:

1. **Транспорт:** TCP по адресу или поток Tor до onion-адреса (порт 443 onion-сервиса).
2. **TLS 1.3**, ALPN `http/1.1`. Сервер предъявляет технический сертификат; клиент его не сверяет, но подпись рукопожатия TLS проверяет. TLS 1.2 и ниже не принимаются. Клиент не отправляет SNI; возобновления сессий и раннего отправления данных нет ни у одной стороны — каждое соединение проходит полное рукопожатие.
3. **Проверка Eidolon** — сразу после рукопожатия, до первого байта HTTP:
   - отпечаток соединения `B` = экспортёр TLS 1.3 (RFC 9266): метка `EXPORTER-Channel-Binding`, пустой контекст, 32 байта;
   - сообщение = `pk` (Ed25519, 32) ‖ `sig(pk)` (64) ‖ `sig(B)` (64), подписи Ed25519 по RFC 8032 над сырыми байтами;
   - клиент пишет своё сообщение первым; сервер читает ровно 160 байт, проверяет обе подписи и отвечает своим сообщением; клиент читает 160 байт, проверяет обе подписи и сравнивает `pk` сервера с ключом из спаривания;
   - любая ошибка — соединение закрывается без ответа; клиент не отправляет ничего, пока не сверил ключ сервера;
   - срок: у клиента — бюджет подключения пути (транспорт, TLS и проверка вместе); у сервера — 10 с от приёма соединения на основном входе и 30 с на onion-входе (TLS и проверка вместе).
4. **HTTP/1.1:** WebSocket `/ws` и `/files/{token}`.

Сервер знает, чей ключ на соединении: спаренное устройство — всё; незнакомый ключ — только `pair` на `/ws` (`session.hello` → `unauthenticated`, прочие команды до приветствия — `invalid_request`, как сегодня); `/files` требует ключ спаренного устройства **и** действующий токен передачи: ключа нет среди спаренных — `401` (токен не тратится); токен негоден — `404`, как и прежде.

`/health` на основном порту больше не обслуживается: он на служебном локальном порту.

Пиннинг по отпечатку сертификата (фаза 036) из контракта уходит.

## §2. Приветствие

```json
{"srv": {"schema_max": 1}}
```

Поле `challenge` уходит. Контрольный вектор Ed25519 для challenge уходит; вместо него — векторы Eidolon (`specs/044-secure-channel/contracts/eidolon-vectors.json`).

## §3. `session.hello`

```json
{"id": "…", "type": "session.hello", "data": {"schema": 1, "since": 0, "label": "…"}}
```

Поля `device_key` и `signature` уходят: устройство уже известно по соединению. Незнакомый ключ на соединении → `unauthenticated`. Остальное в §3 без изменений.

## §8A. `pair`

```json
{"id": "…", "type": "pair", "data": {"token": "<base64url, 16 байт>", "platform": "…", "access_key": "…"}}
```

Поле `device_key` уходит: сервер записывает ключ из проверки Eidolon. `access_key` остаётся до 045. Ответ и правила токенов — без изменений до 046.

### `device.invite`

Поле `onion` в запросе по-прежнему разбирается мягко, но больше ничего не меняет: ответ — всегда ссылка версии 3 и `"onion": false`. Ссылка несёт прямой адрес и, если сервис опубликован, onion-адрес — для связи после спаривания; спаривания через onion до 045 нет, потому что onion-сервис открывается только ключом доступа спаренного устройства. Одноразовые ключи доступа onion-приглашений уходят.

### Ссылка спаривания версии 3

Формат — `contracts/pairing-link-v3.md`; векторы — `contracts/link-vectors.json`. Ссылки `https://nox.app/p/#…` версий 1 и 2 уходят — и у claim, и у приглашений.

## Коды ошибок

| Код | Когда |
|---|---|
| `unauthenticated` | `session.hello` на соединении, ключа которого нет среди спаренных устройств (как и сегодня, этот ответ — сигнал устройству, что его отозвали) |
| `invalid_request` | любая команда, кроме `pair` и `session.hello`, до приветствия — без изменений |
| (без кода) | ошибка проверки Eidolon — соединение закрывается до HTTP; клиент видит вид отказа модуля |

Остальные коды — без изменений.
