# Feature Specification: Защищённый канал — TLS 1.3 и проверка Eidolon в Rust-модуле приложения

**Feature Branch**: `security-rework` (фичи 044–049 идут в одной ветке, решение владельца 2026-10-09)

**Created**: 2026-10-09

**Status**: Draft

**Input**: Тема 1 трекера безопасности `docs/client-backend/roadmap-security.md` (решения 1–9) и раздел 044 его плана реализации; страница темы 1 артефакта NOX Architecture; формат ссылки — тема 3, решение 10.

## Зачем это вообще

Сегодня приложение и сервер узнают друг друга двумя разными механизмами: сервер — по пиннингу отпечатка своего ключа (TLS в Dart), устройство — по подписи над challenge в приветствии. Проверка привязана к TLS, а TLS в Dart не отдаёт отпечаток соединения. Заказчик требует, чтобы проверка «кто есть кто» работала сама по себе, независимо от шифрования, на его библиотеках, и одинаково на любом пути.

Эта фича собирает каждое соединение слоями: транспорт → TLS 1.3, который только шифрует → проверка Eidolon, которая решает, кто на другом конце, и привязана к этому соединению → команды и файлы. Всё до команд делает Rust-модуль приложения на всех пяти платформах.

## Clarifications

### Session 2026-10-09

- Q: По сохранённому прямому адресу ответила машина с чужим ключом — что видит человек? → A: Ничего: адрес считается недоступным, приложение пробует следующий путь. Сообщение о другом сервере — только для onion-адреса: прямые адреса вида 192.168.x.x в чужих сетях заняты чужими машинами, тревога была бы ложной.
- Q: Должна ли передача байтов файла требовать на соединении ключ спаренного устройства, а не только одноразовый токен передачи? → A: Да, оба условия: ключ спаренного устройства на соединении и действующий токен передачи.
- Q: Что делает приложение, когда по onion-адресу ответил другой сервер? → A: Прекращает попытки по этому адресу до смены адреса или ручного повтора («Try again»), как сегодня работает «не тот сервер».

## Решения (заказчик и владелец, 2026-10-09)

1. **Слои соединения:** транспорт (TCP по адресу или поток Tor до onion-адреса) → TLS 1.3 → проверка Eidolon на ключах Ed25519 → команды (WebSocket) и файлы (HTTP).
2. **Шифрование — TLS 1.3**, не Noise. Сертификат сервера технический: приложение его не сверяет.
3. **Отпечаток соединения** — экспортёр TLS 1.3 по RFC 9266 (метка `EXPORTER-Channel-Binding`, пустой контекст, 32 байта). Обе стороны получают его сами, по сети он не ходит.
4. **Eidolon:** каждая сторона отправляет 160 байт — свой ключ Ed25519, подпись над ключом и подпись над отпечатком. Первым показывает себя приложение, вторым — сервер, как в `netservices` заказчика.
5. **Канал — в Rust-модуле приложения** на всех пяти платформах, включая Linux; Dart связан с ним только прямыми вызовами, без локальных портов. Не на чистом Dart: TLS Dart не отдаёт отпечаток соединения.
6. **Сервер на Go:** TLS 1.3, технический сертификат, своя реализация Eidolon по правилам `eidolon-auth`.
7. **Ключ устройства Ed25519** хранится в системном сейфе.
8. **Ссылка спаривания** — `nox://pair/` версии 3 (тема 3, решение 10).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Связь со своим сервером на любом пути (Priority: P1)

Человек со спаренным устройством открывает приложение дома — связь идёт напрямую — и вне дома — через Tor. В обоих случаях соединение проходит проверку: сервер узнаёт устройство по его ключу, приложение — сервер по ключу из ссылки спаривания. Сообщения и файлы идут как раньше; ни одна команда не уходит, пока сервер не проверен.

**Why this priority**: это суть фичи — новый канал должен работать всюду, где работал старый.

**Independent Test**: спаренное устройство подключается напрямую и через Tor, отправляет и получает сообщение и файл; каждое новое соединение (переподключение, передача файла) проходит проверку.

**Acceptance Scenarios**:

1. **Given** устройство спарено и сервер доступен напрямую, **When** приложение открывается, **Then** соединение проходит проверку, и сообщения идут в обе стороны.
2. **Given** напрямую сервер недоступен и onion-адрес известен, **When** приложение подключается через Tor, **Then** проходит та же проверка, и сообщения идут.
3. **Given** соединение для команд проверено, **When** приложение загружает или скачивает файл, **Then** соединение для байтов файла проходит ту же проверку отдельно.
4. **Given** связь оборвалась, **When** приложение подключается снова, **Then** новое соединение проходит проверку заново.
5. **Given** соединение установлено, **When** приложение ещё не сверило ключ сервера, **Then** ни одна команда и ни один токен не отправлены.

---

### User Story 2 — Чужая машина и посредник не проходят (Priority: P1)

По сохранённому прямому адресу в чужой сети отвечает чужая машина; или кто-то встал посредником между приложением и сервером. В обоих случаях проверка не сходится: приложение не отправляет ни команд, ни токена и не выкидывает человека из приложения.

**Why this priority**: это то, ради чего проверка вообще существует.

**Independent Test**: приложение подключается к машине с другим ключом сервера — по прямому адресу и по onion-адресу; посредник с двумя TLS-соединениями пересылает сообщения проверки в обе стороны — проверка не проходит ни у одной стороны.

**Acceptance Scenarios**:

1. **Given** по прямому адресу отвечает машина с другим ключом, **When** приложение подключается, **Then** оно считает адрес недоступным, тихо пробует следующий путь и ничего не отправляет этой машине, кроме своих сообщений проверки.
2. **Given** по onion-адресу отвечает сервер с другим ключом, **When** приложение подключается, **Then** оно показывает, что этот onion-адрес ведёт к другому серверу, и ничего ему не отправляет.
3. **Given** посредник держит два TLS-соединения и пересылает сообщения проверки, **When** стороны проверяют подписи, **Then** подпись над отпечатком одного соединения не сходится с отпечатком другого, и соединение рвётся у той стороны, которая проверяет первой.
4. **Given** проверка не сошлась, **When** человек смотрит на приложение, **Then** его данные и вход на месте: «не тот сервер» никогда не ведёт к выходу.

---

### User Story 3 — Спаривание по ссылке версии 3 (Priority: P1)

Человек сканирует QR-код или вставляет ссылку `nox://pair/…`. Приложение разбирает её: ключ сервера, одноразовый токен, адреса. Подключается к первому отвечающему адресу, показывает свой новый ключ, сверяет ключ сервера с ключом из ссылки и только после этого предъявляет токен. Сервер записывает ключ устройства.

**Why this priority**: без новой ссылки нового канала не построить — ключ сервера, по которому идёт проверка, приходит только в ней.

**Independent Test**: свежий сервер выпускает ссылку версии 3; устройство спаривается по ней напрямую и через Tor; испорченная ссылка, ссылка неизвестной версии и старая ссылка `https://nox.app/p/#…` отклоняются до подключения, каждая — со своим сообщением.

**Acceptance Scenarios**:

1. **Given** ссылка версии 3 с верным токеном, **When** человек её сканирует, **Then** устройство спаривается, а ключ сервера из ссылки становится ключом, по которому приложение проверяет сервер дальше.
2. **Given** ссылка испорчена (длина не сходится, не та схема, старый формат), **When** человек её вставляет, **Then** приложение отказывает до подключения, и этот отказ отличается от отказа токена.
3. **Given** ссылка неизвестной версии, **When** человек её вставляет, **Then** приложение просит обновить приложение.
4. **Given** в ссылке адрес неизвестного типа, **When** приложение её разбирает, **Then** этот адрес пропускается, остальные работают.
5. **Given** ключ сервера по адресу не совпал с ключом из ссылки, **When** приложение подключается, **Then** токен не уходит.

---

### User Story 4 — Отозванное устройство уходит к спариванию (Priority: P2)

Устройство отозвали с другого устройства. Когда оно снова подключается, сервер его ключа не знает и разрешает ему только предъявить токен. Приложение понимает, что его отозвали: стирает свои данные и возвращается к экрану спаривания. Это единственный путь к принудительному выходу; «не тот сервер» к нему никогда не ведёт.

**Why this priority**: сегодня принудительный выход приходит из трёх мест; новый канал должен свести их к одному понятному правилу.

**Independent Test**: отозвать устройство и подключиться им снова — данные стёрты, экран спаривания; подключиться к чужому серверу — данные на месте.

**Acceptance Scenarios**:

1. **Given** устройство отозвано, **When** оно подключается, **Then** приложение стирает локальные данные и показывает экран спаривания.
2. **Given** проверка не сошлась из-за ключа сервера, **When** это случилось на любом пути, **Then** выхода и стирания нет.

---

### User Story 5 — Тот же канал на всех пяти платформах (Priority: P2)

Приложение на iOS, Android, macOS, Windows и Linux подключается одним и тем же модулем канала. На Linux модуль собирается так же, как на остальных платформах.

**Why this priority**: Принцип VI и решение 5; на Linux модуль раньше не собирался вовсе.

**Independent Test**: собрать приложение на каждой из пяти платформ и подключиться к серверу напрямую; Windows и Linux проверяет владелец.

**Acceptance Scenarios**:

1. **Given** сборка под любую из пяти платформ, **When** приложение подключается к серверу напрямую, **Then** соединение проходит проверку.

---

### Edge Cases

- **Сервер переустановлен с новым ключом** по тому же адресу — проверка не сходится; по прямому адресу приложение молча пробует другие пути, по onion-адресу показывает, что адрес ведёт к другому серверу. Чтобы снова связаться, устройство спаривают заново.
- **Сообщение проверки не той длины, с неверной подписью или не пришло вовремя** — соединение рвётся; это неудачная попытка связи, как обрыв, а не выход и не «не тот сервер».
- **Сервер старой версии** (без проверки Eidolon) — соединение не устанавливается; приложение показывает то же, что для недоступного сервера. Совместимости со старыми серверами нет: продукт не выпущен.
- **Устройство, спаренное до этой фичи** — у него нет ключа сервера Ed25519 из ссылки версии 3; при первом запуске приложение стирает локальные данные и возвращается к спариванию, один раз.
- **Ключ устройства не читается из сейфа** — устройство не может себя показать; приложение стирает локальные данные и возвращается к спариванию.
- **Несколько соединений одновременно** (команды и передачи файлов) — каждое проходит проверку само, у каждого свой отпечаток.
- **Незнакомое устройство пытается отправить что-то кроме токена** — сервер отказывает «устройство не знакомо» и рвёт соединение.
- **В ссылке нет ни одного адреса, до которого можно достучаться** — как сегодня: «не удалось подключиться».

## Requirements *(mandatory)*

### Functional Requirements

**Соединение**
- **FR-001**: Каждое соединение приложения с сервером — для команд и для байтов файлов — MUST проходить слои: транспорт → TLS 1.3 → проверка Eidolon → команды или файлы. До успешной проверки по соединению MUST NOT идти ничего, кроме двух сообщений проверки.
- **FR-002**: Соединение MUST использовать только TLS 1.3. Сервер MUST предъявлять технический сертификат; приложение MUST NOT решать по сертификату, кто на другом конце, но подпись рукопожатия TLS MUST быть верной.
- **FR-003**: Отпечаток соединения MUST быть экспортёром TLS 1.3 по RFC 9266: метка `EXPORTER-Channel-Binding`, пустой контекст, 32 байта. Обе стороны MUST получать его сами; по сети он MUST NOT передаваться.
- **FR-004**: Сообщение проверки MUST состоять из 160 байт: ключ Ed25519 (32), подпись над ключом (64), подпись над отпечатком соединения (64). Сторона MUST отклонять сообщение не той длины и с любой неверной подписью.
- **FR-005**: Первым MUST показывать себя приложение; сервер MUST отвечать своим сообщением только после проверки подписей приложения. Приложение MUST NOT отправлять команды или токен, пока не сверило ключ сервера с ключом, полученным при спаривании.
- **FR-006**: Сервер MUST находить устройство по ключу из сообщения проверки. Ключ спаренного устройства — полный доступ; незнакомый ключ с верными подписями — только предъявление токена спаривания (своё сообщение проверки сервер ему отправляет, чтобы новое устройство проверило сервер до токена); всё остальное — отказ «устройство не знакомо».
- **FR-006a**: Передача байтов файла MUST требовать и ключ спаренного устройства на соединении, и действующий токен передачи.
- **FR-007**: Проверка MUST быть одинаковой на любом пути (напрямую и через Tor) и на каждом соединении, включая переподключения и передачи файлов.
- **FR-008**: Проверка, не завершившаяся за время, отведённое пути на подключение, MUST считаться неудачной попыткой связи.

**Ключи**
- **FR-009**: Ключ сервера MUST быть ключом Ed25519, который сервер создаёт при первом запуске и хранит у себя; сервер MUST NOT заменять его (тема 3).
- **FR-010**: Ключ устройства MUST быть ключом Ed25519, новым при каждом спаривании; его закрытая половина MUST храниться в системном сейфе устройства и MUST NOT покидать устройство. Подписи MUST ставиться внутри модуля канала приложения.

**Отказы**
- **FR-011**: Если ключ сервера не совпал с ключом из спаривания по прямому адресу, приложение MUST считать этот адрес недоступным и пробовать следующий путь, ничего не сообщая человеку; по onion-адресу — MUST показывать, что адрес ведёт к другому серверу, и MUST прекращать попытки по этому адресу до смены адреса или ручного повтора («Try again»).
- **FR-012**: Несовпадение ключа сервера MUST NOT вести к выходу из приложения или стиранию данных.
- **FR-013**: Ответ сервера «устройство не знакомо» для устройства, считающего себя спаренным, MUST быть единственным путём к принудительному выходу: приложение стирает локальные данные и возвращается к экрану спаривания.

**Где работает**
- **FR-014**: Транспорт, TLS, проверка и Tor-клиент MUST работать в модуле канала приложения на всех пяти платформах, включая Linux. Приложение MUST общаться с модулем только прямыми вызовами, без локальных портов.
- **FR-015**: Приветствие сессии MUST NOT содержать challenge и подписи: устройство уже известно серверу по проверке соединения.

**Ссылка спаривания**
- **FR-016**: Ссылка MUST иметь вид `nox://pair/<base64url без =>`: версия (1 байт, 3), ключ сервера Ed25519 (32), токен (16), список адресов «тип, длина, значение» — IPv4 (адрес и порт, 6 байт), IPv6 (18), имя (длина имени + 2 байта порта), onion (открытый ключ сервиса, 32 байта; порт — 443).
- **FR-017**: Приложение MUST пропускать адрес неизвестного типа по его длине; ссылку, длина которой не сходится, MUST отклонять до подключения; на неизвестную версию MUST просить обновить приложение. Отказ разбора MUST отличаться от отказа токена. Ссылки старого формата MUST отклоняться как испорченные.
- **FR-018**: Сервер MUST выпускать ссылки только версии 3 — и для первого устройства, и для приглашений.
- **FR-019**: Приложение MUST пробовать адреса из ссылки по порядку: сначала прямые, потом onion.

**Провод, проверка совместимости, приватность**
- **FR-020**: Изменения MUST сначала вноситься в контракт v0 (§1 слои соединения, §2 приветствие, §3, §8A формат ссылки, коды ошибок) — Принцип VII; обе стороны — в этой фиче.
- **FR-021**: Модуль приложения и сервер MUST проходить общие тестовые векторы: одни и те же ключи и отпечаток дают одни и те же 160 байт, и каждая сторона принимает сообщения другой.
- **FR-022**: Логи MUST NOT содержать токены, ссылки, закрытые ключи и подписи; исход проверки пишется только видом.
- **FR-023**: Пиннинг по отпечатку, подпись challenge в приветствии и петлевой мост Tor MUST быть убраны.

**Интерфейс**
- **FR-024**: Сообщения «onion-адрес ведёт к другому серверу», «ссылка испорчена» и «обновите приложение» MUST быть на обеих ширинах, на английском и украинском.

**Совместимость**
- **FR-025**: Миграций нет: сервер MUST начинать с новой базы, а устройство, спаренное до этой фичи, MUST один раз вернуться к спариванию, стерев локальные данные.

### Key Entities

- **Ключ сервера** — пара Ed25519 сервера; открытая половина (32 байта) приходит в приложение в ссылке спаривания и хранится как ключ, по которому сервер проверяется.
- **Ключ устройства** — пара Ed25519 устройства, новая при каждом спаривании; закрытая половина — в системном сейфе, открытая — у сервера в списке спаренных.
- **Отпечаток соединения** — 32 байта, свои у каждого соединения; не хранится и не передаётся.
- **Сообщение проверки** — 160 байт: ключ, подпись над ключом, подпись над отпечатком.
- **Ссылка спаривания версии 3** — версия, ключ сервера, одноразовый токен, список адресов.
- **Технический сертификат** — сертификат сервера только для TLS; его ключ ни в чём не участвует.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Спаренное устройство обменивается сообщениями и файлами с сервером напрямую и через Tor на всех пяти платформах (Windows и Linux проверяет владелец).
- **SC-002**: Посредник с двумя TLS-соединениями не проходит проверку ни в одной из попыток автоматического теста.
- **SC-003**: Ни в одном тесте приложение не отправляет команду или токен машине, чей ключ не совпал с ключом из спаривания.
- **SC-004**: Общие тестовые векторы совпадают у модуля приложения и сервера на 100%.
- **SC-005**: «Не тот сервер» ни разу не приводит к выходу; «устройство не знакомо» всегда приводит к выходу и стиранию данных.
- **SC-006**: Дома напрямую соединение с проверкой устанавливается меньше чем за секунду; проверка добавляет к подключению один обмен двумя сообщениями.

## Assumptions

- Продукт не выпущен: совместимости со старыми серверами и сессиями нет.
- Встроенный tor сервера и ключи доступа Tor в этой фиче не меняются — их убирает 045; путь через Tor работает через модуль канала с теми же ключами доступа.
- Жизненный цикл ссылок (claim без срока, приглашения на 10 минут без подтверждения) до 046 остаётся прежним; меняется только формат.
- `/health` переезжает на служебный локальный порт: на основном порту до проверки не обслуживается ничего.
- Алгоритм технического сертификата не важен приложению.

## Out of Scope

- Отказ от встроенного tor и ключей доступа, адреса в базе, `Use Tor`, экран «Связь» (045).
- Подтверждение `Allow`/`Deny`, ссылка с машины на 10 минут, список устройств (046).
- Шифрование данных на диске (047, 048) и установка сервера (049).
- Открытие `nox://pair/` по нажатию (deep links).
- Постквантовая защита (вне рамок).
