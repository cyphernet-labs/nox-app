# Research: client-backend-chats-messages (фаза 023)

Решения Phase 0. Все «неизвестные» Technical Context закрыты; альтернативы перечислены с причиной отказа.

## R1. Поиск и пагинация `chats.list` — фильтрация в Go, не в SQL

**Decision**: store загружает строки чатов одним запросом `ORDER BY last_activity_at DESC, chat_id ASC` (без OFFSET), фильтрует по подстроке в Go (кейс-фолдинг обеих строк через `unicode.SimpleFold` — тот же фолдинг, что у уникальности имени) и нарезает страницу срезом; `has_more` — по наличию строки за границей страницы.

**Rationale**: юникод-регистронезависимость обязательна (SC-004, единообразно с уникальностью имени из 022) — SQL `LIKE`/`lower()` фолдят только ASCII. Масштаб (сотни чатов на ~10 пользователей) делает полное чтение таблицы дешевле любой индексной акробатики; правильность важнее микрооптимизации.

**Alternatives considered**: `LIKE` c `lower()` — ASCII-only, кириллический поиск ломается; FTS5 — лишняя сложность и словарь токенизации для подстрочного поиска не нужен; хранение `name_ci` + `LIKE` по нему — решает регистр, но не даёт стабильного потолка сложности лучше, чем фильтр в Go, и завязывает поиск на схему.

## R2. Стабильный порядок списка — tiebreaker `chat_id`

**Decision**: сортировка всегда `last_activity_at DESC, chat_id ASC`.

**Rationale**: у двух чатов может совпасть `last_activity_at` (секундная гранулярность); без детерминированного tiebreaker'а строки могут мигрировать между страницами (дубликат/пропуск при склейке). Клиент по контракту дедуплицирует по `chat_id`, но пропуск дедупликацией не лечится.

**Alternatives considered**: без tiebreaker'а — недетерминизм между страницами; `created_at` — тоже секундный, коллизии остаются.

## R3. `messages.list` — SQL-запрос с `LIMIT n+1` и разворотом

**Decision**: `SELECT … FROM messages WHERE chat_id = ? AND seq < ? ORDER BY seq DESC LIMIT ?+1` (при отсутствии `before_seq` — без предиката `seq <`), затем разворот в Go до возрастания `seq`; `has_more` = пришло больше `limit` строк. Обслуживается индексом `(chat_id, seq)` из 001.

**Rationale**: «хвост + листание назад» — это ровно чтение индекса с конца; `n+1`-паттерн даёт `has_more` без COUNT; разворот в Go — O(page) и держит порядок порции по возрастанию (решение владельца).

**Alternatives considered**: `ORDER BY seq ASC` c вычислением окна — требует подзапроса нижней границы; COUNT для `has_more` — второй запрос без выгоды.

## R4. `chat.rename` — мутация через writer с outbox и no-op веткой

**Decision**: одна immediate-транзакция: SELECT текущей строки (`not_found`), сравнение имени **после трима, точное** (совпало → вернуть текущую карточку, никакой записи, никакого события), проверка `name_ci` уникальности с `chat_id != ?` (`name_taken`), UPDATE `name`+`name_ci`, сборка полной wire-карточки, INSERT события `chat.updated` тем же паттерном, что `chat.created`. `last_activity_at` не трогается.

**Rationale**: инварианты 2–4 (writer, outbox, миллисекундные транзакции) — без исключений; точное сравнение — потому что смена регистра («Chat»→«chat») — легитимное переименование (уникальность исключает сам чат), а no-op — только буквально то же имя.

**Alternatives considered**: no-op с эмиссией события — растит журнал и будит всех клиентов впустую (отклонено владельцем); детекция no-op по `name_ci` — съела бы смену регистра.

## R5. `chat.nameAvailable` — read-пул, без транзакции

**Decision**: `SELECT COUNT(1) FROM chats WHERE name_ci = ? [AND chat_id != ?]` на read-пуле; валидация правил имени до запроса → `invalid_request`.

**Rationale**: подсказка при наборе — чтение без гарантий (гонку до фактического применения закрывает проверка внутри транзакции rename/create); read-пул не трогает writer.

**Alternatives considered**: резервирование имени — не нужно: авторитет всё равно транзакция мутации.

## R6. Клампинг и валидация пагинации — в обработчике

**Decision**: обработчик нормализует вход до вызова store: `page < 1` или `page_size < 1`/`limit < 1` → `invalid_request`; `page_size > 100`/`limit > 100` → молча 100 (решение владельца); store получает уже валидные значения.

**Rationale**: store остаётся чистым слоем данных; политика провода — забота адаптера конверта.

**Alternatives considered**: клампинг в store — размывает границу слоёв; отказ вместо клампинга — отклонено владельцем.

## R7. `chat.get` и общий скан строки чата

**Decision**: один разделяемый хелпер сканирования строки `chats` → `protocol.Chat`, используемый `chat.get`, страницами `chats.list` и `RenameChat`.

**Rationale**: одна точка соответствия колонок wire-модели — расхождение полей между командами исключено конструктивно.

## R8. `chat.updated` в существующем конвейере рассылки

**Decision**: новый тип события — константа `EventChatUpdated`; проходит через тот же outbox → диспетчер (порядок по `seq`) → hub → реплей. `eventEnvelope` отдаёт для него общий вариант кадра (Full == Stripped): `client_message_id`-логика касается только `message.new`.

**Rationale**: конвейер 022 типонезависим; событие с полной карточкой чата не содержит пер-адресатных полей.

**Alternatives considered**: отдельная ветка рассылки — нечего выделять.

## R9. Обязательность `body` в `message.send` (срез 023)

**Decision**: валидация 022 (`len(body) == 0` → `invalid_request`) сохраняется дословно; формулировка контракта «`body` опционален при наличии `attachment`» активируется в 024, когда появится `attachment`.

**Rationale**: до файловой фазы сообщение без тела невыразимо; ослаблять валидацию заранее — дыра.
