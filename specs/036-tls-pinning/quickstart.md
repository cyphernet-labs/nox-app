# Проверка фазы 036 — руками и тестами

## Стенд

```bash
./scripts/demo-stand.sh --reset-app
```

База **обязана** быть свежей, и на этой фазе сильнее обычного: ключ сервера меняет тип, и на старой базе сервер намеренно откажется подниматься (FR-020). Свежий стенд — это свежий ключ, а значит **все прежние ссылки мертвы** и все прежние спаривания недействительны.

Второй клиент — симулятор iOS, он делит сеть с хостом:

```bash
fvm flutter build ios --simulator --debug --dart-define-from-file=config/stage.json
xcrun simctl install booted build/ios/iphonesimulator/Runner.app
xcrun simctl launch booted com.cyphernetlabs.noxapp
```

## A. Канал закрыт — главная проверка (SC-001, SC-002)

Перехват **до** того, как приложение что-либо отправит:

```bash
sudo tcpdump -i lo0 -s0 -w /tmp/nox-036.pcap "tcp port 8080" &
```

Дальше: спарить macOS по claim-ссылке, спарить симулятор по приглашению, **отправить сообщение с узнаваемым текстом** (например `PLAINTEXT-CANARY-036`) и **отправить файл** с узнаваемым содержимым.

```bash
kill %1
strings /tmp/nox-036.pcap | grep -c "PLAINTEXT-CANARY-036"   # ожидается 0
strings /tmp/nox-036.pcap | grep -ci "user\|device_key\|nox/"  # ожидается 0
```

Файл проверяется отдельно и обязательно: его байты едут **вторым** транспортом, и до этой фазы они шли открытым текстом. Положить в файл строку-канарейку и поискать её тем же способом.

Ноль совпадений — канал закрыт. Любое совпадение означает, что один из двух транспортов остался снаружи.

## B. Подмена не проходит (SC-003)

Самая важная проверка фазы, и её нельзя получить, просто включив TLS: сервер со **стоковым** сертификатом докажет, что шифрование работает, и ничего не скажет про доверие.

1. Оставить спаренные устройства как есть.
2. Поднять **второй** сервер на другой базе (то есть с другим ключом) на том же порту, погасив первый:

```bash
./scripts/demo-stand.sh --reset-app --port 8080   # другой каталог базы, другой ключ
```

3. Смотреть на устройства: они **не подключаются**. Ни одно.

Это же и есть проверка того, что пиннинг настоящий: адрес прежний, TLS работает, а доверие не перенеслось.

## C. Отказ читается (SC-006, SC-007)

На том же подменённом сервере, не уходя с экрана:

- в списке чатов, в треде и в карточке чата стоит плашка, которая говорит про **сервер**, а не про сеть;
- приложение **перестаёт звонить** — в логе сервера нет потока попыток подключения;
- переписка на месте: ни одно сообщение не исчезло, из аккаунта никто не вышел;
- письма, отправленные при подменённом сервере, стоят в очереди как ожидающие, а **не** помечены ошибкой;
- у плашки есть повтор.

Затем вернуть настоящий сервер и **нажать повтор**: связь возвращается без перезапуска приложения. Если для возврата пришлось убить приложение — FR-011a не выполнено.

## D. Терпимость (SC-005)

Три случая, каждый — сертификат на **верном** ключе, и каждый должен **приниматься**:

- просроченный (`NotAfter` в прошлом);
- с чужим именем в SAN/CN;
- от неизвестного издателя.

Проверяется не на стенде, а тестом клиента (`test/general/pairing/server_pin_test.dart`) — на стенде их неудобно получить, а пропустить нельзя: реализация, отказывающая по сроку, пройдёт все отрицательные проверки и сломается у первого человека, забывшего про свой сервер.

## E. Служебная страница (SC-009)

```bash
curl -s http://127.0.0.1:<status-port>/ | head -3
```

Отвечает по-прежнему: без сертификата, без предупреждений, без `-k`. Она на loopback, и трафика по сети у неё нет.

## Что считается несделанным

- В перехвате нашёлся текст сообщения **или** байт файла.
- Устройство подключилось к серверу с другим ключом.
- Отказ выглядит как «нет связи».
- После отказа приложение продолжает звонить.
- После отказа что-то стёрлось или человека вывело из аккаунта.
- Из отказа нет пути назад, кроме перезапуска приложения.
- Просроченный сертификат на верном ключе отвергнут.
