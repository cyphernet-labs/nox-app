# Проверка фазы 036 — руками и тестами

## Стенд

```bash
./scripts/demo-stand.sh --reset-app
```

База **обязана** быть свежей, и на этой фазе сильнее обычного: ключ сервера меняет тип, и на старой базе сервер намеренно откажется подниматься (FR-020). Свежий стенд — это свежий ключ, а значит **все прежние ссылки мертвы** и все прежние спаривания недействительны.

Второй клиент — симулятор iOS, он делит сеть с хостом:

```bash
fvm flutter build ios --simulator --debug --dart-define-from-file=config/stage.json
xcrun simctl install booted build/ios/iphonesimulator/Runner.app
xcrun simctl launch booted com.cyphernetlabs.noxapp
```

## A. Канал закрыт — главная проверка (SC-001, SC-002)

Перехват **до** того, как приложение что-либо отправит:

```bash
sudo tcpdump -i lo0 -s0 -w /tmp/nox-036.pcap "tcp port 8080" &
```

Дальше: спарить macOS по claim-ссылке, спарить симулятор по приглашению, **отправить сообщение с узнаваемым текстом** (например `PLAINTEXT-CANARY-036`) и **отправить файл** с узнаваемым содержимым.

```bash
kill %1
strings /tmp/nox-036.pcap | grep -c "PLAINTEXT-CANARY-036"   # ожидается 0
strings /tmp/nox-036.pcap | grep -ci "user\|device_key\|nox/"  # ожидается 0
```

Файл проверяется отдельно и обязательно: его байты едут **вторым** транспортом, и до этой фазы они шли открытым текстом. Положить в файл строку-канарейку и поискать её тем же способом.

Ноль совпадений — канал закрыт. Любое совпадение означает, что один из двух транспортов остался снаружи.

## B. Подмена не проходит (SC-003)

Самая важная проверка фазы, и её нельзя получить, просто включив TLS: сервер со **стоковым** сертификатом докажет, что шифрование работает, и ничего не скажет про доверие. Нужен другой **ключ** по тому же адресу — то есть вторая база.

**`--reset-app` здесь запрещён.** Он стирает контейнер приложения и записи keychain, то есть рас-паривает ровно те устройства, чью реакцию мы смотрим. И первый стенд сносить нельзя: к нему возвращается §C.

1. Остановить стенд A, оставив его базу на месте.
2. Поднять стенд B на **другом каталоге базы** и том же порту — другой каталог означает другой ключ:

```bash
./scripts/demo-stand.sh --stand /tmp/nox-demo-mitm     # без --reset-app, порт тот же
```

3. Смотреть на устройства: они **не подключаются**. Ни одно.

Адрес прежний, TLS работает, а доверие не перенеслось — это и есть доказательство, что пиннинг настоящий, а не «включён TLS».

## C. Отказ читается (SC-006, SC-007, SC-007a, SC-007b)

На том же подменённом сервере, не уходя с экрана:

- в списке чатов, в треде и в карточке чата стоит плашка, которая говорит про **сервер**, а не про сеть;
- приложение **перестаёт звонить** — в логе сервера нет потока попыток подключения;
- переписка на месте: ни одно сообщение не исчезло, из аккаунта никто не вышел;
- письма, отправленные при подменённом сервере, стоят в очереди как ожидающие, а **не** помечены ошибкой;
- у плашки есть повтор.

Затем остановить стенд B, поднять обратно стенд A на его прежней базе (`./scripts/demo-stand.sh --stand /tmp/nox-demo`, снова **без** `--reset-app`) и **нажать повтор** на плашке: связь возвращается без перезапуска приложения. Если для возврата пришлось убить приложение — FR-011b не выполнено.

## D. Терпимость (SC-005)

Три случая, каждый — сертификат на **верном** ключе, и каждый должен **приниматься**: просроченный, с чужим именем в SAN/CN, от неизвестного издателя.

Проверяется не на стенде и **не на уровне чистой функции**: функция над `cert.der` имени, срока и издателя структурно не видит, поэтому тест на её уровне не может упасть и ничего не доказывает. Проверка живёт на уровне колбэка — локальный `HttpServer` с таким сертификатом, и соединение должно состояться (`test/data/remote/socket/`).

Пропустить нельзя: реализация, отказывающая по сроку, пройдёт все отрицательные проверки и сломается у первого человека, забывшего про свой сервер.

## E. Служебная страница (SC-009)

```bash
curl -s http://127.0.0.1:<status-port>/ | head -3
```

Отвечает по-прежнему: без сертификата, без предупреждений, без `-k`. Она на loopback, и трафика по сети у неё нет.

## G. Перевыпуск сертификата (SC-004)

Сертификат пересобирается при каждом запуске, поэтому проверка дешёвая и обязательная — иначе «доверие держится на ключе» остаётся словами.

1. Перезапустить стенд A **на той же базе** (без `--reset-app`, без смены каталога).
2. Оба устройства подключаются сами, без пере-спаривания и без единого действия человека.


Отдельно — живые пробники, исключённые из гейта по тегу; им нужен отпечаток, потому что они не спариваются:

```bash
fvm flutter test --tags live \
  --dart-define=address=127.0.0.1:8080 \
  --dart-define=pin=<отпечаток из ссылки>
```

Все четыре пробника должны нести `@Tags(['live'])` — сегодня тег есть только у одного, и без правки команда до остальных трёх не доходит.

## Платформы

§A прогоняется вживую на **macOS и симуляторе iOS**: оба делят с хостом интерфейс `lo0`, поэтому один `tcpdump` видит обе стороны. Windows и Linux проверяются сборкой (`mise run build:windows:stage`, `mise run build:linux:stage`) — интерактивного раннера для них в проекте нет, по той же причине, по которой отложены P15 и P17.

## Что считается несделанным

- В перехвате нашёлся текст сообщения **или** байт файла.
- Устройство подключилось к серверу с другим ключом.
- Отказ выглядит как «нет связи».
- После отказа приложение продолжает звонить.
- После отказа что-то стёрлось или человека вывело из аккаунта.
- Из отказа нет пути назад, кроме перезапуска приложения.
- Просроченный сертификат на верном ключе отвергнут.
- После перезапуска сервера устройство потребовало пере-спаривания.
