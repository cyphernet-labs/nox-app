# Правки контракта v0 — фаза 033

Выдержка того, что должно быть внесено в `docs/client-backend/protocol/contract-draft.md` **до** написания кода (Принцип VII, FR-017). Здесь — форма и правила; сам контракт остаётся единственным авторитетом.

## 1. Поле `owner` в объекте `identity`

Объект `identity` уже едет в двух местах — в ответе на приветствие (§3) и в ответе на `pair` (§8A). Поле добавляется в **оба**, одинаково.

### Ответ на приветствие (§3)

```json
{"id": 1, "ok": true, "data": {
  "schema": 1,
  "cursor": 1042,
  "journal_id": "j_7c1e4a90b3d2f6a1",
  "limits": {"max_message_bytes": 65536, "max_attachment_bytes": 104857600, "max_frame_bytes": 131072},
  "identity": {"id": "u_3f2a1c9d40b7e518", "label": "User7421", "owner": true}
}}
```

### Ответ на `pair` (§8A)

```json
{"id": 1, "ok": true, "data": {
  "identity": {"id": "u_3f2a1c9d40b7e518", "label": "User7421", "created": true, "owner": true}
}}
```

## 2. Правила поля

- **`owner` отвечает на вопрос «владеет ли сервером ТОТ, КТО СПРАШИВАЕТ»** — не «есть ли у сервера владелец» и не «кто он». Идентификатор владельца на провод не уходит: правила владения проверяет сервер, а статусная страница (фаза 035) читает хранилище напрямую.
- **Поле описывает ЛИЧНОСТЬ, а не соединение и не устройство.** Все устройства одного человека получают одинаковое значение.
- **Поле присутствует ВСЕГДА**, в том числе со значением `false`. Опускать его нельзя: пропавшее `false` читается как «не заявлено», а не как «нет» — тот же урок, что с `created` в фазе 032.
- **Отличие от `created`:** `created` описывает **ответ** (что сделала именно эта операция) и потому осмыслен только в ответе на `pair`; `owner` описывает **личность** и потому одинаков в любом ответе про одного и того же человека.
- **Клиент не выводит владение сам.** Ни из того, что этот аппарат предъявлял claim-ссылку, ни из порядка появления. Сервер — единственный источник.

## 3. Правило «сервер забран»

Формулировка §8A, где сегодня описан отказ claim-токена, уточняется:

> **«Сервер забран» значит «у него есть владелец».** Отдельной отметки, по которой принимается это решение, не существует: владелец записан у машины, и его наличие — единственное определение. Момент, когда машину забрали, сервер помнит отдельно, но ни одно правило на него не смотрит.

Действующие правила фазы 032 при этом **не меняются**:

- claim отвергается, если сервер забран **и** у него есть хотя бы одно живое устройство;
- сервер, потерявший все устройства, снова принимает claim и **переприсоединяет** к существующей личности — она остаётся владельцем, второй не появляется;
- повтор одного и того же токена тем же ключом — успех с тем же ответом.

## 4. Что НЕ меняется

- **`device.list`** — без изменений. Команда возвращает устройства одного человека, поэтому признак владения был бы одинаков во всех строках и не нёс бы информации. Вопрос возвращается в фазу 034, где на сервере появится несколько людей.
- **Событие `identity.updated`** — без изменений. Оно несёт имя; владение по нему не меняется и меняться не может.
- **Коды отказов** — новых не появляется. Фаза 033 только называет владельца; запрещать что-либо не владельцу начинает фаза 034.

## 5. Совместимость

Номер схемы **не поднимается**. Развёрнутых установок нет, а поле аддитивное: клиент, не знающий о нём, по правилу §2 игнорирует незнакомые поля входящих кадров. Клиент, знающий о нём, но получивший кадр без него, читает «не заявлено» и отметку не рисует — это и есть корректное поведение против сервера прошлой фазы.
