## Phase 3: US1 — скриншот доходит картинкой (P1) 🎯 MVP

**Независимая проверка**: прикрепить изображение на одном клиенте, отправить, увидеть картинкой на другом; открыть и сохранить.

- [ ] T012 [US1] Убрать отказ вложения в `real_message_remote_data_source.dart`; `message.send` отправляет `attachment: {file_id}`
- [ ] T012a [US1] Дать `fileId` дорогу до провода: сегодня `MessageRepository.sendMessage` и `MessageRemoteDataSource.sendMessage` принимают `MessageAttachment`, у которой `id` — идентификатор **локального черновика**. После загрузки `id` становится серверным идентификатором файла; зафиксировать это в доккомментарии модели, иначе следующий читатель решит, что поле значит что-то одно
- [ ] T013 [US1] Добавить `fileId` в `OutboxEntity`/`OutboxEntry`/`OutboxMapper` (необязательное поле — записи фазы 027 обязаны читаться)
- [ ] T013a [US1] Добавить в `OutboxRepository` способ **записать подтверждённый** `fileId`: сегодня интерфейс умеет только `recordFailure`/`markPending`/`remove`, и сливу нечем сохранить результат загрузки. Запись — через транзакционный `updateIfPresent`, как и всё остальное в этом store
- [ ] T014 [US1] Слив очереди: если у записи есть локальный путь и нет `fileId` — заявка, передача байтов, **запомнить `fileId` только после подтверждения**, затем отправка
- [ ] T014a [US1] Перечитать запись **после** передачи байтов и перед отправкой: фаза 027 завела эту проверку ради отмены, а загрузка растягивает окно с миллисекунд до минут — без повторной проверки отменённое сообщение уйдёт
- [ ] T014b [US1] Пропавший или изменившийся на диске файл: внятный отказ по **этому** сообщению, проход идёт дальше — одно негодное вложение не держит очередь
- [ ] T014c [US1] Протухшая загрузка: сервер вычищает непривязанные байты через сутки, после чего отправка получает `invalid_request`. Такая запись начинает цепочку заново, а не умирает окончательно
- [ ] T015 [US1] Автоподтягивание **изображений** при появлении сообщения; скачанный путь ложится в `localPath` вложения — то же поле, на которое смотрят миниатюра и сохранение
- [ ] T015a [US1] Дать этому пути писателя: сегодня ни `MessageRepository`, ни `MessageDao` не умеют обновить вложение у сохранённого сообщения. Без него скачанный путь некуда положить
- [ ] T015c [US1] `FileRepository.clean()` входит в вайп логаута рядом с очередью — **в этой же фазе**, а не позже: приращение, которое начинает скачивать картинки, не имеет права оставлять их после выхода
- [ ] T015b [US1] Защита от повторного входа: тред перечитывает и перерисовывает на каждый тик `watchMessages`, а запись `localPath` порождает новый тик. Скачивание должно запускаться один раз на файл, иначе получится цикл
- [ ] T016 [US1] Прочие типы — по нажатию; `FileViewPage` переводится с `AnimationController` на настоящий ход загрузки
- [ ] T016a [US1] **`FileViewPage` получает свой Freezed-BLoC.** Блюпринт 05 §5 заканчивает карв-аут «экран без BLoC» дословно этой фазой: «как только к экрану подключается реальный репозиторий/async (клиентский трек 025–028), он получает свой Freezed-BLoC». Не отложенный долг, а часть работы
- [ ] T016b [US1] Маршруты отказов — **по спеке 5.3**, а не изобретённые: «файл удалён сервером» — fatal, передача на универсальный экран 3.1; сетевой сбой — сообщение с повтором (`fileDownloadError` уже есть)
- [ ] T016c [US1] Обновить существующие тесты экрана файла: голден-тест опирается на то, что фиктивный таймер в 1000 мс успевает завершиться при `settle: true`, а виджет-тесты строят страницу без DI. Настоящая загрузка это ломает — тесты правятся вместе с экраном, а не после
- [ ] T017 [P] [US1] Тест датасорса: `mime` из расширения, точный размер, относительные адреса
- [ ] T018 [P] [US1] Тест репозитория: идентификатор возвращается только после подтверждения; превышение предела отсекается до передачи
- [ ] T019 [US1] Тест слива: запись с локальным путём проходит все три шага в правильном порядке

**Контрольная точка**: сценарии 1 и 2 quickstart проходят.
