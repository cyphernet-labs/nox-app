# Quickstart: client-files

Как убедиться, что фаза действительно работает. Первые сценарии — на живом сервере, последний — гейт.

## Предпосылки

```bash
cd client_backend && go build -o /tmp/nox-demo/noxd .
/tmp/nox-demo/noxd -addr 127.0.0.1:8080 -db /tmp/nox-demo/demo.db
```

Два клиента: `fvm flutter run -d macos --dart-define-from-file=config/stage.json` и то же самое на симуляторе. Вход под разными идентификаторами, чтобы имена различались.

## Сценарий 1 — скриншот доходит картинкой (US1, SC-001)

1. На клиенте 1 создать чат и прикрепить изображение (скрепка в композере).
2. Отправить.
3. Ожидаемо: у клиента 2 сообщение появляется **картинкой прямо в переписке**, а не строкой с именем файла. Никаких действий с его стороны.
4. Нажать на картинку — открывается во весь экран. Сохранить — файл ложится на диск.

## Сценарий 2 — не-изображение ждёт нажатия (US1)

1. Отправить PDF или архив.
2. Ожидаемо: у клиента 2 чип с именем, размером и иконкой типа. Байтов ещё нет.
3. Нажать — идёт настоящая загрузка с настоящим ходом индикатора, затем файл доступен.

## Сценарий 3 — вложение переживает перезапуск (US2, SC-002/SC-003)

1. **Остановить сервер.**
2. На клиенте 1 прикрепить файл и отправить — висит неотправленным.
3. **Закрыть приложение целиком**, запустить заново, открыть тот же чат: вложение на месте.
4. Поднять сервер. Ожидаемо: уходит само, у клиента 2 появляется один раз.

Проверка «не перезалилось»: в логе сервера на это сообщение должен быть **один** `file.uploadBegin`, а не два. Если байты успели уйти до падения — ни одного нового.

## Сценарий 4 — слишком большой файл (SC-005)

1. Прикрепить файл больше объявленного предела.
2. Ожидаемо: отказ **в момент прикрепления**, пока человек ещё смотрит на экран. В логе сервера нет ни `uploadBegin`, ни `PUT`.
3. Проверить и офлайн: при выключенном сервере отказ должен прийти так же сразу — предел известен из последнего приветствия, спрашивать сервер не нужно.

## Сценарий 5 — файла больше нет (US3, SC-006)

1. Отправить файл, дождаться получения на клиенте 2, но **не** открывать.
2. Остановить сервер, удалить каталог байтов (`rm -rf /tmp/nox-demo/demo.db-files`), поднять снова.
3. На клиенте 2 нажать на вложение. Ожидаемо: **универсальный экран ошибки** — именно туда спека 5.3 относит «файл удалён сервером». Не вечный индикатор и не предложение повторять.
4. Отдельно проверить сетевой сбой: оборвать связь во время скачивания. Ожидаемо: сообщение с повтором, а не fatal — это разные исходы, и спека разводит их намеренно.

## Сценарий 6 — отмена во время передачи (FR-013)

1. Прикрепить крупный файл и отправить, чтобы передача заняла заметное время.
2. Пока она идёт — убрать сообщение долгим нажатием.
3. Ожидаемо: сообщение **не** появляется у собеседника, даже если байты успели уйти. Осиротевшие байты вычистит сервер.

## Сценарий 7 — выход из аккаунта не оставляет картинок (FR-012)

1. Получить и открыть изображение (значит, байты на устройстве).
2. Settings → Log out.
3. Ожидаемо: кэш скачанного пуст.

## Гейт (SC-007)

```bash
make gate           # generate → format → analyze → test
make golden-verify  # 216 эталонов, без перегенерации
```

Оба обязаны быть зелёными **до** коммита: CI на паузе, и это единственное место, где ловится регресс. `golden-verify` здесь несёт отдельный смысл — фаза не имеет права изменить ни один пиксель, а перегенерация эталонов вместо починки была бы подменой проверки.

## Живая проба

`test/live/live_files_probe.dart` — как и её сёстры, названа без суффикса `_test`, чтобы набор её не собирал:

```bash
fvm flutter test test/live/live_files_probe.dart
```

Гоняет настоящую цепочку против запущенного `noxd`: заявка, передача байтов, отправка сообщения со ссылкой на файл, скачивание обратно и **побайтовое сравнение** с исходником. Это единственный способ проверить то, что принадлежит серверу: что вернулись ровно те байты, которые ушли.
