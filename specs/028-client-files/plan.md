# Implementation Plan: client-files

**Branch**: `028-client-files` | **Date**: 2026-09-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/028-client-files/spec.md`

## Summary

Последнее, что клиент задолжал по проводу: вложения ходят через сервер в обе стороны. Сегодня приложение отклоняет вложение **у себя** — `RealMessageRemoteDataSource` возвращает `invalid_request`, потому что `message.send` требует `file_id`, а выдать его может только файловая цепочка, которой на клиенте нет.

Серверная половина готова и проверена вживую сегодня: `file.uploadBegin` вернул идентификатор и токен, `PUT` байтов ответил `204`, `file.downloadBegin` вернул адрес для скачивания. Строится ровно клиентская половина.

Главное решение фазы — **где живёт загрузка**. Она уходит внутрь слива очереди, а не в момент прикрепления: иначе прикрепить файл офлайн станет нельзя, и обещание фазы 027 сломается ровно на том случае, ради которого очередь делалась.

## Technical Context

**Language/Version**: Dart / Flutter 3.44.1 (FVM-pinned), пакет `nox_app`

**Primary Dependencies**: `web_socket_channel` (заявки), `dio` (байты — первый реальный потребитель `ApiClient`), sembast (память о загруженном), `path_provider` (каталог кэша)

**Storage**: существующий store `outbox` получает поле `fileId`; скачанные байты — файлы в каталоге кэша, не в базе

**Testing**: `flutter_test` + `mockito`; гейт `make gate`, снимки `make golden-verify`; живая проба против `noxd`

**Target Platform**: iOS / Android / macOS / Windows / Linux, обе ширины

**Project Type**: mobile+desktop Flutter app, Clean Architecture слоями-папками

**Performance Goals**: байты не по сокету — большой файл не задерживает интерактивные команды; предел размера проверяется до передачи

**Constraints**: ни одного нового экрана. Две новые строки: «файл больше предела» и «байтов больше нет» — обе сказать сегодня нечем, а `fileDownloadError` для второй не годится, потому что зовёт повторить. Эталоны экрана файла пересматриваются осознанно: его содержимое перестаёт быть фиктивным

**Scale/Scope**: один датасорс, один репозиторий, правка слива очереди, правка двух мест отрисовки

## Design decisions

### Три шага, из которых идемпотентен только последний

Отправка вложения — это `uploadBegin` → передача байтов → `message.send`. Ключ идемпотентности защищает **только третий шаг**. Первые два защищать нечем: пропуск одноразовый, а повторная заявка даёт новый идентификатор файла.

Отсюда конструкция: запись очереди помнит `fileId`, но **только после подтверждённой передачи байтов**. Тогда состояния читаются однозначно:

| Что в записи | Что делает слив |
|---|---|
| локальный путь, `fileId` пуст | заявка → байты → запомнить `fileId` → отправить |
| локальный путь и `fileId` | сразу отправить: байты уже там |
| ни того, ни другого | обычная текстовая отправка |

Падение в любой точке возобновляется с начала соответствующей строки, и ни одно из возобновлений не создаёт второй копии сообщения.

### Почему `fileId` не пишется сразу после заявки

Записать его раньше подтверждения — значит после неудачной передачи сослаться в сообщении на файл, байтов у которого нет. Сервер такое сообщение примет (идентификатор существует), а получатель увидит вечно не скачивающееся вложение. Подтверждение — единственный момент, когда `fileId` становится правдой.

### Передача байтов задерживает очередь — и это принято сознательно

Очередь одна на все чаты, идёт строго по одному, а повторяемый отказ головы останавливает проход целиком. Значит передача большого файла задерживает **все** сообщения во **всех** чатах, пока не закончится.

Принимается как есть, по двум причинам. Во-первых, порядок постановки — обещание фазы 027, данное всему пространству, а не отдельному чату; параллельная передача разошлась бы с ним. Во-вторых, лечение хуже болезни: отдельная дорожка для файлов вернула бы второго отправителя, единственность которого 027 и защищала. Смягчение есть и оно дешёвое — предел размера проверяется при прикреплении, так что заведомо неподъёмный файл в очередь не попадает вовсе.

Пересмотреть стоит, если появятся большие файлы на плохой связи; тогда это отдельная работа с докачкой, а не оговорка внутри этой.

### Отмена во время передачи

Фаза 027 завела перечитывание записи **непосредственно перед отправкой** именно затем, чтобы отменённое не ушло. Загрузка растягивает это окно с миллисекунд до секунд и минут, поэтому проверка нужна и **после** передачи байтов, перед самой отправкой. Байты при этом останутся на сервере осиротевшими — их вычистит сам сервер; важно, что сообщения не будет.

### Скачивание

Изображение подтягивается автоматически, когда сообщение появляется; прочие типы — по нажатию. Байты ложатся в каталог кэша под именем идентификатора, а путь пишется в `localPath` вложения — то самое поле, на которое уже смотрят и миниатюра, и сохранение. Так у вопроса «где лежит файл» остаётся один ответ, а не два.

### Что делает индикатор

Экран 5.3 сегодня крутит `AnimationController` на 1000 мс — фиктивную загрузку из UI-фазы. Он переводится на настоящий ход передачи. Это не новый экран и не новое состояние: тот же индикатор, наполненный правдой.
