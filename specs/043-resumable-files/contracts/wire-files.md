# Contract: файлы с продолжением — дельта §7 контракта v0

Источник истины после слияния — `docs/client-backend/protocol/contract-draft.md`. Этот файл описывает, что в нём меняется: §1 (таблица REST), §7 и §9 п. 6. Номер схемы не поднимается: расширение идёт по правилу эволюции §2.1.

## `file.uploadBegin` — по сокету

| | `data` |
|---|---|
| запрос | `{name, size, mime, file_id?}` |
| ответ | `{file_id, upload_url, upload_token, max_attachment_bytes, received}` |

- **`file_id`** (необязательное) — продолжить незаконченную загрузку этого файла. `name`, `size` и `mime` присылаются те же, что при объявлении: сервер, не знающий продолжения, поле пропускает и заводит новый файл, так что запрос обязан оставаться полным объявлением.
- **`received`** — сколько первых байтов файла сервер хранит надёжно. Для новой загрузки — `0`, для уже загруженного файла — `size`. Сервер 043 и новее присылает его всегда. **Наличие поля — признак поддержки продолжения**: ответ без него значит, что сервер продолжать не умеет, и `PUT` несёт весь файл.
- **Отказы продолжения:**
  - `not_found` — незаконченной загрузки с таким `file_id` нет: не было, вычищена (§7, сутки) или уже привязана к сообщению. Клиент начинает новую загрузку; это не ошибка для человека.
  - `invalid_request` — `name`, `size` или `mime` не совпадают с объявленными.
  - `internal` — прежняя попытка не отпустила файл за 5 секунд.
- Прочие правила прежние: длины полей, `payload_too_large`, лимит из приветствия.

```json
{"id": 41, "cmd": "file.uploadBegin", "data": {"name": "trip.mp4", "size": 83886080, "mime": "video/mp4", "file_id": "f_77"}}
{"id": 41, "ok": true, "data": {"file_id": "f_77", "upload_url": "/files/9c1f…", "upload_token": "9c1f…",
                                "max_attachment_bytes": 104857600, "received": 37748736}}
```

## `PUT /files/{upload_token}` — байты

Тело — байты файла **от `received` до конца**: `Content-Length = size − received`. Остаток может быть пустым. Токен помнит смещение, под которое выдан. Всё, что пришло, сервер сохраняет — и при обрыве тоже: следующая попытка спрашивает `received` заново и шлёт только остальное.

| Код | Когда |
|---|---|
| `204` | файл целиком на сервере. Пустой `PUT` на уже загруженный файл — тоже `204` |
| `404` | любой отказ токена, как прежде; надёжно хранимое начало короче смещения токена |
| `408` | байты не шли дольше 60 секунд; пришедшее сохранено |
| `409` | прежняя попытка не отпустила файл за 5 секунд; повторить позже |
| `413` | байтов больше остатка; пришедшее этим запросом не сохраняется |
| `400` | тело кончилось раньше остатка без обрыва соединения; пришедшее сохранено |

Пишет в файл одна попытка. Новый `PUT` и продолжение `file.uploadBegin` прерывают прежнюю, не дожидаясь её конца.

## `GET /files/{download_token}` — байты

Без изменений по форме: `Range` и условные заголовки (`http.ServeContent`). Правило докачки фиксируется:
- **продолжение** — `Range: bytes=<сколько есть>-` плюс `If-Range: <Last-Modified первого ответа>`;
- **`206`** — остаток. Начало и общий размер — в `Content-Range`;
- **`200`** — файл на сервере не тот, с которого шло скачивание: принятое выбрасывается, тело идёт с начала;
- **`416`** — у клиента не меньше, чем есть на сервере: принятое выбрасывается.

## Время

Предела на всю передачу нет ни в одну сторону. Сервер обрывает загрузку или скачивание только при **застое**: байты не шли дольше 60 секунд. Срок токена (10 минут) проверяется в начале запроса и идущую передачу не обрывает.

## Хранение незаконченного

Незаконченная загрузка живёт по правилу прежних непривязанных загрузок: строка и байты, не привязанные к сообщению за сутки, зачищаются при старте сервера.

## §9 п. 6 — дополнение

Пока байты не подтверждены, в записи очереди хранится не `file_id` для `message.send`, а **ручка продолжения**: `file_id` незаконченной загрузки и слепок исходного файла (размер, время изменения). С ней перезапуск продолжает загрузку, а не начинает её заново. `file_id` для `message.send` по-прежнему пишется только после `204`.
