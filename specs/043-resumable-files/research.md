# Research: Файлы с докачкой — большой файл доходит и через Tor

## 0. Что мешает продолжению сегодня

**Сервер:**
- Токен загрузки гасится до первого байта, а `file.uploadBegin` не принимает `file_id` — каждый вызов заводит новый файл. На уже загруженный файл `PUT` отвечает `404`.
- Любой обрыв вызывает `Abort()`, который удаляет `<id>.part`. `Create` его обнуляет. Сколько байтов пришло, сервер не помнит — есть только флаг `uploaded`.
- `PUT` обязан принести весь заявленный размер одним запросом; `Content-Range` нигде нет.
- `transferTimeout = 15 мин` — абсолютный срок на всё тело (и на чтение, и на запись), а не на простой. 100 MiB обрываются на любой скорости ниже ~0,93 Мбит/с.
- `GET` уже отдаёт `Range` через `http.ServeContent`: `206`, `416`, `Last-Modified`; `ETag` нет, поэтому `If-Range` работает по дате.

**Приложение:**
- Недокачанное удаляется в трёх местах: остаток `.part` — перед скачиванием; Dio по умолчанию — `deleteOnError: true` и `FileMode.write`; репозиторий — после любого `FileTransferException`.
- `Range` не отправляется никогда.
- Загрузка всегда идёт с нулевого байта под новым `uploadBegin`. После перезапуска, пока `fileId == null`, — тоже с нуля.
- `CancelToken` нет нигде.
- `receiveTimeout` Dio (30 с) — пауза между кусками при скачивании, но для `PUT` это 30 с на ответ после последнего байта. `sendTimeout` нет вовсе.
- Отказы сервера на загрузке не упираются в предел: `_uploadFor` не считает `exhausted`, в отличие от `message.send`.
- Экран 5.3 на любой сетевой ошибке показывает `Try again`. Путь в сообщение записывает обработчик закрытого блока — работает случайно.

## 1. Провод: необязательное `file_id` в `file.uploadBegin` и `received` в ответе

**Решение.** Запрос — `{name, size, mime, file_id?}`. С `file_id` это продолжение незаконченной загрузки этого файла. Ответ сервера 043+ всегда несёт `received` — сколько первых байтов файла сервер хранит надёжно: `0` для новой загрузки, `size` для уже загруженной. Наличие `received` — признак поддержки продолжения.

Ответы на продолжение:
- `not_found` — незаконченной загрузки с таким id нет: не было, вычищена, уже привязана к сообщению. Приложение начинает новую без ошибки (FR-004).
- `invalid_request` — `name`, `size` или `mime` не совпадают с объявленными: продолжение названо не тем файлом.

**Почему.** Правило эволюции §2.1: необязательное поле существующей команды признака не требует, незнакомое поле сервер пропускает. Сработало ли оно, клиент видит по ответу. Старый сервер вернёт новый `file_id` без `received`, и приложение загрузит файл целиком, как сегодня (FR-005). Управление остаётся в сокете, где ему и место; HTTP по-прежнему возит только байты.

**Отвергнуто:**
- Новая команда `file.uploadStatus` — новая команда допустима только за признаком поддержки (§2.1), а сведения те же.
- tus или IETF resumable uploads (`PATCH` + `HEAD` + `Upload-Offset`) — второй протокол управления рядом с сокетом; `HEAD` к тому же гасил бы одноразовый токен, поэтому сегодня он запрещён (`405`).
- `Content-Range` на `PUT` — RFC 9110 требует от сервера отвечать на такой `PUT` `400`, а смещение и так известно обеим сторонам из ответа.

## 2. `PUT` несёт остаток; смещение привязано к токену

**Решение.** Токен, выданный `uploadBegin`, помнит смещение `received`. `PUT /files/<токен>` несёт байты от него до конца: `Content-Length = size − received`, это может быть и `0`. Сервер дописывает их в часть. Ответы:

| Код | Когда | Что делает приложение |
|---|---|---|
| `204` | файл целиком на сервере (пустой `PUT` на уже загруженный файл — тоже `204`) | загрузка кончилась |
| `404` | отказ токена (как сегодня); надёжно сохранённое начало короче смещения токена | просит новый токен один раз, потом — отказ |
| `409` | прежняя попытка не отпустила файл за 5 с | повтор позже, отказом не считается |
| `413` | байтов больше остатка; пришедшее этим запросом отброшено | окончательно |
| `400` | тело кончилось чисто, но короче остатка; пришедшее сохранено | окончательно (это ошибка клиента) |
| `408` | застой дольше предела (§5); пришедшее сохранено | повтор с продолжением |

Пустой `PUT` (`received == size`) — единственный путь к завершению. Он переименовывает часть, если сбой случился между последним байтом и переименованием, и отвечает `204`, если файл уже загружен. Поэтому у приложения нет особого случая: оно всегда отправляет `PUT` с остатком.

**Почему.** Смещение, которое приложение получило в ответе, и есть начало тела, так что заголовок, повторяющий его, не нужен. Сервер всё равно сверяет: перед записью часть обрезается до смещения токена. Байты после него — те же байты того же файла, и приложение пришлёт их снова.

**Почему не «части фиксированного размера по своему токену».** Каждая часть стоила бы круга по сокету — через Tor это секунды. Оборванная часть терялась бы целиком, а тело, которое сервер сохраняет по мере прихода, теряет только бывшее в пути (SC-002). «Загрузка частями» из решения владельца выполняется буквально: файл приходит частями между обрывами, и каждая продолжает предыдущую.

## 3. Надёжность части на сервере: `<id>.synced`

**Решение.** Пакет `blob` ведёт рядом с `<id>.part` файл `<id>.synced` — сколько первых байтов части уже на устойчивом носителе.
- **Точка сохранения**: `fsync` части, затем атомарная запись длины (временный файл + переименование). Она ставится каждые 4 MiB и в конце каждого запроса — и удачного, и оборванного, и прерванного.
- **`Received(id)`** — `min(synced, размер части)`; нет `<id>.synced` — `0`.
- **`Resume(id, offset)`** отказывает, если надёжно сохранено меньше `offset`. Иначе он опускает `<id>.synced` до `offset`, если тот больше, потом обрезает часть до `offset` и пишет дальше. У новой загрузки (`offset` 0, части нет) записывать нечего: `<id>.synced` появляется при первой точке сохранения.
- **`Finalize`** — `fsync`, переименование, удаление `<id>.synced`.
- **`Abort` и `Remove`** убирают и его.

**Почему.**
- Размер файла говорит, сколько записано, а не сколько надёжно. После сбоя питания хвост части может оказаться нулями или старыми блоками. Сервер принял бы его как полученное, и приложение никогда не прислало бы эти байты снова — в файле посредине был бы мусор.
- Длина ниже реальной лишь заставляет переслать немного байтов. Поэтому любая сохранившаяся версия `<id>.synced` безопасна: значение только растёт и всегда не больше надёжного.
- При обрезке назад длина опускается **до** первой новой записи. Иначе после сбоя старая длина подтвердила бы новые, ещё не сохранённые байты.
- Шаг 4 MiB: при сбое теряется не больше 4 MiB — через Tor около 2 мин передачи. 25 `fsync` на 100 MiB по локальной сети почти ничего не стоят.

**Отвергнуто:**
- Колонка `received` в `files` — правило «до релиза одна миграция» заставило бы пересоздать каждую базу разработки и стенд владельца (см. Complexity Tracking плана).
- Доверять размеру части — молчаливая порча при сбое.

## 4. Один писатель на файл: прежний `PUT` прерывается

**Решение.** На сервере есть реестр писателей (`writers.go`, мьютекс), id файла → активный `PUT`. И продолжение `uploadBegin`, и `PUT` первым делом прерывают прежнего писателя этого файла:
- **прерывание** сразу будит его чтение: `ResponseController.SetReadDeadline(now)`, под тем же мьютексом, что продление срока, — иначе продление могло бы затереть прерывание;
- **прежний писатель** ставит точку сохранения и выходит;
- **`PUT`** ждёт, пока прежний писатель отпустит файл, до 5 с; не дождался — `409`. Ждёт он в своей горутине HTTP, и это никого больше не держит;
- **продолжение** ждёт не дольше 1 с и отказа из-за этого не даёт. Не дождался — отвечает тем, что уже сохранено надёжно: это может быть чуть меньше пришедшего, а `PUT` по выданному токену обрежет часть до своего смещения.

**Почему.** Соединение, умершее молча (вышел из дома — пакеты уходят в никуда), сервер замечает только по своему пределу застоя. Если новый `PUT` начнёт писать рядом с ним, поздние байты прежнего лягут в ту же часть по его смещению. Прерывание на продолжении к тому же делает `received` точным: обычно прежний писатель успевает отметить всё, что пришло, за миллисекунды.

**Почему продолжение ждёт секунду, а не пять.** Команды сокета обрабатывает тот же цикл, что читает понги. Пинг прямого соединения ждёт ответа 5 с (`defaultWriteTimeout`), так что пятисекундное ожидание в обработчике команды могло бы закрыть живое соединение как мёртвое. Секунда — с запасом и для `fsync` последних 4 MiB.

## 5. Время: только застой

**Решение.**
- **Сервер.** На `PUT` срок чтения продлевается перед каждым чтением тела, на `GET` срок записи — перед каждой записью: 60 с. `transferTimeout` уходит. Предел — поле `Server`, тесты ставят его коротким.
- **Приложение: загрузка.** Свой сторож: таймер на 45 с перезапускается на каждом `onSendProgress` и отменяет запрос через `CancelToken`. Когда последний байт отдан сокету, ответа сервера сторож ждёт до 3 минут (и `receiveTimeout` запроса тоже). «Отдан сокету» не значит «дошёл»: через Tor сокет, мост и цепь держат мегабайты, которые сливаются со скоростью десятков килобайт в секунду, и этого слива с нашей стороны не видно. Предел застоя обрывал бы здоровую загрузку на последней минуте — это показал тест реализации. Мёртвый путь кончается раньше: сокет замечает обрыв, путь меняется, и смена прерывает передачи старого пути (§9).
- **Приложение: скачивание.** `receiveTimeout` = 45 с: в Dio это пауза между кусками тела (`handleResponseStream`).
- **Токены.** Срок 10 минут проверяется только в начале запроса, так что идущую передачу он не обрывает.

**Почему.** FR-009 и SC-004: передачу, в которой байты идут, не обрывает ничто. `sendTimeout` в Dio — срок на весь `addStream`, а не на простой (`io_adapter.dart`), поэтому для загрузки он не годится. Приложение сдаётся раньше сервера (45 < 60): повтор начинает тот, кто его ведёт, а прерывание на сервере (§4) снимает висящий запрос.

**Отвергнуто:**
- Прежний абсолютный срок с запасом — любой запас ломается на медленном пути.
- Порог пропускной способности («меньше N байт за минуту — обрыв») — запрет медленного пути под другим именем.

Цена: соединение, по которому раз в минуту приходит байт, держит горутину сколько угодно. Держатель — устройство этого человека: токен выдаётся только поприветствовавшему соединению.

## 6. Скачивание с продолжением в приложении

**Решение.** Недокачанное лежит в `<кэш>/nox_attachments/<fileId>.<ext>.part`, валидатор сервера (`Last-Modified`) — в `.part.tag` рядом.
- **Попытка с частью.** Запрос: `Range: bytes=<длина части>-`, `If-Range: <валидатор>`. Без валидатора `Range` не отправляется — часть выбрасывается.
- **`206`.** `Content-Range` должен начинаться с длины части и называть общий размер, равный заявленному в сообщении. Тогда тело дописывается.
- **`200`.** Файл не тот, или валидатор не совпал. Порядок: часть обрезается до нуля → пишется новый `.part.tag` → тело пишется с начала. Сбой между шагами оставляет либо пустую часть, либо часть одного файла с его валидатором.
- **`416`.** Часть не короче файла на сервере: часть и валидатор выбрасываются, сразу новая попытка. Отказом это не считается.
- **Конец.** Длина части сверяется с заявленным размером (`MessageAttachment.sizeBytes`). Совпала — часть переименовывается в файл, `.part.tag` удаляется. Не совпала — оба выбрасываются, и это считается отказом.
- **Обрыв** оставляет часть и валидатор. Удаляет их только `clean()` (выход и смена мира) — FR-017.

Тело читается потоком (`ResponseType.stream`) и пишется самим репозиторием: решения о части — не дело источника данных.

**Почему.**
- FR-007: часть проверяется на совпадение с файлом на сервере — и по размеру, и по версии.
- Сервер 043 и сегодняшний сервер оба шлют `Last-Modified` и оба честно обрабатывают `If-Range` с датой (`checkIfRange` в `net/http` сравнивает секунды) — значит, продолжение работает и со старым сервером.
- Файлы на сервере после загрузки не меняются (допущение спецификации). Если байты всё же подменят на диске, сменится время изменения файла, а с ним `Last-Modified`.

**Отвергнуто:**
- Сверять только размер — не замечает другую версию того же размера.
- Ввести `ETag` — старые серверы его не шлют, а `Last-Modified` работает у обоих.
- `dio.download(fileAccessMode: append)` — режим файла выбирается до того, как известен ответ (`206` или `200`), и Dio удаляет файл при отмене.

## 7. Загрузка с продолжением в приложении

**Решение.**
- **Ручка.** Доменная `UnfinishedUpload {fileId, sourceSize, sourceModifiedAt}` хранится в записи очереди (`outbox`: три необязательных поля).
- **Когда пишется.** Репозиторий отдаёт ручку колбэком `onUnfinished`, как только сервер назвал файл и прислал `received`, и ждёт записи **до** первого байта. Перезапуск посреди `PUT` продолжает (FR-003).
- **Слепок источника.** Исходный файл сверяется со слепком (размер и время изменения) перед каждой попыткой и после каждого `PUT`, в том числе удачного. Изменение во время `PUT` иначе прошло бы незамеченным: на сервер ушла бы смесь старых и новых байтов, и сообщение отправилось бы с ней.
  - файла нет или он изменился — `notFound`, окончательно, «как сегодня для исчезнувшего»;
  - очередь при окончательном отказе забывает ручку, поэтому ручной повтор отправит файл как он есть сейчас, новой загрузкой. Брошенная загрузка на сервере вычищается по правилу суток.
- **Сервер потерял загрузку** (`not_found` на продолжение) — ручка забывается, загрузка начинается заново в той же попытке, без ошибки (FR-004).
- **Старый сервер** (нет `received`) — ручка забывается, файл идёт целиком.
- **Отказ токена** (`404` на `PUT`) — одна новая просьба в той же попытке. Второй подряд — `internal`, то есть отказ: он считается, и лестница растёт.
- **Прогресс.** `received/size` сообщается сразу после ответа на продолжение, дальше — `(received + отправлено)/size` (FR-012).
- **Завершение.** `attachFile(fileId)` после подтверждённых байтов забывает ручку.

**Почему.** Запись очереди уже живёт ровно столько, сколько сама отправка: переживает перезапуск, стирается при выходе и смене мира, удаляется вместе с отменённым сообщением. Отдельное хранилище повторяло бы всё это. Слепок дешёвый (`stat`). Байт исходника приложение не читает, кроме тех, что отправляет.

**Отвергнуто:**
- Копировать исходник к себе при постановке в очередь — удваивает место под 100 MiB, а спецификация требует только заметить изменение.
- Хеш файла на проводе — новое поле контракта и чтение всего файла заранее, без требования спецификации.

## 8. Повторы

**Загрузка — очередь исходящих**, её лестница пауз и два счётчика:
- обрыв (`connection`) не считается отказом;
- `_uploadFor` получает предел отказов `exhausted`, как у `message.send`. Сегодня его нет, и загрузку, которой сервер отказывает раз за разом, очередь повторяла бы вечно, держа всех за ней;
- исчерпано — `error` с ручным повтором. Ручка сохраняется, и повтор продолжает с последнего полученного байта (FR-011).

**Скачивание — новый `AttachmentDownloadService`** (домен; реализация в `data/sync`):
- **одна передача на файл**: второй просящий присоединяется и сразу слышит последнюю долю;
- **цикл попыток** через `FileRepository.download` (одна попытка, с продолжением):
  - `connection` — пауза по лестнице, пробуждение раньше, когда канал снова текущий, и так без конца;
  - `internal`, `rateLimited` и прочие повторяемые — отказ; после 10 скачивание кончается ошибкой;
  - `attachmentGone` и `notFound` — сразу;
- **после успеха** путь записывается в сообщение самим сервисом: ему всё равно, слушает ли ещё 5.3 (FR-007a);
- **`reset()`** останавливает циклы, отменяет передачи и ждёт их. Он вызывается при выходе и смене мира — до `clean()`.

Лестница одна — `RetryLadder` (`min(30 с, 1 с × 2^(n−1))` ±20 %), вынесенная из `OutboxService`, и предел отказов один — 10.

**Подкачка картинок** идёт через сервис скачивания и записывает путь не сама. Картинка, на которой автоматика исчерпана, ждёт возвращения канала (`retryNow`) или нажатия — на 5.3, а не следующего обновления ленты. Иначе каждое новое сообщение запускало бы для неё новую лестницу в десять отказов, и «исчерпано» не наступало бы никогда. Окончательные отказы остаются в `_hopeless`, как сегодня.

**Экран 5.3** берёт скачивание у сервиса. `failed` и `Try again` появляются только при исчерпанной автоматике; `gone` — как сегодня.

**Почему так.** FR-010 и FR-011. Политика повторов живёт в сервисах `data/sync`, как у очереди исходящих, а репозиторий отвечает за одну попытку. Блок экрана жив, пока открыт экран, поэтому скачивание, которое переживает экран, не может принадлежать блоку.

**Отвергнуто:**
- Цикл внутри `FileRepositoryImpl.download` — таймеры и подписка на фазу в репозитории, а путь в сообщение всё так же записывал бы закрытый блок.
- Цикл в `FileViewBloc` — умирает с экраном.

## 9. Смена пути

**Решение.** `ApiClient` ведёт реестр идущих передач: у каждой свой токен отмены (`beginTransfer`/`endTransfer`), так что сторож застоя обрывает одну передачу, а законченная не держит ничего. `cancelTransfers()` обрывает все разом — когда `initBase` переводит REST на **другой** адрес (каждое приветствие с нового пути), при выходе и смене мира (`FileRepository.cancelTransfers()`). Прерванная так передача — обычный обрыв: продолжение пойдёт уже по новому адресу. Общий токен «поколения» отвергнут при реализации: к нему пришлось бы цеплять каждую передачу, и цепочки копились бы до следующей отмены.

**Почему.** Иначе смену пути замечает только предел застоя:
- **из дома** прямое соединение молча умирает → до 45 с простоя;
- **домой** Tor останавливается на прямом приветствии → обрыв сразу, но не по нашему решению.

С отменой при смене адреса передача продолжается на новом пути сразу (FR-008, SC-003), а прерывание прежнего писателя на сервере (§4) снимает висящий там запрос.

## 10. Логи

Сервер пишет id файла, размер и смещения: `upload resumed`, `upload checkpoint`, `upload interrupted`, `upload complete`. Приложение — id файла или записи, смещение и код ошибки. Ошибки `dart:io` на исходном файле (`stat`, `open`) перехватываются в репозитории и превращаются в `notFound` раньше, чем `execute` их залогирует: в тексте `FileSystemException` путь, а в пути — имя файла (FR-016). Путь в кэше (`<fileId>.<ext>`) имени не содержит.

## 11. Интерфейс и документы

Новых строк и снимков нет. Существующие голдены 5.3, ленты и списка должны остаться зелёными.

Спецификация 5.3 и оба корпуса обновляются (Принцип II):
- обрыв связи не ошибка — полоса стоит и продолжает сама;
- закрытый экран не останавливает скачивание;
- `Could not download file. Check your connection and try again.` со `Try again` — только когда автоматика исчерпана. Текст остаётся прежним: новой микрокопии фича не вводит (допущение спецификации).

## 12. Известная граница

Загрузка, которая закончилась, но к сообщению не привязалась, вычищается сервером через сутки при перезапуске. Тогда `message.send` с её `file_id` по-прежнему получает `invalid_request`, и сообщение помечается ошибкой. Так с фазы 028, и 043 этого не меняет. Чтобы загрузить заново, приложение должно отличать «файла нет» от других отказов `message.send`, а это новый код ответа в §5. Незаконченная загрузка (FR-004) этим путём не идёт: на продолжение сервер отвечает `not_found`.

## 13. Проверка

- **Go.** Продолжение после оборванного `PUT`; застой с коротким пределом; медленные, но идущие `PUT` и `GET` дольше предела застоя доходят; прерывание висящего писателя, и продолжение не ждёт его дольше секунды; надёжная длина меньше части после «сбоя»; незаконченная загрузка переживает перезапуск сервера; пустой `PUT` завершает; `not_found`, `invalid_request` и `received == size` на продолжение; `If-Range` с датой: `206` при совпадении и `200` при расхождении; зачистка убирает `<id>.synced`; имени файла нет в логе.
- **Dart.**
  - Настоящий источник данных — против локального TLS-сервера на фикстурах пиннинга: `PUT` с остатком и верным `Content-Length`; сторож застоя отменяет застрявший `PUT`; `Range`/`If-Range`; отмена при смене адреса.
  - Репозиторий, очередь, сервис скачивания, подкачка и блок 5.3 — на подделках, включая исходник, изменившийся во время `PUT`, и лог без пути исходника.
- **Вживую** — `quickstart.md`: 100 MiB через onion в обе стороны, обрыв, перезапуск и смена пути посреди передачи, старый сервер.
