# Research: Установка сервера

Опора — 045 (`-public-addr`, `-onion-addr`, tor отдельно), 046 (`noxd link`), 047 (`noxd unlock` из stdin, запертый старт), страница темы 2 («Как поставить tor»), `client_backend/CLAUDE.md` (заметки о tor на macOS: официальная сборка без подписи).

## R1. Скрипты и где что лежит

- **Decision:**

| | Linux | macOS | Windows |
|---|---|---|---|
| Скрипт | `deploy/install-linux.sh` (bash) | `deploy/install-macos.sh` (bash) | `deploy/install-windows.ps1` (PowerShell 5+) |
| Бинарник | `/usr/local/bin/noxd` | `/usr/local/bin/noxd` | `C:\Program Files\NOX\noxd.exe` |
| Данные | `/var/lib/nox` | `/Library/Application Support/NOX` | `C:\ProgramData\NOX` |
| Учётная запись | системный `nox` | системный `_nox` | виртуальная `NT SERVICE\noxd` |
| Автозапуск | systemd `noxd.service` (`KillMode=mixed` не нужен — tor отдельно) | launchd `/Library/LaunchDaemons/com.cyphernetlabs.noxd.plist` | служба `noxd` (`sc.exe`/`New-Service`) |
| tor | пакет дистрибутива ≥ 0.4.9 или репозиторий Tor Project; служба `tor` | Tor Expert Bundle (macOS), подпись ad-hoc (`codesign -s -`), launchd `org.torproject.tor` | Tor Expert Bundle, служба `tor` (`tor --service install`) |

- **Rationale:** FR-001, FR-002; служба под своей учётной записью — доступ только к своим данным.

## R2. Бинарник

- **Decision:** `--binary <путь>` — готовый; иначе, если есть Go, `CGO_ENABLED=0 go build -trimpath -ldflags=-s` из `client_backend/` рядом со скриптом; иначе — отказ с инструкцией.
- **Rationale:** уточнение; поставка архивов — вне рамок.

## R3. tor и onion-сервис

- **Decision:** отдельный файл настроек NOX для tor: `HiddenServiceDir <tor-data>/nox`, `HiddenServicePort 443 127.0.0.1:<порт>`, `HiddenServicePoWDefensesEnabled 1`, `HiddenServiceMaxStreams 16`, `HiddenServiceMaxStreamsCloseCircuit 1` (R9); подключается через `%include` в основной `torrc` (tor ≥ 0.4.0), чужие настройки не трогаются. Onion-адрес — из `<HiddenServiceDir>/hostname` после первого старта tor (ожидание до 60 с). Проверка скачанного: `sha256sums-signed-build.txt` + `.asc` подписью Tor Project через `gpg` (ключ Tor Browser Developers по отпечатку, зашитому в скрипт); нет `gpg` или подпись не сошлась — tor не ставится.
- **Rationale:** FR-002, FR-003, уточнение; PoW на стороне сервиса (тема 2).

## R4. Первый запуск, пароль, ссылка

- **Decision:** порядок: учётная запись и папки → бинарник → tor и onion-адрес (если выбран) → служба сервера с `-addr 0.0.0.0:<порт> -db <данные>/nox.db -status-addr 127.0.0.1:8081 [-onion-addr …] [-public-addr …]` → ожидание `/health` `locked` → на новой установке пароль дважды (без эха, ≥ 12 знаков, повтор при ошибке) → `noxd unlock` из stdin → `noxd link` (ссылка, QR в терминале, срок) → адрес служебной страницы и как открыть сервер после перезагрузки. Пароль передаётся только через stdin команды, не в аргументах и не в файлах.
- **Rationale:** FR-004–FR-007, SC-004.

## R5. Повторный запуск

- **Decision:** есть `<данные>/nox.db` — режим обновления: заменить бинарник, обновить файлы служб и настройку onion-сервиса NOX, перезапустить; пароль не спрашивается (сервер стартует запертым — скрипт напоминает открыть его); ключ onion-адреса (`HiddenServiceDir`) и база не трогаются.
- **Rationale:** FR-008, SC-003.

## R6. Сбои

- **Decision:** проверки до изменений: права администратора, занятость порта (`ss`/`lsof`/`Get-NetTCPConnection`), наличие Go или `--binary`; сбой tor — сервер ставится без него и скрипт говорит, что не вышло; при сбое после частичных изменений — откат созданного этим запуском (служба, файлы службы).
- **Rationale:** FR-009, FR-010.

## R7. QR в терминале

- **Decision:** `noxd link -qr` печатает QR-код символами `▀▄█` (две строки модулей в одной строке терминала) с тихой зоной; кодирует `rsc.io/qr` (уже зависимость сервера).
- **Rationale:** FR-006, уточнение.

## R8. Проверка

- **Decision:** macOS — на этой машине: установка в изолированные пути (`--prefix` для проверки без затрагивания системы), tor из подписанного bundle, служба launchd, перезапуск, `noxd unlock`, спаривание; Linux и Windows — владелец (`shellcheck` и `PSScriptAnalyzer` для статической проверки, если установлены).

## R9. Решения реализации там, где документы молчат

Выбран осторожный вариант; каждое решение записано здесь.

- **Пароль — до любых изменений.** Скрипт спрашивает пароль (и публичный адрес) сразу после проверок, до учётных записей, файлов и служб, а серверу отдаёт его в конце, через стандартный ввод `noxd unlock`. Несовпавший или короткий пароль и Ctrl+C на вопросе не оставляют на машине ничего (FR-010); пароль живёт только в переменной скрипта и не попадает ни в аргументы процессов, ни в файлы. Эхо выключается до того, как показан вопрос: `read -s` сначала печатает вопрос, и вставленное в это мгновение отображалось бы. Без терминала пароль читается двумя строками со стандартного ввода — так скрипт проверяется без человека.
- **Точка невозврата — ответ служебной страницы.** Каждое изменение пишет в журнал скрипта, как его отменить; сбой до ответа `/health` отменяет всё, сделанное этим запуском, в обратном порядке (созданные учётные записи, папки, файлы, службы, правило брандмауэра; прежние файлы возвращаются из копий). После ответа установка стоит: сбой задания пароля или выдачи ссылки только описывается — пароль задаётся на служебной странице или `noxd unlock`. Журнал сервера, который откат удалит, показывается до отката.
- **Откат доводится до конца.** Каждый сигнал, которым можно остановить запуск, ведёт к откату: кроме INT и TERM, свой обработчик есть у HUP (закрытое окно терминала, оборванный SSH), QUIT (`Ctrl+\`) и PIPE (умер `tee`, через который шёл вывод). Без него bash завершался, и обработчик EXIT видел код последней команды, 0, как у законченного запуска. Каждый обработчик сперва глушит все эти сигналы и только потом выходит: закрытый терминал шлёт HUP дважды, с промежутком в доли миллисекунды (так делают zsh и bash 5, а sudo передаёт оба), и второй `exit` внутри обработчика EXIT завершал скрипт раньше, чем тот что-либо отменял. По той же причине обработчик EXIT первым делом отмечает, что скрипт уже выходит: сигнал, пришедший после ошибки, тогда только глушит следующие. В самом откате эти сигналы игнорируются — и командами, которые он запускает, — и действует `set +e`: оборванный откат оставил бы машину в состоянии, которого никто не выбирал, а пакетные менеджеры и `launchctl`, получив сигнал, бросили бы шаг на середине. Вывод — по возможности: после первой неудачной записи всё идёт в `/dev/null`, и буфер bash сразу сбрасывается туда же. bash держит текст неудавшейся записи и пишет его в следующий вывод, в том числе в подстановку команды, — и откат читал свои же сообщения вместо pid. Шаг уходит из журнала, как только выполнен. На Windows откат — в `finally`, не в `catch`: Ctrl+C останавливает скрипт мимо всех `catch`, выполняются только `finally`, и копии прежних файлов удаляются уже после отката; вывод там тоже по возможности. Ctrl+C во время отката процесс игнорирует (`SetConsoleCtrlHandler(NULL, TRUE)`) и тогда, когда стандартный ввод — файл с паролем, перенаправленный через `cmd`, как описано в `deploy/README.md`; `TreatControlCAsInput` требует консоль на входе и остаётся запасным путём. Откату, начатому Ctrl+C, это не нужно — конвейер уже останавливается, — защита нужна откату, начатому сбоем. Чего в самом процессе не поймать: запущенный из конвейера PowerShell или с перенаправленным в PowerShell выводом установщик родительский PowerShell при Ctrl+C просто убивает, а закрытое окно консоли или оборванный SSH завершают процесс за секунды; это откатывает следующий запуск (ниже).
- **Запись до шага — везде.** Каждое изменение записывается в журнал до самого шага, и отмена того, что не успело случиться, — не ошибка отката: удаление пакета, который не был установлен (apt, dnf, pacman, в том числе `epel-release`), ключа Tor Project в rpm, которого не было до импорта (запись называет этот ключ и только его: её может откатывать и следующий запуск, а ключ, импортированный между запусками вручную или для другого репозитория, не его), учётной записи и группы, которых не было (группу, что уже была, откат не трогает), папок и журналов, правила брандмауэра. Ссылка, ведущая в никуда, — отказ до любой записи, с её именем: папка данных на втором диске, который не смонтирован, выглядит отсутствующей, и откат неудавшегося mkdir через неё удалил бы ссылку владельца, а следующий запуск создал бы новую базу и новую личность сервера на корневом диске. apt доводит свой прогон dpkg до конца сквозь обрыв терминала и Ctrl+C, а скрипт останавливается сразу после него: запись после шага не успевала, и пакет оставался, хотя скрипт говорил, что машина как была.
- **Запись прерванного запуска — на диске.** Журнал отката хранится и на диске — в `/var/lib/nox-install` (Linux), `/var/db/nox-install` (macOS), `C:\ProgramData\NOX-install` (Windows), — переписывается целиком перед каждым шагом, через переименование, вместе с копиями заменённых файлов; пароля в нём нет. Писать туда могут только root или SYSTEM и администраторы, а не учётная запись сервера: команды из записи выполняются. Запуск, который откатить себя не смог, — убитый процесс, выключенная машина, а на Windows ещё закрытое окно, оборванный SSH и Ctrl+C в конвейере PowerShell, — оставляет запись, и следующий запуск первым делом откатывает её, говорит об этом и только потом делает своё. Запись принимается, только если её мог написать лишь этот пользователь (владелец и права папки и файла), а процесс, который её написал, уже не идёт: иначе — отказ, а при живом процессе — «another run of this script is under way». Шаг, который не откатился, остаётся в записи; продолжение, в котором что-то не откатилось, откладывает запись в `journal.failed` и останавливается — и, если прежний сервер при этом снова запущен, говорит, что он заперт и как его открыть, — а следующий запуск отказывается, пока владелец не уберёт папку, — без бесконечного повтора. На Windows папку в `ProgramData` может создать любая учётная запись и остаться её владельцем при любых правах, поэтому папка записи, у которой после установки прав владелец не SYSTEM, не администраторы и не запустивший или право записи есть у кого-то ещё, — отказ до первой записи. Отметка «установка стоит» удаляет запись первой, поэтому успешный запуск, прерванный после ответа сервера, следующим никогда не откатывается. Без синхронизации диска при каждом шаге: после пропажи питания запись — то, что диск успел сохранить.
- **Откат обновления говорит, что сервер заперт.** Прежний сервер, остановленный для обновления, откат запускает снова, а он, как после любого старта, заперт (047). На обновлении скрипт пароля не спрашивает и не хранит, поэтому сервер не открывает: в конце отката сказано, что всё отменено, что прежний сервер запущен и заперт, и как его открыть — служебная страница или `noxd unlock` на прежнем порту страницы. Шаг, который отменить не удалось, назван, и вместо «машина как была» сказано, что вернулось не всё.
- **Остановленное запускается, когда его файлы на месте.** Запуск того, что этот запуск остановил, — прежнего задания launchd (`job_restore`), прежнего `noxd` под systemd — лежит в отдельном, последнем списке своего журнала и выполняется после всего остального в нём. В общем порядке «от нового к старому» он шёл бы раньше, чем вернутся бинарник, `nox-tor.conf` и другие файлы, заменённые раньше, и прежнее задание запускало бы бинарник и настройки этого запуска. Каждая запись делается до самого шага — до остановки, до `enable`, до `systemctl restart`, — чтобы откатывался и прерванный шаг. Системный tor на Linux откат оставляет таким, каким нашёл: запускает снова (последним) только работавший, иначе останавливает, и выключает автозапуск, если его не было, — Fedora, RHEL и Arch установленный tor не запускают и не включают. На Windows остановка службы записывается до остановки и предшествует замене её файлов, поэтому её запуск и так идёт после них; запуск ждёт остановку, которую прерванный `Stop-Service` оставил идти (`StopPending`), и неудачу сообщает, а не глотает. Так же записываются `service-stop` до `Start-Service` и `service-delete` до `New-Service`.
- **Обновление.** Установка считается существующей, если есть база, файл ключа или описание службы. Порт, порт служебной страницы и публичный адрес берутся из установленной службы, если их не передали; свои порты, занятые своим же сервером, проверку портов проходят. База, `nox.db.key`, папка ключа onion-адреса не трогаются; перед перезапуском tor удаляется только файл `hostname` — tor пишет его из ключа при каждом старте, и ожидание доказывает именно этот старт.
- **tor на Linux — системная служба.** Onion-сервис NOX — отдельный файл `/etc/tor/nox-tor.conf`, подключённый к `/etc/tor/torrc` одной строкой `%include` между метками; остальные настройки tor, включая `SocksPort`, не меняются. tor берётся из дистрибутива, если кандидат 0.4.9+ и сборка умеет PoW, иначе — из репозитория Tor Project (apt и dnf; pacman — только дистрибутив). Пакет, поставленный этим запуском, при сбое tor удаляется.
- **Ключи репозиториев Tor Project.** Скачанный файл ключа принимается, только если каждый ключ в нём — пинованный, по основному отпечатку: apt доверяет каждому ключу связки `signed-by`, rpm импортирует каждый ключ файла, и ключ, дописанный после настоящего, получил бы то же доверие. Ставится не скачанный файл, а то, как gpg его прочёл (`--import-options import-export`: без того, что gpg счёл недействительным, например подключа без привязки; связка ключей при этом не пишется), — и оно проверяется ещё раз. dnf получает ключ локальным файлом `/etc/pki/rpm-gpg/RPM-GPG-KEY-torproject` (`gpgkey=file://…`), не адресом: ключ по адресу `dnf -y` импортирует сам, без сверки отпечатка. Ключ, впервые импортированный в rpm этим запуском, при откате удаляется (`rpm -e gpg-pubkey-…`).
- **Порты ниже 1024 — отказ до изменений.** На Linux служба работает под `nox` без `CAP_NET_BIND_SERVICE`, и порт ниже `net.ipv4.ip_unprivileged_port_start` (1024) скрипт не принимает — и основной, и служебной страницы. Иначе установка дошла бы до ответа `/health` (страница слушает с первого старта), а основной порт сервер открывает только после пароля — и не открыл бы. Выбран отказ, а не право в юните: служба не получает права, без которого обходится, а 443 снаружи даёт проброс на роутере. macOS пускает на порты ниже 1024 без root только на всех адресах сразу (проверено здесь: `0.0.0.0` — да, `127.0.0.1` — нет), поэтому там отвергается только порт служебной страницы.
- **Папка бэкапов.** `noxd backup` пишет файл сам работающий сервер, под своей учётной записью, а ей можно писать только в папку данных: скрипт заводит в ней `backups` (с правами папки данных) и называет её в конце установки и в `deploy/README.md` вместе с тем, как унести файл с правами администратора.
- **tor на macOS и Windows — своя служба.** Tor Expert Bundle ставится своей службой с метками `com.cyphernetlabs.nox-tor` (launchd) и `nox-tor` (служба Windows) вместо `org.torproject.tor` и `tor` из R1: имя Tor Project может принадлежать tor, поставленному иначе, и его настройки этот скрипт не трогает. У своей службы — своя учётная запись (`_noxtor`, `NT SERVICE\nox-tor`), свой `torrc` с `SocksPort 0`, пустой `torrc-defaults` (сборка Tor Browser иначе подхватывает свой). «tor уже стоит и подходит» здесь — tor, поставленный этим скриптом раньше, или `--tor-bin`; tor, поставленный иначе (Homebrew — без PoW), не используется. Из архива ставятся только `tor` и библиотеки рядом (на macOS — `libevent`), без мостов и GeoIP.
- **launchd: остановка с ожиданием.** `launchctl bootout` возвращается, пока задание ещё завершается, а `bootstrap` той же метки в это время отвергается (`5: Input/output error`). Штатная остановка noxd укладывается в 25 с (по 5 с на основной сервер и служебную страницу, до 15 с на закрытие соединений устройств), а задание, пережившее свой `ExitTimeOut`, launchd убивает раньше. Поэтому скрипт после `bootout` ждёт до 30 с, пока метка не пропадёт из `launchctl print`, повторяя `bootout`, и только тогда загружает новое задание; отказ `bootstrap` в первое мгновение повторяется дважды. Откат останавливает новое задание с тем же ожиданием, а прежнее загружает последним (см. выше).
- **`--binary` на macOS — копия без карантина.** Файл, пришедший через AirDrop, Messages, почту или браузер, несёт `com.apple.quarantine`, и Gatekeeper не запускает такую программу без нотаризации — а `noxd` её не имеет, — значит, не прошла бы и проверка `noxd unlock -h`. Скрипт копирует файл в рабочую папку, снимает карантин с копии, проверяет и ставит её; исходный файл не трогается. Отказ приводит, что программа сказала, и что карантин ни при чём.
- **PoW — обязательное свойство tor.** tor без модуля `pow` отвергает настройки с `HiddenServicePoWDefensesEnabled 1` и не стартует; такой tor считается неподходящим, как старее 0.4.9 (`tor --list-modules` → `pow: yes`).
- **Предел потоков.** Onion-адрес открыт любому, кто его знает, а PoW ограничивает только новые подключения к сервису: каждая настройка onion-сервиса несёт `HiddenServiceMaxStreams 16` и `HiddenServiceMaxStreamsCloseCircuit 1` (замечание ревью кода 045) — устройству хватает сокета и нескольких передач, а цепочку, по которой открыли больше, tor закрывает. `HiddenServicePort 443` ведёт на `127.0.0.1:<порт>`, сервер слушает `0.0.0.0:<порт>`, и loopback до него доходит.
- **Кавычки в `torrc`.** Пути в `DataDirectory`, `HiddenServiceDir` и `%include` пишутся в кавычках с экранированием `\` и `"` — tor читает там экранирование C, и путь с пробелом работает. В строке `Log` кавычки не разбираются: служба Windows пишет журнал tor по пути без пробелов (иначе — без журнала, с предупреждением), launchd и проверка без служб берут вывод tor сами.
- **Проверка подписи.** Сначала `gpgv` с ключом в роли связки: ему не нужны ни папка ключей, ни агент (у `gpg` без агента код выхода ненулевой даже после верной проверки). Вердикт — по строкам состояния: `VALIDSIG`, последнее поле которой — отпечаток основного ключа, равный зашитому, и ни одной `BADSIG`, `ERRSIG`, `REVKEYSIG`; затем SHA-256 архива — по строке подписанного списка. Ключ скачивается по WKD Tor Project; `NOX_TOR_DIST`, `NOX_TOR_VERSION` и `NOX_TOR_KEY_URL` указывают на зеркало или локальную копию (`file://`), отпечаток проверяется всегда. На macOS скачанный tor подписывается ad hoc после проверки.
- **Сервер на Windows — служба Windows сам.** Консольную программу диспетчер служб убивает, если она не отчиталась; поэтому `noxd`, запущенный диспетчером, работает через `golang.org/x/sys/windows/svc` (до сих пор — косвенная зависимость модуля): `Running` сразу, `Stop` и `Shutdown` — штатная остановка сервера, журнал — в `noxd.log` рядом с базой, откладывается в `noxd.log.1` на 16 МиБ. Виртуальные учётные записи `NT SERVICE\noxd` и `NT SERVICE\nox-tor`; папки данных — только им, SYSTEM и администраторам (SID, а не имена — одинаково на любом языке Windows); перезапуск при сбое; правило брандмауэра на порт сервера для `noxd.exe` во всех профилях — без него прямые соединения на Windows не доходят.
- **Остановка по просьбе диспетчера — чистый выход.** Служба зарегистрирована с действиями при сбое, которые считают сбоем и ненулевой код остановки (`sc failureflag 1`, перезапуск через 5 с), а штатная остановка сервера возвращает ошибку, когда истёк её срок, — например, пока идёт передача файла через Tor. Остановка, о которой попросил диспетчер, поэтому всегда завершается кодом 0, а ошибка остановки уходит в журнал; сбой — только сервер, остановившийся сам: его диспетчер и перезапускает.
- **Windows: пароль из перенаправленного ввода — UTF-8.** `[Console]::In` декодирует кодовой страницей консоли, и пароль вне ASCII менялся бы по дороге к серверу; скрипт читает байты как UTF-8 (BOM UTF-8 и UTF-16 учитывается), недопустимые байты — отказ. Windows PowerShell 5.1 в конвейере заменяет не-ASCII на `?` ещё до скрипта, этого скрипт не видит — в `deploy/README.md` сказано, как подать файл.
- **Windows: `-TorBin` копируется.** Служба tor работает под `NT SERVICE\nox-tor`, которая читает `Program Files`, но не папки владельца, где tor.exe обычно лежит (Tor Browser на рабочем столе, архив в загрузках); заданный tor.exe ставится в `C:\Program Files\NOX\tor\` вместе с библиотеками рядом — как скачанный, у которого библиотеки рядом тоже копируются.
- **Команды без `sudo`.** Подсказки говорят `noxd unlock` и `noxd link -qr` без `sudo` (в отличие от T006 и quickstart): команды ходят на loopback-страницу и прав администратора не требуют, а `sudo` спросил бы пароль учётной записи macOS прямо перед паролем сервера.
- **Сборка.** Под `sudo` сервер собирается от имени запустившего (`SUDO_USER`): его кэш модулей и сборки, и git доверяет его копии репозитория для отметки версии; от root без `SUDO_USER` при отказе git — сборка без отметки версии. Бинарник проверяется запуском: `noxd unlock -h` и `noxd link -h` должны знать `-status-addr` и `-qr`.
- **Брандмауэр.** Windows — правило ставит скрипт (см. выше); macOS, ufw и firewalld — только подсказка с командой: политику брандмауэра скрипт не меняет.
- **`--prefix` и `--no-service` — только вместе.** Проверка без изменения системы: все файлы под префиксом, включая временные и кэш сборки; ни учётных записей, ни служб, ни пакетов; описания служб пишутся под префикс для просмотра (`plutil -lint` на macOS), сервер и tor работают фоновыми процессами с файлами pid и той же маской `077`, что у служб.
- **Удаление** — вне рамок (spec, Out of Scope): таблица «Где что лежит» в `deploy/README.md` перечисляет всё, что ставит скрипт.

## Проверка исправлений четвёртого ревью (2026-10-10)

Те же ограничения; запись на диске под префиксом — `var/db/nox-install` (macOS) и `var/lib/nox-install` (Linux).

| Проверка | Итог |
|---|---|
| Ссылка в никуда | `PREFIX/usr/local/var` ведёт на несуществующий том: прежде откат удалял ссылку и говорил «This machine is as it was before the run.»; теперь — отказ с именем ссылки и целью, ссылка на месте |

| Убитое обновление | на установленном сервере обновление с подставным бинарником убито SIGKILL: следующий запуск вернул прежний бинарник из копии в записи, затем обновил; ключ данных и onion-адрес те же, верный пароль открывает |

**За владельцем:**

- macOS: `sudo deploy/install-macos.sh` на машине — учётные записи `_nox` и `_noxtor`, службы launchd, скачанный tor под `_noxtor`, спаривание телефона напрямую и через Tor, перезагрузка (сервер и tor поднялись, сервер заперт, пароль на странице или `noxd unlock`), повторный запуск — в том числе при подключённом телефоне (остановка с ожиданием), `noxd backup` в папку `backups` и копия оттуда через `sudo cp`, `--binary`, перенесённый через AirDrop.
- Linux: `sudo deploy/install-linux.sh` на Debian или Ubuntu и на Fedora — tor из дистрибутива и из репозитория Tor Project (ключ — по всему файлу, на dnf — `gpgkey=file://`, импорт в rpm и его откат), `%include` в `/etc/tor/torrc`, AppArmor и SELinux, служба `noxd`, перезагрузка, отказ `--port 443`, `noxd backup` в `/var/lib/nox/backups`.
- Windows: `deploy\install-windows.ps1` от администратора — разбор скрипта PowerShell 5.1 и 7, Gpg4win, служба `noxd` под диспетчером (журнал `noxd.log`; `Stop-Service` во время передачи файла — служба остаётся остановленной; тесты `service_windows_test.go`), служба `nox-tor`, `-TorBin` из папки владельца (копируется в `C:\Program Files\NOX\tor\`), Ctrl+C во время скачивания tor при обновлении — откат и запуск прежнего сервера, Ctrl+C, пока `Stop-Service` ждёт сервер с подключённым телефоном, — сервер снова запущен, и в конце сказано, что он заперт и как его открыть; откат после сбоя при пароле из файла (`cmd /c "… < pw.txt"`) — Ctrl+C его не прерывает; пароль из файла через `cmd /c "… < pw.txt"` с не-ASCII знаками, права на папки (`backups` — только служба, SYSTEM и администраторы), правило брандмауэра, перезагрузка.
- Linux и macOS: оборванный SSH и закрытое окно терминала во время обновления — откат, прежний сервер запущен со своим бинарником, в конце сказано, что он заперт; на Fedora — tor, установленный, но не включённый, после отката сбоя tor остаётся остановленным и выключенным; обрыв во время `apt-get install` — пакет удалён откатом; на Rocky или Alma без EPEL — после отката `epel-release` удалён; `/var/lib/nox` — ссылка на несмонтированный диск: отказ, ссылка цела; выключить машину посреди установки — следующий запуск откатывает её первым.
- Windows: закрыть окно консоли (или оборвать SSH, или нажать Ctrl+C, запустив установщик из конвейера PowerShell) во время обновления — следующий запуск сначала откатывает прерванный, говорит об этом и запускает прежний сервер, затем обновляет; права `C:\ProgramData\NOX-install` — только SYSTEM и администраторы.

## Пробный прогон `install-windows.ps1` (2026-10-10)

PowerShell 7.4.6 на macOS, режим проверки (`-Prefix … -NoService`). Скрипт — копия с правками только там, где macOS не Windows: снята проверка системы; пути под префиксом с `/` вместо `\`; имя процесса сверяется без `.exe` (на Windows .NET его отрезает сам); фоновые процессы запускаются через `sh` с выводом прямо в файлы (на Unix `Start-Process` пишет перенаправленный вывод через сам pwsh, и после его выхода Go-сервер получал SIGPIPE на первой строке журнала — на Windows файл получает свой дескриптор); `/usr/bin/tar` вместо `tar.exe`; библиотеки tor — `*.dylib`. `Get-NetTCPConnection` и `Get-CimInstance` подставлены: `lsof` и `ps`. Службы, `icacls`, брандмауэр, `Get-Acl` и Ctrl+C здесь не исполнить — их проверяет владелец.

| Проверка | Итог |
|---|---|
| Найдено | **Каждая установка на Windows падала на втором шаге записи**: `[System.IO.File]::Replace($tmp, $file, $null)` — PowerShell передаёт `$null` строковому параметру .NET как пустую строку, и `Replace` отвергает пустой путь копии (так же и .NET Framework под Windows PowerShell 5.1); вторая запись журнала бросала исключение, и запуск откатывался. Теперь `[NullString]::Value`. Ещё: откат проверки оставлял в префиксе пустую `ProgramData` — папку над записью; теперь убирается, как в скриптах для Linux и macOS |
| С нуля, без tor | сборка из репозитория, заперт → пароль со стандартного ввода → открыт → QR, ссылка, срок; `cmd/smoke` по выданной ссылке — все шаги (первое устройство, приглашение с `Allow`, `Deny`, сообщение) |
| Обновление | без портов — порты из записи службы, `nox.db.key` тот же, сервер перезапущен и заперт; неверный пароль — «Wrong password.», верный — открыт; папки записи после успеха нет |
| Откат | сервер, который не отвечает (подставной `noxd`): с нуля — префикс пуст, процессов нет; обновление — бинарник возвращён байт в байт |
| Убитый запуск | SIGKILL установщика, пока подставной сервер стартует: запись на диске с копиями; следующий запуск — «Taking back an interrupted run», подставной сервер остановлен, бинарник возвращён, затем обновление до конца |
| Пароль из файла | кириллица в UTF-8 и в UTF-16 с BOM (как пишет Windows PowerShell) — задан, после перезапуска открывается тем же паролем в UTF-8; не UTF-8, короткий, несовпавший — отказ до изменений, префикс пуст |
| tor | `-TorBin` (tor 0.4.9.13): `torrc` с `SocksPort 0`, `nox-tor.conf` с PoW и пределом потоков, onion-адрес передан серверу и есть в ссылке; обновление — тот же ключ и адрес; tor 0.4.8 — отказ, записи tor откатаны, сервер без tor |
| Скачивание tor | настоящий Tor Expert Bundle 15.0.24 для Windows: версия с aus1, подпись списка сумм пинованным ключом, сумма архива, `tor\tor.exe` в архиве (запустить его здесь нельзя — «it does not run», сервер без tor); подмена через `NOX_TOR_DIST=file://…`: лишний байт в архиве и изменённая строка списка — отказ |
| Шаг отката, который не удался | на Windows удаление, после которого путь остался, и отказ `sc.exe` (кроме «службы нет» и «уже удаляется») — названный шаг, «not everything could be taken back», запись в `journal.failed`; прежде такие шаги проходили молча, и итог говорил «как было». Проверено на удалении из папки, закрытой на запись |
| Кавычки | `ConvertTo-Argument`: 400 случайных командных строк (пробелы, кавычки, `\` в конце, табуляция, пустые аргументы) — разбор .NET возвращает те же аргументы |
