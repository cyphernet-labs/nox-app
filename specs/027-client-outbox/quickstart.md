# Quickstart: client-outbox

Как убедиться, что фаза действительно работает. Первые три сценария — на живом сервере, последний — гейт.

## Предпосылки

- Собранный `noxd` этапа 1 (см. `client_backend/README.md`), слушающий локально.
- `config/stage.json` с заполненным `apiUrl` — без адреса приложение остаётся на кэше и канал не открывает.
- FVM: `fvm use 3.44.1`.

## Сценарий 1 — неотправленное переживает перезапуск (US1, SC-001)

1. Поднять сервер, запустить приложение: `fvm flutter run --dart-define-from-file=config/stage.json -d macos`.
2. Открыть чат, **остановить сервер**.
3. Отправить два сообщения. Оба висят пузырями `pending`.
4. **Полностью закрыть** приложение (не свернуть) и запустить заново, открыть тот же чат.
5. Ожидаемо: оба сообщения на месте, по-прежнему неотправленные, **в том же порядке**.
6. Поднять сервер. Ожидаемо: без единого действия оба уходят, статус меняется на отправленный, порядок сохранён.

## Сценарий 2 — повтор не делает второй копии (US2, SC-002)

1. Сервер поднят, приложение запущено, второй клиент открыт на тот же чат.
2. Отправить сообщение и **сразу** оборвать сеть, чтобы ответ не дошёл (сервер сообщение уже принял).
3. Закрыть и запустить приложение заново, вернуть сеть.
4. Ожидаемо: у второго клиента **ровно одна** копия сообщения. Сервер узнаёт `client_message_id` и возвращает прежнее эхо вместо второй записи.

Быстрая проверка со стороны сервера: в журнале чата у сообщения один `seq`, а не два соседних с одинаковым текстом.

## Сценарий 3 — уход с экрана ничего не теряет (US3, SC-004)

1. Остановить сервер, написать сообщение — висит `pending`.
2. Уйти в список чатов, затем в настройки, затем в другой чат.
3. Поднять сервер, **не открывая** исходный чат.
4. Ожидаемо: сообщение уходит; вернувшись в чат, видим его отправленным.

## Сценарий 4 — окончательный отказ не держит очередь

1. Остановить сервер. Отправить сообщение длиннее объявленного в приветствии предела, затем ещё одно обычное.
2. Поднять сервер.
3. Ожидаемо: длинное помечено ошибкой и ждёт ручного повтора; обычное **уходит**, не застревая за ним.

## Сценарий 5 — убранное не возвращается (SC-007)

1. Остановить сервер, написать сообщение, дождаться пузыря с ошибкой (или взять зависшее `pending`).
2. Долгое нажатие по пузырю (на десктопе — правая кнопка мыши).
3. Ожидаемо: пузырь исчез. Поднять сервер — сообщение **не** уходит. Перезапустить приложение — его нет.

## Сценарий 6 — выход из аккаунта не оставляет текстов (SC-005)

1. Остановить сервер, написать сообщение — висит `pending`.
2. Настройки → выход.
3. Ожидаемо: после повторного входа очередь пуста, неотправленное не всплывает.

## Гейт (SC-006)

```bash
make gate           # generate → format → analyze → test
make golden-verify  # 216 эталонов, без перегенерации
```

Оба обязаны быть зелёными **до** коммита: CI на паузе, и это единственное место, где ловится регресс. `golden-verify` здесь несёт отдельный смысл: фаза не имеет права изменить ни один пиксель, и перегенерация эталонов вместо починки кода была бы подменой проверки.
