# Контракт: добавления на проводе (фаза 039)

Всё ниже — **добавления** к контракту v0 (`docs/client-backend/protocol/contract-draft.md`). Номер схемы не меняется. Ни одна существующая команда, событие или код ошибки не меняют смысла: клиент, который ничего из этого не знает, работает как раньше. В `contract-draft.md` эти формы вносятся до кода — правило Принципа VII.

## 1. Транспорт: onion — второй путь к тому же TLS-входу

Сервер с включённым Tor публикует onion-сервис. Виртуальный порт — **443**, цель — внутренний вход сервера на loopback с тем же сертификатом. Поэтому:

- через onion действует тот же пин — отпечаток TLS-ключа из ссылки спаривания. Onion даёт достижимость, а не доверие;
- через onion доступны те же команды, события и REST, что по прямому пути, **кроме claim**: claim-токен, предъявленный через onion, получает `invalid_token`, и токен при этом не тратится. Повтор уже израсходованного claim-токена через onion — тоже `invalid_token`;
- порт onion-адреса закреплён — **443**. Правило §1 «порт не закреплён» относится к прямому входу: его порт по-прежнему приезжает ссылкой;
- служебной страницы через onion нет;
- доступ — только с **ключом доступа** (авторизация клиентов Tor v3). Без ключа из списка сервиса Tor не строит соединение.

Onion-сервис публикуется, только пока в его списке есть хотя бы один ключ. Пустой список сделал бы сервис открытым, поэтому без ключей onion-адреса нет вовсе.

## 2. `session.hello` — текущие адреса в ответе

```json
{"id": 1, "ok": true, "data": {
  "schema": 1,
  "cursor": 1042,
  "journal_id": "j_7c1e4a90b3d2f6a1",
  "limits": {"max_message_bytes": 65536, "max_attachment_bytes": 104857600, "max_frame_bytes": 131072},
  "identity": {"id": "u_3f2a1c9d40b7e518", "label": "User7421"},
  "addresses": {
    "direct": ["192.168.1.20:8080", "[fd12:3456::20]:8080"],
    "onion": "6bauzvyr6myctqykmykeuo3p3yc3iy7tilx5g3sxxpuifdwab54o56id.onion:443"
  }
}}
```

- **`addresses.direct`** — массив `host:port`. IPv6 записывается в квадратных скобках. Длина — от 0 до 16. Есть всегда, при необходимости пустой. Порядок значения не несёт. Если сервер слушает на всех интерфейсах, это адреса поднятых интерфейсов без loopback и link-local; если на конкретном адресе — только он.
- **`addresses.onion`** — onion-адрес с портом. Поле **отсутствует**, если сервер onion не предлагает. Предлагает, пока Tor включён, tor найден подходящей версии и в списке есть хотя бы один ключ доступа. Временный сбой tor поле не убирает.

Адреса приходят по каналу, уже проверенному пином, поэтому подделать их нельзя. Ссылка спаривания onion-адреса не несёт (кроме приглашения версии 2, §6).

**`addresses` — ещё и признак поддержки.** Его наличие в ответе на приветствие говорит, что сервер знает всё из этого документа. Клиент шлёт `device.setAccessKey` и полагается на `access_key` в `pair` и `onion` в `device.invite`, **только если** видел `addresses`. Иначе новая команда к старому серверу получила бы `invalid_request`, а это фатальный экран (§2.1): контракт растёт без разрыва событиями, а не командами, и признак — то, что делает новую команду безопасной.

## 3. Событие `server.addresses`

```json
{"seq": 0, "event": "server.addresses", "data": {
  "direct": ["192.168.1.21:8080"],
  "onion": "6bauzvyr6myctqykmykeuo3p3yc3iy7tilx5g3sxxpuifdwab54o56id.onion:443"
}}
```

- Нагрузка — тот же объект, что `addresses` в ответе на приветствие.
- Уходит всем поприветствовавшим соединениям, когда список меняется: прямой адрес — не позже чем через минуту, появление и уход onion — сразу.
- **`seq: 0`, внежурнальное**, как `device.paired`: номера не занимает, в догоне не участвует, разрыв не переживает. Надёжная половина — ответ на приветствие, он всегда несёт текущий список.
- Клиент прошлой сборки отбрасывает событие защитой курсора — `seq: 0` не больше никакого курсора, — как любое незнакомое.

## 4. `pair` — необязательный ключ доступа

```json
{"id": 1, "cmd": "pair", "data": {
  "token": "<16 байт, base64url>",
  "device_key": "<base64: публичный ключ устройства, Ed25519>",
  "platform": "ios",
  "access_key": "<base64: открытый ключ x25519, 32 байта>"
}}
```

- **`access_key`** — необязательный. Если есть, он становится ключом доступа этого устройства в той же транзакции, что и спаривание. Устройство, пришедшее через onion по одноразовому ключу, так сохраняет доступ, когда этот ключ перестаёт действовать.
- Неверная форма — не base64 или не 32 байта — даёт `invalid_request`, и спаривание не происходит.
- Повторное спаривание своего устройства с новым `access_key` заменяет прежний ключ. Повтор того же токена тем же ключом устройства отвечает записанным исходом и ключ доступа не меняет.
- Старый сервер необязательное поле просто пропускает: спаривание проходит без ключа доступа, а `addresses` в приветствии нет (§2).
- Claim через onion — `invalid_token` (§1).

## 5. `device.setAccessKey` — регистрация ключа доступа

```json
{"id": 6, "cmd": "device.setAccessKey", "data": {"access_key": "<base64: открытый ключ x25519, 32 байта>"}}
```

```json
{"id": 6, "ok": true, "data": {}}
```

- Только после приветствия. Ключ доступа ставится **тому устройству, которым поздоровалось это соединение**. Чужому устройству поставить ключ нельзя: в команде нет параметра, который бы его называл.
- Повторная регистрация заменяет прежний ключ: у устройства не больше одного.
- Принимается и при выключенном Tor: ключ хранится и начинает действовать, как только Tor включат.
- Отказы: `invalid_request` — ключа нет или он неверной формы; `unauthenticated` — устройства, которым поздоровалось соединение, уже нет (отозвано посреди сессии). Ответ тот же, что у приветствия отозванного устройства.
- Регистрация того же ключа, что уже стоит, — успех без перепубликации.
- Зачем команда, если ключ можно передать в `pair`: устройства, спаренные до фазы 039, регистрируют ключ ею при первом подключении.

## 6. `device.invite` — приглашение с onion-адресом

```json
{"id": 5, "cmd": "device.invite", "data": {"onion": true}}
```

```json
{"id": 5, "ok": true, "data": {"token": "<16 байт, base64url>", "link": "https://nox.app/p/#…", "onion": true}}
```

- **`onion`** в запросе — необязательный. Без него, как и с `data: {}`, `null` или не-булевым значением, приглашение прежнее: ссылка версии 1, в ответе `"onion": false`. Ошибки разбора здесь нет: поле — пожелание, а не обязательство.
- `onion: true` при включённом Tor, когда tor подключён к сети, даёт ссылку **версии 2**: прямой адрес, onion-адрес и одноразовый ключ доступа. В ответе `"onion": true`.
- `onion: true`, когда Tor выключен или tor не подключён, даёт ссылку версии 1 и `"onion": false`. Приглашение, которое заведомо не сработает снаружи, хуже честного «только дома».
- Одноразовый ключ живёт столько же, сколько приглашение, — 10 минут. Он перестаёт действовать, когда приглашение использовано, истекло или погашено, в том числе отзывом устройства. Закрытая половина существует только в ссылке, на сервере её нет.
- Прямой адрес в приглашении, запрошенном через onion, — сетевой адрес сервера, а не onion-имя из заголовка `Host`: первый IPv4 из `addresses.direct`, иначе первый адрес оттуда, иначе адрес привязки — правило ссылки claim. Правило §8A «адрес — тот, по которому дозвонилось устройство» действует для прямого пути.
- Поле `onion` в ответе клиент прошлой сборки пропускает как незнакомое.

### Ссылка версии 2

Префикс и кодирование — как у версии 1: `https://nox.app/p/#<base64url без выравнивания>`.

| Смещение | Поле | Размер | Значение |
|---|---|---|---|
| 0 | `version` | 1 | `0x02` |
| 1 | `host_type` | 1 | как в версии 1 |
| 2 | `host` | 4 / 16 / 1+N | как в версии 1 |
| … | `port` | 2 | big-endian, порт прямого входа |
| … | `server_fingerprint` | 32 | как в версии 1 |
| … | `token` | 16 | как в версии 1 |
| … | `onion_pub` | 32 | **открытый** ключ Ed25519 onion-сервиса |
| … | `onion_port` | 2 | big-endian, 443 |
| … | `one_time_priv` | 32 | **закрытый** одноразовый ключ x25519 |

- Длина: 122 байта для IPv4 (163 знака base64url), 134 для IPv6, 119 + N для DNS-имени длиной N.
- Onion-адрес выводится из `onion_pub` по rend-spec-v3: `base32(onion_pub ‖ SHA3-256(".onion checksum" ‖ onion_pub ‖ 0x03)[0:2] ‖ 0x03)` в нижнем регистре, плюс `.onion`. Ключ, а не адрес, — потому что он короче и не несёт контрольной суммы, которую можно испортить.
- Имена полей говорят, какая это половина: `onion_pub` открытый, `one_time_priv` закрытый. На проводе (`pair`, `device.setAccessKey`) `access_key` всегда открытый.
- Claim-ссылка версию 2 не использует никогда.
- Клиент, знающий только версию 1, отказывает ссылке версии 2 с отдельной причиной — правило §8A о неизвестной версии. Поэтому сервер выдаёт версию 2 только по просьбе.

## 7. Что меняется в существующих местах контракта

- §1, порт: «порт приезжает ссылкой» — для прямого входа; onion-вход — всегда 443.
- §2.1, таблица кодов спаривания и §8A, отказы `pair`: `invalid_token` — ещё и claim через onion.
- §2.1, правило эволюции: новая команда безопасна только за признаком поддержки (§2 этого документа).
- §8A, `device.invite`: правило адреса из `Host` — для прямого пути; через onion — §6.
- §8A, событие `device.paired`: «общее для всех трёх внежурнальных событий» → четырёх, с `server.addresses`.

## 8. Чего нет

- Новых кодов ошибок нет.
- Номер схемы не меняется: все поля необязательны или новы, и старый клиент корректен без них.
- Onion-адрес не печатается в журнал сервера и не показывается на странице статуса.
