# Implementation Plan: Сервер в сети Tor — onion-адрес только для своих устройств

**Branch**: `039-tor-server` | **Date**: 2026-10-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/039-tor-server/spec.md`

## Summary

Клиентский сервер запускает собственный tor отдельным процессом, командует им через управляющий порт и публикует onion-сервис. Сервис ведёт на отдельный внутренний TLS-вход того же сервера. Доступ к onion — только по ключам доступа: авторизация клиентов Tor v3, x25519.

- **Ключи доступа.** Устройство регистрирует ключ в спаривании или отдельной командой. Приглашение с onion-адресом несёт одноразовый ключ.
- **Адреса.** Свои адреса — прямые и onion — сервер сообщает в ответе на приветствие и внежурнальным событием при их смене.
- **Без Tor** сервер работает по прямому пути как раньше, и страница статуса говорит почему.
- **Провод** меняется только добавлениями, поэтому нынешнее приложение работает без изменений; его сторона — этап 2.

Решения и замеры — [research.md](./research.md).

## Technical Context

**Language/Version**: Go 1.27 (`client_backend/`); Dart 3.12 / Flutter 3.44.1 — только тест совместимости, кода приложения фаза не трогает

**Primary Dependencies**: без новых. Четыре прямых зависимости остаются (`coder/websocket`, `modernc.org/sqlite`, `x/sync`, `rsc.io/qr`); `crypto/ecdh`, `crypto/sha3`, `crypto/ed25519`, `os/exec` — стандартная библиотека. Внешняя программа — **C tor ≥ 0.4.9**: не зависимость сборки, а соседний процесс

**Storage**: SQLite — три новых столбца в `001_init.sql` ([data-model.md](./data-model.md)); каталог состояния tor `<db>-tor` (кэш, вне бэкапа)

**Testing**: `go test -race ./...` — модульные тесты без сети: фальшивый управляющий порт, векторы адреса, хранилище, обработчики через настоящий TLS-стек. Сквозной тест через настоящий Tor включается переменной `NOX_TOR_TEST_BIN` и без неё пропускается. На стороне приложения — `flutter test` для совместимости, плюс `make gate` и `make golden-verify` перед коммитом Dart-кода

**Target Platform**: сервер на Linux, macOS и Windows; поиск tor по флагу, рядом с бинарём и в `PATH`. Проверяется на macOS arm64 с tor 0.4.9.13

**Project Type**: сервер (web-service) + протокол

**Performance Goals**:
- смена списка ключей доходит до сети не позже чем через минуту; в спайке публикация занимает 0–2 секунды;
- смена прямого адреса доходит до устройств не позже чем через минуту — наблюдатель опрашивает раз в 30 секунд;
- tor уходит не позже чем через 30 секунд после гибели сервера; в спайке — 2 секунды

**Constraints**:
- тайм-ауты на onion-входе выдерживают задержку круга до 10 секунд — им дано 30;
- onion-адрес и ключи не попадают ни в журнал, ни на страницу;
- ни одна неудача tor не останавливает прямой путь;
- провод — только добавления

**Scale/Scope**: один человек, единицы устройств; список ключей — устройства плюс живые приглашения, единицы — десятки записей

**Structure Decision**: новый пакет `internal/tor` владеет всем, что знает о tor, — процессом, протоколом, seed и адресом. Сервер видит его через супервизор: `Status()`, `KeysChanged()`, `ReadyForInvite()`, `Offered()`, `OnionPublicKey()`, `Address()`. При выключенном Tor — выключенная реализация тех же методов. Хранилище остаётся единственным писателем базы; tor её не открывает. Интерфейсов в `internal/tor` два — управляющее соединение и запуск процесса, — и оба нужны ровно затем, чтобы логику супервизора можно было проверить на подставных.

**Порядок остановки** (research, решение 16): три HTTP-сервера — onion, основной, страница статуса, каждый со своим сроком → параллельное закрытие WebSocket-соединений → ожидание до 15 с → наблюдатель и супервизор (свой контекст) → хаб → база.

## Complexity Tracking

| Отступление | Зачем | Почему не проще |
|---|---|---|
| Второй процесс рядом с сервером — tor, вопреки «no sidecars» инварианта 1 | Без tor onion-адреса нет. Решение владельца от 2026-10-03: «сервер — Go-бинарь и процесс tor рядом». Tor не открывает базу, поэтому суть инварианта — один процесс у файла базы — сохраняется. Формулировка правится в этом же наборе изменений, первыми задачами — до кода; конституция — поправкой 1.3.1 → 1.3.2 (PATCH), одобренной владельцем 2026-10-03 в обсуждении трека («давай так и оставим»). | tor внутри бинаря через cgo ломает «один статический бинарь без C-кода»; Arti отдельным процессом без официальных сборок вне Linux; системный tor не подконтролен серверу. |
| Провод меняется в этапе 1, а клиентская сторона приходит в этапе 2 | Владелец выбрал разбиение «сервер+контракт → приложение». Каждое добавление необязательно или ново, и нынешний клиент корректен, не зная о нём. Это закрепляется тестом совместимости (SC-011), а не допущением. | Тянуть сторону приложения сюда значит делать этап 2 внутри этапа 1: Tor-клиента в приложении ещё нет, и пользоваться адресами и ключами ему нечем. |
