# Feature Specification: Сервер в сети Tor — onion-адрес только для своих устройств

**Feature Branch**: `039-tor-server`

**Created**: 2026-10-03

**Status**: Draft

**Input**: Этап 1 трека Tor ([roadmap-tor.md](../../docs/client-backend/roadmap-tor.md)) по решениям владельца от 2026-10-03. Клиентский сервер за домашним NAT или CGNAT становится достижим из любой сети через onion-сервис Tor — и только для спаренных устройств этого человека. Сервер сам запускает свой tor и останавливает его вместе с собой; onion-адреса нет в ссылках — свои адреса сервер сообщает устройствам после подключения; доступ к onion — по ключам доступа, которые устройства регистрируют сами; приглашение второго устройства может нести onion-адрес и одноразовый ключ. Приложение (Tor-клиент, выбор пути, экран) — этап 2.

## Зачем это вообще

Сервер стоит у человека дома, за роутером, а часто ещё и за CGNAT провайдера. Входящие соединения снаружи до него не доходят, и устройство человека видит его, только пока находится в той же сети. Вне дома переписка просто недоступна.

Onion-сервис Tor снимает это целиком. Сервер сам выходит в сеть Tor исходящими соединениями и публикует там свой адрес; устройство тоже звонит наружу, и обе стороны встречаются внутри сети. Роутер, провайдер, белый IP и доменное имя в этой картине не участвуют.

Этот этап делает серверную половину: сервер публикует onion-адрес, пускает к нему только устройства своего человека и сообщает им, где его искать. Приложение научится всем этим пользоваться на этапе 2.

## Пять слов, которые нельзя путать

- **Прямой адрес** — `host:port`, на котором сервер слушает в сети. Именно он сегодня едет в ссылке спаривания.
- **Onion-адрес** — имя сервера в сети Tor, 56 знаков и `.onion`. Оно само является открытым ключом onion-сервиса, поэтому Tor проверяет, что ответил владелец этого ключа.
- **Ключ onion-адреса** — пара, из которой выводится onion-адрес. Хранится в базе сервера рядом с TLS-ключом фазы 036. Это **адрес, а не личность**: доверие к серверу по-прежнему держится только на отпечатке TLS-ключа из ссылки. Поэтому второй ключ на машине не противоречит правилу фазы 036 «у машины одна личность»: onion-ключ ничего не удостоверяет, а onion-адрес устройство получает по каналу, уже проверенному отпечатком.
- **Ключ доступа** — пара устройства для авторизации клиентов Tor. Закрытая часть живёт только на устройстве, открытая — в списке onion-сервиса. Без ключа из списка Tor не построит соединение и не даст узнать, в сети ли сервер.
- **Одноразовый ключ доступа** — ключ, который сервер выпускает для приглашения второго устройства. Его закрытая часть есть только в выданной ссылке; живёт он, пока живёт приглашение.

## Что этап меняет на проводе — и почему нынешний клиент этого не заметит

Контракт меняется **только добавлениями**: текущие адреса в ответе на приветствие, внежурнальное событие о смене адресов, необязательный ключ доступа в спаривании, команда регистрации ключа доступа и приглашение нового формата — только по явной просьбе устройства. Ни одна существующая команда, событие или код ошибки не меняют смысла.

Нынешний клиент остаётся корректным, ничего об этом не зная. Незнакомое поле и незнакомое событие он пропускает (§2.1 контракта), необязательного поля не шлёт, нового формата приглашения не просит. Клиентская сторона всех добавлений — этап 2. Так этот этап читает Принцип VII («обе стороны в одном change-set'е с контрактом»): у клиента здесь нет обязанностей, которые он мог бы нарушить. То, что нынешний клиент действительно пропускает новое, проверяется в этом же этапе.

## Clarifications

### Session 2026-10-03

Вопросы решены автономно по поручению владельца («сделай всё самостоятельно», 2026-10-03): каждый ответ — рекомендация, принятая без опроса, и пересматривается на ревью PR.

- Q: При каком состоянии Tor сервер выдаёт приглашение с onion-адресом? → A: только если Tor включён и tor сейчас подключён к сети; иначе — приглашение прежнего формата. Приглашение, которое заведомо не сработает снаружи, хуже честного «только дома».
- Q: Допустим ли короткий обрыв onion-соединений других устройств, когда сервис перепубликуется из-за спаривания, отзыва, выдачи или истечения приглашения? → A: да. Изменения, пришедшие подряд, объединяются в одну перепубликацию, а ответ на вызвавшую её команду уходит первым. Спаривание и отзыв редки, а переподключение — обычная работа клиента.
- Q: Какие прямые адреса попадают в список адресов сервера? → A: если сервер слушает на всех интерфейсах — адреса всех поднятых интерфейсов, IPv4 и IPv6, кроме loopback и link-local; если на конкретном адресе — только он. Порт — порт основного входа. В списке не больше 16 прямых адресов.
- Q: Принимает ли сервер регистрацию ключа доступа, когда Tor выключен? → A: да. Ключ хранится и начинает действовать, как только Tor включат; иначе устройство пришлось бы регистрировать заново.
- Q: Что страница статуса называет «опубликован»? → A: сеть приняла описание onion-адреса после последней публикации или перепубликации. До этого — «публикуется»; если ключей доступа нет — «не опубликован: нет устройств с доступом».

**Уточнения по результатам спайка на этапе plan** (2026-10-03, замерено против tor 0.4.9.13 — [research.md](./research.md)):

- Перепубликация без ключа не отрезает клиента с уже построенной цепочкой встречи: tor переиспользует её для новых соединений. Поэтому любое удаление ключа из списка рвёт сервисные цепочки (FR-017), и все onion-подключения переподключаются. Это тот самый короткий обрыв, который допускает FR-018.
- Onion-адрес входит в список адресов, только если tor найден и подходящей версии (FR-024): сервер, на котором tor не установлен, не обещает устройствам адрес, которого не будет.

## User Scenarios & Testing *(mandatory)*

Приложение подключается к onion-адресу только на этапе 2, поэтому «устройство» в проверках этого этапа — тестовый клиент, который ходит через настоящую сеть Tor.

### User Story 1 — Сервер достижим из любой сети (Priority: P1)

Сервер стоит дома за NAT без проброса портов. Устройство человека — в мобильной сети. До этой фазы между ними нет пути вообще. После неё устройство с ключом доступа подключается по onion-адресу из любой сети — тем же протоколом, с тем же TLS и с той же проверкой отпечатка.

**Почему первый**: это единственная причина трека.

**Независимая проверка**: сервер за NAT; тестовый клиент с зарегистрированным ключом доступа подключается из другой сети, проходит проверку отпечатка, здоровается, обменивается сообщением и файлом.

**Acceptance Scenarios**:

1. **Given** сервер запущен с Tor и у устройства зарегистрирован ключ доступа, **When** устройство из другой сети подключается по onion-адресу, **Then** соединение устанавливается, отпечаток TLS-ключа совпадает с тем, что в ссылке спаривания, и приветствие проходит.
2. **Given** устройство подключено через onion, **When** оно шлёт команды и байты файлов, **Then** всё работает так же, как по прямому пути.
3. **Given** сервер перезапущен, **When** устройство подключается снова, **Then** onion-адрес тот же.
4. **Given** база перенесена из бэкапа — одного файла — на другую машину, **When** сервер запущен там, **Then** onion-адрес тот же, и устройства подключаются без нового спаривания.

---

### User Story 2 — Чужому onion-адрес ничего не даёт (Priority: P1)

Onion-адрес мог утечь: со скриншота, из лога, вместе с отозванным устройством. Тот, у кого есть только адрес, не должен получить ничего — ни соединения, ни знания, в сети ли сервер.

**Почему тоже первый**: публичный onion-сервис открыт всему интернету. Его можно сканировать, заваливать соединениями и по доступности следить, когда сервер в сети. Авторизация клиентов закрывает это на уровне Tor — до того, как соединение дойдёт до сервера.

**Независимая проверка**: клиент, знающий onion-адрес, но без ключа в списке, не может открыть соединение; отозванное устройство — тоже.

**Acceptance Scenarios**:

1. **Given** клиент знает onion-адрес, но его ключа нет в списке, **When** он подключается, **Then** соединение не строится.
2. **Given** устройство отозвано, **When** оно подключается по onion-адресу, **Then** соединение не строится.
3. **Given** ни одного ключа доступа нет, **When** сервер запущен с Tor, **Then** onion-адрес не публикуется вовсе: пустой список сделал бы сервис открытым.
4. **Given** клиент с ключом доступа подключился через onion, **When** он предъявляет claim-ссылку, **Then** claim отклоняется.
5. **Given** onion-адрес опубликован, **When** через него запрашивают страницу статуса, **Then** её там нет.

---

### User Story 3 — Без Tor сервер работает как раньше (Priority: P1)

Tor выключен флагом, не установлен, слишком старый, не смог подключиться к сети или упал.

**Почему тоже первый**: Tor — добавка к прямому пути, а не его замена. Сервер, который перестал работать дома из-за того, что не поднялся tor, хуже сервера без Tor.

**Независимая проверка**: при выключенном, отсутствующем и упавшем tor все проверки прямого пути проходят, а страница статуса называет причину.

**Acceptance Scenarios**:

1. **Given** Tor выключен флагом запуска, **When** сервер запущен, **Then** tor не запускается, onion-адрес не публикуется и не сообщается, прямой путь работает как до фазы.
2. **Given** tor не найден или его версия ниже минимальной, **When** сервер запущен, **Then** сервер работает по прямому пути, а в логе и на странице статуса названы причина и что сделать.
3. **Given** tor упал во время работы, **When** сервер это замечает, **Then** он запускает tor заново с растущей паузой, и onion-адрес возвращается тем же.
4. **Given** процесс сервера завершился любым способом, включая аварийный, **When** проходит 30 секунд, **Then** запущенного им tor больше нет.

---

### User Story 4 — Устройство знает, где сервер (Priority: P2)

Адрес сервера меняется: роутер выдаёт машине другой IP, onion-адрес появляется, когда устройство впервые регистрирует ключ доступа. Ссылку после спаривания не обновить, поэтому свои адреса сервер сообщает устройствам сам.

**Почему второй**: без этого устройство не узнает onion-адрес вовсе — в ссылке его нет. Но пользоваться адресами начнёт только приложение этапа 2.

**Независимая проверка**: тестовый клиент получает адреса в ответе на приветствие и новый список — при их смене.

**Acceptance Scenarios**:

1. **Given** устройство подключилось любым путём, **When** приходит ответ на приветствие, **Then** в нём текущие адреса сервера: прямые и — пока сервер публикует onion — onion-адрес.
2. **Given** устройство на связи, **When** у сервера сменился прямой адрес или onion-адрес появился в списке либо ушёл из него, **Then** устройство получает новый список не позже чем через минуту.
3. **Given** список адресов, **When** его читают, **Then** в нём нет адресов, бесполезных вне машины: loopback и link-local.
4. **Given** устройство прошлой сборки, **When** оно подключается, **Then** оно работает как раньше: новое поле и новое событие ему незнакомы и пропускаются.

---

### User Story 5 — Второе устройство спаривается из другой сети (Priority: P2)

Человек на работе хочет добавить ноутбук, а сервер — дома. Спаренный телефон показывает приглашение, в котором кроме прямого адреса есть onion-адрес и одноразовый ключ доступа. Ноутбук спаривается через Tor.

**Почему второй**: без этого добавить устройство можно только дома. Это не блокирует основной сценарий, но иначе Tor работает лишь для тех устройств, что уже спарены.

**Независимая проверка**: тестовый клиент в другой сети спаривается по приглашению с одноразовым ключом, регистрирует свой ключ доступа и подключается снова уже им; одноразовый ключ после этого не работает.

**Acceptance Scenarios**:

1. **Given** Tor включён и tor подключён к сети, **When** спаренное устройство просит приглашение с onion-адресом, **Then** ссылка несёт прямой адрес, onion-адрес и одноразовый ключ доступа и живёт 10 минут, как любое приглашение.
2. **Given** новое устройство в другой сети, **When** оно предъявляет такое приглашение через onion и передаёт в спаривании свой ключ доступа, **Then** оно спаривается и дальше подключается по onion своим ключом.
3. **Given** приглашение использовано, истекло или погашено, **When** кто-то подключается с его одноразовым ключом, **Then** соединение не строится.
4. **Given** устройство не просило приглашение с onion-адресом, **When** оно запрашивает приглашение, **Then** получает ссылку прежнего формата.
5. **Given** приглашение запрашивает устройство, подключённое через onion, **When** сервер собирает ссылку, **Then** прямой адрес в ней — сетевой адрес сервера, а не onion-имя, по которому пришёл запрос.

---

### User Story 6 — Видно, что с Tor (Priority: P2)

Человек открывает страницу статуса на машине сервера и хочет понять: работает ли Tor, достижим ли сервер снаружи и не пора ли обновлять tor.

**Почему второй**: Tor может сломаться тихо — устареть, не подключиться, упасть. Без этой страницы человек узнает об этом, только когда вне дома не получит сообщений.

**Независимая проверка**: страница показывает каждое из состояний ниже, а onion-адреса и ключей на ней нет.

**Acceptance Scenarios**:

1. **Given** сервер забран, **When** открыта страница статуса, **Then** видно: включён ли Tor, версия tor, вердикт сети о ней, подключён ли tor к сети, опубликован ли onion-адрес, а если нет — почему, сколько устройств имеют доступ из любой сети и последняя ошибка.
2. **Given** сеть объявила версию tor устаревшей или негодной, **When** открыта страница, **Then** это видно как предупреждение.
3. **Given** страница открыта, **When** её видят через плечо, **Then** на ней нет ни onion-адреса, ни ключей.

---

### Edge Cases

- **Что, если ключей доступа нет ни одного?** Onion-адрес не публикуется: с пустым списком сервис стал бы открытым для всех. Поэтому сервер, который ещё не забран или остался без устройств, через onion недостижим в принципе, и claim через onion для него невозможен по построению. Отказ claim на onion-входе остаётся вторым рубежом.
- **Что, если tor из пакетов дистрибутива слишком старый?** Во многих LTS-дистрибутивах в пакетах лежат ветки 0.4.7 и 0.4.8, которые сеть больше не пускает. Такой tor не используется, а лог и страница статуса предлагают поставить tor из репозитория Tor Project.
- **Что, если tor не может подключиться к сети** — сеть его блокирует или часы машины сильно сбиты? Страница статуса показывает причину, которую назвал tor; прямой путь работает. Мосты — отдельный этап.
- **Что, если сеть объявила версию tor негодной?** tor останавливается сам. Сервер показывает «не годится», работает по прямому пути, а повторные запуски идут с растущей паузой, а не подряд.
- **Что, если на машине уже работает системная служба tor или второй сервер NOX?** Каждый сервер запускает собственный tor со своим каталогом состояния и своим управляющим входом. Чужой tor не используется, и экземпляры друг другу не мешают.
- **Что, если список ключей изменился** — спаривание, отзыв, приглашение, его истечение? Сервис перепубликуется; изменения, пришедшие подряд, объединяются в одну перепубликацию. Onion-соединения других устройств могут на короткое время оборваться — они переподключаются сами. Ответ на команду, вызвавшую изменение, уходит **до** перепубликации, иначе перепубликация съела бы ответ на спаривание.
- **Что, если отозвано последнее устройство?** Список пуст, onion-адрес снимается, и уже построенные цепочки сервиса рвутся так же, как при любом удалении ключа (FR-017). Сервер снова принимает claim — но только по прямому пути.
- **Что, если сервер перезапущен, пока живы приглашения?** Одноразовые ключи истёкших приглашений в список не возвращаются.
- **Что, если Tor выключили и включили снова?** Onion-адрес тот же, и ключи доступа те же: ни то, ни другое при выключении не стирается.
- **Что, если устройство зарегистрировало новый ключ доступа?** Прежний перестаёт действовать: у устройства один ключ.
- **Что, если адреса сервера сменились, пока устройство было офлайн?** Оно узнает их из следующего приветствия: событие о смене не журналируется и разрыв не переживает, а ответ на приветствие всегда несёт текущий список.
- **Что, если одна база запущена на двух машинах сразу?** У обеих будет один и тот же onion-адрес. Это не поддерживается — так же, как два сервера с одним TLS-ключом.

## Requirements *(mandatory)*

### Functional Requirements

**tor рядом с сервером**

- **FR-001**: Сервер ДОЛЖЕН сам запускать собственный экземпляр tor, управлять им и останавливать его вместе с собой. Управлять этим tor НЕ ДОЛЖЕН никто, кроме самого сервера.
- **FR-002**: tor ДОЛЖЕН завершаться сам, если процесс сервера завершился любым способом, включая аварийный.
- **FR-003**: tor НЕ ДОЛЖЕН открывать базу сервера. Ключ onion-адреса сервер передаёт ему при каждом запуске, и tor его не сохраняет.
- **FR-004**: tor на сервере ДОЛЖЕН только публиковать onion-сервис. Он НЕ ДОЛЖЕН открывать других входов — ни прокси, ни ретранслятора — и НЕ ДОЛЖЕН работать в режиме single onion, который ускоряет сервис ценой того, что сервер легко найти.
- **FR-005**: Сервер ДОЛЖЕН находить tor в таком порядке: путь из флага запуска, рядом со своим исполняемым файлом, в системе. Путь из флага — окончательный: если там tor нет, сервер не ищет дальше и говорит, что tor не найден. Иначе явное указание молча подменялось бы чем-то другим. Минимальная версия — **0.4.9**: более старый tor не используется, и сервер говорит, что сделать.
- **FR-006**: Флаг запуска ДОЛЖЕН выключать Tor совсем. Тогда tor не запускается, onion-адрес не публикуется и не сообщается; ключ onion-адреса и ключи доступа при этом сохраняются.
- **FR-007**: Любая неудача tor — не найден, слишком старый, не запустился, не подключился к сети, упал — НЕ ДОЛЖНА мешать прямому пути. Сервер повторяет запуск с растущей паузой, а причина последней неудачи видна в логе и на странице статуса.

**Onion-адрес**

- **FR-008**: Ключ onion-адреса ДОЛЖЕН появляться вместе с хранилищем, храниться в базе рядом с TLS-ключом и не меняться за жизнь хранилища. Бэкап остаётся одним файлом, а восстановление из него сохраняет onion-адрес.
- **FR-009**: Onion-адрес ДОЛЖЕН публиковаться, только пока Tor включён и в списке есть хотя бы один ключ доступа.
- **FR-010**: Onion-трафик ДОЛЖЕН приходить на отдельный внутренний вход, который ведёт только на основной TLS-вход. Через onion доступно всё, что доступно по прямому пути, кроме claim (FR-011). Страницы статуса там нет.
- **FR-011**: Claim, пришедший через onion, ДОЛЖЕН отклоняться так же, как claim на занятый сервер, — включая повтор уже израсходованного claim-токена. Отказ НЕ ДОЛЖЕН тратить токен.
- **FR-012**: На onion-входе ожидания сервера ДОЛЖНЫ быть рассчитаны на задержки Tor: соединение с задержкой круга до 10 секунд сервер НЕ ДОЛЖЕН рвать по тайм-ауту.
- **FR-013**: Сертификат и отпечаток ДОЛЖНЫ быть одними и теми же на прямом и на onion-входе. Onion даёт достижимость, а не доверие: доверие по-прежнему держится только на проверке отпечатка из ссылки.

**Ключи доступа**

- **FR-014**: У каждого спаренного устройства ДОЛЖЕН быть не более чем один ключ доступа. Открытую часть устройство регистрирует само по проверенному соединению; повторная регистрация заменяет прежний ключ. Регистрация принимается и при выключенном Tor: ключ хранится и начинает действовать, как только Tor включат.
- **FR-015**: Новое устройство ДОЛЖНО иметь возможность передать свой ключ доступа в самом спаривании. Устройство, пришедшее через onion по одноразовому ключу, иначе потеряло бы доступ, как только этот ключ перестанет действовать.
- **FR-016**: Закрытые части ключей доступа устройств НЕ ДОЛЖНЫ попадать на сервер.
- **FR-017**: Отзыв устройства ДОЛЖЕН удалять его ключ доступа. После этого устройство не может открыть новое соединение по onion-адресу. Любое удаление ключа из списка — отзыв, использование, истечение или погашение одноразового ключа — ДОЛЖНО рвать уже построенные onion-цепочки сервиса: иначе клиент с живой цепочкой продолжает открывать соединения и после удаления ключа (замерено, research, решение 15).
- **FR-018**: Изменение списка ключей ДОЛЖНО доходить до сети без перезапуска сервера и не позже чем через минуту. Изменения, пришедшие подряд, объединяются в одну перепубликацию. Ответ на команду, вызвавшую изменение, ДОЛЖЕН уходить до перепубликации. Короткий обрыв onion-соединений других устройств при перепубликации допустим: они переподключаются сами.

**Приглашение с onion-адресом**

- **FR-019**: Спаренное устройство ДОЛЖНО иметь возможность попросить приглашение, которое кроме прямого адреса несёт onion-адрес и одноразовый ключ доступа. Такое приглашение выдаётся, только если Tor включён и tor сейчас подключён к сети; иначе выдаётся приглашение прежнего формата.
- **FR-020**: Закрытая часть одноразового ключа ДОЛЖНА существовать только в выданной ссылке, на сервере её нет. Открытая часть остаётся в списке, пока приглашение не использовано, не истекло и не погашено, — и ни минутой дольше.
- **FR-021**: Устройство, не просившее приглашение с onion-адресом, ДОЛЖНО получать ссылку прежнего формата: нынешние клиенты продолжают работать.
- **FR-022**: Прямой адрес в приглашении, запрошенном через onion, ДОЛЖЕН быть сетевым адресом сервера, а не onion-именем, по которому пришёл запрос.
- **FR-023**: Claim-ссылка НЕ ДОЛЖНА меняться: она по-прежнему несёт только прямой адрес.

**Адреса сервера**

- **FR-024**: Ответ на приветствие ДОЛЖЕН нести текущие адреса сервера: прямые — сетевые адреса с портом — и onion-адрес с портом, пока сервер намерен его публиковать, то есть пока Tor включён, tor найден подходящей версии и в списке есть хотя бы один ключ доступа. Временный сбой tor список не меняет: иначе он менялся бы при каждом перезапуске tor.
- **FR-025**: Когда список меняется, все поприветствовавшие соединения ДОЛЖНЫ получать новый список внежурнальным событием, и ни одно соединение НЕ ДОЛЖНО получить список старее того, что оно уже получило — в ответе на приветствие или событием. Смену прямого адреса сервер ДОЛЖЕН замечать не позже чем через минуту.
- **FR-026**: Если сервер слушает на всех интерфейсах, прямые адреса — это адреса всех поднятых интерфейсов, IPv4 и IPv6; если на конкретном адресе — только он, если это не loopback. Порт — порт основного входа. В список НЕ ДОЛЖНЫ попадать адреса, бесполезные вне машины, — loopback и link-local, — и в нём не больше 16 прямых адресов. Сервер, привязанный к loopback, прямых адресов не сообщает: устройство и так знает адрес из своей ссылки.

**Страница статуса**

- **FR-027**: В состоянии «забран» страница ДОЛЖНА показывать: включён ли Tor; версию tor; вердикт сети о ней — рекомендована, устарела, не годится или пока неизвестно; подключён ли tor к сети; опубликован ли onion-адрес, а если нет — почему; сколько устройств имеют доступ из любой сети; последнюю ошибку. «Опубликован» значит, что сеть приняла описание onion-адреса после последней публикации или перепубликации; до этого — «публикуется»; без ключей доступа — «не опубликован: нет устройств с доступом»; при неработающем tor — «не опубликован: tor не работает». В состоянии «не забран» страница ДОЛЖНА показывать одну строку о Tor — включён ли он и, если что-то не так, почему: свежая установка без подходящего tor — самый частый случай, и узнать о нём человек должен до спаривания.
- **FR-028**: Вердикт о версии ДОЛЖЕН браться у самой сети Tor, а не вычисляться сервером по номеру. Номер нужен серверу только для минимальной версии.
- **FR-029**: Версия «устарела» или «не годится» ДОЛЖНА быть видна как предупреждение. Как обновлять tor — вне этапа ([Q24](../../docs/client-backend/open-questions.md)).
- **FR-030**: На странице НЕ ДОЛЖНО быть ни onion-адреса, ни ключей.

**Журнал**

- **FR-031**: Ни onion-адрес, ни ключи — onion-ключ, ключи доступа, одноразовые ключи — НЕ ДОЛЖНЫ попадать в лог и в последнюю ошибку на странице. Это касается и текста ошибок: ошибка команды tor называет только саму команду, без её аргументов и без строк ответа. Сообщения tor, нужные для диагностики, доходят до лога сервера без адресов и ключей.

**Контракт и правила**

- **FR-032**: Контракт ДОЛЖЕН быть дополнен **до** кода: onion как второй путь к тому же TLS-входу, адреса в ответе на приветствие, событие о смене адресов, ключ доступа в спаривании, команда регистрации ключа и приглашение нового формата по просьбе устройства. Ни одна существующая команда, событие или код ошибки НЕ ДОЛЖНЫ менять смысл.
- **FR-033**: Новых прямых Go-зависимостей быть НЕ ДОЛЖНО: управление tor и все ключи — собственный код и стандартная библиотека.
- **FR-034**: Инварианты сервера в `client_backend/CLAUDE.md` и рабочий режим в конституции ДОЛЖНЫ называть процесс tor: сервер остаётся одним статическим файлом без C-кода, а рядом с ним работает tor, которым сервер управляет и который не открывает базу.

### Key Entities

- **Ключ onion-адреса** — пара в хранилище сервера. Закрытая половина не покидает его, кроме как в tor при запуске, и tor её не сохраняет.
- **Onion-адрес** — производная от открытой половины. Сообщается устройствам, в ссылках не едет, в лог и на страницу статуса не попадает.
- **Ключ доступа устройства** — открытая часть, привязанная к спаренному устройству; у устройства не больше одного. Удаляется вместе с устройством.
- **Одноразовый ключ доступа** — открытая часть, привязанная к приглашению; живёт, пока живёт приглашение.
- **Адреса сервера** — текущий список прямых адресов и onion-адреса. Не хранится, а вычисляется заново.
- **Состояние Tor** — включён ли, версия, вердикт сети, подключение к сети, опубликован ли адрес, последняя ошибка. Живёт в памяти, видно на странице статуса.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Тестовый клиент с зарегистрированным ключом доступа из сети без прямого доступа к серверу подключается по onion-адресу, проходит проверку отпечатка, здоровается и обменивается сообщением и файлом.
- **SC-002**: Без ключа в списке ни одна из 20 попыток подключиться по onion-адресу не открывает соединение.
- **SC-003**: Onion-адрес совпадает до и после перезапуска сервера и после восстановления из бэкапа на другой машине.
- **SC-004**: Отозванное устройство не открывает соединение по onion-адресу уже через минуту после отзыва; одноразовый ключ — через минуту после использования или истечения приглашения.
- **SC-005**: Claim через onion не проходит ни разу; по прямому пути — проходит, как раньше.
- **SC-006**: При выключенном, отсутствующем, слишком старом и упавшем tor все существующие проверки прямого пути проходят, а страница статуса называет причину.
- **SC-007**: Через 30 секунд после любого завершения сервера, включая аварийное, запущенного им tor нет.
- **SC-008**: Смена прямого адреса, появление onion-адреса в списке и его уход доходят до подключённого устройства не позже чем через минуту.
- **SC-009**: Сессия через onion с задержкой круга до 10 секунд держится 30 минут без разрывов со стороны сервера.
- **SC-010**: Тестовый клиент спаривается из другой сети по приглашению с одноразовым ключом и подключается снова уже собственным ключом.
- **SC-011**: Нынешняя сборка приложения работает с сервером этого этапа без изменений: приветствие, спаривание по приглашению прежнего формата и переписка проходят.
- **SC-012**: Поиск по логу и по странице статуса не находит ни onion-адреса, ни ключей.
- **SC-013**: У сервера не появилось ни одной новой внешней зависимости.

## Assumptions

- **Этап серверный.** Приложение начнёт ходить через Tor на этапе 2. Проверки этого этапа идут тестовым клиентом через настоящую сеть Tor; в автоматическом наборе, которому сеть Tor недоступна, такие проверки пропускаются, а не падают.
- **Развёрнутых установок нет.** Схема живёт в одной миграции до первого релиза и правится на месте; базы разработки пересоздаются.
- **Поставки сервера пока нет:** он собирается из исходников. Решение «на macOS и Windows tor в комплекте с сервером» выполняется вместе с поставкой; до неё сервер находит tor по флагу, рядом с собой или в системе (FR-005). На macOS для разработки годится tor из Homebrew.
- **Пакеты дистрибутивов бывают устаревшими.** На Linux tor берётся из пакетов ОС, а если там он старше 0.4.9 — из репозитория Tor Project.
- **Сеть Tor доступна из сети сервера.** Там, где Tor заблокирован, нужны мосты — отдельный этап.
- **Часы машины сервера идут примерно верно**: без этого tor не подключится к сети.
- **Каталог состояния tor — кэш.** В бэкап он не входит; без него tor лишь дольше подключается при первом запуске.

## Вне объёма

- **Приложение** — Tor-клиент, выбор пути, состояние связи с бейджем Tor, регистрация ключа доступа на стороне устройства: этап 2 (`tor-app`).
- **Файлы с докачкой** — этап 3 (`resumable-files`).
- **Поиск сервера в локальной сети, Tor в приложении на Linux, мосты** — отложенные этапы трека.
- **Обновление tor без участия человека** — [Q24](../../docs/client-backend/open-questions.md). Этот этап только показывает версию и вердикт сети.
- **Упаковка, подпись и нотаризация сервера** для macOS и Windows — вместе с поставкой сервера.
- **Анонимность сервера.** Цель — достижимость. Сервис, доступный круглосуточно, можно вычислить по доступности, и обещать обратное нельзя.
- **Смена onion-ключа.** Ключ живёт столько же, сколько хранилище, — как и TLS-ключ.
