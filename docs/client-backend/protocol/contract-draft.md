# Контракт «приложение ↔ client-сервер» — черновик v0

**Дата:** 2026-08-20 · Заменяет инвентарную часть [wire-surface.md](wire-surface.md). Сверен с приложением: каждая команда и каждое поле проверены против реального кода `lib/`.

**Этапность реализации:**

| Этап | Что | Где |
|---|---|---|
| **1 — инфраструктура, без аутентификации** | Конверт §2, WebSocket-команды §3–§6, REST-поверхность §1/§7, SQLite | Реализация — каталог `client_backend/` этого репозитория |
| **2 — безопасность** | Спаривание и аутентификация по [authentication.md](../architecture/authentication.md) (документ одобрен; сознательно не на первом этапе) — §8.1 | там же |

Конверт помечен **v0**: пока обе стороны наши, правка формата — дешёвая; поле `schema` в рукопожатии существует ровно для этого.

---

## 1. Транспорт

Постоянный **WebSocket поверх TLS** (`wss`), порт 443, пиннинг ключа сервера из ссылки спаривания, самоподписанный сертификат. Внутри кадров — **JSON**. Само спаривание (откуда берутся адрес, пиннутый ключ и токен) — вне этого контракта: [../architecture/authentication.md](../architecture/authentication.md).

**REST-поверхность этапа 1** (тот же процесс, тот же порт):

| Endpoint | Что |
|---|---|
| `PUT /files/{upload_token}` | байты вложения (§7) |
| `GET /files/{download_token}` | скачивание с поддержкой Range (§7) |
| `GET /health` | живость процесса — для служб ОС и туннеля |
| локальная страница спаривания | только LAN-интерфейс; вне контракта (authentication.md) |

**Формат времени:** все поля `*_at` — целое unix-время в секундах, UTC. Других форматов дат в протоколе нет.

## 2. Конверт кадра — v0

Четыре вида кадров. Других нет.

**Приветствие сервера (сервер → приложение, ровно один раз при открытии сокета, до любых команд):**

```json
{"srv": {"schema_max": 1, "challenge": "<base64, 32 байта>"}}
```

`challenge` — 32 случайных байта на **каждое** соединение. Устройство подписывает его своим ключом и кладёт подпись в `signature` команды `session.hello` (§3); сервер подпись **проверяет** и при несовпадении соединение отклоняет.

Подписывается **не сам challenge, а `"nox/challenge/v1:" ‖ challenge`**, и подписываются **сырые байты**, а не их base64-запись. Префикс разделяет домены: без него подпись, снятая здесь, была бы валидной подписью над теми же байтами в любом будущем месте протокола, где подписывается что-то ещё. Сырые байты — потому что две реализации, по-разному расставившие padding, дали бы разные подписи над одним и тем же challenge.

**Контрольный вектор** (Ed25519, RFC 8032; закреплён, чтобы совпадение двух реализаций было свойством провода, а не удачей):

```
seed      = 0x00 0x01 0x02 … 0x1f      (32 байта)
public    = A6EHv/POEL4dcN0Y50vAmWfk1jCbpQ1fHdyGZBJVMbg=
message   = "nox/challenge/v1:probe"
signature = puHNSjLy6sqx5MEgiAuZiz6Zuyjohrz0EIEjkdQ9iazgyIEeUvGbK+UAIhHjpscFPCMBN7rpbfeoXr1UZXQZBQ==
```

**Команда (приложение → сервер):**

```json
{"id": 7, "cmd": "message.send", "data": { ... }}
```

**Ответ на команду (сервер → приложение):**

```json
{"id": 7, "ok": true,  "data": { ... }}
{"id": 7, "ok": false, "error": {"code": "name_taken", "message": "Chat name already exists"}}
```

**Событие (сервер → приложение):**

```json
{"seq": 1042, "event": "message.new", "data": { ... }}
```

Правила:

- **`id`** — корреляция команда↔ответ: выдаёт клиент, монотонно в рамках соединения; каждый ответ несёт `id` своей команды. Сопоставление устаревших ответов — только по `id`, никогда по содержимому.
- **`seq`** — сквозная нумерация событий: выдаёт сервер, **строго возрастающая на всю базу** (единственный писатель + AUTOINCREMENT). `seq` — это и есть курсор синхронизации.
- Один кадр — один JSON-объект; вид кадра различается по наличию `srv` / `cmd` / `ok` / `event`.

### 2.1. Коды ошибок v0

| Код | Когда | Реакция клиента и повторяемость |
|---|---|---|
| `invalid_request` | Кадр не разобран, нет обязательного поля, нарушены правила поля (длина, пустота) | Ошибка программиста — лог, фатальный экран; не повторять |
| `not_found` | Сущность по id не существует | Контекстно; не повторять |
| `name_taken` | Имя **чата** занято | Inline у поля ввода; не повторять. Имя человека этим кодом на этапе 1 **не отвечается**: §3 фиксирует, что сервер длину, набор символов и уникальность label не проверяет и отказать в приветствии из-за имени не может. На этапе 2 label назначает сервер при спаривании |
| `payload_too_large` | Превышен лимит из рукопожатия | Inline в композере; **не повторять** — предотвращается предполётной проверкой лимитов |
| `attachment_gone` | Срок хранения байтов истёк либо байты физически отсутствуют/повреждены | **Терминальное error-состояние экрана файла (5.3), без кнопки повтора** — не фатальный экран всего приложения |
| `rate_limited` | Слишком часто | **Автоповтор с backoff** |
| `internal` | Ошибка сервера | Inline-повтор вручную |
| `unauthenticated` | Подпись/сессия не прошли | §8.1; на этапе 1 не используется |
| `unsupported_schema` | Версия контракта клиента не поддерживается | Фатальный экран с предложением обновить приложение |

Правило эволюции: **неизвестный клиенту код трактуется как `internal`** (inline-повтор).

Коды спаривания (§8.1):

| Код | Когда |
|---|---|
| `invalid_token` | токена нет, он уже израсходован, либо это claim на занятом сервере |
| `token_expired` | приглашение предъявлено позже своего срока |

Разделены не ради полноты: у человека в этих случаях **разные действия**. Израсходованное и просроченное приглашение оба требуют выпустить новое, но `unauthenticated` требует спариться заново — одно общее «не получилось» не даёт выбрать, что делать.

## 3. Рукопожатие и синхронизация

Первая команда после открытия сокета — всегда `session.hello`. **Единственное исключение — `pair`** неспаренного устройства (§8.1): подписать challenge ему нечем, поэтому иначе спариться нельзя вообще.

```json
{"id": 1, "cmd": "session.hello", "data": {
  "schema": 1,
  "since": 1041,
  "label": "Anna",
  "device_key": "<base64: публичный ключ устройства, Ed25519>",
  "signature": "<base64: подпись \"nox/challenge/v1:\" ‖ challenge>"
}}
```

```json
{"id": 1, "ok": true, "data": {
  "schema": 1,
  "cursor": 1042,
  "journal_id": "j_7c1e4a90b3d2f6a1",
  "limits": {"max_message_bytes": 65536, "max_attachment_bytes": 104857600, "max_frame_bytes": 131072},
  "identity": {"id": "u_3f2a1c9d40b7e518", "label": "User7421"}
}}
```

- **`schema`** — версия контракта; несовместимость → `unsupported_schema`.
- **`since`** — курсор клиента: последний обработанный `seq`. Сервер после ответа досылает **все события с `since+1`** и переходит к живому потоку. Порядок строго: **подписка → replay → live**; дубликаты на стыке допустимы (клиент дедуплицирует по `seq`), потеря — нет.
- **Первое подключение устройства:** `since` опускается — replay не выполняется; клиент бутстрапится командами `chats.list`/`messages.list` и **принимает `cursor` из ответа как стартовый**.
- **Правило «догнан»:** клиент считается догнанным, когда обработан `seq ≥ cursor` из ответа hello (при `since == cursor` — сразу). Это единственный способ отличить конец replay от live — сами события неотличимы.
- **`limits`** — объявленные сервером пределы; клиент обязан проверять их **до** отправки (ограничитель в композере, предполётная проверка размера вложения).
- **`journal_id`** — идентификатор **хранилища** сервера, выданный один раз при его создании. Клиент обязан хранить его рядом с локальным кэшем и при **любом** расхождении считать, что кэшированный им мир исчез: полностью сбросить кэш переписки, отметку синхронизации и запомненный `identity.id`, затем подключиться заново. Правило существует потому, что по одному лишь курсору пересборку хранилища не распознать: пересобранное и уже обогнавшее прежнюю отметку хранилище от приветствия неотличимо, и клиент молча применил бы чужие события с совпавшими номерами. Проверка выполняется **до** применения первого кадра replay. Оставленный от прежнего мира `identity.id` разметил бы чужие сообщения как свои — поэтому он входит в сбрасываемое.
- **`identity`** — авторитет по собственной личности: `id` — собственный author-id клиента (им ключуется own/other-разметка сообщений), `label` — текущее имя. **Формат `id`:** `u_` + 16 строчных шестнадцатеричных знаков; выдаётся сервером, непрозрачен для клиента, разбору не подлежит, ни с каким секретом входа не совпадает (**Q11 закрыт 2026-09-02**). Зарезервированные локальные значения клиента (`system`, `me`, `other:*`) сервером не выдаются. **Обязанность клиента:** персистить **`id` и `label`** в сессию при каждом подключении **сессии, у которой есть вошедший человек**, и раскатывать по поверхностям (существующий канал `watchLabel`); подключение без входа личность **не усваивает** — иначе следующий вошедший унаследует чужое имя и чужой author-id. Префилл экрана выбора имени берётся отсюда, не из константы. Это же закрывает догоняющее обновление label, изменённого с другого устройства офлайн.
- **`identity.created`** — заведена ли эта личность **данным ответом**. Признак описывает ответ, а не личность: **персистированию не подлежит**, и приложение обязано вывести из него решение об онбординге один раз — при спаривании, — а не перевыводить его из каждого приветствия. Оба дефолта платит человек: `false` отбирает у нового человека выбор имени, `true` прогоняет вернувшегося через онбординг и затирает его имя, поэтому **отсутствие поля значит «исход не заявлен»**, и клиент не подставляет ни один из исходов. ⚠️ **Место чтения переехало:** на этапе 1 поле приходило в ответе на приветствие; с приходом спаривания его несёт **ответ `pair`/`recover`** (§8.1) — тем же объектом `identity` и с тем же полем, так что клиент читает исход в одном месте и от кадра не зависит. Приветствие спаренного устройства исход больше не заявляет: устройство спарено, а значит вопрос уже решён.
- **`label`** (необязательное; **поле этапа 1**) — заявление «я только что переименовался», **а не** «вот моё имя». Клиент присылает его только после реального переименования (включая выбор имени при онбординге) и перестаёт, как только сервер подтвердил новое имя в ответе. **Приветствие без `label` имя не меняет.** Правило нормативно: устройство с устаревшим кэшем, присылающее имя при каждом подключении, возвращает старое имя поверх нового — переименования начинают пинг-понговать между устройствами одного человека. Новой личности без заявленного имени сервер назначает `User<случайное четырёхзначное число>`. Сервер не проверяет длину, набор символов и уникальность и **не может отказать в приветствии из-за имени**. На этапе 2 источником label становится сервер (спаривание), и поле уходит из контракта.
- **`device_key`/`signature`** — аутентификация подключением: подпись `"nox/challenge/v1:" ‖ challenge` (§2) ключом устройства. `device_key` — **публичный ключ Ed25519** в base64; сервер хранит список ключей, которым разрешено подключаться, и проверяет подпись на **каждом** соединении. Личность находится по этому ключу. Входа по идентификатору-секрету в контракте **не существует**: устройство авторизуется спариванием (§8.1), соединение — подписью. Ключ, которого сервер не знает, и несошедшаяся подпись дают `unauthenticated` — для устройства это одно и то же событие «это больше не мой сервер», и обрабатывается оно как отзыв.

⚠️ **Смена смысла 2026-09-02 (фаза 030).** До этой даты при `schema: 1` поля `identity.id` и `author_id` (§5) везли отображаемое имя; после — публичный `user_id`. Номер схемы намеренно не поднят: развёрнутых установок не было, а `unsupported_schema` отправил бы существующие сборки в фатальный экран. Кадры, снятые до этой даты, несовместимы по смыслу — записанные ранее фикстуры и базы подлежат пересозданию.

**Принцип, стоящий за `since`/`seq`:** уведомление — оптимизация, а не транспорт; единственный гарантированный момент синхронизации — когда приложение само вышло на связь. Догоняющая синхронизация обязательна при каждом появлении на переднем плане, реконнекте и пробуждении машины — поэтому сервер отдаёт «что произошло с курсора X», а не «последние N».

## 4. Команды: чаты — этап 1

| Команда | `data` запроса | `data` ответа |
|---|---|---|
| `chats.list` | `{page, page_size, query?}` | `{chats: [Chat], has_more}` |
| `chat.get` | `{chat_id}` | `{chat: Chat}` |
| `chat.create` | `{name}` | `{chat: Chat}` — сервер авторитет по уникальности имени |
| `chat.rename` | `{chat_id, name}` | `{chat: Chat}` — переименовать может любой (открытое пространство); проверка уникальности **исключает сам `chat_id`**; переименование в неизменившееся (точно то же) имя — успех без события |
| `chat.nameAvailable` | `{name, exclude_chat_id?}` | `{available: bool}` |
| `chat.files` | `{chat_id, before_seq?, limit}` | `{files: [Attachment + message_id + seq], has_more}` — полный список вложений чата независимо от глубины локальной истории (панель 5.4); пагинация — по правилам `messages.list` (§5: `before_seq`, общий потолок 100, порция по возрастанию `seq`) |

Правила поля `name`: trim по краям; непустое после трима; **≤64 символов**; charset неограничен; нарушение → `invalid_request`. **Уникальность имени чата — регистроНЕзависимая** (правило регистрозависимости относится к label, не к имени чата): `chat.create` / `chat.rename` / `chat.nameAvailable` применяют одно правило при выдаче `name_taken` / `available:false`.

Пагинация: `page` — 1-базный; `page_size` выбирает клиент (серверный потолок 100 — общий для `chats.list` и `messages.list`; больший запрошенный размер сервер **молча ограничивает** потолком, значения меньше 1 → `invalid_request`). Порядок — по `last_activity_at` по убыванию, при равенстве — по `chat_id` по возрастанию (стабильный tiebreaker между страницами); порядок живой, поэтому клиент **дедуплицирует строки по `chat_id`** при склейке страниц. `query` — регистронезависимое (юникод-фолдинг, как у уникальности имени) вхождение подстроки в `name`, trim по краям; пустая строка = нет фильтра.

`chat.get` обязателен: входящее событие о чате **за пределами загруженного префикса** иначе ссылается на недостижимую сущность (пуш по чату из холодного старта, восстановление выбора на десктопе — те же случаи).

**`Chat` (wire):**

```json
{"chat_id": "c_9f2", "name": "Kitchen talks",
 "created_at": 1755600000, "created_by_label": "Anna",
 "last_message_preview": "...", "last_activity_at": 1755600123}
```

- `created_by_label` — label создателя: из него + `created_at` клиент рендерит генезис-строку треда («Chat created by …»). **Системных сообщений на проводе нет** — генезис-строка всегда собирается клиентом.
- `last_activity_at` изменяют **только сообщения и создание чата**; `chat.rename` его не трогает — строка не прыгает в списке.
- Превью и порядок — авторитет сервера **для страниц `chats.list`**; при живом событии `message.new` превью/порядок обновляет клиент из данных события (§6).

⚠️ Поля `unread_count` в wire-модели **нет** — счётчик устройство-локальный (§8.3). ⚠️ При «E2EE на устройстве» (Q1) серверное превью и `chat.files` невозможны в открытом виде — тот же шов, что у `body` (§5).

## 5. Команды: сообщения — этап 1

| Команда | `data` запроса | `data` ответа |
|---|---|---|
| `messages.list` | `{chat_id, before_seq?, limit}` | `{messages: [Message], has_more}` — обратная пагинация; внутри порции сообщения по возрастанию `seq`; `limit` под общим потолком 100 (§4); `total` не существует |
| `message.send` | `{chat_id, client_message_id, body?, attachment?: {file_id}}` | `{message: Message}` — серверное эхо |

- **`body` опционален при наличии `attachment`** (сообщение-вложение без текста — штатный случай); хотя бы одно из двух обязательно.
- **Авторства в запросе нет:** `author_id`/`author_label` сервер берёт из сессии и денормализует сам.
- **`client_message_id`** (UUID) — обязателен: ключ идемпотентности. Сервер хранит его и при повторе возвращает прежнее эхо. **Эхо и `message.new` собственных сообщений несут `client_message_id`** — очередь исходящих сверяется с replay после рестарта без холостого resend. Идемпотентность **на человека**: два разных человека, случайно совпавших ключом отправки, между собой не конфликтуют.
- **`author_id`/`author_label`** — `author_id` называет **личность** (формат — §3), `author_label` — вмороженная копия её имени **на момент отправки**: позднейшее переименование автора её не меняет, поэтому история показывает то имя, которое было тогда.
- **Таймаут отправки — 10 секунд** (согласован с keepalive §9): нет ответа → локальный статус `error`, повтор с тем же `client_message_id`.
- Статусы `sent`/`pending`/`error` — **локальные**, на провод не выходят; собственное сообщение, пришедшее с сервера (эхо или replay), = `sent`.

**`Message` (wire):**

```json
{"message_id": "m_51c", "seq": 1042, "chat_id": "c_9f2",
 "author_id": "u_3f2a1c9d40b7e518", "author_label": "Anna",
 "client_message_id": "3f0e…",
 "sent_at": 1755600123,
 "body": {"type": "text", "text": "..."},
 "attachment": {"file_id": "f_77", "name": "report.pdf", "size": 123456,
                "mime": "application/pdf", "expires_at": 1758200000}}
```

- **`body` — единственное место, которое заденет Q1 (граница E2EE):** при «E2EE на устройстве» объект `body` целиком заменяется на `{"type": "blob", "data": "<base64>"}`, и сервер перестаёт его интерпретировать. Реализация уже сейчас обязана не заглядывать внутрь `body` нигде, кроме клиента.
- **`Message.seq`** — это `seq` события `message.new` данного сообщения: глобальный, внутри одного чата разрежен. `before_seq` = минимальный загруженный `seq` чата; пер-чатовой нумерации не существует — обе реализации держат одну, глобальную.
- `attachment.expires_at` — срок хранения байтов: клиент персистит его вместе с вложением и гасит кнопку Save заранее, а не узнаёт при открытии.
- `client_message_id` присутствует только в собственных сообщениях автора-получателя кадра. Собственное — это `author_id == identity.id`, то есть **личность, а не устройство**: второе устройство того же человека тоже получает `client_message_id` чужой отправки. Незнакомый ключ клиент обязан считать отсутствующим — сверка идёт по его собственной очереди исходящих.

## 6. События — этап 1 (3 события)

| Событие | Когда | Обязанность клиента |
|---|---|---|
| `message.new` | Кто-то написал | Вставка в тред, если открыт; превью и порядок списка клиент обновляет **из данных события**; непрочитанное — **пересчётом от `seq` последнего открытия чата** (§8.3), инкрементный счётчик недопустим: §3 разрешает дубликаты на стыке replay/live |
| `chat.created` | Кто-то создал чат | Строка в списке — включая чат за пределами загруженного префикса (данные события полны; `chat.get` — для остальных путей) |
| `chat.updated` | Переименование | Раскатка по всем поверхностям (механизм `WatchChat` уже есть). **По изменению превью `chat.updated` не эмитится** — превью при новом сообщении обновляет клиент из `message.new`; серверный `last_message_preview` — снапшот для страниц `chats.list` |

- События несут **полную** wire-модель сущности, не только id.
- **Слияние wire-модели с локальной записью — merge, а не replace:** устройство-локальные поля (unread-состояние чата, `localPath` вложения, локальный статус сообщения) не перезаписываются применением события/эха. Прямое следствие §5 (статусы локальные) и §8.3 (счётчик локальный).
- **Свёртка превью едина** для серверного снапшота и клиентского обновления: одна строка, усечение до 120 символов; сообщение-вложение без текста → имя файла. Расхождение формул даст «мигание» строки списка между источниками.
- `ack`/`error` из инвентаря закрыты конвертом §2 (кадр «ответ»); события этапа 2 — `label.assigned`, `session.expired`, `device.revoked`, `identity.updated` — §8.1.

## 7. Файлы — вне сокета, этап 1

| Команда (по сокету) | `data` запроса | Ответ | Дальше (HTTP, §1) |
|---|---|---|---|
| `file.uploadBegin` | `{name, size, mime}` | `{file_id, upload_url, upload_token, max_attachment_bytes}` | `PUT` байтов с токеном |
| `file.downloadBegin` | `{file_id}` | `{download_url, download_token}` | `GET` с поддержкой Range (докачка) |

Цепочка вложения: `file.uploadBegin` → `PUT` байтов → `message.send {attachment: {file_id}}` → сервер собирает объект `attachment` из метаданных загрузки в эхо и в `message.new`. Метаданные (`name`, `size`, `mime`) сервер берёт из `uploadBegin`, а не из байтов; правила полей: `name` ≤ 255 символов, `mime` ≤ 128 (после трима, непустые) — нарушение → `invalid_request`; **`mime` клиент выводит из расширения имени файла** (локальная таблица; неизвестное расширение → `application/octet-stream`) — байты пикер не читает.

Причина выноса: по сокету большой файл блокирует все интерактивные команды (head-of-line), нет докачки, буферизация в память. Токены **одноразовые, TTL 10 минут**, гасятся первым обращением независимо от исхода; после обрыва клиент запрашивает новый токен той же командой. `upload_url`/`download_url` — **относительные** пути `/files/<токен>` (сервер своего публичного адреса не знает). Все отказы токена на HTTP — единый `404` без раскрытия причин; `PUT` принимает **ровно заявленный `size`** (больше → `413`, меньше → `400`, байты не сохраняются).

Хранение байтов на этапе 1 — **бессрочное**: `expires_at = created_at + 10 лет` (поле обязательно, клиентская логика гашения Save по сроку остаётся рабочей); настоящий TTL — после решения о политике хранения. `attachment_gone` отдаётся, когда срок истёк **или** байты физически отсутствуют. Загрузки, не привязанные к сообщению за сутки, зачищаются при старте сервера (строка и байты).

## 8A. Спаривание и аутентификация

Реализовано фазой 032. Модель — [authentication.md](../architecture/authentication.md); здесь только провод.

### Ссылка спаривания

```
https://nox.app/p/#<base64url без padding>
```

Полезная нагрузка живёт **во фрагменте** после `#`: фрагмент браузер на сервер не отправляет, поэтому ссылка, случайно открытая в браузере, токен никуда не сливает. Приложение читает её сканом QR или вставкой текста; открытие по клику (глубокие ссылки) не обещается. Разбор обязан принимать и один фрагмент без схемы — человек может вставить только его.

| Смещение | Поле | Размер | Значение |
|---|---|---|---|
| 0 | `version` | 1 | `0x01` |
| 1 | `host_type` | 1 | `0x01` IPv4 · `0x02` IPv6 · `0x03` DNS-имя |
| 2 | `host` | 4 / 16 / 1+N | по типу; для DNS — байт длины, затем имя в UTF-8 |
| … | `port` | 2 | big-endian |
| … | `server_key` | 32 | публичный ключ сервера, Ed25519 |
| … | `token` | 16 | значение токена |

56 байт для IPv4 → 75 знаков base64url. QR невысокой плотности, уверенно снимается с экрана.

**Тип адреса записан явно.** Выводить его разбором нельзя: `1.2.3.4` читается и как IPv4, и как имя хоста, и один байт снимает неоднозначность навсегда.

**Тип токена в ссылке не передаётся.** Сервер сам его выпустил и знает; при предъявлении токен находится по значению.

Правила разбора: неизвестная `version` — отказ с **отдельной** причиной, а не попытка угадать раскладку; несходящаяся длина — отказ **до** попытки соединиться. Отказ разбора обязан быть отличим от отказа токена: у человека разные действия.

⚠️ **`server_key` разбирается и хранится, но пока ни с чем не сверяется** — сверять не с чем, пока транспорт не TLS. Носится в ссылке уже сейчас, чтобы приход пиннинга не менял формат и не требовал пере-спаривания.

### `pair` — единственная команда до приветствия

```json
{"id": 1, "cmd": "pair", "data": {
  "token": "<16 байт, base64url>",
  "device_key": "<base64: публичный ключ устройства, Ed25519>",
  "platform": "ios | android | macos | windows | linux"
}}
```

```json
{"id": 1, "ok": true, "data": {
  "identity": {"id": "u_3f2a1c9d40b7e518", "label": "User7421", "created": true}
}}
```

Исключение из правила «первая команда — hello» не удобство, а необходимость: неспаренному устройству нечем подписать challenge. После успешного `pair` устройство переподключается и здоровается уже подписью.

`created` говорит, **приведёт ли эта операция к выбору имени**: `true` для claim, `false` для приглашения устройства (личность уже есть, выбора имени быть не должно). Считается **от типа токена**. Раньше считалось от того, завела ли операция строку личности, — и повтор потерянного ответа отвечал `false`, потому что строка к тому моменту уже была: устройство проскакивало выбор имени из-за одного потерянного кадра.

`platform` — семейство ОС и ничего больше. Точная модель железа не передаётся: узнать своё устройство в списке из трёх этого достаточно, а на сервере она была бы отпечатком.

Отказы: `invalid_token` (токена нет; израсходован **другим** ключом; либо claim предъявлен занятому серверу), `token_expired` (приглашение предъявлено позже своего срока).

**Занятость считается по устройствам, а не по отметке claim.** Сервер, у которого не осталось ни одного устройства, принимает claim снова и снова печатает ссылку при запуске: «занят» значит «внутрь ещё кто-то может войти», и сервер, потерявший последнее устройство, иначе оставался бы неприступным навсегда. Повторный claim **переприсоединяется к уже существующей личности**, если она есть, — заводить вторую, оставив всю переписку у первой, значит потерять её.

**Повтор одного и того же токена тем же ключом — успех**, с тем же ответом: ответ мог потеряться по дороге, и второй заход должен привести к тому же исходу, а не к отказу.

**Успешный claim гасит все прочие непредъявленные claim-токены**, а отзыв устройства гасит непредъявленные приглашения его человека. Ссылки печатаются в лог и живут в переписке; погашение — единственное, что мешает старой ссылке сработать позже.

**Сроки жизни.** Приглашение устройства живёт **10 минут** — дойти с телефоном до второго устройства успеть можно, а скриншот QR через сутки уже бесполезен. У claim-токена **срока нет**: он умирает от использования, видит его только тот, у кого есть доступ к машине, а истекающий claim оставил бы свежепоставленный сервер невостребуемым навсегда.

### `device.list`

```json
{"id": 2, "cmd": "device.list", "data": {}}
```

```json
{"id": 2, "ok": true, "data": {"devices": [
  {"device_key": "<base64>", "platform": "ios", "created_at": 1788496080, "last_seen_at": 1788499999}
]}}
```

### `device.invite`

```json
{"id": 5, "cmd": "device.invite", "data": {}}
```

```json
{"id": 5, "ok": true, "data": {"token": "<16 байт, base64url>", "link": "https://nox.app/p/#…"}}
```

Выпускает приглашение для **нового устройства той же личности** и сразу отдаёт готовую ссылку. Ссылку собирает сервер, а не устройство: только он знает свой публичный ключ и адрес, по которому доступен. Живёт 10 минут.

**Адрес в ссылке — тот, по которому спрашивающее устройство дозвонилось** (заголовок `Host` его подключения), если сервер слушает `0.0.0.0`/`::`. Адрес привязки в этом случае не отвечает на вопрос «куда идти», а loopback заведомо неверен: приглашение несут на **другое** устройство. Явно указанный адрес привязки — решение оператора и остаётся как есть.

Не путать с приглашением нового **человека** в круг — это `invite-user`, и он заблокирован Q15.

### `device.revoke`

```json
{"id": 3, "cmd": "device.revoke", "data": {"device_key": "<base64>"}}
```

Ключ удаляется из разрешённых, живое соединение отозванного устройства рвётся **сразу**, а не при его следующей попытке. Отзыв ключа, которого в списке нет, — **успех**: конечное состояние достигнуто.

Отозванное устройство неотличимо от неизвестного, и это сделано намеренно: пересобранное с нуля хранилище сервера выглядит для устройства так же, и вести себя оно обязано одинаково — очистить локальные данные и вернуться к предъявлению ссылки.

**Logout — частный случай:** устройство отзывает свой собственный ключ. При живой связи отзыв уходит **до** локальной очистки; без связи очистка безусловна, а осиротевший ключ отзывается с другого устройства — принятая цена.

Личность **переживает отзыв последнего своего устройства**: строка личности остаётся, иначе восстановлению не к чему будет прицепиться.

### `identity.setLabel`

```json
{"id": 4, "cmd": "identity.setLabel", "data": {"label": "Anna"}}
```

```json
{"id": 4, "ok": true, "data": {"label": "Anna"}}
```

Имя доезжает **отдельной командой**. До этого единственным путём было приветствие, и переименование требовало переподключения — задокументированный костыль этапа 1, который с несколькими устройствами у одной личности перестаёт быть неудобством и становится источником расхождений. Поле `label` в `session.hello` остаётся для выбора имени при онбординге.

**Занятость имени не проверяется и командой проверки не сопровождается.** Имена людей не уникальны (решение владельца 2026-09-02); `identity.labelAvailable` **вычеркнут** из контракта, а не отложен — оставленный в нём, он однажды был бы реализован и вернул бы спиннер проверки, убранный фазой 031. `identity.completeOnboarding` вычеркнут по другой причине: исход онбординга уже несёт ответ `pair`, а второй источник той же истины разойдётся с первым.

### Событие `device.revoked`

```json
{"seq": 0, "event": "device.revoked", "data": {"device_key": "<base64>"}}
```

Уходит отзываемому устройству перед закрытием сокета. Устройство, получившее его о себе, обязано вычистить локальные данные и вернуться к предъявлению ссылки.

### Событие `identity.updated`

```json
{"seq": 0, "event": "identity.updated", "data": {"label": "Anna"}}
```

Уходит **остальным** живым подключениям того же человека после `identity.setLabel` — тому, кто переименовался, имя приходит ответом на команду. Получатель обязан обновить кэшированное имя; `author_id` событие не несёт и трогать его не должно.

Как и `device.revoked`, событие несёт `seq: 0` и **в журнал не попадает**: журнал общий, а личность — не общий мир (инвариант 3 сервера). Без события второе устройство держит старое имя, пока что-нибудь его не переподключит, — а стабильный сокет не здоровается заново и вмораживает старое имя в `author_label` истории.

## 9. Требования к реализации соединения

**Обе стороны:**

- **Keepalive:** ping/pong WebSocket, интервал ~25 с — сотовые NAT сбрасывают простой за ~30 с; полуоткрытый TCP детектируется ack-таймаутом на уровне приложения.
- **Реконнект:** экспоненциальный backoff **с джиттером**, сброс по успеху; переподключение по событию пробуждения машины, не по таймауту.
- Аутентификация — **одноразовая при установлении соединения**, не на каждый запрос (текущий `AuthInterceptor` с Bearer-токеном — не наша модель).

**Фазы сессии на клиенте** (второе понятие связности, отдельное от «есть ли интернет»):

`нет сокета → connecting → catching-up (replay) → live`

Offline-баннер показывают первые две фазы, «догоняем» — индикатор третьей; конец catching-up — по правилу «догнан» из §3. Сегодняшние потребители `ConnectivityService.watchOnline()`, переключаемые на фазы сессии: **три** блока — chats list, thread, chat card; слив очереди исходящих — по входу в `live`.

**Переходные требования к клиенту** (данные аудита против реального `lib/`; выполняются до DI-флипа 016, чтобы репозитории и UI при флипе не менялись). Статус (порядок трека пересмотрен 2026-08-30): **1, 2, 4, 5, 7 закрыты фазой 025**; **фазы сессии из шапки и текстовая часть 6 (форма `message.send`) закрыты фазой 026** вместе с транспортом и DI-флипом; **3 и 8 закрыты фазой 027** (store `outbox`, ключ минтится при постановке, единственный сливающий сервис); **файловая часть 6 закрыта фазой 028** — цепочка `uploadBegin` → `PUT` → `message.send {attachment:{file_id}}` и обратная `downloadBegin` → `GET`, проверены живьём побайтовым сравнением. Оговорка «выполняются до DI-флипа 016» относилась к исходному порядку и более не действует: флип выполнен в 026.

1. **`seq` становится ключом хранения, сортировки и пагинации сообщений** — вместо сортировки по `sentAt` и математики `page/page_size/total`: `PageMetadata`/`PagingState` переводятся на `has_more`, «догрузить старше» = `before_seq` от минимального загруженного `seq` чата.
2. **Wire-DTO переписываются 1:1 под контракт:** `MessageWireEntity`/`ChatWireEntity` эпохи 018 расходятся по именам (`id`→`message_id`), типам (`sent_at` ISO-строка → unix-секунды), структуре (плоский `text` → объект `body`; вложение → `{file_id, name, size, mime, expires_at}`) и несут поля, которых на проводе нет (`status`, `is_system`, `unread_count`) — required-поля уронят парсинг контрактного JSON. Категория `FileType` выводится из расширения имени.
3. **Ключ идемпотентности назначается при постановке в очередь** и персистится вместе с ней; повтор после реконнекта и после рестарта идёт с тем же `client_message_id`. ✅ Фаза 027: ключ минтит `OutboxRepository.enqueue` и он же служит ключом записи store `outbox` — вторая строка под тем же ключом невозможна структурно.
4. **Персистентный курсор** `since` на устройство + `seq` в локальной записи каждого сообщения — сегодня поля `seq` нет ни в одной модели, курсор хранить негде.
5. **`limits` из hello сохраняются в data-слое** и доступны композеру/пикеру для предполётных проверок; `RepositoryException` расширяется кодами провода (сейчас все send-ошибки схлопываются в один `error`).
6. **`MessageRemoteDataSource` приводится к форме контракта** (без `authorId`/`authorLabel`; + `client_message_id`, `attachment: {file_id}`) и добавляется файловый датасорс `uploadBegin → PUT → send`. ✅ Текстовая часть — фаза 026; файловая — фаза 028. Выданный `file_id` хранится **в записи очереди** и записывается только после подтверждённой передачи байтов: раньше он указывал бы на файл без байтов, который сервер примет, а получатель не скачает никогда.
7. **`expires_at` добавляется в модели вложения** (домен + Sembast) — гейтинг кнопки Save.
8. **Очередь исходящих** переезжает из `ChatThreadBloc` в data-слой и переживает перезапуск приложения. ✅ Фаза 027: store `outbox` + `OutboxService` — единственный отправитель, слив по входу в `live`, строго по порядку постановки, запись удаляется только после персиста сообщения. Сознательное сужение: очередь принимает **только отправку сообщений**. Остальные команды фазы интерактивны — пользователь ждёт ответа на экране, и отложенное выполнение через час было бы не улучшением, а сюрпризом; расширение — когда появится команда, которую осмысленно откладывать.
9. **Личность становится серверной сущностью, а `author_id` перестаёт быть именем.** ✅ Фаза 030: человек узнавался по производной от идентификатора входа, устройство — по `device_key`; ✅ фаза 032: производная убрана с провода, человек находится по спаренному ключу устройства, `author_id` несёт `user_id`. Переход требует **чистого старта хранилища сервера**: `events.payload` собирается один раз при записи и никогда не переписывается, поэтому строки, записанные до фазы, навсегда держат в `author_id` отображаемое имя, а раннер миграций гейтится `PRAGMA user_version` и правку схемы к наполненной базе не применит. Клиент распознаёт пересборку по `journal_id` (§3) и сбрасывает локальный мир сам — без этого устройство с курсором выше нового журнала молча перестаёт получать события навсегда.

## 10. Срез этапа 1 для старта в `client_backend/`

Минимальный срез «пощупать Go», совпадающий с контрактом (ничего не придётся выбрасывать):

1. **Конверт §2 целиком** (включая приветствие с challenge — подпись не проверяется) — ~50 строк на каждой стороне.
2. `session.hello`: `limits` + `identity` + replay с `since` и правилом «догнан».
3. `chat.create`, `chats.list`, `message.send` (идемпотентность по `client_message_id`), `messages.list` c `before_seq`.
4. События `message.new`, `chat.created` через `seq`.
5. SQLite: таблицы `chats`, `messages`, `events` — сообщение и его событие пишутся **одной транзакцией**, broadcast после commit.
6. REST-заготовка §1: `GET /health` сразу; файловые endpoint'ы — следующим шагом (§7).

Референс архитектуры — прототип [docs/client-backend/client_backend_pattern/go-backend](../client_backend_pattern/go-backend/): его `seq`/`events`/replay `?since=N`/транзакционный outbox — ровно §3 и §6 этого контракта. Расхождение одно — REST+push-сокет вместо командного сокета; в `client_backend/` команды сразу идут в конверт §2.
