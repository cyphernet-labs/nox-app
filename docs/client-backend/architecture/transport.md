# Транспорт «приложение ↔ client-сервер»

**Дата:** 2026-08-17

---

## 1. Решение

| | Выбор | Одной строкой почему |
|---|---|---|
| **Канал** | Постоянный **WebSocket поверх TLS** (`wss`) | Двунаправленный, фрейминг и keepalive из коробки, зрелые библиотеки в Dart (все 5 платформ) и Go |
| **Порт** | **приезжает ссылкой спаривания** (дефолт разработки — 8080) | 443 остаётся лишь возможным значением для сервера, выставленного наружу: там оно проходит корпоративные сети, отели и captive-порталы, потому что для middlebox'ов это HTTPS. Фиксировать его нельзя — домашний сервер слушает там, где ему сказали |
| **Пути** | **Два пути к одному порту**: напрямую — адреса сервера в локальной сети и его публичный адрес, если он задан; через Tor — к onion-сервису, который публикует **отдельная служба tor** на машине сервера и ведёт на тот же основной порт | Дома прямой путь быстрее; вне дома onion-сервис достижим из любой сети без проброса портов. Сервер соединения не различает, поэтому tor живёт вне его кода |
| **Шифрование** | **TLS 1.3** с техническим сертификатом сервера — самоподписанным, на одноразовом ключе, новом при каждом запуске; клиент его не сверяет | Ни домена, ни ACME, ни продления; TLS только шифрует, кто на другом конце — решает проверка ниже |
| **Кто на другом конце** | **Проверка Eidolon** на каждом соединении: ключи Ed25519, подписи над экспортёром TLS 1.3 (RFC 9266), первым показывает себя приложение; ключ сервера — из ссылки спаривания | Проверка привязана к конкретной TLS-сессии: посредник с двумя сессиями получает два разных отпечатка и не проходит; чужая машина по сохранённому адресу предъявляет не тот ключ |
| **Где живёт канал в приложении** | **Rust-модуль** на всех пяти платформах: транспорт (TCP или поток Tor через Arti), TLS (rustls на ring) и Eidolon; Dart связан с ним прямыми вызовами | TLS в Dart не отдаёт экспортёр соединения, без которого проверку не к чему привязать |
| **Файлы** | Отдельные HTTP-запросы к тому же серверу | Иначе большой файл блокирует все интерактивные команды (head-of-line) |
| **Формат внутри кадра** | Сначала JSON, поле версии в рукопожатии | Быстро отлаживать; переезд на бинарный — смена версии, не транспорта |

**Правило, которое держит всё решение: труба стандартная, всё интересное — внутри кадров.** Так устроены Signal, WhatsApp и Wire; SimpleX для self-hosted серверов независимо сошёлся к похожей конфигурации (порт 443, опция WebSocket, ключ сервера в его адресе).

### Два пути — один вход

- **Напрямую** — по адресам сервера в локальной сети, которые он находит сам, и по его публичному адресу, если тот задан (проброшенный порт, публичный IP или DNS-имя). Приложение всегда начинает с прямого пути.
- **Через Tor** — к onion-сервису сервера. Публикует его **отдельная служба tor** на машине сервера и ведёт виртуальный порт 443 на основной порт сервера; сервер tor не запускает, ключей Tor не хранит и знает только свой onion-адрес — строку в базе. В приложении Tor встроен (Arti в Rust-модуле, на всех пяти платформах) и используется, только когда прямой путь не отвечает, у человека включено `Use Tor` и onion-адрес известен; как только прямой путь снова отвечает, приложение возвращается на него.
- **Вход один.** Соединение от tor приходит на тот же порт и проходит те же слои — TLS 1.3, проверку Eidolon, HTTP; пришло ли оно через Tor, сервер не знает. Поэтому сроки медленного пути через Tor действуют для всех соединений: проверка канала — 30 с от приёма соединения, запись кадра и ожидание pong — 30 с. На входе сервер различает только источник: соединения с самой машины — с loopback или с адреса, на который они пришли, — а с ними и все через onion держатся в одной ограниченной доле.
- **Onion даёт достижимость, а не доверие.** Ключей доступа Tor нет: onion-адрес открыт любому, кто его знает, а дальше пускает только проверка Eidolon и права ключа устройства. От наплыва защищают настройки самой службы tor и пределы сервера. PoW удорожает новые цепочки (встроенный в приложение Tor решает его задачи сам), но потоков на уже построенной цепочке не ограничивает, поэтому в настройках tor есть и предел — 16 потоков на цепочку разом. Сервер держит соединения через onion в доле этой машины, не давая им вытеснять чужие, а незнакомому ключу даёт 2 минуты на спаривание.

## 2. Почему не свой протокол поверх сырого TCP

«Свой протокол» у мессенджеров — почти всегда **слой над любым транспортом, а не замена WebSocket**: Telegram сам перечисляет WebSocket среди транспортов MTProto; спецификация SimpleX допускает «TCP, HTTP long polling, websockets»; Noise Pipes у WhatsApp — криптослой, которому по спецификации Noise нужен внешний фрейминг. Настоящий выбор — не «WebSocket или своё», а «какие слои внутри трубы».

Что своё покупает и чего стоит — по задокументированным самими проектами причинам:

| Мотив своего протокола | Кто и как формулирует | Почему нас не убеждает |
|---|---|---|
| Меньше оверхед | Telegram Abridged: «the lightest protocol available», 1–4 байта против 6–14 у WS | Единицы байт на кадр — шум на фоне TLS-записей и TCP/IP; бенчмарков со значимой разницей не существует |
| Единообразие трафика | SimpleX: блоки 16 КБ «for traffic uniformity» | Достигается паддингом **внутри** WebSocket-кадров — транспорт менять не нужно |
| Свойства Noise (скрытие метаданных, быстрый resume) | WhatsApp, whitepaper | Noise вкладывается в кадры любого транспорта — это слой поверх, не вместо |
| Обход блокировок | Telegram: padded-вариант «to bypass ISP blocks» | Это **цена** своего, а не бонус: бинарный протокол выглядит как «полностью зашифрованный» трафик — ровно тот класс, который Китай (с 2021) и Россия (с 2024) блокируют пассивными эвристиками, явно освобождая трафик с TLS-отпечатком. Telegram пришлось дописывать обфускацию вдогонку |

Цена сопровождения задокументирована владельцем самого известного своего протокола: MTProto 1.0 → 2.0, затем правки после академической работы «Four Attacks and a Proof for Telegram» (2021). Направление движения индустрии одностороннее: XMPP добавил WebSocket-байндинг (RFC 7395) и direct-TLS на 443 (XEP-0368, «обход файрволов, пропускающих только 443»); Threema новую multi-device-подсистему построила на WebSocket, оставив свой CSP как наследие 2012 года. Обратных переходов — со стандартного на своё — в разобранной выборке нет.

Антицензурная практика Signal подтверждает выбор с другой стороны: их стратегия — не стелс-протокол, а **неотличимость от обычного HTTPS** (domain fronting 2016-го, TLS-прокси для Ирана 2021-го).

## 3. Точки расширения — что добавляется без смены транспорта

| Будущая потребность | Как добавляется |
|---|---|
| E2EE полезной нагрузки (Q1a) | Тело кадра становится непрозрачным блобом; транспорт не меняется |
| Скрытие метаданных подключения | Отдельный криптослой внутри кадров |
| Устойчивость к анализу трафика | Кадры фиксированного размера (паддинг) — модель SimpleX |
| Бинарный формат вместо JSON | CBOR/Protobuf по полю версии в рукопожатии |
| HTTP/2 / HTTP/3 | RFC 8441 / RFC 9220 переносят WebSocket в новые транспорты с той же семантикой — код уровня сообщений не меняется |

## 4. Ограничения, принятые сознательно

⚠️ **Мультиплексирования нет** — одно TCP-соединение, head-of-line blocking. Закрыто дизайном: единственный реальный источник блокировки — файлы — вынесен в отдельные HTTP-запросы.

⚠️ **Встроенного resume нет.** Закрыто дизайном: догоняющая синхронизация «что нового с курсора X» обязательна в любом случае ([notification-delivery.md](notification-delivery.md) §9) — она и есть resume.

⚠️ **TLS-отпечаток клиента — сам по себе сигнатура.** Используются распространённые TLS-стеки с обычным ClientHello — стандартный `crypto/tls` Go на сервере, rustls в клиенте, — не экзотика: в 2022 Китай блокировал обходные инструменты предположительно по отпечатку рукопожатия. Имени сервера (SNI) клиент не отправляет: постоянное имя в открытом ClientHello метило бы трафик NOX.

⚠️ **Туннель для CGNAT не может терминировать TLS**: проверка Eidolon привязана к TLS-сессии между приложением и client-сервером, и сессия, разорванная посредине, проверку не проходит. Маршрутизации по SNI нет — клиент его не отправляет; как достучаться до сервера за NAT — открытый вопрос Q22.
