# План клиентского трека — приложение поверх живого сервера

> **Живой трекер.** Подключение Flutter-приложения к client-серверу этапа 1 ([этап 1 завершён](roadmap-stage1.md)) по переходным требованиям контракта §9 ([protocol/contract-draft.md](protocol/contract-draft.md)). Ведётся фичами Spec Kit, нумерация продолжает ряд (последняя — 024). Статусы: `☐` не начата · `◐` в работе · `☑` смёржена.
>
> Создан: 2026-08-27. Ключевой принцип §9: **переходные требования выполняются до DI-флипа 016** — чтобы при флипе репозитории и UI не менялись. Аутентификации нет (этап 1 сервера). Фаза 025 прошла целиком на моках с замороженным UI; с фазы 026 приложение подключается к живому серверу.

## Порядок и зависимости

```
025 wire-alignment ──→ 026 live-exchange ──→ 027 outbox ──→ 028 files
     (моки, UI заморожен)   (ЖИВОЙ сервер)      (надёжность)   (вложения)
```

**Порядок пересмотрен 2026-08-30 (решение владельца).** Исходный план (026 outbox → 027 transport → 028 flip) давал владельцу первый видимый результат только после трёх фаз, причём две из них ничего не показывают на экране. Транспорт и флип слиты в одну вертикаль, чтобы живой обмен app ↔ `noxd` появился сразу; персистентная очередь и файлы — надёжность и полнота поверх уже работающего канала. Аутентификация этому не мешает: этап 1 контракта работает без неё.

Каждая фаза заканчивается зелёным `make gate` + `make golden-verify`; 026–028 дополнительно проверяются вручную против локального `noxd` (сборка и смоуки — `client_backend/README.md`).

## Фаза 025 — `client-wire-alignment` ◐

**Цель:** данные приложения говорят на языке контракта, оставаясь на моках.

Скоуп (§9: 1, 2, 4, 5, 7):

- `seq` в моделях сообщения (домен + Sembast + мок-генераторы); сортировка треда и «догрузить старше» — по `seq`/`before_seq` c `has_more` вместо `page/page_size/total`.
- Wire-DTO переписаны 1:1 (`message_id`, unix-секунды, объект `body`, вложение `{file_id, name, size, mime, expires_at}`); поля, которых нет на проводе (`status`, `is_system`, `unread_count`), уходят из wire-слоя; парсинг проверяется фикстурами из **живых кадров `noxd`**.
- Персистентный курсор `since` устройства; `expires_at` в моделях вложения (домен + Sembast) — гейтинг Save.
- `limits` рукопожатия сохраняются в data-слое (шов для композера/пикера); `RepositoryException` расширяется кодами провода §2.1.

**DoD:** гейт + голдены зелёные без изменений UI-поведения; контрактные JSON-фикстуры сериализуются/парсятся дословно; тред пагинируется по `seq` на моках.

## Фаза 026 — `client-live-exchange` ☑

**Цель:** приложение реально обменивается сообщениями через `noxd` — это первая фаза с видимым результатом.

Скоуп (шапка §9 + §9.6 в текстовой части):

- **Транспорт.** WebSocket-клиент конверта v0: приветствие `srv`, команды с `id`, ответы, события; `session.hello` c `since` из персистентного курсора (025), replay с правилом «догнан» (`seq ≥ cursor`), дедупликация по `seq`; реконнект с экспоненциальным backoff и джиттером (сброс по успеху), keepalive ~25 с.
- **Фазы сессии** `нет сокета → connecting → catching-up → live` — понятие, отдельное от «есть ли интернет». Три потребителя `ConnectivityService.watchOnline()` (chats list, thread, chat card) переходят на них; слив накопленных отправок — по входу в `live`.
- **Реальные датасорсы.** `RealChatRemoteDataSource` / `RealMessageRemoteDataSource` поверх транспорта; `MessageRemoteDataSource` приводится к форме контракта (без `authorId`/`authorLabel`, с `client_message_id`). Вложения на этой фазе остаются мок-путём — файловая цепочка в 028.
- **DI-флип** тремя шагами по `specs/016-remote-datasource-seam/contracts/di-binding.md`, **в окружении `dev`** (куда ведёт флейвор `stage`; флейворов всего два — `stage` и `prod`): `Environment.dev` смотрит на живой сервер, `Environment.test` остаётся на моках (весь сьют и голдены не двигаются), prod — решение фичи.
- **`apiUrl`** появляется в `config/stage.json`; адрес локального `noxd` — рабочий дефолт разработки.
- **Долг из 025** (найден ревью PR #16, на моках не срабатывает — здесь становится реальным):
  - `ChatThreadBloc._refreshMessages` просит хвост длиной `items.length + pageSize`; сервер молча обрежет до 100 (§5), и загруженный отрезок схлопнется. Рефреш должен идти по курсору либо перечитывать только новейший батч.
  - Курсор `since` в `app.db` хранит мок-значения `MockSeq` (~1,8·10¹⁵). На входе в живой транспорт его нужно сбросить (эпоха/версия), иначе первый `hello` попросит replay «из будущего» и пропустит всю историю.
- **Блюпринты** `04`/`14`/`15`/`16` переводятся с плейсхолдеров на реальную транспортную модель (Принцип III).

**DoD:** dev-приложение против локального `noxd`: список чатов и тред приходят с сервера, отправленное сообщение возвращается эхом и появляется у второго клиента, обрыв связи переживается реконнектом с догоном по курсору. `Environment.test` на моках, `make gate` + `make golden-verify` зелёные.

## Фаза 027 — `client-outbox` ☑

**Цель:** отправка переживает рестарт и повторяется без дублей.

Скоуп (§9: 3, 8):

- Очередь исходящих переехала из `ChatThreadBloc` в data-слой: store `outbox` в Sembast, **ключом записи служит сам `client_message_id`** — вторая строка под тем же ключом невозможна структурно, а не по договорённости.
- Ключ назначается **при постановке в очередь** и персистится вместе с записью; повтор после реконнекта и после рестарта идёт с тем же ключом — сервер отвечает прежним эхом (идемпотентность §5 проверена вживую).
- Порядок отправки задаёт поле `ordinal`, назначаемое в транзакции постановки, а не время: под замороженными в снимках часами у пачки сообщений `createdAt` совпадает до миллисекунды.
- `OutboxService` — **единственный отправитель**; проходы сериализованы, так что мигание связи не запускает два прохода по одной записи. Слив — по входу сессии в `live`.
- Отказы классифицированы: `connection` / `rate_limited` / `internal` / нераспознанный повторяются с нарастающей паузой от счётчика попыток **записи**; прочие — окончательные, помечаются ошибкой, и проход идёт дальше, чтобы одно негодное сообщение не держало очередь.
- Выход из аккаунта останавливает слив и стирает store вместе с чатами и сообщениями: записи содержат тексты.

**Сознательное сужение против исходной формулировки.** Требование §9.8 говорит «работает для всех команд». Очередь принимает **только отправку сообщений**: остальные команды фазы (создание и переименование чата, проверка имени) интерактивны — пользователь ждёт ответа на экране, и отложенное выполнение через час было бы не улучшением, а сюрпризом. Расширение — когда появится команда, которую осмысленно откладывать.

**DoD:** убить приложение с непустой очередью → рестарт → отправка уходит с прежним `client_message_id`, дублей на сервере нет. ✅ Гейт 828 тестов + 216 голденов зелёные без перегенерации — фаза не меняет ни одного пикселя.

## Фаза 028 — `client-files` ☑

**Цель:** вложения ходят вживую в обе стороны.

Скоуп (§9.6, файловая часть):

- Файловый датасорс: `file.uploadBegin` → `PUT` байтов по одноразовому токену → `message.send {attachment: {file_id}}`; `mime` клиент уже выводит из расширения (`MimeTypes`, фаза 025) и передаёт в `uploadBegin`.
- Скачивание: `file.downloadBegin` → `GET` c Range; прогресс-бар 5.3 переводится с таймера на реальную загрузку, `attachment_gone` — терминальное состояние.
- Сверка live-поведения: merge-не-replace при применении событий, пересчёт непрочитанного от `seq` последнего открытия (§6/§8.3).

**DoD:** отправить файл с одного клиента и скачать его на другом — вживую против `noxd`. ✅ `test/live/live_files_probe.dart` гоняет цепочку целиком и сверяет байты **побайтово**: это единственный вопрос, ответ на который принадлежит серверу, а не нашему коду.

**Что оказалось важнее, чем ожидалось.** Отправка вложения — три шага, а ключ идемпотентности защищает только последний: пропуск на передачу одноразовый, и повторная заявка даёт новый идентификатор файла. Поэтому `file_id` живёт **в записи очереди** и пишется только после подтверждённой передачи. Записанный раньше, он указывал бы на файл без байтов — сервер такое сообщение примет, а получатель не скачает никогда.

Отдельно: классификацию отказов пришлось делать **свою**, а не наследовать от 027. Контракт делает любой отказ пропуска голым `404` и называет это штатным исходом, а общий маппер превращает `404` в `notFound`, который слив считает окончательным — то есть протухший за время ожидания пропуск убил бы сообщение навсегда.
