### 0. Поправка конституции

Редакция 1.3.2 противоречила решённому: сервер управляет tor, доверие — пиннинг по отпечатку, Rust нужен только для Tor и не на Linux, нет запертого старта и шифрования данных на диске. Поправка — `/speckit-constitution`, до спецификаций: 1.4.0 (2026-10-09). Редакция 1.5.0 (2026-10-15, фича 050) заменила Eidolon проверкой `/auth` и `/auth2` с RustSecureBox.

### 044 — Канал

*Заменено фазой 050 (2026-10-15):* Eidolon (`eidolon-auth`, `cyphergraphy`, отпечаток-экспортёр TLS 1.3, своя реализация на Go и векторы с `eidolon-auth`) заменён запросами `POST /auth` → `POST /auth2` с RustSecureBox (тема 1); где ниже сказано «Eidolon», действует эта проверка. Ключ устройства — пара RustSecureBox (`session.device_key`), а не семя Ed25519. Остальное в плане 044 — TLS 1.3 в Rust-модуле, свой `Socket`, ссылка версии 3, «не тот сервер» без принудительного выхода — действует.

- **Rust-модуль.** `packages/nox_tor` становится модулем связи:
  - соединение — TCP по адресу или поток Arti до onion-адреса; поверх — TLS 1.3 (rustls на ring): сертификат принимается любой, подпись рукопожатия TLS проверяется; отпечаток — экспортёр TLS 1.3 (RFC 9266);
  - Eidolon (`eidolon-auth`, подписи — `ec25519` через `cyphergraphy`): приложение — инициатор и показывает ключ устройства первым, ключ сервера сверяется с ключом из ссылки;
  - FFI для Dart: открыть, писать, закрыть соединение; события — сообщениями в родной порт изолята (`Dart_PostCObject`), так что умерший изолят не роняет процесс; отказы по видам — сеть, TLS, проверка, «не тот сервер», ошибки Tor («устройство не знакомо» — ответ сервера на приветствие, а не отказ соединения);
  - петлевой мост, его секрет и право `network.server` на macOS уходят; подстраховочное второе подключение к onion сохраняется;
  - модуль собирается на всех пяти платформах, Linux включается.
- **Dart.**
  - Свой `Socket` поверх FFI и один `connectionFactory` для WebSocket и Dio вместо `PinnedHttpClient`; `ServerPin` и проверка листа уходят.
  - `session.hello` без challenge и подписи; `pair` идёт после Eidolon.
  - «Не тот сервер» — на любом пути, по ключу из Eidolon, и никогда не ведёт к принудительному выходу. У принудительного выхода один хозяин (до 044 их было три: `unauthenticated`, `device.revoked`, ответ Dio 401).
  - Эпоха мира — по ключу сервера, вместо `fp:<отпечаток>`.
  - Проверка прямого адреса — соединение с Eidolon, а не `/health` с пином.
- **Сервер.**
  - Ключ сервера Ed25519 в базе; технический сертификат.
  - Eidolon на каждом соединении: обёртка слушателя — TLS, затем Eidolon, затем HTTP; итог — в контексте соединения, в том числе для `/files`.
  - Устройство находится по ключу из Eidolon; незнакомый ключ может только `pair`.
  - Уходят `PinnedTLSConfig`, `FingerprintOfSPKI`, `ErrLegacyServerKey`, фикстуры пина, challenge в приветствии.
  - Своя реализация Eidolon на Go и общие тестовые векторы с `eidolon-auth`; `cmd/smoke` переходит на Eidolon.
- **Ссылка версии 3** — выпуск на сервере и разбор в приложении по формату темы 3. Ссылки версий 1 и 2 и одноразовые ключи onion-приглашений уходят: в версии 3 им нет места, поэтому до 045 приглашение работает только дома и так и подписано.
- **Контракт:** §1 (слои соединения), §2 (приветствие), §3, §8A (формат ссылки), коды ошибок.
- **Без миграций:** новая база на сервере, одно повторное спаривание.
- **Уточнено:** по прямому адресу с чужим ключом приложение молча пробует следующий путь, сообщение о другом сервере — только для onion (владелец). `/health` переезжает на служебный локальный порт (допущение спецификации). Модуль получает семя ключа устройства из сейфа через Dart при каждом открытии канала (план 044, R11).

### 045 — Tor отдельной службой

- **Сервер.**
  - Уходят `internal/tor`, отдельный вход для onion и всё о ключах доступа Tor: `device.setAccessKey`, `pair.access_key`, колонки и индекс ключей, `onion_seed` (ссылку версии 2 и onion-приглашения убирает 044).
  - Адреса в базе: публичный и onion; адреса в локальной сети сервер находит сам и не хранит. Параметры запуска пишут в базу, только когда сами появились или изменились. Служебная страница — адреса и `Set` (POST с проверкой `Host`, `Origin` и токеном формы); onion-адрес проверяется до записи; новый адрес действует сразу и уходит устройствам событием `server.addresses`.
  - Спаривание через Tor разрешено, первое тоже.
- **Приложение.**
  - Уходят `AccessKeyRepository`, `AccessKeyRegistrar` и одноразовые ключи ссылки версии 2.
  - `Use Tor`, по умолчанию выключен. Экран «Связь» в настройках: адрес сервера, onion-адрес, `Use Tor`. Экран адресов после скана QR-кода.
  - Путь: сначала напрямую; Tor — только с `Use Tor`; возврат на прямой путь, как только тот отвечает; подсказка включить `Use Tor`.
  - Шесть сообщений об ошибках по видам ошибок Arti; PoW в Arti (`hs-pow-full`), версия Arti закреплена точно; Tor на Linux.
- **Интерфейс:** новые экраны и сообщения — на обеих ширинах, с описанием в спецификации дизайна.
- **Контракт:** §1 (onion), §3 (`addresses`), `server.addresses`, удаление команд ключей доступа.
- **Уточнено:** адреса сервера заменяют ручную правку; испорченный параметр запуска не останавливает сервер — прежний адрес и предупреждение на служебной странице (владелец). Один порт для прямых и Tor-соединений, тайм-ауты медленного пути для всех (допущение спецификации).

### 046 — Спаривание и устройства

**Реализовано 2026-10-10** (ветка `046-pairing-devices`, слита в `security-rework` — PR #34). Сверх плана ниже: вторая команда до приветствия — `pair.cancel` (новое устройство отзывает свой запрос); исход ожидания устройство читает повтором `pair` с тем же токеном, а не одним событием; ожидание переживает перезапуск приложения; семейство системы в `pair` — одно из пяти; выход отзывает свой ключ только по поприветствовавшему соединению. Сквозная проверка на macOS без интерфейса прошла (`specs/046-pairing-devices/research.md`); проход по экранам обеих ширин и на устройствах — за владельцем.

- **Сервер.**
  - Ссылка с машины сервера: живёт 10 минут, живая одна, в журнал не пишется. Служебная страница — `Add a device`, QR-код, `Link expired`, `New link`. Команда в терминале говорит с работающим процессом: базу открывает только он.
  - Приглашение: 10 минут; сервер держит запрос нового устройства до `Allow` или `Deny` на выдавшем; новые события и команда ответа; в запросе — система нового устройства.
  - Отзыв с любого устройства, выход — отзыв своего; в списке устройств — система, дата спаривания, последний выход на связь. Остатки «владельца» убираются.
- **Приложение.**
  - Новое устройство: скан или вставка ссылки → адреса → подключение → `Waiting for approval on your other device` → отказ или истечение срока.
  - Выдавшее устройство: запрос `Allow`/`Deny`.
  - Список устройств с `Revoke`; отозванное устройство — незнакомый ключ: стирает данные и возвращается к спариванию.
- **Интерфейс:** экраны ожидания, запроса и списка устройств, правка 2.1, 2.2 и 7.8 — на обеих ширинах.
- **Контракт:** §8A — ссылка с машины, приглашение, ожидание ответа, коды отказа.
- **Не входит:** открытие `nox://pair/` по нажатию (deep links).

### 047 — Данные на диске: сервер

**Статус: реализована** — ветка `047-server-data-at-rest`, слита в `security-rework` (PR #35, 2026-10-10); гейт Go зелёный, сквозной прогон на macOS — `specs/047-server-data-at-rest/research.md`, R12, и после слияния с 046 — R13. За владельцем — Linux и Windows: запуск, пароль, бэкап и восстановление между машинами.

- SQLite: `modernc.org/sqlite` → `ncruces/go-sqlite3` с `vfs/adiantum`, без CGO; ключ данных заперт ключом из пароля (Argon2id, `golang.org/x/crypto`), запертый ключ лежит рядом с базой.
- Пароль задаётся при первом запуске, не короче 12 знаков. Запертый старт: служебная страница показывает только поле пароля, устройствам сервер не отвечает; разблокировка со страницы или командой в терминале через работающий процесс; неверный пароль ничего не меняет; новая база поверх существующей не создаётся.
- Смена пароля перезапирает ключ данных.
- Вложения — кусками по 64 КиБ: докачка (`received` — по границам кусков), чтение по частям (расшифровывающий `ReadSeeker` под `ServeContent`), признаки «готов» и «оборван» — по зашифрованному размеру.
- Бэкап одним файлом (снимок базы, файлы, запертый ключ) и восстановление.
- Новый порядок запуска и остановки.
- **Уточнено:** после восстановления сервер получает новое имя журнала, устройства перечитывают переписку (владелец). Бэкап, ключ которого сделала другая реализация RustSecureBox, восстановление перевыпускает, как первый запуск (050): все устройства спариваются заново ссылкой с машины, переписка остаётся. Иначе устройства восстанавливаются на момент бэкапа: отозванное позже снова принято, `noxd restore` называет устройства бэкапа, и такое отзывают заново. Формат файла бэкапа — tar: `nox.key`, `nox.db`, `files/<id>`, последним `manifest` с MAC от ключа данных (план 047, R6).

### 048 — Данные на диске: устройство

- База Sembast шифруется: кодек на криптографии Rust-модуля (ring); ключ — 32 байта в сейфе с пометкой «только это устройство»; база переезжает из «Документов» в папку данных приложения.
- Вложения и копии исходящих шифруются кусками; загрузка и докачка (`.part`) — по зашифрованным кускам; чтение через расшифровку: картинки, видео (временная копия, потом стирается), «Открыть в…», «Сохранить» (открытая копия туда, куда выбрал человек).
- Ключ не прочитать — данные стираются, устройство спаривается заново; выход стирает базу, файлы и ключ.
- Ничего в системных бэкапах: iOS и macOS — пометка «не в бэкап», Android — `allowBackup="false"` и правила извлечения данных, Windows и Linux — локальная папка данных приложения.
- Ключ устройства Ed25519 — тоже «только это устройство».
- **Решено в плане:** macOS — связка ключей с защитой данных в релизной сборке (её подписывает команда, которую выбирает владелец), отладочная сборка — обычная связка ключей, без команды; Windows — локальная папка данных `%LOCALAPPDATA%\Cyphernet Labs\NOX\data`, туда же файл сейфа.
- **Реализовано 2026-10-10** (ветка `048-device-data-at-rest`, с 044–046 внутри; слита в `security-rework` — PR #36, 2026-10-11): сейф в модуле (`nox_vault_*`, `NoxVault`); ключ `device.storage_key` и опции «только это устройство» на пяти платформах — для всех записей сейфа, ожидание одобрения 046 тоже; решения при запуске (ключа нет при базе или ключ её не открывает — стирание и спаривание, ошибка сейфа — повтор без стирания); база с кодеком `nox-vault-1`; файлы — заголовок `NOXF` и куски по 64 КиБ, докачка с последнего целого куска, загрузка через поток расшифровки; картинки из памяти, видео — из временной копии, ошибка открытия на 5.3; метки «не в бэкап», манифест Android; выход — после отзыва своего ключа (046) — стирает сессию, хранилища, базу, файлы и ключ один раз, присоединяя эхо отзыва. На владельце: профиль подписи macOS, бэкапы iOS и Android, Time Machine на собранном приложении, Windows и Linux.

### Итог переделки тем 1–4

- **Канал (тема 1, 044, переделана в 050).** Каждое соединение — напрямую или через Tor — это TLS 1.3 с техническим сертификатом и проверка `POST /auth` → `POST /auth2` с RustSecureBox: приложение сверяет ключ сервера с ключом из ссылки `nox://pair/` версии 3, сервер пускает спаренное устройство ко всему, а незнакомый ключ — только к спариванию. На стороне приложения канал целиком живёт в Rust-модуле.
- **Tor (тема 2, 045, 049).** tor — отдельная служба ОС на машине сервера; сервер его не запускает и хранит в базе только свои адреса — публичный и onion, заданные параметрами запуска или на служебной странице. Скрипт установки ставит tor 0.4.9+ с onion-сервисом NOX: PoW и предел потоков на цепочку, порт 443 ведёт на сервер через loopback. В приложении — Arti, путь через Tor включает `Use Tor`, когда напрямую не достучаться.
- **Спаривание (тема 3, 046).** Устройство добавляется ссылкой с машины сервера (служебная страница или `noxd link`, 10 минут, живая всегда одна) или приглашением со своего устройства, которое срабатывает только после `Allow`. Отзыв — с любого устройства; отдельного восстановления нет.
- **Данные на диске (тема 4, 047, 048).** База и вложения сервера зашифрованы ключом данных, который запирает пароль владельца: после каждого запуска сервер заперт, пока пароль не введён; бэкап — один зашифрованный файл. На устройстве база и файлы зашифрованы ключом из сейфа модуля с пометкой «только это устройство» и не попадают в системные бэкапы.
- **Установка (049).** Один запуск скрипта на Linux, macOS или Windows ставит сервер и tor, задаёт пароль, включает автозапуск и выдаёт ссылку для первого устройства; повторный запуск обновляет, не трогая данных.

## 1. Вход и защита канала — ☑

Описано на странице темы 1. Решения 2026-10-15 — заказчик заменил Eidolon своей схемой проверки; редакция темы на Eidolon заменена целиком.

Схема заказчика, нарисованная от руки: [набросок](assets/auth-scheme-sketch.png) — устройство и личный сервер, RustSecureBox у каждого как «чёрный ящик» за C API, обмен `/auth` и `/auth2`; [снимок экрана со встречи 2026-10-13](assets/auth-scheme-sketch-call.png) — тот же набросок до пометок. На наброске запросы `PUT`, в реализации — `POST` (решение 9).

1. **Соединение — слоями:** транспорт (TCP напрямую или поток через Tor) → шифрование TLS 1.3 → проверка «кто есть кто» двумя запросами, `POST /auth` и `POST /auth2` → команды (WebSocket) и файлы (HTTP). *Почему:* так просил заказчик — проверка сторон одинакова на любом пути.
2. **RustSecureBox — одна библиотека на Rust, один код в приложении и на сервере** (название — владелец). Отвечает только за ключи и подписи; соединения, запросы и решение, кого пускать, — на стороне приложения и сервера. RustSecureBox пишет другой разработчик, интерфейс задаём мы; до него работает заглушка с тем же интерфейсом, и весь процесс работает с ней так же, как будет работать с настоящим RustSecureBox. RustSecureBox ничего не хранит и не держит состояния: его можно звать из любого потока и сколько угодно раз (владелец).
3. **Интерфейс RustSecureBox:** `generate_keys` → закрытый ключ (32 байта) и открытый (32 байта); `get_challenge(свой закрытый ключ)` → челлендж (32 случайных байта) и свой открытый ключ; `sign_challenge(свой закрытый ключ, челлендж другой стороны)` → подпись (64 байта); `check_signature(открытый ключ, челлендж, подпись)` → верна или нет. Каждая функция сообщает об успехе или ошибке. Три функции — из схемы заказчика, создание ключей добавлено (владелец); размер челленджа выбран при проработке темы и принят владельцем.
4. **Логика и ключи — как у прежней проверки:** Ed25519 по RFC 8032, ключи по 32 байта, подпись 64 байта (владелец). Комментарии заглушки описывают, что делает настоящий RustSecureBox.
5. **Обмен — по схеме заказчика:** приложение берёт у RustSecureBox челлендж и свой ключ и шлёт их в `POST /auth`; сервер берёт свои, подписывает челлендж приложения и отвечает `{pk, challenge, signature}`; приложение проверяет подпись, подписывает челлендж сервера и шлёт `POST /auth2 {signature}`; сервер проверяет подпись. Тела — JSON, значения — base64url.
6. **Допущение заказчика:** соединение TLS считается неперехватываемым; стороны подписывают сами челленджи, отпечатка соединения в проверке нет; сертификат, который сверяет приложение, может появиться позже. *Почему:* так описал заказчик; владелец — делать максимально близко к его схеме.
7. **Проверка принадлежит соединению** (владелец): проходит в момент соединения — для сокета и для каждой передачи файла, — сразу после TLS; дальше по этому же соединению идут `/ws` или передача файла. Токена нет. Челлендж сервера и ключ устройства сервер держит при соединении: `/auth2` принимается один раз и только на том же соединении; до `/auth2` на любой другой запрос — `401` и разрыв.
8. **После подписи** (владелец, по рекомендации): приложение сверяет ключ сервера с ключом из ссылки — ссылка его уже несёт и не меняется; сервер ищет ключ устройства среди спаренных: спаренному — всё, незнакомому — только спаривание (тема 3).
9. **Запросы — `POST`**, не `PUT` (владелец): каждый `/auth` выдаёт новый челлендж.
10. **Ключи хранят приложение и сервер**, RustSecureBox получает их в каждый вызов: устройство — системный сейф, «только это устройство» (тема 4); сервер — своя зашифрованная база. Пару устройства RustSecureBox создаёт один раз перед первым спариванием, пару сервера — при первом запуске.
11. **Сервер выполняет RustSecureBox в WebAssembly, без cgo** (владелец, по рекомендации). *Почему:* все три установщика собирают сервер с `CGO_ENABLED=0`; через cgo на машине сервера понадобились бы Rust и компилятор C, на Windows — MinGW. Так же сервер уже работает с SQLite: её код на C собран в WebAssembly и переведён в Go (`ncruces/go-sqlite3`). Для этого RustSecureBox — только вычисления: без файлов, сети и обращений к системе; случайные байты на сервере даёт Go.
12. **Шифрование — TLS 1.3, сертификат сервера технический**, приложение его не сверяет; у приложения сертификата нет. В приложении транспорт, TLS и проверка — в Rust-модуле, RustSecureBox встроен в него; Dart передаёт поверх готового соединения команды и файлы.
13. **Библиотеки:** в приложении — `rustls` 0.23.45, `tokio-rustls` 0.26.6, `ring` 0.17.14, `arti-client` 0.47.0, `native_toolchain_rust` 1.0.4, `dart:ffi`, `flutter_secure_storage` 10.3.1 и RustSecureBox; на сервере — `crypto/tls`, `crypto/x509`, `crypto/ecdsa` (Go 1.27) и RustSecureBox.

**Для реализации:**

- Заглушка ведёт себя как настоящий RustSecureBox во всём, кроме стойкости: подпись своим ключом проходит, чужая — нет, поэтому все отказы проверяются уже с ней. Подделать её подпись может любой, кто знает открытый ключ: с заглушкой стороны по-настоящему не проверяются. Заглушку видно (владелец, 2026-10-15): сервер узнаёт её по известному ответу на пробный ключ — 32 байта `0x01`, не нулевой, потому что библиотеки Ed25519 отказывают на нулевом, — и при каждом старте пишет предупреждение в журнал, а служебная страница показывает `RustSecureBox is a stub: devices are not really verified.`. Сборки не ограничиваются; с настоящим RustSecureBox предупреждение исчезает само.
- Открытые ключи заглушки не совпадают ни с ключами Eidolon, ни с ключами настоящего RustSecureBox: при переходе на заглушку и при её замене все устройства спариваются заново. Сервер сам видит ключ другой реализации (владелец, 2026-10-15): открытый ключ в базе не тот, что RustSecureBox даёт для закрытого, — и тогда переписывает открытый ключ и отпускает все устройства одной транзакцией; переписка остаётся, страница сразу показывает ссылку. Приложение один раз уходит к спариванию, когда пара ключей устройства сделана не текущим RustSecureBox.
- Go выполняет WebAssembly переводом в Go-код `wasm2go`, как SQLite: сгенерированный код лежит в репозитории, новых зависимостей у сервера нет (`make box-wasm`, `make box-verify`).
- Только TLS 1.3 с обеих сторон; rustls в приложении принимает любой сертификат, но подпись рукопожатия TLS 1.3 проверяет; сервер создаёт технический сертификат заново в памяти при каждом запуске.
- Rust-модуль нужен на всех пяти платформах, Linux тоже.

## 2. Tor — ☑

Пересматривает решения трекера [roadmap-tor.md](roadmap-tor.md): сервер больше не управляет tor сам. Страница — `tor.html`.

**Решения владельца, 2026-10-08:**

1. **Сервер про Tor не знает.** tor — отдельная служба на машине сервера; ставит её наш скрипт или сам владелец, когда захочет. Из всего Tor серверу нужен только onion-адрес: он хранится в базе сервера (решение 11), сервер кладёт его в QR-код и сообщает устройствам. *Почему:* так просил заказчик — код сервера не должен зависеть от Tor.
2. **В приложении Tor встроен:** Arti в Rust-модуле — официальная реализация, одна и та же на всех пяти платформах, включая Linux.
3. **QR-код несёт onion-адрес**, только если он задан на сервере; иначе — только обычные адреса.
4. **Экран подключения:** адрес сервера и onion-адрес подставляются из QR-кода и правятся вручную; галочка `Use Tor`; если напрямую не вышло — подсказка включить `Use Tor`. Ручная правка безопасна: сервер проверяется по ключу из QR, а не по адресу.
5. **«Выбирать, через какой Tor»** у заказчика — это onion-адрес. Мосты вне рамок и нигде не упоминаются.
6. **Onion-адрес открыт для всех, кто его знает**, плюс защита PoW, — по рекомендации. Ключей доступа Tor нет: данные защищают TLS и проверка `/auth` и `/auth2` (тема 1).
7. **Настройки Tor правятся в приложении.** Адреса, onion-адрес и `Use Tor` — в настройках связи; после правки приложение сразу подключается заново по новым данным. Если onion-адрес сменился — например, сервер переехал без папки tor, — человек вписывает новый, переспаривать не нужно.
8. **Своё понятное сообщение на каждую причину неудачи:** onion-адрес записан с ошибкой; по адресу никто не отвечает; адрес верный, но сервер не отвечает; адрес ведёт к другому серверу; нет связи с сетью Tor; напрямую не достучались, а onion-адрес есть. Arti различает эти виды ошибок (`tor-error`: `OnionServiceAddressInvalid`, `OnionServiceNotFound`, `OnionServiceNotRunning` и ошибки доступа к сети Tor); чужой сервер распознаёт проверка ключа.
9. **`Use Tor` — Tor, когда напрямую нельзя.** Приложение всегда сначала пробует напрямую; через Tor идёт, только если прямой путь не отвечает и `Use Tor` включён, и возвращается на прямой путь, как только тот снова отвечает. По умолчанию галочка выключена (решение 4); подпись под ней говорит, что Tor включается, только когда напрямую не достучаться. *Почему:* главный сценарий — дома быстро, вне дома через Tor, без ручных переключений. *Следствие:* у сервера с публичным адресом приложение вне дома подключается по нему — сеть телефона видит этот адрес, но не содержимое.
10. **Спаривание через Tor разрешено** — и первого устройства (по ссылке с машины сервера), и следующих; у сервера один вход для обоих путей. *Почему:* сервер, поставленный в чужой локальной сети, куда напрямую не дотянуться, должен спариваться из любой сети. Для этого onion-адрес задаётся на сервере до показа QR-кода — скрипт установки так и делает.
11. **Адреса хранятся в базе сервера**, отдельного файла настроек нет. Задаются двумя путями, оба пишут в базу: параметрами запуска (сервер сразу записывает их в базу; так делает скрипт установки) и на служебной странице — она показывает все адреса, найденные и заданные, с кнопкой `Set` у каждого заданного. Новый адрес проверяется до записи и действует сразу, без перезапуска: новые QR-коды несут его, подключённые устройства получают его тут же. Параметр запуска перезаписывает базу, только когда сам появился или изменился, — правка на странице переживает перезапуск. *Почему:* никакой дополнительной инфраструктуры и никаких перезапусков ради смены адреса.
12. **Защита PoW в приложении включена:** Arti собирается с `hs-pow-full`. Возможность экспериментальная, поэтому версия Arti закреплена точно и проверяется при каждом обновлении. *Почему:* onion-адрес открыт намеренно (решение 6), а без решателя защита сервера не помогает своему же приложению.

**Для реализации:**

- Служебная страница слушает только loopback и уже сверяет `Host` — защита от DNS rebinding. Форма `Set` — первая запись через страницу: нужны ещё проверка `Origin` и токен формы, иначе форму отправит чужой сайт, открытый в браузере на машине сервера.
- Onion-адрес проверяется до записи: v3, 56 символов base32, контрольная сумма и версия.
- Правило «параметр перезаписывает, только когда изменился»: сервер хранит в базе последнее применённое значение каждого параметра.
- Без `hs-pow-full` в Arti стоит заглушка, которая не решает задач никогда (`tor-hsclient`, `pow/v1_stub.rs`); с ним Arti берёт сложность из описания onion-сервиса, решает задачу в отдельном потоке и повышает сложность при повторах (потолок 10 000). Решатель ускоряет JIT (`hashx`: по умолчанию сначала компиляция, при отказе — интерпретатор); на iOS JIT запрещён — время решения замерить.

**Ревью безопасности, 2026-10-08** (темы 1 и 2; ни одна находка не прошла порог 8 из 10):

13. **Ссылка с машины сервера живёт недолго** — 10 минут — и не пишется в журнал сервера; если ею не воспользовались, на машине сервера получают новую. *Почему:* раз спариваться можно через Tor, утёкшая ссылка давала бы вход из любой точки, а срок жизни сужает окно. Подробности — тема 3.
14. **Выход с последнего устройства возвращает сервер к состоянию «устройств нет»:** служебная страница сразу показывает ссылку с машины, и устройство, спаренное по ней, присоединяется к тому же человеку — со всей перепиской.
15. **Подмена служебной страницы и правка адресов кнопкой `Set` другими пользователями машины сервера** — вне рамок (см. «Границы»).

## 3. Спаривание и жизненный цикл ключей — ☑

Страница — `pairing.html`.

**Решения владельца, 2026-10-08:**

1. **Новое устройство подтверждается** на устройстве, выдавшем приглашение: `Allow` / `Deny`. Без ответа запрос истекает вместе с приглашением (10 минут); `Deny` гасит токен. *Почему:* утёкший QR-код без нажатия ничего не даёт, а спариваться теперь можно через Tor из любой точки. `pair` снова ждёт ответа — для своих устройств; ожидание для приглашения человека ушло вместе с 034.
2. **Отдельного восстановления нет** — ни фразы, ни кодов, ни аварийного комплекта ([Q16](open-questions.md) снят). Устройство добавляется двумя путями: приглашением со спаренного устройства (с подтверждением) или ссылкой с машины сервера — она работает всегда: первое устройство, возврат после выхода с последнего, потеря всех устройств. Человека на сервере ещё нет — ссылка его создаёт; человек есть — новое устройство присоединяется к нему со всей перепиской, а потерянные отзывает из своего списка. Отметки владельца на сервере нет (046). *Почему:* владелец не хочет долгоживущего секрета, а без устройств владение доказывает только доступ к машине. *Цена:* без живых устройств и без доступа к машине войти нельзя.
3. **Ссылка с машины сервера** живёт 10 минут. Пока устройств нет, служебная страница показывает её сразу; когда устройства есть — по кнопке `Add a device`, чтобы просто открытая страница не держала живую ссылку. Сама себя ссылка не перевыпускает: истёкшая — `Link expired` и кнопка `New link`; живая всегда одна — новая гасит прежнюю. На машине без экрана ссылку печатает команда в терминале; в журнал службы она не пишется.
4. **Без коротких кодов и PIN:** ссылка несёт то же, что QR-код; без камеры её вставляют текстом или читают QR-код из картинки.
5. **Ссылка и QR-код:** ключ сервера Ed25519 (32 байта), токен, один прямой адрес, публичный и onion — если заданы; остальные адреса устройство получает после спаривания.
6. **Отзыв** — с любого спаренного устройства; выход из приложения — отзыв своего. Отзыва со служебной страницы нет: потерянные устройства отзывает новое, добавленное ссылкой с машины.
7. **Ключ сервера** лежит в базе: бэкап базы оставляет сервер «тем же» для всех устройств. Замены ключа без переспаривания нет: утечка ключа или потеря базы — новый ключ и спаривание заново.
8. **Ключ устройства** — новый при каждом спаривании; после выхода стирается.
9. **Уже спаренные устройства** спаривают заново один раз: продукт не выпущен, кода перехода не будет.
10. **Формат ссылки:** `nox://pair/<base64url без =>`. Данные: версия (1 байт, сейчас 3), ключ сервера (32), токен (16), список адресов «тип, длина, значение» — IPv4 (6), IPv6 (18), имя (N + 2), onion — открытый ключ сервиса (32), порт 443; неизвестный тип пропускается по длине. *Почему:* домен `nox.app` проекту не принадлежит, а страница на нём прочитала бы всё после `#` — и токен; ссылку своей схемы браузер никуда не отправляет, а приложение уже пользуется `nox://id/`. Версия 3 — чтобы старые сборки, знающие версии 1 и 2, отказывали, а не читали мусор.

**Для реализации:** ссылка — только `nox://pair/` (044, контракт §8A). Своего домена у проекта нет, а ссылка на чужом домене, открытая в браузере, целиком досталась бы странице этого домена — вместе с токеном (владелец, 2026-10-08). Ссылку вида `https://nox.app/p/#…` приложение читает как неверную, а не как старую.

## 4. Данные на диске — ☑

- **Сервер:** переписка, закрытый ключ сервера и адреса — в базе SQLite (`ncruces/go-sqlite3`, чистый Go), вложения — файлами рядом с ней. База и файлы вместе с запертым ключом данных — это весь сервер (решения 1, 2, 7, 9; фаза 047).
- **Устройство:** локальная база (Sembast), скачанные вложения и копии исходящих лежат в папке данных приложения; ключи — в системном сейфе с пометкой «только это устройство» (решения 3, 4, 6; фаза 048).
- **Граница:** всё, что делается с доступом к машине сервера, вне рамок (см. «Границы»): данные сервера защищаются от кражи диска или машины и от утечки копий.
- **Возможность:** шифрование SQLite без CGO есть у `github.com/ncruces/go-sqlite3` v0.35.6 — слои `vfs/adiantum` и `vfs/xts`; сервер остаётся одним статическим бинарём.
- **Ожидание владельца:** база сервера зашифрована. В ней лежат и адреса сервера, в том числе onion-адрес (тема 2, решение 11).

Страница — `storage.html`.

**Решения владельца, 2026-10-08:**

1. **Сервер шифрует базу и файлы вложений сам.** Ключ данных — случайный; его запирает пароль, который владелец задаёт при установке (Argon2id). Шифрованию диска средствами системы не доверяем и на него не опираемся — ни на сервере, ни на устройствах. Забытый пароль — потерянные данные: придумать и сохранить пароль — забота владельца.
2. **Бэкап сервера зашифрован тем же паролем:** снимок базы, файлы вложений и запертый ключ данных одним файлом; восстановление — на любой машине, с тем же паролем.
3. **Ничего не попадает в системные бэкапы:** iOS — ни в iCloud, ни на компьютер; Android — ни в автобэкап, ни в перенос; macOS — ни в Time Machine; на Windows и Linux данные лежат в папке данных приложения, а не в «Документах».
4. **Локальная база на устройстве шифруется** случайным ключом локальной базы, который лежит в системном сейфе с пометкой «только это устройство». Ключ не прочитать — приложение стирает локальные данные и возвращается к спариванию; выход стирает базу и ключ.
5. **Блокировки приложения кодом нет:** потерянное устройство отзывают с другого (тема 3).

**Решения владельца, 2026-10-09:**

6. **Файлы на устройстве тоже шифруются** — скачанные вложения и копии исходящих, ключом локальной базы, кусками, как на сервере, чтобы просмотр и докачка работали. Для видео и «Открыть в…» файл на время расшифровывается во временную папку приложения и потом стирается; «Сохранить» отдаёт открытую копию туда, куда выбрал человек.
7. **Приняты при вычитке страницы:** пароль сервера не короче 12 знаков; вложения на сервере шифруются тем же ключом данных кусками по 64 КиБ, чтобы докачка и чтение по частям (043) продолжали работать; смена пароля перезапирает ключ данных без перешифровки.
8. **Названия ключей:** «ключ локальной базы» — случайный ключ шифрования данных на устройстве; «ключ устройства» — только ключ Ed25519 для проверки (темы 1 и 3).
9. **Пароль после перезапуска — вариант А** (пока так, владелец уточнит позже): сервер запускается запертым и ждёт пароль — на служебной странице или командой в терминале. Пока пароль не введён, служебная страница показывает только поле пароля, а устройствам сервер не отвечает: даже ключ сервера лежит в зашифрованной базе. Неверный пароль не открывает ключ данных и ничего не меняет на диске; новую базу поверх существующей сервер не создаёт. Не выбраны: пароль на той же машине (параметр, переменная, файл) — шифрование базы перестало бы защищать от кражи диска; ключ данных в хранилище системы (Keychain, DPAPI) — опора на защиту системы, от которой отказались в решении 1.

**Для реализации:**

- Сервер: драйвер `modernc.org/sqlite` → `github.com/ncruces/go-sqlite3` со слоем `vfs/adiantum` (без CGO). Запертый ключ данных лежит рядом с базой. Ключ сервера Ed25519 лежит в зашифрованной базе — пока база не открыта, сервер не отвечает устройствам.
- Приложение: на Windows и Linux `getApplicationDocumentsDirectory` — это «Документы» пользователя (`path_provider`), поэтому данные лежат в папке данных приложения. Android — `allowBackup="false"` и правила извлечения данных; iOS и macOS — пометка «не в бэкап» на папке с данными. Шифр локальной базы — `ring` в Rust-модуле, та же библиотека, что под TLS.
