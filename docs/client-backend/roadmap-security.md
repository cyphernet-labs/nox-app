## 1. Вход и защита канала — ☑

Описано на странице темы 1. Решения 2026-10-09 — заказчик дал свои библиотеки; прежняя редакция темы на взаимном TLS заменена целиком:

1. **Соединение — слоями:** транспорт (TCP напрямую или поток через Tor) → шифрование TLS 1.3 → проверка «кто есть кто» по протоколу Eidolon на ключах Ed25519 → команды (WebSocket) и файлы (HTTP). *Почему:* так просил заказчик — проверка сторон отдельно от шифрования и одинакова на любом пути.
2. **Шифрование — TLS 1.3, не Noise** (владелец). В приложении — rustls на криптографии ring в Rust-модуле, на сервере — `crypto/tls`. Старые версии TLS не принимаются.
3. **Вызов для проверки — отпечаток соединения:** экспортёр TLS 1.3 по RFC 9266 (метка `EXPORTER-Channel-Binding`, пустой контекст, 32 байта). Обе стороны получают его из TLS сами, по сети он не ходит. *Почему:* отпечаток свой у каждого соединения, поэтому посредник не перенесёт подпись из одного соединения в другое.
4. **Eidolon:** каждая сторона шлёт 160 байт — ключ Ed25519 (32), подпись над ключом (64), подпись над отпечатком (64); проверки — длина, обе подписи, ключ из списка разрешённых. В приложении список — один ключ, ключ сервера из ссылки; на сервере список пуст (годится любой ключ с верными подписями), права даёт сам сервер: спаренному устройству — всё, новому — только предъявить токен (тема 3). Первым показывает себя приложение, вторым — сервер, как в `netservices` заказчика (открывший соединение — инициатор); команды или токен приложение отправляет только после того, как сверило ключ сервера с ключом из ссылки. *Следствие:* машина, оказавшаяся по адресу вместо сервера, видит открытый ключ устройства, но войти с ним не может — подпись привязана к её соединению.
5. **Не на чистом Dart:** транспорт, TLS, Eidolon и Tor — в Rust-модуле приложения. *Почему:* TLS Dart не отдаёт отпечаток соединения. Dart и Rust-модуль связаны прямыми вызовами функций внутри одного процесса, без локальных адресов и портов; WebSocket, команды и Dio остаются в Dart поверх своего `Socket`.
6. **Сервер на Go:** TLS — `crypto/tls` (отпечаток — `ConnectionState.ExportKeyingMaterial`), технический сертификат — `crypto/x509`, подписи — `crypto/ed25519`, Eidolon — своя реализация по правилам `eidolon-auth`.
7. **Ключ устройства Ed25519 хранится в системном сейфе** на всех пяти платформах, с пометкой «только это устройство»: в бэкапы и на другие устройства он не попадает (тема 4). Хранение в чипе — возможное усиление позже, только с ключом P-256; тогда и Eidolon понадобятся подписи P-256.
8. **Библиотеки** (версии на 2026-10-09): в приложении — `rustls` 0.23.45, `ring` 0.17.14, `eidolon-auth` 0.3.1, `ec25519` 0.1.0 (через `cyphergraphy` 0.3.1; оба подключает `cyphernet` 0.5.4 с возможностями `eidolon` и `ed25519`), `arti-client` 0.47.0, `native_toolchain_rust` 1.0.7, `dart:ffi`, `flutter_secure_storage` 11.2.0; на сервере — `crypto/tls`, `crypto/x509`, `crypto/ed25519` (Go 1.27.2).

**Предложено мной, ждёт подтверждения:**

- **Сертификат TLS у сервера технический, приложение его не сверяет; у приложения сертификата нет.** *Почему:* кто на другом конце, проверяет Eidolon по подписи над отпечатком именно этого TLS-соединения; сверка сертификата повторила бы ту же проверку вторым ключом, и проверка перестала бы быть независимой от TLS.

**Для реализации:**

- Только TLS 1.3 с обеих сторон: экспортёр годится как отпечаток в TLS 1.3, а в TLS 1.2 — только с Extended Master Secret (RFC 9266).
- Отпечаток: rustls — `export_keying_material(…, b"EXPORTER-Channel-Binding", Some(b""))`, Go — `ExportKeyingMaterial("EXPORTER-Channel-Binding", nil, 32)`. В TLS 1.3 отсутствующий и пустой контекст дают одно значение (RFC 8446, §7.5).
- rustls в приложении: своя проверка сертификата сервера принимает любой сертификат, но подпись рукопожатия TLS 1.3 проверяет (`rustls::crypto::verify_tls13_signature`); `with_no_client_auth()`. Сервер: `MinVersion: tls.VersionTLS13`, `ClientAuth: tls.NoClientCert`, технический сертификат создаётся при первом запуске.
- Роли в `eidolon-auth`: приложение — инициатор, сервер — отвечающий. До успешной проверки Eidolon по соединению не идёт ничего, кроме двух её сообщений.
- Eidolon на Go проверяется общими тестовыми данными с `eidolon-auth`: Ed25519 детерминирован (RFC 8032), поэтому те же ключ и отпечаток дают те же 160 байт.
- Сервер ищет устройство по ключу на каждом соединении — по ключу из сообщения Eidolon после проверки подписей.
- Возобновление сессий TLS проверку не обходит: Eidolon идёт в каждом соединении, а отпечаток у возобновлённого соединения свой.
- **Rust-модуль нужен на всех пяти платформах, Linux тоже:** TLS и Eidolon живут только в нём. Сейчас хук сборки `packages/nox_tor` пропускает Linux, а в `rust-toolchain.toml` нет Linux-целей — меняется вместе с переделкой; сборка под Linux начнёт требовать Rust.
- **Платформы проверены 2026-10-09:** `eidolon-auth` и `cyphergraphy` с `ed25519` — чистый Rust без C-кода, `cargo check` проходит для всех 12 целей пяти платформ; rustls 0.23.45 на ring 0.17.14 уже собираются Flutter-сборкой в Rust-модуле под iOS (симулятор), Android (arm64; библиотека выровнена на 16 КБ, как требует Google Play) и macOS; `native_toolchain_rust` и нативные сборки Flutter 3.44.1 знают все пять платформ. Ни разу не собирались: Windows (задача T055 из 040 у владельца) и Linux — машин под них нет; iOS на устройстве — только компиляцией. Для Windows на ARM ring нужен clang.

## 2. Tor — ☑

Пересматривает решения трекера [roadmap-tor.md](roadmap-tor.md): сервер больше не управляет tor сам. Страница — `tor.html`.

**Решения владельца, 2026-10-08:**

1. **Сервер про Tor не знает.** tor — отдельная служба на машине сервера; ставит её наш скрипт или сам владелец, когда захочет. Из всего Tor серверу нужен только onion-адрес: он хранится в базе сервера (решение 11), сервер кладёт его в QR-код и сообщает устройствам. *Почему:* так просил заказчик — код сервера не должен зависеть от Tor.
2. **В приложении Tor встроен:** Arti в Rust-модуле — официальная реализация, одна и та же на всех пяти платформах, включая Linux.
3. **QR-код несёт onion-адрес**, только если он задан на сервере; иначе — только обычные адреса.
4. **Экран подключения:** адрес сервера и onion-адрес подставляются из QR-кода и правятся вручную; галочка `Use Tor`; если напрямую не вышло — подсказка включить `Use Tor`. Ручная правка безопасна: сервер проверяется по ключу из QR, а не по адресу.
5. **«Выбирать, через какой Tor»** у заказчика — это onion-адрес. Мосты вне рамок и нигде не упоминаются.
6. **Onion-адрес открыт для всех, кто его знает**, плюс защита PoW, — по рекомендации. Ключей доступа Tor нет: данные защищают TLS и проверка Eidolon (тема 1).
7. **Настройки Tor правятся в приложении.** Адреса, onion-адрес и `Use Tor` — в настройках связи; после правки приложение сразу подключается заново по новым данным. Если onion-адрес сменился — например, сервер переехал без папки tor, — человек вписывает новый, переспаривать не нужно.
8. **Своё понятное сообщение на каждую причину неудачи:** onion-адрес записан с ошибкой; по адресу никто не отвечает; адрес верный, но сервер не отвечает; адрес ведёт к другому серверу; нет связи с сетью Tor; напрямую не достучались, а onion-адрес есть. Arti различает эти виды ошибок (`tor-error`: `OnionServiceAddressInvalid`, `OnionServiceNotFound`, `OnionServiceNotRunning` и ошибки доступа к сети Tor); чужой сервер распознаёт проверка ключа.
9. **`Use Tor` — Tor, когда напрямую нельзя.** Приложение всегда сначала пробует напрямую; через Tor идёт, только если прямой путь не отвечает и `Use Tor` включён, и возвращается на прямой путь, как только тот снова отвечает. По умолчанию галочка выключена (решение 4); подпись под ней говорит, что Tor включается, только когда напрямую не достучаться. *Почему:* главный сценарий — дома быстро, вне дома через Tor, без ручных переключений. *Следствие:* у сервера с публичным адресом приложение вне дома подключается по нему — сеть телефона видит этот адрес, но не содержимое.
10. **Спаривание через Tor разрешено** — и первое (claim), и следующих устройств; у сервера один вход для обоих путей. *Почему:* сервер, поставленный в чужой локальной сети, куда напрямую не дотянуться, должен спариваться из любой сети. Для этого onion-адрес задаётся на сервере до показа QR-кода — скрипт установки так и делает.
11. **Адреса хранятся в базе сервера**, отдельного файла настроек нет. Задаются двумя путями, оба пишут в базу: параметрами запуска (сервер сразу записывает их в базу; так делает скрипт установки) и на служебной странице — она показывает все адреса, найденные и заданные, с кнопкой `Set` у каждого заданного. Новый адрес проверяется до записи и действует сразу, без перезапуска: новые QR-коды несут его, подключённые устройства получают его тут же. Параметр запуска перезаписывает базу, только когда сам появился или изменился, — правка на странице переживает перезапуск. *Почему:* никакой дополнительной инфраструктуры и никаких перезапусков ради смены адреса.
12. **Защита PoW в приложении включена:** Arti собирается с `hs-pow-full`. Возможность экспериментальная, поэтому версия Arti закреплена точно и проверяется при каждом обновлении. *Почему:* onion-адрес открыт намеренно (решение 6), а без решателя защита сервера не помогает своему же приложению.

**Для реализации:**

- Служебная страница слушает только loopback и уже сверяет `Host` — защита от DNS rebinding. Форма `Set` — первая запись через страницу: нужны ещё проверка `Origin` и токен формы, иначе форму отправит чужой сайт, открытый в браузере на машине сервера.
- Onion-адрес проверяется до записи: v3, 56 символов base32, контрольная сумма и версия.
- Правило «параметр перезаписывает, только когда изменился»: сервер хранит в базе последнее применённое значение каждого параметра.
- Без `hs-pow-full` в Arti стоит заглушка, которая не решает задач никогда (`tor-hsclient`, `pow/v1_stub.rs`); с ним Arti берёт сложность из описания onion-сервиса, решает задачу в отдельном потоке и повышает сложность при повторах (потолок 10 000). Решатель ускоряет JIT (`hashx`: по умолчанию сначала компиляция, при отказе — интерпретатор); на iOS JIT запрещён — время решения замерить.

**Ревью безопасности, 2026-10-08** (темы 1 и 2; ни одна находка не прошла порог 8 из 10):

13. **Ссылка claim живёт недолго** и не пишется в журнал сервера; если ею не воспользовались, на машине сервера получают новую. *Почему:* вместе с claim через Tor утёкшая ссылка давала бы захват сервера из любой точки, а срок жизни сужает окно. Подробности — тема 3.
14. **Выход с последнего устройства возвращает сервер к claim:** устройство, спаренное по новому QR-коду с машины сервера, снова становится устройством владельца — со всей перепиской.
15. **Подмена служебной страницы и правка адресов кнопкой `Set` другими пользователями машины сервера** — вне рамок (см. «Границы»).

## 3. Спаривание и жизненный цикл ключей — ☑

Страница — `pairing.html`.

**Решения владельца, 2026-10-08:**

1. **Новое устройство подтверждается** на устройстве, выдавшем приглашение: `Allow` / `Deny`. Без ответа запрос истекает вместе с приглашением (10 минут); `Deny` гасит токен. *Почему:* утёкший QR-код без нажатия ничего не даёт, а спариваться теперь можно через Tor из любой точки. `pair` снова ждёт ответа — для своих устройств; ожидание для приглашения человека ушло вместе с 034.
2. **Отдельного восстановления нет** — ни фразы, ни кодов, ни аварийного комплекта ([Q16](open-questions.md) снят). Устройство добавляется двумя путями: приглашением со спаренного устройства (с подтверждением) или ссылкой с машины сервера — она работает всегда: первое устройство, возврат после выхода с последнего, потеря всех устройств. Владельца нет — первое устройство становится им; владелец есть — новое присоединяется к нему со всей перепиской, а потерянные отзывает из своего списка. *Почему:* владелец не хочет долгоживущего секрета, а без устройств владение доказывает только доступ к машине. *Цена:* без живых устройств и без доступа к машине войти нельзя.
3. **Ссылка с машины сервера** живёт 10 минут. Пока устройств нет, служебная страница показывает её сразу; когда устройства есть — по кнопке `Add a device`, чтобы просто открытая страница не держала живую ссылку. Сама себя ссылка не перевыпускает: истёкшая — `Link expired` и кнопка `New link`; живая всегда одна — новая гасит прежнюю. На машине без экрана ссылку печатает команда в терминале; в журнал службы она не пишется.
4. **Без коротких кодов и PIN:** ссылка несёт то же, что QR-код; без камеры её вставляют текстом или читают QR-код из картинки.
5. **Ссылка и QR-код:** ключ сервера Ed25519 (32 байта), токен, один прямой адрес, публичный и onion — если заданы; остальные адреса устройство получает после спаривания. Аварийный комплект — та же ссылка без токена.
6. **Отзыв** — с любого спаренного устройства; выход из приложения — отзыв своего. Отзыва со служебной страницы нет: потерянные устройства отзывает новое, добавленное ссылкой с машины.
7. **Ключ сервера** лежит в базе: бэкап базы оставляет сервер «тем же» для всех устройств. Замены ключа без переспаривания нет: утечка ключа или потеря базы — новый ключ и спаривание заново.
8. **Ключ устройства** — новый при каждом спаривании; после выхода стирается.
9. **Уже спаренные устройства** спаривают заново один раз: продукт не выпущен, кода перехода не будет.
10. **Формат ссылки:** `nox://pair/<base64url без =>`. Данные: версия (1 байт, сейчас 3), ключ сервера (32), токен (16), список адресов «тип, длина, значение» — IPv4 (6), IPv6 (18), имя (N + 2), onion — открытый ключ сервиса (32), порт 443; неизвестный тип пропускается по длине. *Почему:* домен `nox.app` проекту не принадлежит, а страница на нём прочитала бы всё после `#` — и токен; ссылку своей схемы браузер никуда не отправляет, а приложение уже пользуется `nox://id/`. Версия 3 — чтобы старые сборки, знающие версии 1 и 2, отказывали, а не читали мусор.

**Для реализации:** нынешние ссылки (`https://nox.app/p/#…`, контракт §8A; `pairingLinkPrefix` на сервере, `PairingLink._prefix` в приложении) ведут на чужой домен. Открытая в браузере, такая ссылка целиком достаётся странице этого домена: токен, а у ссылки версии 2 ещё и одноразовый ключ доступа к onion. Своего домена у проекта нет; префикс меняется на `nox://pair/` вместе с переделкой, до неё код не трогается (владелец, 2026-10-08).

## 4. Данные на диске — ◐

- **Сервер:** база SQLite (драйвер `modernc.org/sqlite`, чистый Go) хранит переписку открытым текстом; закрытый ключ сервера лежит в ней же; вложения — обычными файлами рядом с базой. Бэкап базы — это весь сервер.
- **Устройство:** локальная база (Sembast) лежит в Documents и не зашифрована, её защищает песочница системы и шифрование хранилища самой системой. Documents и Application Support, где лежат копии исходящих файлов, по умолчанию попадают в бэкап iCloud и в автобэкап Android: `allowBackup` в манифесте не выключен. Кэш вложений лежит в Caches — туда бэкап не заглядывает. Ключи хранятся в системном сейфе, на iOS — «только это устройство».
- **Граница:** всё, что делается с доступом к машине сервера, вне рамок (см. «Границы»): данные сервера защищаются от кражи диска или машины и от утечки копий.
- **Возможность:** шифрование SQLite без CGO есть у `github.com/ncruces/go-sqlite3` v0.35.6 — слои `vfs/adiantum` и `vfs/xts`; сервер остаётся одним статическим бинарём.
- **Ожидание владельца:** база сервера зашифрована. В ней лежат и адреса сервера, в том числе onion-адрес (тема 2, решение 11).

Страница — `storage.html`.

**Решения владельца, 2026-10-08:**

1. **Сервер шифрует базу и файлы вложений сам.** Ключ данных — случайный; его запирает пароль, который владелец задаёт при установке (Argon2id). Шифрованию диска средствами системы не доверяем и на него не опираемся — ни на сервере, ни на устройствах. Забытый пароль — потерянные данные: придумать и сохранить пароль — забота владельца.
2. **Бэкап сервера зашифрован тем же паролем:** снимок базы, файлы вложений и запертый ключ данных одним файлом; восстановление — на любой машине, с тем же паролем.
3. **Ничего не попадает в системные бэкапы:** iOS — ни в iCloud, ни на компьютер; Android — ни в автобэкап, ни в перенос; macOS — ни в Time Machine; на Windows и Linux данные лежат в папке данных приложения, а не в «Документах».
4. **Локальная база на устройстве шифруется** случайным ключом локальной базы, который лежит в системном сейфе с пометкой «только это устройство». Ключ не прочитать — приложение стирает локальные данные и возвращается к спариванию; выход стирает базу и ключ.
5. **Блокировки приложения кодом нет:** потерянное устройство отзывают с другого (тема 3).

**Решения владельца, 2026-10-09:**

6. **Файлы на устройстве тоже шифруются** — скачанные вложения и копии исходящих, ключом локальной базы, кусками, как на сервере, чтобы просмотр и докачка работали. Для видео и «Открыть в…» файл на время расшифровывается во временную папку приложения и потом стирается; «Сохранить» отдаёт открытую копию туда, куда выбрал человек.
7. **Приняты при вычитке страницы:** пароль сервера не короче 12 знаков; вложения на сервере шифруются тем же ключом данных кусками по 64 КиБ, чтобы докачка и чтение по частям (043) продолжали работать; смена пароля перезапирает ключ данных без перешифровки.
8. **Названия ключей:** «ключ локальной базы» — случайный ключ шифрования данных на устройстве; «ключ устройства» — только ключ Ed25519 для проверки (темы 1 и 3).

**Для реализации:**

- Сервер: драйвер `modernc.org/sqlite` → `github.com/ncruces/go-sqlite3` со слоем `vfs/adiantum` (без CGO). Запертый ключ данных лежит рядом с базой. Ключ сервера Ed25519 лежит в зашифрованной базе — пока база не открыта, сервер не отвечает устройствам.
- Приложение: на Windows и Linux `getApplicationDocumentsDirectory` — это «Документы» пользователя (`path_provider`), там сейчас лежит `app.db`; данные переезжают в папку данных приложения. Android — `allowBackup="false"` и правила извлечения данных; iOS и macOS — пометка «не в бэкап» на папке с данными. Шифр локальной базы — `ring` в Rust-модуле, та же библиотека, что под TLS.

**Открыто:**

- **Как пароль попадает к серверу после перезапуска** — разбирается. Варианты: сервер запускается запертым и ждёт пароль на служебной странице или в терминале; пароль лежит на той же машине (параметр, переменная, файл); ключ данных хранит система (Keychain, DPAPI, TPM). Неверный пароль в любом варианте ничего не меняет и не портит: ключ данных просто не открывается.

## 5. Постквантовый обмен ключами — ☐

Гибрид X25519MLKEM768 защищает записанный трафик от расшифровки в будущем. Go включает его по умолчанию (с Go 1.24); в rustls он есть только с криптопровайдером aws-lc-rs (проверено по исходникам rustls 0.23.45), а в теме 1 выбран ring. Решить: нужен ли гибрид сейчас и меняем ли ring на aws-lc-rs.
