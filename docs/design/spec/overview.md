# Верхнеуровневые требования к UI

> Продуктовая модель NOX, принятые решения по UI и глобальные UI-конвенции, общие для всех экранов. Здесь — только то, что видит человек; протоколы, шифрование и клиентский сервер описаны в [docs/client-backend](../../client-backend/).

## Ориентир

Функциональная близость к [Signal](https://signal.org/): мессенджер для обмена текстом и файлами. Структура экранов и навигации частично заимствуется у Signal с отличиями, перечисленными ниже.

**Модель (владелец, 2026-09-10, фаза 037).** Пространство чатов NOX — **личное**: оно живёт на собственном клиентском сервере человека и видно на всех его устройствах и больше нигде. Разные люди не делят сервер, и их серверы между собой не соединяются. Общение между людьми — дело **relay-сервера**, протокол которого ещё не спроектирован ([Q13](../../client-backend/open-questions.md)). Поэтому механики, завязанные на 1:1-аудиторию Signal (delivered/read-квитанции, membership, per-chat подписки), в этой итерации не появляются — см. соответствующие разделы.

## Терминология и брендинг

- **Имя продукта** — **NOX** (все заглавные буквы). Так оно появляется в UI (wordmark на splash, заголовки), в прозе документации и в публичных материалах. Имя репозитория — `nox-app` (нижний регистр, технически).
- **Единица коммуникации** — **чат** (chat). Это финальный термин в UI и в документации; «канал», «форум», «комната» не используются.
- **Идентификатор пользователя в UI** — `Your ID`. Это единый термин на всех экранах, где идентификатор упоминается (карта идентичности 7.1); `Identifier` как отдельное слово в UI не используется. Вход идёт не по идентификатору, а по ссылке спаривания — её поле называется `Pairing link`.
- **Глаголы входа/выхода** — `Sign in` (вход) и `Log out` (выход). Пара зафиксирована; `Log in` / `Sign out` не используются.
- **Язык UI-текстов в дизайне** — **английский**. Все label-ы полей, тексты кнопок, плейсхолдеры, сообщения об ошибках и прочие UI-строки в спецификациях экранов фиксируются на английском. Украинский перевод живёт в локализации приложения рядом с английским (каждая строка — на обоих языках). Русский в UI продукта не используется (это язык документации и общения, не язык пользователя).

## Дизайн-фреймворк

UI строится на **Material Design 3** (Material You).

- Базовая мотивация — снижение стоимости реализации (готовые Flutter-компоненты Material) и узнаваемые для пользователя паттерны взаимодействия.
- Цветовая палитра, типографика и брендинг — в [дизайн-системе](design-system.md) (цвет извлечён из логотипа, seed = бирюза).
- Часть компонентов будет кастомизирована: в частности, нижняя панель с центральной «+» (см. [4.1 Tab bar shell](screens/tab-bar-shell.md)) не сводится к стандартному `NavigationBar`.
- Общее правило — держаться «плюс/минус» в рамках стандартных Material-контролов, не уходить в полностью кастомную систему.
- **Темизация:** поддерживаем светлую и тёмную темы (выбор пользователя — в настройках 7.3, по умолчанию системная). Все Material 3 компоненты — `AppBar`, `TextField`, кнопки, фон, иконки — автоматически адаптируются через `ColorScheme`. Кастомные элементы (нижняя панель с «+») должны переключать цвета вместе с темой.
  - **Два исключения (brand-fixed, не зависят от темы):** фон **splash (1.1)** — всегда тёмный `brand/canvas-dark`; поверхность **QR-кода приглашения в 7.8** — всегда светлая `brand/qr-surface` (чтобы код сканировался и в dark). См. [дизайн-систему](design-system.md).

## Запуск приложения

- Стартовый экран — splash с логотипом, **только при холодном старте** (при тёплом возврате из бэкграунда splash не показывается).
- На splash приложение определяет состояние авторизации:
  - устройство не спарено → экран входа (2.1);
  - спарено, но шаг выбора имени не пройден → 2.3;
  - спарено → основной шелл.
- Пока на старте не открылись локальные данные (системное хранилище секретов ещё не отвечает), splash остаётся на экране, а хранилище опрашивается повторно. Если ключ локальных данных потерян, данные стираются и открывается 2.1 — устройство спаривается заново. Экрана ошибки на старте нет: ошибка чтения сессии считается «не спарено», а не падением.
- После спаривания сессия хранится на устройстве; при следующем запуске пользователь сразу попадает в основной шелл (авто-вход). Имя пользователя при этом всегда уже существует (см. «Идентичность пользователя»), поэтому состояния «вошёл, но имени нет» не возникает.

## Аутентификация / вход

- Вход анонимный — без телефона, без e-mail.
- Устройство спаривается **ссылкой** `nox://pair/…`. Её выдаёт сама машина сервера — служебная страница или команда `noxd link` (**ссылка с машины**), — или выпускает другое устройство человека (**приглашение**, [7.8](screens/devices.md)). Ссылка несёт ключ сервера, одноразовый токен и адреса сервера и живёт 10 минут.
- Ссылка с машины спаривает сразу: на сервере без человека она его заводит (дальше — выбор имени, 2.3), на сервере с человеком присоединяет к нему новое устройство со всей перепиской. Отдельного восстановления нет: потерявший все устройства возвращается ссылкой с машины.
- Приглашение спаривает только после **`Allow`** на устройстве, которое его выпустило: оно спрашивает диалогом поверх любого экрана ([8.2](screens/pair-request.md)), а новое устройство ждёт на экране подключения 2.4 и может отозвать запрос кнопкой `Cancel`. Закрытие приложения запрос не отзывает: после перезапуска ожидание продолжается тем же запросом, пока не вышел его срок. Без ответа запрос истекает вместе с приглашением.
- Три способа предъявить ссылку:
  - вставка или набор (2.1);
  - сканирование QR-кода камерой (2.2; iOS, Android, macOS);
  - картинка с QR-кодом (2.1; Windows, Linux).
- Любая читаемая ссылка ведёт на **экран подключения** [2.4](screens/connect.md): адрес сервера и onion-адрес из ссылки можно поправить, галочка `Use Tor` выключена, спаривает кнопка `Connect`. Ключ сервера не показывается и не правится: правка адреса безопасна, потому что на каждом соединении сервер доказывает ключ из ссылки, и токен уходит только ему.
- **Ошибки входа** разделены: нечитаемая ссылка и ссылка новее приложения — **inline** на 2.1 ([login.md](screens/login.md)); связь, [причины неудачи](#причины-неудачи) и отказы токена — под `Connect` на 2.4.

## Идентичность пользователя

В системе сосуществуют две сущности:

- **Идентификатор** — публичный идентификатор личности, который назначает клиентский сервер. Анонимный и не секретный: входа по нему нет — устройство спаривается ссылкой и доказывает владение своим ключом, который никуда не уезжает. В UI обозначается как `Your ID` и показывается в 7.1 целиком.
- **Имя пользователя** (label / display name) — публичная метка, под которой пользователя видят другие в чатах.

Имя пользователя:

- сервер назначает имя вида `User<random>` (например `User1234`) **в момент, когда спаривание заводит личность**, поэтому у пользователя имя есть всегда;
- сразу после такого спаривания экран онбординга 2.3 предлагает **изменить** это имя — шаг **опциональный** (можно пропустить, оставив `User<random>`); устройство, присоединённое к уже существующему человеку, 2.3 не видит;
- редактируется позднее в настройках с теми же правилами;
- **на занятость не проверяется** (решение владельца 2026-09-02): сервер занятость label не проверяет и не сообщает, поэтому на экранах установки и редактирования проверки занятости нет — решают только charset и длина, и решают сразу при вводе. На личном сервере человек один, сравнивать имя не с кем; уникальность имён между людьми — вопрос relay, и решаться он будет там;
- максимальная длина — **32 символа**, минимальной нет;
- допустимый charset — **латиница, цифры и `-`, `_`, `.`** (без пробелов, кириллицы и других символов).

На одном устройстве поддерживается **одна идентичность**. Смена идентичности возможна только через Logout с последующим повторным входом.

## Обработка ошибок

- В приложении используется **один универсальный экран ошибки** (3.1), параметризованный иконкой, заголовком/сообщением и кнопкой `Try again`.
- Два режима: блокирующий (кнопки «назад» нет, последний экран в стеке; системный back на Android сворачивает приложение) и встраиваемый (со стрелкой back — не последний в стеке).
- 3.1 используется только для fatal / неожиданных ошибок. Уровни ошибок ниже fatal — см. «Глобальные UI-конвенции».

## Основной шелл

После входа пользователь попадает в основной шелл с **нижней панелью навигации из трёх элементов** — полная спецификация в [4.1 Tab bar shell](screens/tab-bar-shell.md):

| # | Элемент | Тип | Содержимое |
|---|---|---|---|
| 1 | **Chats** | таб | все чаты этого человека и вход в чат |
| 2 | **+** | действие (по центру, docked FAB) | создание нового чата (видна на обоих табах) |
| 3 | **Settings** | таб | имя пользователя, идентификатор, устройства, связь, тема, язык, уведомления, выход |

Центральный элемент — кнопка действия, не самостоятельный таб с собственным состоянием. Отдельного экрана профиля нет: всё, что обычно лежит в профиле, помещено в раздел «Настройки».

На широкой ширине (от 840dp) вместо нижней панели — боковой рейл с двумя назначениями (`Chats`, `Settings`) и аватаром аккаунта внизу; «+» стоит в шапке панели чатов (решение владельца 2026-09-20), поэтому при открытой вкладке `Settings` кнопки создания на широкой ширине нет.

## Чаты

### Модель

- Чаты — **личное пространство одного человека**, живущее на его собственном сервере. Видны они на всех его устройствах и больше нигде: общего для всех списка чатов не существует.
- **Прав и пермишенов нет** — не потому, что пространство открыто, а потому, что на сервере один человек и разграничивать некого.
- Создать чат можно в любой момент; спрашивать разрешения не у кого.
- **Сценария «присоединиться» нет**: присоединяться некому. Это не отложенная функция, а несуществующая — она появится вместе с relay, и её форма будет решаться там.
- **Чаты не удаляются**: ни создателем, ни кем-либо ещё. История существует постоянно.
- Лимита числа созданных чатов нет.

### Внутри чата

- Просмотр ленты сообщений.
- Отправка **текстовых сообщений**.
- **Обмен файлами**.
- Каждое сообщение подписывается именем пользователя (label) автора. Автор и выравнивание «свои / чужие» определяются по **идентификатору** (стабильный ключ), не по label; отображаемый label — текущий на момент рендера.
- **Статус сообщений:** только локальный `sent` (принято сервером), плюс `pending` (в очереди на отправку) и `error` (отправка получила отказ → тап для повтора). Неотправленное своё сообщение (`pending` или `error`) снимается с отправки долгим нажатием, на десктопе — правым кликом. **delivered / read не используются** — доставлять некому: сообщение принимает собственный сервер человека, а не другая сторона. Вопрос вернётся вместе с relay.
- Способ отображения файлов — type-icon chip (иконка типа + имя + размер); **image-вложения показывают миниатюру + full-screen**, а на 5.3 **картинка показывается, а видео проигрывается** (owner-ревизии F4 и 2026-09-20, см. [«Файлы: иконки типов и превью»](#файлы-иконки-типов-и-превью)).

### Список чатов

- В хедере списка чатов — **поисковая строка по имени чата** (минимальный механизм для масштабирования). Сортировка, категории, фильтры — позже, при необходимости.
- **Непрочитанные:** считаются от момента последнего открытия чата этим устройством. Никогда не открытый чат бейджа не имеет. Бейдж — число, с переполнением `99+`.

## Создание чата

- Точка входа — центральная «+» в нижней панели; на широкой ширине — «+» в шапке панели чатов.
- Доступно всегда; спрашивать разрешения не у кого.
- Поток — минимальный: поле `Chat name`, кнопка `Create`.
- Имя чата **уникально в пределах этого сервера**: чат создаётся локально, единого пространства имён не существует. На форме создания действует валидация в реальном времени — по локальной базе всегда и сервером, когда он может ответить сразу; занятое имя выбрать нельзя; авторитет по занятости — сервер.
- **Создание не ждёт связи** (фаза 041). Чат создаётся на устройстве сразу, под id, который придумало устройство, и сразу открывается; на сервере его создаёт очередь исходящих — раньше его сообщений, как только появится любой путь. Последнее слово по имени — за сервером в этот момент: если имя к тому времени занято, чат помечается и ждёт переименования, которое делается на устройстве и само запускает создание снова ([5.1](screens/chats-list.md), [5.2](screens/chat.md)).
- Максимальная длина имени чата — **64 символа**.
- Charset для имени чата **не ограничен** — любые символы (отличается от charset label-а пользователя).

## Настройки

Состав раздела:

- **Имя пользователя.** Просмотр и редактирование label (с той же валидацией, что и при первом вводе: charset и длина, без проверки занятости — см. выше).
- **Идентификатор (`Your ID`).** Показан **целиком**, моноширинным, без маски: `Your ID` — публичный идентификатор личности, прятать нечего. Действий у карты идентичности два: `Edit name` и `Copy ID`.
- **Устройства.** Список устройств человека, отзыв любого из них и приглашение для нового — [7.8](screens/devices.md).
- **Связь.** Адрес сервера, onion-адрес и `Use Tor` — [7.10](screens/connection.md). Адреса применяются кнопкой `Save`, `Use Tor` — сразу; после применённой правки приложение подключается заново. Пока связи нет, раздел показывает причину.
- **Уведомления.** Один переключатель push (on/off) — по всем чатам своего сервера: на личном сервере все чаты свои, отбирать не из чего.
- **Внешний вид.** Переключение темы (System / Light / Dark).
- **Язык.** Выбор языка UI:
  - **Системный** (по умолчанию) — если системный язык устройства English или Українська, используется он; иначе автоматический fallback на **English**.
  - **English**.
  - **Українська**.
- **Terms** и связанная юридическая информация.
- **О приложении.**
- **Выход (Logout).** Действие с диалогом подтверждения, без отдельного экрана. **Полностью очищает сессию и локальные данные с устройства** (вместе с ключом, которым они зашифрованы); следующий вход — с нуля через 2.1 / 2.2. При живой связи — соединение поздоровалось — выход сначала отзывает ключ этого устройства на сервере; без связи очищает сразу, а ключ отзывают с другого устройства. Выход с последнего устройства возвращает сервер к состоянию «устройств нет»: его служебная страница сразу показывает ссылку с машины, а человек и переписка остаются.

> Раздел **Support** в этой версии **исключён** (вне scope).

## Глобальные UI-конвенции

Переиспользуемые правила, чтобы экраны не решали одно и то же по-разному. Конкретные значения цветов/отступов уточняются в дизайн-системе.

### Уровни ошибок и обратной связи

| Уровень | Когда | Компонент |
|---|---|---|
| Field-level | ошибка валидации конкретного поля | `TextField` `errorText` |
| Transient | разовая ошибка/подтверждение, восстановление не требуется | `SnackBar` (M3), снизу |
| Persistent | нужно повторить/восстановить (offline, не удалось загрузить список) | `MaterialBanner` (M3), сверху |
| Fatal | неожиданная / server-fatal (5xx) | экран **3.1** |

«banner / snackbar» как неопределённость устранена: transient → `SnackBar`, persistent → `MaterialBanner` (именно `MaterialBanner`, не «Banner»).

### Snackbar

`SnackBar` показывается снизу, **над нижней панелью и docked-«+»** (не перекрывая FAB). Нейтральный — `inverseSurface` / `onInverseSurface`; ошибка — `errorContainer` / `onErrorContainer` (см. [design-system §9.11](design-system.md)); опциональное одиночное action; авто-скрытие ~4 c.

### Offline / нет соединения

Постоянный `MaterialBanner` сверху затронутого экрана (5.1 / 5.2 / 5.4) на время offline. Его текст — [причина неудачи](#причины-неудачи), если она известна, иначе `No connection`; действие `Try again` перезапускает подключение. Offline наступает, когда целый раунд поиска пути до сервера — прямые адреса и, если включена `Use Tor`, Tor — не дал ничего, и держится до первого подключения; пока путь только ищется, в углу экрана `Connecting…` (см. ниже), а баннера нет. Отправка офлайн → сообщение в `pending` до восстановления; обрыв связи, сколько бы он ни длился, сообщение в `error` не переводит — `error` значит отказ (сервер отказал или прикреплённый файл больше не открывается). Точечные ошибки операций — по таблице уровней выше.

**Связь ничего не держит** (owner, 2026-10-04). То, что уже лежит на устройстве, показывается сразу, что бы ни делала связь: список чатов (5.1), лента (5.2) и файлы карточки чата (5.4) читаются из локальной базы, а ответ сервера догружается в фоне и приходит в них сам. Чтение, у которого есть локальный ответ, не ждёт соединения, которого нет: подъём Tor бывает долгим, и локальные чаты и сообщения не должны всё это время стоять за спиннером. Когда связь появляется, экраны спрашивают сервер снова. Спиннер остаётся только там, где на устройстве ничего нет, а сервер уже спрашивают; без связи пустой экран — правда, и он показывается сразу. Писать можно всегда: сообщение ложится в очередь на устройстве с часиками и уходит, как только появится любой путь до сервера — прямой или через Tor. Создать чат тоже можно всегда (фаза 041): id придумывает устройство, а очередь создаёт чат на сервере раньше его сообщений. Переименование уже созданного чата и имя человека требуют ответа сервера; чат, которого ещё нет на сервере, переименовывается на устройстве.

### Путь до сервера и `Use Tor`

До сервера два пути (решения владельца 2026-10-08, тема 2 трекера безопасности):

- **Напрямую** — всегда первым: по адресам сервера в локальной сети, по его публичному адресу (если сервер его задал) и по адресу, который человек вписал сам.
- **Через встроенный Tor** к onion-адресу сервера — только когда одновременно: напрямую никто не ответил, включена галочка **`Use Tor`** и onion-адрес известен. Возврат на прямой путь — как только тот отвечает: сразу при смене сети, иначе не позже чем через 2 минуты. Tor встроен одинаково на всех пяти платформах, Linux включительно.
- **`Use Tor`** по умолчанию выключена, хранится на устройстве и между устройствами не синхронизируется. С выключенной галочкой приложение не открывает через Tor ни одного соединения. Подпись к ней везде одна: `NOX uses Tor only when it can't reach your server directly.`
- **Где настраивается:** на экране подключения [2.4](screens/connect.md) при спаривании и в разделе [7.10 Связь](screens/connection.md) после него.
- **Адреса сервера — источник истины.** Публичный и onion-адрес человек задаёт на машине сервера (параметры запуска или служебная страница); клиентский сервер сообщает их устройствам сам, и его значение заменяет ручную правку того же поля. Ручная правка нужна, когда до сервера не достучаться, и действует, пока сервер не сообщит новое. Правка безопасна: кто бы ни ответил по адресу, он обязан доказать ключ сервера из ссылки спаривания.
- **Защита от наплыва** (PoW) на onion-сервисе включается в настройках tor на машине сервера; встроенный Tor решает задачу сам — подключение при этом медленнее, на iOS заметно.

### Состояние связи в углу экрана

Человеку не нужно знать, каким путём идёт связь, поэтому угол показывает **только отклонения** от обычного:

| Связь | Угол | Баннер |
|---|---|---|
| напрямую, на связи | пусто | — |
| через Tor, на связи | бейдж `Tor` | — |
| поднимается или догоняет, путь не выбран или прямой | `Connecting…` | — |
| поднимается или догоняет через Tor | `Connecting…` + бейдж `Tor` | — |
| нет связи, причина неизвестна | пусто | `No connection` |
| нет связи, причина известна | пусто | текст причины (см. «Причины неудачи») |
| сервер по onion-адресу предъявил чужой ключ | пусто | `This onion address belongs to a different server.` |
| сеть Tor объявила встроенный клиент устаревшим | как выше | плашка `Update NOX to connect away from home` на 5.1 |

- **Место.** Узкая ширина — справа в верхней панели 5.1 (перед аватаром аккаунта) и 5.2 (перед действием приглашения). Широкая — правый край заголовка окна оболочки, виден на всех её экранах.
- **Бейдж** `Tor` — цвета `secondaryContainer` / `onSecondaryContainer`. Текст `Connecting…` — `onSurfaceVariant`.
- **Нажатие** открывает пояснение с заголовком `Connection`: на узкой ширине нижний лист, на широкой — диалог. Через Tor: `NOX can't reach your server directly, so it connects through Tor. It's slower, but it works from any network.` Пока подключается: `NOX is connecting to your server.` На iOS и macOS добавляется `If you're at home, check that NOX has Local Network access in Settings.`
- **Доступность.** Текстовое имя для диктора — `Connected through Tor`, `Connecting to your server` или `Connecting to your server through Tor`. Область касания — не меньше 48×48.
- **Процентов и полос нет**: подъём Tor бывает долгим, и на это время локальные чаты остаются доступны.
- **Чужой ключ на прямом адресе** — не аномалия, а «не дома»: на другой сети тот же адрес принадлежит чужой машине. Баннера `This onion address belongs to a different server.` тогда нет — приложение идёт к следующему пути. С выключенной `Use Tor` и без onion-адреса этого баннера не бывает вовсе. Ключ сервера проверяется на каждом соединении проверкой `POST /auth` → `POST /auth2` по ключу из ссылки спаривания; «другой сервер» никогда не ведёт к выходу из приложения.

### Причины неудачи

Если подключиться не удалось, приложение говорит, что именно не так и что делать (решение владельца 8 темы 2 [трекера безопасности](../../client-backend/roadmap-security.md)). Причина — это итог последнего неудачного раунда поиска пути; удачное подключение её снимает. Раунд, причину которого назвать нельзя, оставляет общее `No connection`.

| Причина | Когда | Текст (EN) |
|---|---|---|
| неверный onion-адрес | onion-адрес не проходит проверку версии 3 (Tor-модуль отказался его набирать или вписанное не прошло проверку формата) | `This isn't a valid onion address.` |
| никто не отвечает по onion-адресу | по адресу не опубликован onion-сервис: адрес неверный или tor на машине сервера не запущен | `No server answers at this onion address. Check the address and that Tor is running on the server.` |
| сервер не отвечает через Tor | onion-сервис есть, а сервер за ним не отвечает или не успел ответить | `Your server isn't answering through Tor right now. Check that it is running.` |
| другой сервер | за onion-адресом сервер с другим ключом | `This onion address belongs to a different server.` |
| нет сети Tor | встроенный Tor не поднялся: сеть Tor недоступна | `Can't connect to the Tor network. Check your internet connection.` |
| включите `Use Tor` | напрямую никто не ответил, `Use Tor` выключена, а onion-адрес известен | `Can't reach the server directly. Turn on Use Tor to connect through Tor.` |

Где видна — там, где видно, что связи нет (уточнение 2026-10-09):

- **плашка на 5.1, 5.2 и 5.4** (обе ширины; на десктопе — в обеих панелях и в side-sheet карточки чата) — вместо `No connection`, когда причина известна; глиф `wifi_off` и действие `Try again` остаются. «Другой сервер» — плашка с глифом ошибки и тем же действием `Try again`;
- **раздел [7.10 Связь](screens/connection.md)** — строка над полями, кроме неверного onion-адреса (см. ниже);
- **экран подключения [2.4](screens/connect.md)** — под кнопкой `Connect`, как только причина найдена;
- **неверный onion-адрес** — у самого поля, и на 2.4, и в 7.10: и вписанный человеком, и отвергнутый Tor-модулем при подключении. Строка над полями в 7.10 и текст под `Connect` на 2.4 его не повторяют.

### Generated avatar (для чатов)

Аватар чата генерируется из имени:

- 1–2 инициала (первые буквы первых двух слов; иначе первые 1–2 латинские буквы или цифры имени);
- детерминированный фон из фиксированной **палитры аватаров** (контраст-выверенная, см. [design-system §2.5](design-system.md)) по хешу имени;
- круглая форма;
- если имя не даёт корректных инициалов (нелатинские буквы / эмодзи / символы / пусто — charset имени чата не ограничен) → глиф `forum` на детерминированном фоне.

Используется в списке чатов (5.1), в шапке ленты на широкой ширине (5.2) и в шапке карточки (5.4). **Per-author аватаров в ленте 5.2 нет** — только текстовый label автора. Аватар **человека** (аккаунт в шелле, строка `People` в 5.4) берёт тот же хеш-цвет, но инициалы по своему правилу: первая буква первой и последней части label, разделённого `.`, `_`, `-`.

### Файлы: иконки типов и превью

Решения владельца: миниатюры картинок — 2026-07-26 (F4, фича 020); картинка, байты которой ещё идут, видео на 5.3 и картинка на 5.3 — 2026-09-20.

- **Картинка, файл которой на устройстве**, — в ленте 5.2 **инлайн-миниатюра**, тап → **полноэкранный просмотр** (зум, закрытие; на широкой ширине — lightbox-диалог).
- **Картинка, байты которой ещё идут**, — **на месте будущей миниатюры**: глиф изображения и индикатор, той же коробки. Приходящие картинки приложение подкачивает само при открытии ленты; чип на их месте выглядел бы инертным и звал бы нажать и запустить вторую загрузку тех же байтов. Миниатюрой и этим местом становятся только форматы, которые приложение умеет нарисовать (jpg, jpeg, png, gif, webp, bmp; heic — на iOS и macOS); картинка другого формата (svg и т. п.) остаётся чипом всегда — индикатор над ней обещал бы картинку, которая не придёт.
- **На 5.3** скачанная картинка **показывается** вместо глифа, а видео **проигрывается** — на **iOS, Android и macOS**. Плеер играет **только из локального файла**: нативный плеер ходит своим HTTP-стеком мимо канала Rust-модуля, то есть мимо проверки `POST /auth` → `POST /auth2`, а клиентский сервер до этой проверки ни на что не отвечает.
- ⚠️ **Платформенный разрыв, принят владельцем осознанно:** у `video_player` нет реализаций для Windows и Linux; `media_kit` закрывает все пять, но тянет libmpv нативными библиотеками и добавляет ровно те две платформы, которые в этом проекте нельзя проверить (та же причина, по которой отложены P15 и P17). На Windows и Linux 5.3 показывает для видео глиф типа, имя, размер и `Save` — без обещаний. Предикат один: `VideoPlaybackCapability`.
- **Файлы на устройстве зашифрованы (фаза 048).** Скачанные вложения и копии исходящих лежат на диске зашифрованными ключом локальных данных. Миниатюра, полноэкранный просмотр и картинка на 5.3 расшифровываются **в память** — открытой копии на диске нет. Видео играет из **временной открытой копии** во временной папке приложения: она стирается, когда закрыт экран с плеером, а все оставшиеся — при каждом запуске и при выходе. Действия «Открыть в…» на 5.3 нет. `Save` отдаёт **открытый** файл туда, куда выбрал человек. Когда временную копию сделать нельзя (нет места на диске), на месте плеера — `Couldn't open this file. Free up some space and try again.` (обе ширины).
- **Все остальные файлы** — превью содержимого нет нигде: вложение рендерится как chip (иконка типа + имя + размер).

Маппинг типа на глиф (Material Symbols Rounded):

| Тип | Глиф |
|---|---|
| Изображение | `image` |
| Видео | `videocam` |
| Аудио | `music_note` |
| PDF | `picture_as_pdf` |
| Документ (doc/docx/odt/pages) | `description` |
| Таблица (xls/xlsx/csv/ods/numbers) | `table_chart` |
| Текст (txt/md/rtf/log) | `article` |
| Архив (zip/rar/7z/tar/gz) | `folder_zip` |
| Прочее / неизвестно | `draft` |

Используется в 5.2 (chip в сообщении; для картинки — миниатюра или её место), 5.3 (крупный глиф, если файл не показывается и не проигрывается), 5.4 (ячейка списка/сетки вложений — глиф для любого типа, включая картинки).

### Форматы времени и даты

- **Список чатов (5.1)** — относительное: `now`, `5 min`, `2 h`, `Yesterday`, `12 May`, `12 May 2025` (для прошлых лет).
- **Лента чата (5.2)** — время на каждом сообщении `HH:mm`; между днями — date-separator: `Today`, `Yesterday`, день недели (в пределах недели), иначе `12 May` / `12 May 2025`.

### Сетевые ошибки — копирайт

Канонический паттерн: `Could not <verb>. Check your connection and try again.` Слово `connection` (не `internet`). Исключение: на 5.1 допускается `Could not load chats. Pull to refresh.`

## Лимиты и валидация (сводка)

| Поле | Лимит | Валидация |
|---|---|---|
| Имя пользователя (label) | ≤ 32 символа | Уникальность **не проверяется и на своём сервере смысла не имеет** — человек один; вопрос переезжает к relay. Charset латиница + цифры + `-`, `_`, `.` — проверяется сразу при вводе |
| Имя чата | ≤ 64 символа | Уникальность **в пределах этого сервера**, проверка в реальном времени (локальная база + сервер, когда отвечает сразу; окончательно — при создании на сервере); charset не ограничен |
| Число чатов | без лимита | — |

## Вне scope этапа

Сознательно **не делаем** в этой итерации:

- голосовые и видеозвонки;
- эмодзи, реакции, стикеры как функцию;
- голосовые сообщения;
- истории;
- упоминания, тематические треды;
- отдельный экран профиля;
- модерирование, права, бан-листы, владельцы чатов, удаление чатов, любые пермишены;
- мультиаккаунт / несколько идентичностей на устройстве;
- delivered / read-квитанции (только локальный `sent`);
- per-chat настройки (mute / pin), follow-подписки;
- раздел Support;
- превью содержимого файлов, кроме картинок (миниатюра и показ на 5.3) и видео (проигрывание на 5.3 на iOS, Android и macOS);
- **общение с другими людьми и всё, что оно тянет за собой** — состав участников чата, вступление и выход, приглашения. Это работа relay-сервера, протокол которого не спроектирован. Единственный видимый след в продукте — **выключенная** кнопка `Invite a person` в 5.2 и 5.4. Подпись `Available in a future version` стоит только в 5.4, под кнопкой.

| `Use Tor` | Галочка на экране подключения 2.4 и переключатель в 7.10; по умолчанию выключена, хранится на устройстве; подпись `NOX uses Tor only when it can't reach your server directly.` |
| Адреса сервера | Одно поле «адрес сервера» (публичный адрес, иначе прямой из ссылки) и поле onion-адреса; правятся на 2.4 и в 7.10; значение, которое сообщает сервер, заменяет ручную правку того же поля |
| Экран подключения | 2.4 — после любой читаемой ссылки (вставка, скан, картинка), на всех платформах; ключ сервера не показывается |
| Раздел «Связь» | 7.10 — адреса (`Save`) и `Use Tor` (сразу); после применённой правки — подключение заново; новый onion-адрес вписывается без повторного спаривания |
| Состояние связи | В углу экрана, только отклонения: бейдж `Tor`, `Connecting…`; связи нет — баннер с причиной или `No connection` (решение владельца 2026-10-03, причины — 2026-10-08) |
| Причины неудачи | Шесть причин, у каждой свой текст: на плашках 5.1, 5.2, 5.4, в 7.10 и на 2.4; неверный onion-адрес — у поля |
| «Другой сервер» | Только когда чужой ключ предъявлен за onion-адресом — `This onion address belongs to a different server.`; чужой ключ на прямом адресе — «не дома» |
| Приглашение устройства | Ссылка `nox://pair/…` версии 3 несёт публичный и onion-адрес, если они заданы на сервере; карточка говорит `This link works only on your home network.`, только когда в ссылке нет ни того, ни другого |
| Ссылка с машины сервера | Служебная страница (сразу, пока устройств нет; иначе по `Add a device`) или `noxd link`; 10 минут; живая всегда одна; спаривает без подтверждения — заводит человека или присоединяет к нему (фаза 046) |
| Подтверждение нового устройства | Приглашение спаривает только после `Allow` на выдавшем устройстве — диалог 8.2 поверх любого экрана, обе ширины; новое устройство ждёт на 2.4 с `Cancel`; `Deny` — `Your other device declined this request.`; без ответа — как истёкшая ссылка (фаза 046) |
