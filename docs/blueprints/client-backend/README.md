## 2. Раскладка

Консенсус жанра (main в корне + `internal/`) поверх официального гайда `go.dev/doc/modules/layout`; `pkg/` не существует — golang-standards/project-layout дезавуирован лично Russ Cox (issue #117).

```
client_backend/
  main.go              # ~3 строки: flags → internal/server.Run
  go.mod               # go 1.27; tool-директивы вместо tools.go (Go 1.24+)
  migrations/          # append-only нумерованные .sql, embed.FS
  internal/
    config/            # флаги + NOX_*-env; валидация при старте
    db/                # открытие пулов, прагмы, миграции user_version
    store/             # типы + ВСЕ чтения/записи; единственный писательский код
    hub/               # горутина-владелец множества подписчиков
    server/            # wiring: обёртка слушателя (TLS 1.3 + Eidolon), ServeMux, WS-endpoint, REST, graceful shutdown
    eidolon/           # проверка Eidolon: сообщение 160 байт, подписи над экспортёром TLS 1.3, векторы
    protocol/          # конверт v0: типы кадров, коды ошибок, (un)marshal
```

Один уровень вложенности под `internal/`, однословные имена пакетов, никаких `util`/`common`/`helpers` (запрещены Google style guide). Тесты — colocated `_test.go` в том же пакете.

## 3. Рецепт SQLite (выжимка из PocketBase + официальные оговорки)

**Два пула на одну базу:**

```go
// DSN: busy_timeout первым (порядок PocketBase), затем WAL и остальные.
dsn := "file:" + path + "?_pragma=busy_timeout(5000)" +
    "&_pragma=journal_mode(WAL)" +
    "&_pragma=synchronous(NORMAL)" +
    "&_pragma=foreign_keys(1)"

read, _  := sql.Open("sqlite", dsn)              // читающий пул
write, _ := sql.Open("sqlite", dsn+"&_txlock=immediate")
write.SetMaxOpenConns(1)                          // ЕДИНСТВЕННЫЙ писатель
```

- `_txlock=immediate` на writer снимает класс ошибок `SQLITE_BUSY_SNAPSHOT`.
- **Никогда `:memory:` с `database/sql`** — каждое соединение пула получает свою приватную базу (официальная ловушка). В тестах — файл в `t.TempDir()`.
- Миграции: `PRAGMA user_version` + `embed.FS` с `*.sql`, применяются при старте до открытия endpoint'ов. Файлы append-only.
- Бэкап: `VACUUM INTO` во временный файл + rename. Живой файл БД не копировать. WAL ломается на сетевых ФС — только локальный диск.
- Транзакция записи и её `events`-строка — **атомарно**; broadcast — только после commit (транзакционный outbox; сериализацию даёт `MaxOpenConns(1)`).
- Три исключения из этого правила осознанны и бессобытийны: жизненный цикл файловой метаданности, **разрешение личности** (`internal/store/identity.go`) и **спаривание** — токены, запросы на спаривание и строки устройств (`internal/store/{pairing,requests,devices}.go`): кто может войти на машину — не общий мир, который ведёт журнал. Об исходах спаривания устройствам говорят события вне журнала (`seq: 0`); у каждого, чья потеря что-то ломает, есть надёжная половина — повтор `pair` отвечает записанным исходом, а приветствие выдавшего приглашение устройства заново присылает ждущие его запросы (инвариант 3 в `client_backend/CLAUDE.md`).

## 4. Рецепт WebSocket (coder/websocket + hub gotify-стиля)

- **Один читающий goroutine на соединение** — жёсткий инвариант библиотеки; конкурентные записи coder сериализует сам.
- **Hub** — горутина, владеющая множеством подписчиков; взаимодействие только через каналы register/unregister/broadcast. Мьютексов в проекте нет: если правка «требует» мьютекс — перестроить на владение одной горутиной.
- **Медленный клиент:** буферизованный канал ~16 кадров на подписчика; переполнился → `Close(StatusPolicyViolation)`. Это безопасно по построению: клиент переподключится с `since` и догонится по seq-логу — replay и есть наша защита от потери.
- **Keepalive не автоматический:** свой ticker с `Ping(ctx)` (~25 с) при работающем читателе.
- **`SetReadLimit`** = `max_frame_bytes` из контракта (131072; дефолт библиотеки 32 КиБ — мал).
- **`http.Server.Shutdown` документированно НЕ ждёт hijacked-соединений.** Обязательно: `RegisterOnShutdown` + собственный реестр соединений + `Close(StatusGoingAway)` каждому. Порядок остановки: HTTP-drain → закрыть WS и дождаться обработчиков → остановить наблюдатель адресов, сборщик просроченных запросов спаривания и hub → закрыть БД.
- Кадры JSON: `encoding/json` v1-API (в 1.27 уже работает поверх v2); двухфазный разбор через `json.RawMessage` для поля `data`. Неизвестные поля **игнорировать** (эволюция v0); `DisallowUnknownFields` — только в контрактных тестах.

## 5. Каркас процесса

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
g, ctx := errgroup.WithContext(ctx)
// g.Go: net.Listen → channel listener (TLS 1.3 + Eidolon) → srv.Serve; g.Go: hub.Run(ctx);
// on ctx.Done() → srv.Shutdown(timeout)
```

- **Вход — обёртка слушателя** (`internal/server/channel.go`, контракт §1). Сервер сам принимает TCP и отдаёт `http.Server` только соединения, прошедшие оба слоя: каждое в своей горутине проходит рукопожатие TLS 1.3 и проверку Eidolon под **одним** сроком от момента приёма — 30 с для любого соединения. Вход один: служба tor на машине сервера ведёт onion-сервис на тот же основной порт, соединение от неё приходит как любое другое, и пришло ли оно через Tor, сервер не знает, поэтому все сроки, которые растягивает путь через Tor, — медленного пути для всех (проверка канала, `ReadHeaderTimeout`, запись кадра и ожидание pong — по 30 с). Не прошедшее закрывается без ответа: соединение, которое не доказало ключ, не получает ничего, даже 404. Цикл приёма никогда не ждёт и нового соединения не отвергает: от одного источника (адрес IPv4 или сеть IPv6 /64) одновременно проверяются не больше 8 соединений, и следующее от него вытесняет самое старое из них — устройство проходит проверку за доли секунды, поэтому вытесняется почти всегда молчащее соединение, а поток соединений с одного источника соперничает только сам с собой; эта машина — один источник со своей долей в 64 соединения; соединение не с этой машины, не приславшее ни байта за 5 с, обрывается; всего на вход проверяются не больше 256 соединений, и новое вытесняет то, что ждёт дольше всех. Источник — часто целый дом: устройства за одним роутером или в одной сети /64, — и отказ новичку отдал бы источник тому, кто молча держит его места. Эта машина — loopback или тот самый адрес, на который пришло соединение: так подключается служба tor, куда бы ни вёл её `HiddenServicePort`, а извне такой источник не подделать — ответ на TCP-рукопожатие с адресом сервера в поле источника уходит самому серверу. Её доля больше обычной, потому что проверка через цепочку Tor идёт секунды, и ограничена, потому что onion-адрес открыт любому, кто его знает: поток через onion вытесняет только свои же соединения. Предела первого байта у неё нет. Вытеснения попадают в лог предупреждением не чаще раза в минуту — одни счётчики (`evicted_local` — доля этой машины), без адресов. Доказанный ключ устройства несёт обёртка соединения, `ConnContext` кладёт её в контекст запроса — ключ читают и `/ws`, и `/files`. Сам `http.Server` TLS не делает и HTTP/2 не видит: единственный TLS здесь предлагает ALPN `http/1.1`. Его сроки — `ReadHeaderTimeout` 30 с, 30 с на тело, которое не читает ни один обработчик (хук `ConnState`: `net/http` сам отвечает на неподдерживаемый `Expect` и дочитывает объявленное тело, прежде чем отпустить соединение), и `IdleTimeout` 2 минуты между запросами — ставит одно место, `configureMain`, общее для `Run` и тестового стенда; там же `OPTIONS *` отдаётся обработчику, а не отвечается самим `net/http` мимо двери.
- **TLS** (`internal/server/tls.go`) — только сессия и отпечаток для проверки: технический самоподписанный сертификат на одноразовом ключе ECDSA P-256, новом при каждом старте и только в памяти; `MinVersion` — TLS 1.3, ALPN `http/1.1`, `SessionTicketsDisabled` — каждое соединение проходит полное рукопожатие с подписью сервера. Кто на другом конце, решает не сертификат, а проверка.
- **Eidolon** (`internal/eidolon`): сообщение 160 байт — ключ Ed25519 ‖ подпись над ключом ‖ подпись над экспортёром TLS 1.3 (RFC 9266: метка `EXPORTER-Channel-Binding`, пустой контекст, 32 байта). Клиент пишет первым; сервер читает ровно 160 байт, проверяет обе подписи и только потом отвечает своим сообщением. Сервер принимает любой ключ с верными подписями, а права даёт по нему: ключ спаренного устройства — всё, незнакомый — только `pair` и `pair.cancel` (`session.hello` → `unauthenticated`), `/files` с незнакомым ключом — `401`. Перед обработчиками стоит дверь (`limitStrangers`, `internal/server/unpaired.go`): ключ ищется на каждом запросе, и незнакомому ключу соединение служит один запрос — любой ответ, кроме перехода на WebSocket, идёт с `Connection: close`, а объявленное тело запроса, на который ответил обработчик, сервер не ждёт вовсе. Соединение `/ws` с незнакомым ключом держится не дольше 2 минут без спаривания, и таких одновременно не больше 32 — для нового закрывается самое старое, а не новичок; спаривание на соединении (`pair` с ответом `identity`) или прошедший `session.hello` снимают с него оба предела, соединение спаренного устройства под них не попадает. `pair` с ответом `pending` (приглашение, 046) переводит соединение из мест в **ожидание** запроса (`Server.waits`): пока запрос ждёт `Allow`, срок и предел к нему не применяются, а держит запрос одно соединение — предъявившее его последним. Закрывший запрос — ответ, отмена, сборщик, отзыв — заканчивает и ожидание: `allowed` отпускает соединение, иной исход возвращает его в места со свежими 2 минутами; закрытие, успевшее между ответом хранилища и ожиданием, ловит повторное чтение запроса. Отказ проверки (длина, подпись над ключом, подпись над экспортёром) — строка в логе без ключа и адреса; не завершённый TLS — только в отладочном. Общие векторы с модулем приложения — `specs/044-secure-channel/contracts/eidolon-vectors.json` (копия — `internal/eidolon/testdata/vectors.json`).
- **Ключ сервера** — семя Ed25519 в `server_identity.private_key` (base64), открытый ключ — в `public_key`, в той же базе. Читается один раз при старте (`store.ServerKey`, который сверяет семя с открытым ключом и не запускает сервер при расхождении) и уходит только в обёртку слушателя; с TLS он не встречается.
- **Tor — отдельная служба ОС, не часть сервера.** Сервер tor не запускает, не настраивает и ключей Tor не хранит; onion-сервис публикует служба, которую ставят вручную или скриптом установки, и ведёт его виртуальный порт 443 на основной порт сервера на loopback (`HiddenServicePort 443 127.0.0.1:<порт>`; сервер слушает все адреса или loopback). В настройках tor — защита PoW и предел потоков на цепочку (`HiddenServiceMaxStreams 16`, `HiddenServiceMaxStreamsCloseCircuit 1`): PoW удорожает только новые цепочки, и без предела одна построенная цепочка открывала бы сколько угодно соединений с сервером. Из всего Tor серверу нужен только onion-адрес — строка в базе.
- **Адреса в базе** (`internal/store/addresses.go`): публичный адрес (`host:port`) и onion-адрес (`<56>.onion`) — колонки `public_address` и `onion_address` строки `server_identity`; рядом — `public_address_param` и `onion_address_param`, последнее применённое значение каждого параметра запуска. Адреса в локальных сетях сервер не хранит, а находит сам. Проверка и запись — `internal/server/address_settings.go`: onion — версия 3, 56 знаков base32, контрольная сумма (`crypto/sha3`) и байт версии; публичный — IP-литерал или DNS-имя и порт 1–65535, не onion-имя. Две дороги в базу, обе через одну проверку: параметры запуска `-public-addr` / `-onion-addr` (и `NOX_PUBLIC_ADDR` / `NOX_ONION_ADDR`) применяются при старте до открытия слушателей, только если параметр появился или изменился с последнего применённого (значение и параметр — одной записью), а испорченный параметр не применяется и старт не останавливает — сервер работает с прежним адресом, пишет ошибку в лог и показывает предупреждение на служебной странице; и кнопка `Set` на служебной странице — `POST /addresses` (`kind`, `value`, `token`), который принимается, только если `Host` локальный, `Origin` равен `http://<Host>` и токен формы (32 случайных байта на процесс) совпал при сравнении за постоянное время, а CSP страницы несёт `form-action 'self'`; пустое значение удаляет адрес, ответ — `303` на `/?saved=` или `/?invalid=`, значение в адрес не попадает. Записанный адрес действует сразу: снимок адресов (`internal/server/addresses.go`) читает его из базы, новая версия снимка уходит в `server.addresses` (единственный отправитель — наблюдатель адресов, `Set` его будит) и в ответ на приветствие (`addresses.public`, `addresses.onion`), ссылки спаривания несут адреса в порядке публичный → прямой → onion, ответ `device.invite` — флаги `onion` и `public`. Onion-адрес в лог не попадает.
- REST: `PUT /files/{token}` и `GET /files/{token}` за той же обёрткой, что `/ws`; `GET /health`, формы служебной страницы и `POST /control/link` — на служебном loopback-слушателе, основной порт до проверки не отвечает ничем; middleware — `func(http.Handler) http.Handler`.
- **Служебная страница** — свой loopback-слушатель с открытым HTTP: сама страница (состояние машины, ссылка с машины, адреса), формы `POST /link` (`Add a device`, `New link`) и `POST /addresses` — с проверкой `Host`, `Origin` и токена формы, — и `POST /control/link` для подкоманды `noxd link`: локальный `Host`, заголовок `X-Nox-Control: 1` и **без** `Origin`, иначе `403`. Подкоманда базу не открывает — ссылку выпускает работающий сервер.
- **Фоновые горутины** со своими контекстами — наблюдатель адресов и сборщик просроченных запросов спаривания (раз в 2 с): обе пишут соединениям и ходят в базу, поэтому останавливаются после прощания соединений и до закрытия базы.
- Загрузка: `http.MaxBytesReader` лимитом — остатком файла от смещения, под которое выдан токен. Пришедшее дописывается в `<id>.part` и сохраняется при любом обрыве; надёжную длину части пакет `blob` пишет в `<id>.synced` — после `fsync` и каждые 4 MiB. Продолжение — `file.uploadBegin` с `file_id`, ответ несёт `received`. Скачивание: `http.ServeContent` — `Range`, `If-Range` и условные заголовки обрабатывает сам.
- Предела времени на передачу нет: срок чтения (`PUT`) и записи (`GET`) продлевается перед каждым чтением и записью, и передачу обрывает только застой — 60 с без байта — или отзыв устройства (следующий пункт). Через Tor 100 MiB идут десятки минут, и предел на всю передачу обрывал бы именно путь вне дома. Пишет в часть один запрос: новый прерывает прежний (`internal/server/writers.go`).
- Идущая передача записана под ключом своего соединения (`Server.transfers`) — запись делается до проверки ключа по хранилищу, — и отзыв устройства обрывает её соединение сразу, вместе с сокетом. Передачу без предела времени иначе не остановило бы ничто, кроме застоя: потерянный телефон качал бы файлы, пока читает.
- Логи: `slog` + `JSONHandler`, request-middleware с методом/путём/статусом/длительностью. Каждую строку процесса пропускает один обработчик `ScrubLogs` (`internal/server/logscrub.go`): onion-адреса заменяются на `[onion]`, ссылки спаривания — на `[link]`, откуда бы текст ни пришёл — из кода сервера, из ошибки библиотеки или из пути чужого запроса. Ни ссылку, ни токен сервер в лог не пишет вовсе: ссылку с машины выдают служебная страница и `noxd link`, приглашение — устройство, которое его попросило, а строка запуска, пока ни одного устройства нет, говорит, где взять ссылку, но не саму ссылку.
- Сборка: `CGO_ENABLED=0 go build -trimpath -ldflags="-s -X main.version=$(git describe)"` (`-s` теперь подразумевает `-w`).

## 6. Тестирование

- Табличные тесты + `t.Run`; БД — файл в `t.TempDir()`, миграции с нуля в каждом тесте.
- HTTP и WS — за той же обёрткой канала, что в `Run`: `httptest.NewUnstartedServer(srv.Handler())`, у которого `Listener` — `newChannelListener(...)`. Клиент теста открывает канал, как приложение, — TLS 1.3, затем `eidolon.Initiate` от имени тестового устройства — и только потом говорит HTTP (`websocket.Dial` с `DialOptions.HTTPClient`, который так набирает). Не `httptest.NewTLSServer`: его стандартный TLS поставил бы обработчик за слой, которого продукт не использует, и оставил бы непроверенным главный вопрос — кто какой ключ доказал.
- **`go test -race ./...` — всегда**, не опционально (race detector требует CGo только в тестовом контуре — на маке это штатно).
- Конкурентность и replay — `testing/synctest` (GA с 1.25; в 1.27 добавлен `httptest.NewTestServer` с in-memory сетью специально под него).
- Идеи из жанра: leaktest на WS-хендлерах (gotify), сценарные хелперы на группу endpoint'ов (PocketBase `ApiScenario`).

## 7. Линт и проверки

`gofmt` (диф пустой) → `go vet ./...` → `staticcheck` (или `golangci-lint` **v2** — конфиг `version: "2"`, примеры v1 из старых статей не годятся) → `govulncheck` → `go test -race`. Не отключать `errcheck` (антипример miniflux/gotify — осознанно отвергнут).

## 8. Что отвергнуто сознательно

| Практика | Откуда | Почему нет |
|---|---|---|
| Роутер-фреймворк (chi, gin, echo) | привычка | `ServeMux` 1.22+ покрывает всё; «advanced routing needs» у нас нет |
| `pkg/`-каталог, golang-standards/project-layout | карго-культ | Дезавуирован Go-командой |
| `util`/`common`-пакеты | ntfy/gotify | Запрещены Google style guide — имя пакета должно описывать содержимое |
| Мьютексы в бизнес-коде | привычка | Владение состоянием — одна горутина + каналы (hub) или один writer-пул (БД) |
| ORM / query builder | привычка | Сырой параметризованный SQL — аудируемый артефакт |
| `viper`, `testify`-везде | привычка | Ни один из четырёх эталонов жанра не использует viper; miniflux живёт на голом `testing` |
