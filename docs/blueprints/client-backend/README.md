## 2. Раскладка

Консенсус жанра (main в корне + `internal/`) поверх официального гайда `go.dev/doc/modules/layout`; `pkg/` не существует — golang-standards/project-layout дезавуирован лично Russ Cox (issue #117).

```
client_backend/
  main.go              # флаги → internal/server.Run (под диспетчером служб Windows — runService); подкоманда noxd link
  commands.go          # таблица подкоманд noxd по имени: link, unlock, password, backup, restore
  service_windows.go   # noxd службой Windows (049): x/sys/windows/svc, Stop и Shutdown диспетчера
  service_other.go     # вне Windows службы нет: launchd и systemd запускают обычную программу
  servicelog.go        # лог службы Windows — noxd.log рядом с базой, при 16 МиБ откладывается в noxd.log.1
  go.mod               # go 1.27.0; восемь прямых зависимостей, tool-директив нет (wasm2go — через go run)
  migrations/          # нумерованные .sql, embed.FS; до первого релиза — одна 001_init.sql
  internal/
    config/            # флаги + NOX_*-env; валидация при старте
    db/                # открытие пулов, ключ данных и VFS adiantum, прагмы, миграции user_version, снимок
    vault/             # ключ данных: <db>.key, Argon2id, смена пароля
    blob/              # байты вложений: куски по 64 КиБ, AEAD, докачка, чтение диапазонов
    backup/            # бэкап одним tar-файлом и восстановление
    prompt/            # пароль: терминал без эха или строки stdin
    store/             # типы + ВСЕ чтения/записи; единственный писательский код
    hub/               # горутина-владелец множества подписчиков
    server/            # wiring: запертый старт, обёртка слушателя (TLS 1.3 + /auth и /auth2), ServeMux, WS-endpoint, REST, graceful shutdown
    connauth/          # проверка POST /auth → POST /auth2: сторона сервера (Respond) и сторона устройства для тестов (Initiate)
    securebox/         # RustSecureBox: пул экземпляров WebAssembly, случайные байты из crypto/rand, векторы; boxwasm/ — сгенерированный код
    protocol/          # конверт v0: типы кадров, коды ошибок, (un)marshal
```

Один уровень вложенности под `internal/` (кроме сгенерированного `securebox/boxwasm`), однословные имена пакетов, никаких `util`/`common`/`helpers` (запрещены Google style guide). Тесты — colocated `_test.go` в том же пакете.

## 3. Рецепт SQLite (выжимка из PocketBase + официальные оговорки)

**Два пула на одну базу, оба — через шифрующую VFS:**

```go
// URI: абсолютный путь, экранированный, без authority (на Windows — file:C:/…);
// ключа в нём НЕТ.
uri := "file:/abs/nox.db?vfs=adiantum"
connect := func(c *sqlite3.Conn) error {
    // Ключ первым: до него файл читается как пустой.
    c.Exec("PRAGMA hexkey='…'")
    // Затем busy_timeout (порядок PocketBase), WAL и остальные.
    for _, p := range []string{"busy_timeout=5000", "journal_mode=WAL",
        "synchronous=NORMAL", "foreign_keys=1", "temp_store=memory"} {
        c.Exec("PRAGMA " + p)
    }
    return nil
}
read, _  := driver.Open(uri, connect)                        // читающий пул
write, _ := driver.Open(uri+"&_txlock=immediate", connect)   // писатель
write.SetMaxOpenConns(1)                                       // ЕДИНСТВЕННЫЙ писатель
```

- Ключ — прагмой в хуке соединения, а не в URI: URI расходится по сообщениям об ошибках и по видимому VFS имени файла. `temp_store=memory` — временных файлов на диске нет вовсе.
- Чужой ключ (`db.ErrWrongKey`) распознаётся **до SQLite**: `db.Open` расшифровывает первый блок базы, её WAL и журнала отката так, как их пишет VFS, и отказывает ключу, под которым ни один не показывает свой заголовок. SQLite сам узнаёт чужой ключ лишь на первой странице — уже после восстановления WAL этим ключом, — и, закрываясь, удаляет WAL, который не смог прочитать, вместе с неперенесёнными в базу транзакциями. Любого из трёх файлов достаточно: сбой посреди checkpoint может порвать первый блок базы, пока страница ещё в WAL. Пустую базу проверка не спрашивает, как и SQLite, который удаляет WAL и журнал рядом с базой без страниц, не читая их: так выглядит новая база, оборванная в первой транзакции, — журнал рядом с ней ещё без магического числа.

- `_txlock=immediate` на writer снимает класс ошибок `SQLITE_BUSY_SNAPSHOT`.
- **Никогда `:memory:` с `database/sql`** — каждое соединение пула получает свою приватную базу (официальная ловушка). В тестах — файл в `t.TempDir()`.
- Миграции: `PRAGMA user_version` + `embed.FS` с `*.sql`, применяются при старте до открытия endpoint'ов. Файлы append-only — с первого релиза; до него вся схема живёт в одной `001_init.sql`, которая правится на месте: развёрнутых баз ещё нет. Отпечаток схемы (хеш текста миграций в `PRAGMA application_id`) сервер сверяет при старте и базу другой схемы не открывает, а говорит, что делать.
- Бэкап: `VACUUM INTO` снимка рядом с базой тем же ключом — URI с ключом уходит параметром запроса, а ключ вырезается из текста ошибки, — затем один tar-файл (см. ниже). Живой файл БД не копировать. WAL ломается на сетевых ФС — только локальный диск.
- Транзакция записи и её `events`-строка — **атомарно**; broadcast — только после commit (транзакционный outbox; сериализацию даёт `MaxOpenConns(1)`).
- Три исключения из этого правила осознанны и бессобытийны: жизненный цикл файловой метаданности, **разрешение личности** (`internal/store/identity.go`) и **спаривание** — токены, запросы на спаривание и строки устройств (`internal/store/{pairing,requests,devices}.go`): кто может войти на машину — не общий мир, который ведёт журнал. Об исходах спаривания устройствам говорят события вне журнала (`seq: 0`); у каждого, чья потеря что-то ломает, есть надёжная половина — повтор `pair` отвечает записанным исходом, а приветствие выдавшего приглашение устройства заново присылает ждущие его запросы (инвариант 3 в `client_backend/CLAUDE.md`).

**Данные на диске (фаза 047).** Модель угроз — кража диска или машины и утечка копий; всё, что делается с доступом к работающей машине, вне рамок.

- **Ключ данных** — 32 случайных байта; ими зашифрованы база и вложения. На диске он лежит только запертым: `<db>.key` (JSON: версия, `argon2id` с параметрами 64 МиБ / 3 прохода / 4 потока, соль 16 байт, nonce 24 байта, запечатанный ключ — XChaCha20-Poly1305 под ключом Argon2id от пароля, AAD `nox/datakey/v1`). Пароль нигде не хранится. Смена пароля — новая соль и nonce, файл рядом, `fsync`, переименование поверх, `fsync` каталога: после сбоя открывается прежний или новый пароль; база и файлы не трогаются.
- **Вложения** — заголовок 32 байта (`NOXF`, версия 1, размер куска), затем куски по 64 КиБ открытых байтов, каждый запечатан ChaCha20-Poly1305 ключом файла `HKDF-SHA256(ключ данных, "nox/file/v1|" + file_id)`; nonce — номер куска, AAD — номер и признак последнего. Кусок запечатывается, когда пришёл целиком, — до тех пор он в памяти запроса; поэтому часть `<id>.part` держит только целые куски, `.synced` считает их, а продолжение загрузки идёт с начала незаконченного куска. Чтение — `blob.Reader` (`io.ReadSeeker`) под `ServeContent`: диапазон открывает только свои куски.
- **Бэкап** (`noxd backup`) — работающий сервер пишет один tar: `nox.key`, `nox.db` (снимок), `files/<id>` (вложения, которые называет снимок, как есть, уже зашифрованные) и последним `manifest` — имена и размеры записей, `created_at` и `HMAC-SHA256` с ключом `HKDF(ключ данных, "nox/backup/v1")`. Файл появляется под своим именем только целым (`.partial` → `fsync` → переименование) и никогда не пишется поверх другого. MAC закрывает то, чего не даёт шифрование страниц: подмену бэкапа.
- **Восстановление** (`noxd restore <файл> -db <путь>`) — без сервера, на пустое место: пароль открывает `nox.key` бэкапа, MAC и `quick_check` проверяются до того, как что-то встаёт на место; затем новое `journal_id`, и на место — вложения, база, последним ключ. Ключ сервера тот же — устройства подключаются без спаривания и перечитывают переписку (контракт §3). Исключение — бэкап, ключ которого сделала другая реализация RustSecureBox: восстановление перевыпускает ключ, как сделал бы первый запуск (`store.ServerKey`), и все устройства спариваются заново ссылкой с машины, переписка остаётся; команда так и пишет. Иначе список устройств — тоже бэкапа: отозванное после бэкапа устройство снова принято, поэтому команда печатает момент бэкапа и устройства, которые примет сервер, — такое отзывают заново.

## 4. Рецепт WebSocket (coder/websocket + hub gotify-стиля)

- **Один читающий goroutine на соединение** — жёсткий инвариант библиотеки; конкурентные записи coder сериализует сам.
- **Hub** — горутина, владеющая множеством подписчиков; взаимодействие только через каналы register/unregister/broadcast. У hub мьютекса нет: если правка «требует» его там — перестроить на владение одной горутиной. Мьютексы инфраструктуры перечислены и обоснованы в инварианте 7 `client_backend/CLAUDE.md`: реестр соединений (`Server.mu`), хранилище токенов передачи, реестр писателей загрузок и реестр рукопожатий слушателя канала; мьютекс `stallReader` живёт в одном запросе `PUT`.
- **Медленный клиент:** буферизованный канал ~16 кадров на подписчика; переполнился → `Close(StatusPolicyViolation)`. Это безопасно по построению: клиент переподключится с `since` и догонится по seq-логу — replay и есть наша защита от потери.
- **Keepalive не автоматический:** свой ticker с `Ping(ctx)` (~25 с) при работающем читателе.
- **`SetReadLimit`** = `max_frame_bytes` из контракта (131072; дефолт библиотеки 32 КиБ — мал).
- **`http.Server.Shutdown` документированно НЕ ждёт hijacked-соединений.** Обязательно: `RegisterOnShutdown` + собственный реестр соединений + `Close(StatusGoingAway)` каждому. Порядок остановки: HTTP-drain (основной порт, затем служебная страница, которая сначала отменяет контексты своих запросов — бэкап на ходу останавливается раньше, чем закроется база) → закрыть WS и дождаться обработчиков → остановить хранитель ворот, наблюдатель адресов, сборщик просроченных запросов спаривания и hub → закрыть БД.
- Кадры JSON: `encoding/json` v1-API (в 1.27 уже работает поверх v2); двухфазный разбор через `json.RawMessage` для поля `data`. Неизвестные поля **игнорировать** (эволюция v0); `DisallowUnknownFields` — только в контрактных тестах.

## 5. Каркас процесса

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
// служебная страница (loopback) поднимается первой — в неё вводится пароль;
// ворота ждут пароль → ключ данных → db.Open, миграции, остальное
g, ctx := errgroup.WithContext(ctx)
// net.Listen основного порта — только теперь; g.Go: channel listener (TLS 1.3 + /auth, /auth2) → srv.Serve;
// g.Go: hub.Run(ctx); g.Go: хранитель ворот; on ctx.Done() → srv.Shutdown(timeout)
```

- **Запертый старт** (`internal/server/gate.go`, фаза 047). Состояние определяет диск: ни базы, ни `<db>.key` — сервер ждёт первый пароль (пароль и повтор, не короче 12 знаков); есть оба — заперт; одно без другого — старт отказывает и говорит, что делать. Пока пароль не введён, слушает только служебная страница — только с полем пароля, — а основной порт не занят вовсе: устройство видит то же, что при выключенном сервере. `/health` — `200 {"status":"locked"}`, после открытия — `{"status":"ok"}`. Пароль вводится на странице (формы с проверкой `Host`, `Origin` и токена формы) или командой `noxd unlock` через `/control/unlock` (локальный `Host`, `X-Nox-Control: 1`, без `Origin`); `noxd password` и `noxd backup` — так же. Неверный пароль ничего не меняет на диске. Всё, что касается файла ключа, по очереди обслуживает одна горутина: горутина `Run`, пока сервер заперт, потом хранитель. `-status-addr` не может быть пустым, и занятый порт страницы останавливает старт.
- **Вход — обёртка слушателя** (`internal/server/channel.go`, контракт §1). Сервер сам принимает TCP и отдаёт `http.Server` только соединения, прошедшие оба слоя: каждое в своей горутине проходит рукопожатие TLS 1.3 и проверку `POST /auth` → `POST /auth2` под **одним** сроком от момента приёма — 30 с для любого соединения. Вход один: служба tor на машине сервера ведёт onion-сервис на тот же основной порт, соединение от неё приходит как любое другое, и пришло ли оно через Tor, сервер не знает, поэтому все сроки, которые растягивает путь через Tor, — медленного пути для всех (проверка канала, `ReadHeaderTimeout`, запись кадра и ожидание pong — по 30 с). Не прошедшее получает только отказ проверки (`400`, `401` или `405` с `Connection: close`) или, если вышел срок, — ничего, и закрывается: ни один обработчик `http.Server`, даже 404, не отвечает соединению, которое не доказало ключ. Цикл приёма никогда не ждёт и нового соединения не отвергает: от одного источника (адрес IPv4 или сеть IPv6 /64) одновременно проверяются не больше 8 соединений, и следующее от него вытесняет самое старое из них — устройство проходит проверку за доли секунды, поэтому вытесняется почти всегда молчащее соединение, а поток соединений с одного источника соперничает только сам с собой; эта машина — один источник со своей долей в 64 соединения; соединение не с этой машины, не приславшее ни байта за 5 с, обрывается; всего на вход проверяются не больше 256 соединений, и новое вытесняет то, что ждёт дольше всех. Источник — часто целый дом: устройства за одним роутером или в одной сети /64, — и отказ новичку отдал бы источник тому, кто молча держит его места. Эта машина — loopback или тот самый адрес, на который пришло соединение: так подключается служба tor, куда бы ни вёл её `HiddenServicePort`, а извне такой источник не подделать — ответ на TCP-рукопожатие с адресом сервера в поле источника уходит самому серверу. Её доля больше обычной, потому что проверка через цепочку Tor идёт секунды, и ограничена, потому что onion-адрес открыт любому, кто его знает: поток через onion вытесняет только свои же соединения. Предела первого байта у неё нет. Вытеснения попадают в лог предупреждением не чаще раза в минуту — одни счётчики (`evicted_local` — доля этой машины), без адресов. Доказанный ключ устройства несёт обёртка соединения, `ConnContext` кладёт её в контекст запроса — ключ читают и `/ws`, и `/files`. Сам `http.Server` TLS не делает и HTTP/2 не видит: единственный TLS здесь предлагает ALPN `http/1.1`. Его сроки — `ReadHeaderTimeout` 30 с, 30 с на тело, которое не читает ни один обработчик (хук `ConnState`: `net/http` сам отвечает на неподдерживаемый `Expect` и дочитывает объявленное тело, прежде чем отпустить соединение), и `IdleTimeout` 2 минуты между запросами — ставит одно место, `configureMain`, общее для `Run` и тестового стенда; там же `OPTIONS *` отдаётся обработчику, а не отвечается самим `net/http` мимо двери.
- **TLS** (`internal/server/tls.go`) — только шифрование соединения: технический самоподписанный сертификат на одноразовом ключе ECDSA P-256, новом при каждом старте и только в памяти; `MinVersion` — TLS 1.3, ALPN `http/1.1`, `SessionTicketsDisabled` — каждое соединение проходит полное рукопожатие с подписью сервера. Кто на другом конце, решает не сертификат, а проверка.
- **Проверка** (`internal/connauth`, контракт §1) — два первых запроса HTTP/1.1 соединения, которые читает сам слушатель (`http.ReadRequest`, весь этап — не больше 16 КиБ), а не `http.Server`. `POST /auth {pk, challenge}`: сервер получает у RustSecureBox свой челлендж и свой ключ, подписывает челлендж устройства и отвечает `200 {pk, challenge, signature}`; свой челлендж и ключ устройства он держит при соединении до `/auth2` и нигде не записывает. `POST /auth2 {signature}`: подпись ключом устройства над челленджем сервера сошлась — `200`, и соединение уходит в `http.Server` вместе с доказанным ключом; не сошлась — `401`. Отказы — `405` (метод не `POST`), `401` (любой другой путь до проверки, неверная подпись), `400` (ступень не по порядку, тело не разбирается или не той длины) — без тела, с `Connection: close`, и разрыв; ошибка RustSecureBox и вышедший срок — разрыв без ответа. Отпечатка соединения в проверке нет: по допущению схемы соединение TLS считается неперехватываемым. Сервер принимает любой ключ с верной подписью, а права даёт по нему: ключ спаренного устройства — всё, незнакомый — только `pair` и `pair.cancel` (`session.hello` → `unauthenticated`), `/files` с незнакомым ключом — `401`. Перед обработчиками стоит дверь (`limitStrangers`, `internal/server/unpaired.go`): ключ ищется на каждом запросе, и незнакомому ключу соединение служит один запрос — любой ответ, кроме перехода на WebSocket, идёт с `Connection: close`, а объявленное тело запроса, на который ответил обработчик, сервер не ждёт вовсе. Соединение `/ws` с незнакомым ключом держится не дольше 2 минут без спаривания, и таких одновременно не больше 32 — для нового закрывается самое старое, а не новичок; спаривание на соединении (`pair` с ответом `identity`) или прошедший `session.hello` снимают с него оба предела, соединение спаренного устройства под них не попадает. `pair` с ответом `pending` (приглашение, 046) переводит соединение из мест в **ожидание** запроса (`Server.waits`): пока запрос ждёт `Allow`, срок и предел к нему не применяются, а держит запрос одно соединение — предъявившее его последним; прежнее сервер закрывает (1013), а не возвращает в места: новейшим там оно встало бы позади пришедших после него, и повторы `pair` переставляли бы места без новых соединений. Закрывший запрос — ответ, отмена, сборщик, отзыв — заканчивает и ожидание: `allowed` отпускает соединение, иной исход возвращает его в места со свежими 2 минутами; закрытие, успевшее между ответом хранилища и ожиданием, ловит повторное чтение запроса. Отказ проверки — строка в логе с видом отказа, без ключа, челленджа, подписи и адреса; ошибка RustSecureBox — предупреждение; не завершённый TLS — только в отладочном.
- **RustSecureBox** (`internal/securebox`) — та же библиотека на Rust, что в модуле приложения (`packages/rust_secure_box`), здесь — её WebAssembly, переведённая в Go (`boxwasm`, сгенерированный код: `make box-wasm` пересобирает, `make box-verify` сверяет с крейтом, руками не правится). Четыре функции без состояния: `generate_keys`, `get_challenge`, `sign_challenge`, `check_signature`. Импорт у модуля ровно один — случайные байты, их даёт `crypto/rand`. Экземпляр однопоточен, поэтому `Box` держит пул: каждый вызов берёт свой экземпляр, ловушка WebAssembly становится ошибкой RustSecureBox, а экземпляр выбрасывается. Сейчас внутри заглушка: `Box.IsStub()` узнаёт её по ответу на пробный ключ, и пока она работает, сервер при каждом старте пишет предупреждение в лог, а служебная страница открытого сервера показывает строку `RustSecureBox is a stub: devices are not really verified.`. Общие векторы с модулем приложения — `specs/050-rust-secure-box/contracts/rsb-vectors.json` (копия — `internal/securebox/testdata/rsb-vectors.json`).
- **Ключ сервера** — закрытый ключ RustSecureBox (32 байта) в `server_identity.private_key` (base64), открытый — в `public_key`, в той же базе; пару создаёт `generate_keys` при первом запуске. Читается один раз при старте и уходит только в обёртку слушателя; с TLS он не встречается. `store.ServerKey` сверяет хранимый открытый ключ с тем, что RustSecureBox даёт для хранимого закрытого: не совпал — ключ сделан другой реализацией, и сервер одной транзакцией переписывает открытый ключ при том же закрытом и удаляет все записи устройств, ссылки, приглашения и запросы спаривания. Люди, чаты, сообщения, файлы и журнал событий остаются, в лог — предупреждение, что все устройства спариваются заново, а служебная страница сразу показывает ссылку с машины.
- **Tor — отдельная служба ОС, не часть сервера.** Сервер tor не запускает, не настраивает и ключей Tor не хранит; onion-сервис публикует служба, которую ставят вручную или скриптом установки, и ведёт его виртуальный порт 443 на основной порт сервера на loopback (`HiddenServicePort 443 127.0.0.1:<порт>`; сервер слушает все адреса или loopback). В настройках tor — защита PoW и предел потоков на цепочку (`HiddenServiceMaxStreams 16`, `HiddenServiceMaxStreamsCloseCircuit 1`): PoW удорожает только новые цепочки, и без предела одна построенная цепочка открывала бы сколько угодно соединений с сервером. Из всего Tor серверу нужен только onion-адрес — строка в базе.
- **Адреса в базе** (`internal/store/addresses.go`): публичный адрес (`host:port`) и onion-адрес (`<56>.onion`) — колонки `public_address` и `onion_address` строки `server_identity`; рядом — `public_address_param` и `onion_address_param`, последнее применённое значение каждого параметра запуска. Адреса в локальных сетях сервер не хранит, а находит сам. Проверка и запись — `internal/server/address_settings.go`: onion — версия 3, 56 знаков base32, контрольная сумма (`crypto/sha3`) и байт версии; публичный — IP-литерал или DNS-имя и порт 1–65535, не onion-имя. Две дороги в базу, обе через одну проверку: параметры запуска `-public-addr` / `-onion-addr` (и `NOX_PUBLIC_ADDR` / `NOX_ONION_ADDR`) применяются при старте до открытия слушателей, только если параметр появился или изменился с последнего применённого (значение и параметр — одной записью), а испорченный параметр не применяется и старт не останавливает — сервер работает с прежним адресом, пишет ошибку в лог и показывает предупреждение на служебной странице; и кнопка `Set` на служебной странице — `POST /addresses` (`kind`, `value`, `token`), который принимается, только если `Host` локальный, `Origin` равен `http://<Host>` и токен формы (32 случайных байта на процесс) совпал при сравнении за постоянное время, а CSP страницы несёт `form-action 'self'`; пустое значение удаляет адрес, ответ — `303` на `/?saved=` или `/?invalid=`, значение в адрес не попадает. Записанный адрес действует сразу: снимок адресов (`internal/server/addresses.go`) читает его из базы, новая версия снимка уходит в `server.addresses` (единственный отправитель — наблюдатель адресов, `Set` его будит) и в ответ на приветствие (`addresses.public`, `addresses.onion`), ссылки спаривания несут адреса в порядке публичный → прямой → onion, ответ `device.invite` — флаги `onion` и `public`. Onion-адрес в лог не попадает.
- REST: `PUT /files/{token}` и `GET /files/{token}` за той же обёрткой, что `/ws`; `GET /health`, формы служебной страницы, `POST /control/link` и `/control/state|unlock|password|backup` (047) — на служебном loopback-слушателе, основной порт до проверки не обслуживает ничего (любой запрос, кроме `/auth` и `/auth2`, — `401`), а пока сервер заперт, не занят вовсе; middleware — `func(http.Handler) http.Handler`.
- **Служебная страница** — свой loopback-слушатель с открытым HTTP, поднятый раньше всего остального (047): пока сервер заперт, страница показывает только поле пароля — ни ссылки, ни адресов, ни цифр, — а `POST /link`, `POST /addresses` и `POST /control/link` отвечают `409`; у открытого сервера — сама страница (состояние машины, ссылка с машины, адреса, смена пароля), формы `POST /link` (`Add a device`, `New link`), `POST /addresses` и формы пароля `POST /password/{setup,unlock,change}` — с проверкой `Host`, `Origin` и токена формы, один токен на процесс от запертой страницы до открытой, — и `/control/*` для подкоманд `noxd link`, `noxd unlock`, `noxd password`, `noxd backup`: локальный `Host`, заголовок `X-Nox-Control: 1` и **без** `Origin`, иначе `403`. Подкоманды базу не открывают — ссылку, пароль и бэкап обслуживает работающий сервер.
- **Фоновые горутины** со своими контекстами — наблюдатель адресов, сборщик просроченных запросов спаривания (раз в 2 с) и хранитель ворот (047: смена пароля и бэкап, по одному запросу за раз): все три стартуют только после того, как пароль открыл данные, все ходят в базу, а первые два ещё и пишут соединениям, поэтому останавливаются после прощания соединений и до закрытия базы.
- Загрузка: `http.MaxBytesReader` лимитом — остатком файла от смещения, под которое выдан токен. Пришедшее запечатывается кусками по 64 КиБ и дописывается в `<id>.part`; запечатанное сохраняется при любом обрыве, а недописанный кусок уходит вместе с запросом. Надёжную длину части пакет `blob` пишет в `<id>.synced` — после `fsync` и каждые 4 MiB. Продолжение — `file.uploadBegin` с `file_id`, ответ несёт `received` — по границе кусков. Скачивание: `http.ServeContent` поверх расшифровывающего `blob.Reader` — `Range`, `If-Range` и условные заголовки обрабатывает сам.
- Предела времени на передачу нет: срок чтения (`PUT`) и записи (`GET`) продлевается перед каждым чтением и записью, и передачу обрывает только застой — 60 с без байта — или отзыв устройства (следующий пункт). Через Tor 100 MiB идут десятки минут, и предел на всю передачу обрывал бы именно путь вне дома. Пишет в часть один запрос: новый прерывает прежний (`internal/server/writers.go`).
- Идущая передача записана под ключом своего соединения (`Server.transfers`) — запись делается до проверки ключа по хранилищу, — и отзыв устройства обрывает её соединение сразу, вместе с сокетом. Передачу без предела времени иначе не остановило бы ничто, кроме застоя: потерянный телефон качал бы файлы, пока читает.
- Логи: `slog` + `JSONHandler`, request-middleware с методом/путём/статусом/длительностью. Каждую строку процесса пропускает один обработчик `ScrubLogs` (`internal/server/logscrub.go`): onion-адреса заменяются на `[onion]`, ссылки спаривания — на `[link]`, откуда бы текст ни пришёл — из кода сервера, из ошибки библиотеки или из пути чужого запроса. Ни ссылку, ни токен сервер в лог не пишет вовсе: ссылку с машины выдают служебная страница и `noxd link`, приглашение — устройство, которое его попросило, а строка запуска, пока ни одного устройства нет, говорит, где взять ссылку, но не саму ссылку. Обработчик ставится в `Run` до того, как сервер ждёт пароль, поэтому строки запертого старта проходят через него так же; журнал ошибок `net/http` обоих слушателей — тоже. Ни пароль, ни ключ данных, ни путь бэкапа в лог не попадают (047): строки ворот говорят, что пароль принят, отвергнут или сменён и что бэкап записан, — и только.
- Сборка: `CGO_ENABLED=0 go build -trimpath -ldflags=-s` (`-s` подразумевает `-w`). Версию для служебной страницы бинарник берёт из себя (`debug.ReadBuildInfo`: ревизия и время коммита), а не из `-ldflags`: так её не надо пробрасывать ни в одну сборку, и она не расходится с тем, что собрано.

## 6. Тестирование

- Табличные тесты + `t.Run`; БД — файл в `t.TempDir()`, миграции с нуля в каждом тесте; каждая тестовая база и каталог файлов зашифрованы постоянным тестовым ключом, ключ данных запирается дешёвыми параметрами Argon2id (`run(..., kdf)`), а производственные параметры и их время проверяет пакет `vault`.
- HTTP и WS — за той же обёрткой канала, что в `Run`: `httptest.NewUnstartedServer(srv.Handler())`, у которого `Listener` — `newChannelListener(...)`. Клиент теста открывает канал, как приложение, — TLS 1.3, затем `connauth.Initiate` от имени тестового устройства — и только потом говорит HTTP (`websocket.Dial` с `DialOptions.HTTPClient`, который так набирает). Не `httptest.NewTLSServer`: его стандартный TLS поставил бы обработчик за слой, которого продукт не использует, и оставил бы непроверенным главный вопрос — кто какой ключ доказал.
- **`go test -race ./...` — всегда**, не опционально (race detector требует CGo только в тестовом контуре — на маке это штатно).
- Конкурентность и replay — `testing/synctest` (GA с 1.25; в 1.27 добавлен `httptest.NewTestServer` с in-memory сетью специально под него).
- Идеи из жанра: leaktest на WS-хендлерах (gotify), сценарные хелперы на группу endpoint'ов (PocketBase `ApiScenario`).

## 7. Линт и проверки

`gofmt` (диф пустой) → `go vet ./...` → `staticcheck` (или `golangci-lint` **v2** — конфиг `version: "2"`, примеры v1 из старых статей не годятся) → `govulncheck` → `go test -race`. Не отключать `errcheck` (антипример miniflux/gotify — осознанно отвергнут).
