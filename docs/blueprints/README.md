# Архитектурные блюпринты

Дом для **per-component архитектурных блюпринтов** — авторитетных референсов «как устроено и как писать код» для каждого компонента NOX. Блюпринт описывает слои, паттерны, DI, конвенции и пошаговый скаффолдинг компонента. Сейчас у NOX один компонент — кросс-платформенный Flutter-клиент (пакет `nox_app`, таргеты iOS/Android/Windows/Linux/macOS); по мере появления новых компонентов каждый получает свою папку `blueprints/<component>/` со своим `README.md`.

> **Чем блюпринт отличается от соседей по `docs/`:** `blueprints/` = **как строить** (архитектура/паттерны реализации, DI, конвенции, скаффолдинг); [`../design/`](../design/spec/README.md) = **как выглядит** (UI/UX-спека и дизайн-система); [`../vision.md`](../vision.md) + [`../requirements.md`](../requirements.md) = **зачем / что** (видение продукта и функциональные требования); [`../../specs/`](../../specs/) = **спецификации фич** (Spec Kit; per-feature контракты лежат в `specs/NNN-*/contracts/`).
>
> **Контракты бэкенда вынесены намеренно.** Транспортный протокол, модель синхронизации и сервер NOX ещё не выбраны, поэтому отдельного каталога контрактов (`spec/`) пока нет: сетевые/auth/envelope/endpoint-специфики в блюпринте помечены как **пример/TBD** и заменяются на реальный контракт, когда бэкенд будет выбран.

## Правила работы с блюпринтом

Связывающие правила для `mobile/` (AI-binding) зафиксированы в корневом [`CLAUDE.md`](../../CLAUDE.md) (раздел *«Flutter architecture blueprint»*) и в ратифицированной конституции [`.specify/memory/constitution.md`](../../.specify/memory/constitution.md) (Принцип III): **(1)** в начале любой Flutter/клиентской задачи (на всех пяти таргетах) — сверяться с блюпринтом и строить по нему; **(2)** docs-in-sync — при расхождении реального кода и блюпринта расхождение чинится в том же change-set'е (правится код либо сам блюпринт). Новый компонентный блюпринт добавляется отдельной папкой `blueprints/<component>/` со своим `README.md`.
