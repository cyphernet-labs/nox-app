## 1. Задача

Пользователь развернул свой client-сервер. Нужно, чтобы приложение узнало о нём, убедилось, что это именно он, и получило право с ним работать — за один жест пользователя и без ввода адресов.

Неснимаемое ограничение: **дома за CGNAT входящее соединение невозможно на уровне сети провайдера.** Раз домашнее железо в scope, схема обязана работать и там, не заставляя приложение знать о вспомогательной инфраструктуре.

## 2. Части решения

| Часть | За что отвечает | Есть сейчас? |
|---|---|---|
| Приложение (Flutter, 5 платформ) | Единственный клиент. Держит сокет к своему client-серверу, пинит его ключ, хранит ключ устройства | 🟡 UI есть, транспорта нет |
| Client-сервер | Принимает сообщения 24/7, хранит недоставленное, отдаёт данные приложению. Свой у каждого пользователя (или круга) | 🔴 нет |
| Публикатор адреса | Даёт client-серверу адрес, по которому он достижим извне: либо собственный белый IP, либо назначенная туннельная точка | 🔴 нет |
| Артефакт спаривания | Ссылка (она же QR), несущая адрес, ключ и одноразовый токен | 🔴 нет |
| Relay-сервер | Держит учётные данные APNs/FCM и отправляет пуши (§3.1) | 🔴 нет, вне этого документа |

## 3. Взаимодействие

Приложение разговаривает **только** со своим client-сервером. Один сокет, один адрес, один пиннутый ключ.

Client-сервер отдельно разговаривает с relay-сервером — но это его собственная связь, и приложение о ней не знает и знать не должно.

**Связи, которых намеренно НЕТ** (читатель обычно домысливает лишние стрелки):

- приложение ↔ relay-сервер — **отсутствует**; в приложении нет ни адреса релея, ни понятия о нём;
- байты файлов по сокету — **не ходят**, для них отдельные HTTP-запросы к тому же client-серверу;
- push при убитом приложении — **не через сокет**, это APNs/FCM (§3.1).

### 3.1. Почему APNs и FCM обязаны быть на relay-сервере

Не выбор архитектуры, а ограничение платформ, которое обойти нельзя.

Чтобы отправить пуш **в конкретное приложение**, нужно предъявить учётные данные, привязанные к **издателю этого приложения**: у APNs — ключ (`.p8` или сертификат), привязанный к bundle id и Apple Developer Team; у FCM — service account проекта Firebase, привязанного к package name. Device token, который телефон получает от ОС, действителен **только для пары «это приложение + эти учётные данные»**.

Отсюда следствие: чтобы client-сервер пользователя мог послать пуш в NOX, ему нужны были бы **наши приватные ключи**. Раздать их всем пользователям невозможно — любой, кто их достанет, сможет слать пуши всем клиентам NOX. Поэтому:

1. **Ключи живут в одном месте** — на relay-сервере. Не копируются в пользовательские инстансы даже в управляемом варианте.
2. **Пуш физически не может идти по сокету:** приложение в этот момент убито, сокета не существует, будить его умеет только ОС через APNs/FCM.

Это подтверждено разбором Snikket по их коду (`docs/research/snikket-fit.md` §4): их самостоятельно поднятый сервер **навсегда зависит** от двух хостов компании, и в quickstart об этом не сказано ни слова. К тому же выводу независимо пришли Zulip, Mattermost, Rocket.Chat, Prosody и Delta Chat.

Что при этом остаётся в нашей власти — **насколько релей слеп**: содержимое пуша шифруется, а на Android он вообще вырождается в контентно-пустой «звонок в дверь». Механика — там же, §4.3–4.5.

**Цена для пользователя — ноль:** в мастере установки client-сервера push не упоминается.

## 4. Контракты и форматы

### 4.1. Ссылка спаривания

```
https://nox.app/p/#<base64url(payload)>
```

Всё после `#` браузер на сервер **не отправляет** — фрагмент обрабатывается только клиентом. Поэтому одну и ту же страницу можно использовать, чтобы отрисовать QR прямо в браузере, а наш веб-сервер payload при этом не увидит.

Universal link, а не своя схема `nox://`: если приложение установлено — открывается оно; если нет — открывается веб-страница со ссылкой на скачивание. Своя схема во втором случае даёт тупик.

### 4.2. Payload

| Поле | Что | Размер |
|---|---|---|
| `version` | версия формата | 1 байт |
| `flags` | тип хоста (IPv4 / IPv6 / имя), наличие токена | 1 байт |
| `port` | порт | 2 байта |
| `host` | адрес | 4 / 16 / переменной длины |
| `server_key` | публичный ключ client-сервера (Ed25519) | 32 байта |
| `claim_token` | одноразовый токен спаривания | 16 байт |

Итого ~56 байт → **около 75 символов base64url**. QR невысокой плотности, уверенно сканируется с экрана.

Отдельного id сервера нет — он выводится из `server_key`. Ключ **самосертифицирующийся**: доказать право на этот id может только владелец приватной половины.

### 4.3. QR

QR несёт **ту же самую ссылку** целиком, не отдельный формат. Одна кодировка, один парсер, один набор тестов.

### 4.4. Спаривание

1. Приложение разбирает payload → `host:port`, `server_key`, `claim_token`.
2. Открывает `wss://host:port/`.
3. **Сверяет ключ на том конце с `server_key`.** Не совпал — обрыв, ошибка, **без кнопки «всё равно продолжить»**.
4. Генерирует у себя пару ключей устройства, отправляет `pair` с `claim_token` и публичной половиной.
5. Client-сервер проверяет токен (не использован, не протух), записывает ключ устройства как авторизованный, токен сжигает.
6. Дальше каждое подключение приложение подписывает ключом устройства.

Пароля и любого другого секрета-предъявителя в схеме **не существует**. Приватный ключ рождается на устройстве и никогда его не покидает.

### 4.5. Протокол после спаривания

Постоянный WebSocket поверх TLS, модель publish/subscribe. Полный инвентарь — `docs/protocol/wire-surface.md`: **17 команд, 6 событий**. Конверт (корреляция команда↔ack, коды ошибок) не зафиксирован — зависит от Q1a.

Порт по умолчанию **443**: через него исходящие соединения проходят в корпоративных сетях, отелях и за captive-порталами. Публичный сертификат не нужен — ключ пинится из ссылки, значит на client-сервере достаточно самоподписанного. Ни домена, ни ACME, ни продления.

## 5. Установка client-сервера

### 5.1. Верхний уровень — что делает пользователь

| Шаг | Действие | Облако | Дома |
|---|---|---|---|
| 1 | Выбирает площадку | VPS у любого провайдера | Raspberry Pi / NAS / старый ПК |
| 2 | Разворачивает | образ из маркетплейса или одна команда | готовый образ на карту |
| 3 | Задаёт параметры | см. §5.3 — все со значениями по умолчанию | то же |
| 4 | Получает ссылку | в выводе установки | на локальной странице коробки |
| 5 | Открывает ссылку в браузере | видит QR | видит QR |
| 6 | Сканирует приложением | готово | готово |

Ни IP, ни портов, ни ключей пользователь не видит.

### 5.2. Нижний уровень — что происходит при первом запуске

1. Генерируется пара ключей client-сервера; id выводится из публичной половины.
2. Выпускается самоподписанный TLS-сертификат на этом ключе.
3. **Определяется публичный адрес** (§5.4).
4. Генерируется одноразовый `claim_token`, 16 байт, с TTL.
5. Собирается payload → ссылка; она печатается в вывод установки и показывается на локальной странице.
6. Client-сервер ждёт спаривания.
7. После первого успешного claim токен сгорает, и **повторное спаривание возможно только с доступом к самой машине** — иначе тот, кто перехватил ссылку, заберёт сервер себе.

### 5.3. Конфигурация

| Параметр | По умолчанию | Когда менять |
|---|---|---|
| каталог данных | зависит от площадки | своя точка монтирования |
| лимит диска | **обязателен**, конечное значение | больше вложений |
| порт | 443 | занят другим сервисом |
| TTL недоставленного | конечный | политика хранения |
| режим адреса | автоопределение | принудительно туннель или прямой |

⚠️ Лимит диска обязан иметь конечное значение по умолчанию. У Snikket `SNIKKET_UPLOAD_STORAGE_GB` без лимита — пользователь узнаёт об этом, когда диск кончился.

### 5.4. Как client-сервер получает адрес

Это единственное место, где облако и дом расходятся, и расхождение **не доходит до приложения**.

- **Есть белый IP** (обычный VPS) — адрес и есть этот IP. Ничего дополнительного не нужно.
- **Белого IP нет** (дом за CGNAT) — client-сервер поднимает исходящий туннель и получает назначенную точку входа. В ссылку идёт её адрес.

Для приложения оба случая **неразличимы**: в ссылке лежит адрес, приложение к нему подключается и пинит ключ.

Требование к туннелю: **TLS терминируется на client-сервере пользователя**, туннель маршрутизирует по SNI и содержимого не видит. Референс — SniTun (Apache-2.0, в проде у Home Assistant Cloud). Плюс приложение пинит ключ client-сервера, поэтому подменить его туннель не может даже теоретически.

## 6. Решения и отклонённые альтернативы

| Решение | Выбрали | Отклонили | Почему | Пересмотреть, если |
|---|---|---|---|---|
| Кто кого находит | Адрес в ссылке, приложение соединяется напрямую | Маршрутизация через релей по id сервера | Решение владельца: приложение не должно знать о релее | Захотим убрать зависимость от статичности адреса |
| Учётные данные | Ключевая пара, сгенерированная на устройстве | Пароль (как у Snikket) | Нечего перехватить и нечего утечь; отзыв устройства даром | Понадобится вход на новом устройстве без старого — тогда нужен код восстановления |
| Доверие к серверу | Пиннинг ключа из ссылки | Публичный CA + домен | Убирает домен, регистратора, ACME и продление | Понадобится доступ из браузера |
| Формат артефакта | Universal link, QR = та же ссылка | Своя схема `nox://` | Без приложения своя схема даёт тупик | — |
| Транспорт | WebSocket поверх TLS, порт 443 | gRPC, SSE, raw TCP | Двунаправленный, проходит через middlebox'ы, есть в Dart на всех 5 платформах | Понадобится мультиплексирование и backpressure |
| Файлы | Отдельные HTTP-запросы к тому же client-серверу | Бинарные фреймы в сокете | Head-of-line blocking, нет докачки, буферизация в память | — |
| Дом за CGNAT | Туннель на стороне client-сервера | Проброс портов / отказ от домашней площадки | Проброс за CGNAT невозможен, а площадку владелец оставил в scope | — |

## 7. Пограничные случаи

| Случай | Что происходит | Решено? |
|---|---|---|
| Ключ сервера не совпал с тем, что в ссылке | Обрыв и ошибка. Кнопки «продолжить» нет | 🟢 |
| Ссылку перехватили раньше владельца | Кто первый — тот и владелец. Митигация: короткий TTL, одноразовость, запрет повторного claim без доступа к машине | 🟢 |
| Токен протух | Спаривание отклонено; новый токен выпускается с машины | 🟢 |
| IP сервера сменился | Уже спаренные устройства теряют его — помнят адрес из ссылки | 🔴 **не решено** |
| Приложение переустановили | Ключ устройства утерян → нужен повторный claim или код восстановления | 🔴 **не решено** |
| Телефон утерян | Ключ был только на нём | 🔴 **не решено**, см. §7 реестра |
| Второе устройство | Спаренное выпускает новое приглашение — тот же формат, другой тип токена | 🟡 механизм ясен, детали нет |
| Client-сервер лежит | Приложение показывает офлайн-состояние. Сейчас `ConnectivityService` знает только про интернет устройства — нужно второе понятие «жива ли сессия» | 🟡 |
| Нет камеры для QR | Нужен вводимый вручную путь. Наш адрес и ключ длинные, руками не набираются | 🔴 **не решено** |
