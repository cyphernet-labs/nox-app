# Инвентарь операций на проводе: что приложение обязано уметь сказать client-серверу

> **Назначение.** Полный перечень операций, которые пересекают границу «приложение ↔ client-сервер». Это вход для проектирования протокола: пока перечень неполон, протокол писать нельзя — забытая операция ломает его после релиза.
>
> **Дата:** 2026-08-04. **Метод:** четырёхлинзовый скан кодовой базы (presentation, domain+data, продуктовая модель, транспорт) плюс adversarial-проверка полноты по независимому свипу. 105 операций до дедупликации, все с привязкой к `path:line`.
>
> **Статус:** черновик для обсуждения. §2 содержит пять находок, которые надо решить **до** проектирования протокола.

## 1. Итог в цифрах

| | Сколько |
|---|---|
| Команд «приложение → client-сервер» | **17** |
| Событий «client-сервер → приложение» | **6** |
| Операций вне сокета (HTTP / APNs) | **3** |
| Строго локальных (на провод не выходят) | 6 групп |

Первоначальная оценка «5–10 команд» оказалась вдвое оптимистичной. При этом модель открытого пространства действительно сильно экономит: нет подписок, ростера, управления членством и presence — обычно это половина протокола мессенджера.

Важнее другое: **из 17 команд сегодня по-настоящему реализованы 4.** Остальные либо подделаны локально (проверка занятости имени идёт против константного `Set` в коде), либо отсутствуют вовсе. Приложение живёт в закрытом мире: **оно никогда ничего ни от кого не получает.** Все шесть входящих событий — новые.

## 2. Пять находок, которые надо решить до протокола

### 2.1. 🔴 Идентификатор входа утекает в каждое сообщение

**Это дыра безопасности в текущей модели, а не деталь протокола.**

Приложение отличает свои сообщения от чужих сравнением `authorId` из полезной нагрузки с идентификатором устройства:

```dart
final isOwn = m.authorId == currentId;              // app_thread_view_widget.dart:212
```

а `currentId` разрешается в `session.identifier` (`identity_resolver.dart:21`) — **ту самую строку, которую пользователь вставляет или сканирует при входе** и которая лежит в `flutter_secure_storage`. Это же закреплено нормативно в `overview.md:97`.

В открытом общем пространстве каждое сообщение видно всем. Значит, если `author_id` на проводе равен идентификатору входа, **каждое сообщение публикует учётные данные своего автора всем остальным**. Наш собственный текст в приложении говорит: «Keep your identifier safe; anyone who has it can sign in as you» (`app_en.arb:49`), а экран 7.1 прячет идентификатор за `••••••••` с отдельными кнопками Show/Copy — именно потому, что это секрет.

Обратная развилка не бесплатна: если сервер выдаёт отдельный публичный `user_id`, то определение «свой/чужой» **молча инвертируется** — все свои сообщения станут рисоваться как чужие (левое выравнивание, другой цвет пузыря, появится заголовок автора, исчезнет глиф статуса `sent`/`pending`/`error`, который показывается только для своих).

И положить публичный id сегодня некуда: `SessionModel` — это `{identifier, label, onboardingComplete}`, `resolveIdentity` возвращает `({id, label})`, `ChatThreadState.currentId` — одна строка.

**Что решить:** либо сервер выдаёт публичный `user_id` отдельно от секрета входа (тогда меняются `SessionModel`, `resolveIdentity`, `ChatThreadState` и хранение), либо идентификатор становится настоящим публичным ключом, а для хендшейка заводится отдельный приватный секрет — но тогда переспецифицировать надо и `saveIdentifier`, и QR-конверт `nox://id/<identifier>`, который сейчас показывают другим людям.

### 2.2. Вход умеет ровно одну ошибку, а спека требует двух

`login.md:40` определяет inline-ошибку как «сервер вернул неверный формат **или** произошла ошибка сети», и `login.md:43` проводит границу: формат и сеть — inline, всё остальное — фатальный экран 3.1.

Статус `LoginStatus.errorFormat` существует, и `login_page.dart:189` уже рисует для него `Invalid identifier`. Но в реальном потоке `login_bloc.dart:59-62` схлопывает **любую** ошибку `signIn` в `errorNetwork` — то есть готовая ветка UI недостижима.

Это важно структурно: клиент **принципиально не валидирует идентификатор** (FR-011, `canSubmit` — это только «поле непустое»). Сервер — единственное место, где кривой идентификатор вообще может быть пойман. Если протокол отдаст один общий код ошибки, пользователь с обрезанным ключом будет вечно видеть «проверьте соединение», хотя с соединением всё в порядке.

**Что решить:** `auth.signIn` должен отдавать трёхчастный исход — успех, типизированный отказ `invalid_identifier`, транспортный сбой. Всё остальное → фатальный экран.

### 2.3. «Файл удалён сервером» — отдельный исход, и обработчика для него нет

`file-view.md:14` называет две фатальные ветки из 5.3, и первая — «файл удалён сервером»: она ведёт на экран 3.1, а не на inline-повтор.

Продакшн-путь `_startDownload()` (`file_view_page.dart:92-105`) **не имеет ветки отказа вообще**: он либо коротко замыкается на локальный файл, либо докручивает анимацию до конца. Состояния «файл пропал» в `_FileViewPageState` не существует. То, что выглядит как готовый обработчик ошибки, — это `_simulateError()`, доступный только из dev-меню галереи.

Для нас это особенно актуально: чаты не удаляются никогда, а вот **байты вложений вполне могут вычищаться по TTL** — ресёрч склоняется к ограниченному спулу, а не к полному архиву.

**Что решить:** отдельный код `attachment_gone` (→ 3.1) против транспортной ошибки (→ inline-повтор), плюс поле срока хранения в DTO вложения, чтобы клиент мог погасить кнопку Save заранее, а не узнавать об этом при открытии.

### 2.4. Ограничений на размер нет нигде

У поля ввода сообщения `minLines: 1, maxLines: 6` — это визуальный предел прокрутки, и всё. Ни `maxLength`, ни `inputFormatters`. Во всём `lib/` `maxLength` встречается четыре раза, и все — на именах (32 для label, 64 для имени чата). Единственная проверка в отправке — «текст непустой или есть вложение».

Значит, вставка строки на 50 МБ станет одним фреймом `message.send`, оптимистично отрисуется, запишется в базу по ack — и в открытом пространстве без удаления разойдётся всем навсегда. На постоянном сокете она вдобавок **заблокирует все интерактивные команды** на этом соединении (head-of-line blocking).

То же самое с вложениями: лимита размера нет нигде в репозитории.

**Что решить:** хендшейк должен приносить объявленные сервером лимиты — `max_message_bytes`, `max_attachment_bytes`, `max_frame_bytes` — плюс типизированный отказ `payload_too_large`. На клиенте это новая работа в двух местах: ограничитель в композере и предполётная проверка размера в `_onAttachmentPicked`.

### 2.5. Нет способа получить один чат по id

`ChatRepository` умеет `getChats` (страница списка) и `watchChat` — но `watchChat` **локальный по построению**: это стрим записи Sembast, который отдаёт `null` для отсутствующего чата и намеренно не запускает подсев. Все экраны принимают целый `ChatModel`, а не id.

Три реальных пути ломаются без такой операции:

1. Входящее `message.new` или `chat.created` для чата **за пределами загруженного префикса** — существующий механизм «тик → перечитать страницы 1..N» структурно не может достать чат, которого в префиксе нет. Строка и её счётчик непрочитанного просто теряются.
2. Открытие чата по тапу на пуш из холодного старта, когда у клиента есть только id.
3. Восстановление выбранного чата на десктопе.

**Что решить:** либо команда `chat.get {chat_id}`, либо входящие события несут полный `ChatWireEntity` внутри себя. Первое решает все три пути, второе — только первый.

### 2.6. Отдельно: непрочитанное — на устройстве или на сервере?

Противоречие, которое надо снять явно. Спека делает непрочитанное **строго устройство-локальным**: «считается от последнего открытия чата **этим устройством**; никогда не открытый чат бейджа не имеет» (`chats-list.md:36`, `overview.md:104`). А `ChatWireEntity` уже везёт `unread_count` как серверные данные, и моки сеют ненулевые счётчики (3, 12, 142) на чаты, которые никто не открывал, — что прямо нарушает это правило.

При этом представить правило спеки сегодня нельзя ни на одной стороне: в `ChatEntity` только `int unreadCount`, без `lastOpenedAt` и без флага «открывался».

## 4. События «client-сервер → приложение»

Все шесть — новые: сегодня входящего канала нет вообще.

| Событие | Когда | Что должно произойти в клиенте |
|---|---|---|
| `message.new` | Кто-то написал в чат | Вставка в тред, если открыт; инкремент непрочитанного; обновление превью и порядка в списке |
| `chat.created` | Кто-то создал чат | Появление строки в списке — **включая случай за пределами загруженного префикса** (§2.5) |
| `chat.updated` | Переименование, изменение превью или порядка | Уже есть готовый механизм: `WatchChat` разнесёт по всем поверхностям без перезагрузки |
| `label.assigned` | Сервер назначил `User<random>` при первом входе | Сегодня это захардкоженная константа `User7421` |
| `session.expired` | Сервер разорвал сессию | Должно попасть в тот же путь, что и нынешний `401 → logout(forced)`, чтобы сработал существующий снекбар |
| `ack` / `error` | Ответ на команду | Корреляция по id. Сегодня защита от устаревших ответов сделана **сравнением значений**, а не идентификаторов — на мультиплексированном сокете так нельзя |

## 5. Ловушка на пути Skip

Найдено проверяющим и стоит отдельного абзаца, потому что это не косметика.

`resolveIdentity` подставляет `User7421` только когда `session.label` пуст. Пользователь, выбравший имя, этой константы не увидит никогда. А вот тот, кто нажал **Skip**, попадает в `completeOnboarding()` **без label** — и `session.label` остаётся пустым навсегда.

Последствие: `sendMessage` штампует `authorLabel: 'User7421'` в **каждое** его сообщение, это денормализуется в `MessageWireEntity.author_label`, пишется в базу и рисуется всем остальным как заголовок автора. То есть **все Skip-пользователи схлопываются в один и тот же label** — в пространстве, где label обязан быть глобально уникальным.

**Вывод для протокола:** назначенный сервером `User<random>` должен быть реальным значением из ответа на вход, которое клиент сохраняет и на пути Skip тоже.

## 6. Что не идёт по сокету

| Что | Куда вместо | Почему |
|---|---|---|
| Байты файлов | Отдельные HTTP-запросы по токену, полученному через сокет | Нет range-запросов (значит нет докачки), нет потоковой записи на диск без буферизации, и большой файл блокирует все интерактивные команды на том же соединении |
| Доставка при убитом приложении | APNs / FCM через релей компании | Сокета в этот момент не существует |
| Первое соединение | Спаривание по QR | Чтобы открыть сокет, надо уже знать адрес и чей ключ доверять |

## 7. Что остаётся строго локальным

Проверено — на провод не выходит:

- **Настройки:** тема, язык, переключатель уведомлений (`SharedPreferences`).
- **Разрешения ОС:** камера, уведомления.
- **Статус сообщения** `sent`/`pending`/`error` — по продуктовой модели локальный, доставки и прочтения нет.
- **Кэш чатов и сообщений** в Sembast — проекция, а не источник истины.
- **`getChatFiles`** — намеренная локальная выборка по вложениям из кэша сообщений (удалённый источник был осознанно ретайрен в фиче 017). Станет сетевой операцией **только если** история начнёт обрезаться на сервере — тогда панель 5.4 начнёт молча недоговаривать.
- **Выбор файла** (`FilePickerService`) — работа с ОС.

## 8. Транспортные требования

Из скана, всё привязано к реальному коду:

- **Жизненного цикла соединения в приложении нет вообще** — ни connect/reconnect, ни backoff, ни состояния «подключаемся» в UI. `ConnectivityService` отвечает только «есть ли интернет у устройства». Нужно второе понятие: «жива ли сессия с client-сервером», и offline-баннер должен слушать именно его.
- **Гонка на старте:** сплеш отпускает навигацию по **локально** разрешённому состоянию, поэтому список чатов рисуется раньше, чем существует сокет. Протокол обязан определить, что показывать в этом окне.
- **Очередь исходящих** сегодня живёт в `ChatThreadBloc` (оптимистичная отправка, `pending`/`error`, повтор, слив очереди по фронту «офлайн → онлайн»). Ей место в data-слое: чтобы работала для всех команд и переживала перезапуск приложения.
- **Идемпотентность:** переотправка `message.send` после реконнекта без `clientMessageId` даст дубликаты.
- **Таймаут отправки:** спека требует перевода в `error` по таймауту (`overview.md:154`) — такого таймера в клиенте нет.
- **Аутентификация одноразовая**, при установлении соединения, а не на каждый запрос, как сейчас в `AuthInterceptor`.
- **Keepalive обязателен:** сотовые NAT сбрасывают простаивающие сопоставления секунд за 30, а полуоткрытый TCP выглядит живым с обеих сторон.
- **Реконнект с джиттером:** без него перезапуск client-сервера превращается в лавину.
- **Версия схемы** в хендшейке — приложение и client-сервер будут обновляться независимо.

## 9. Что дальше

1. **Решить §2.1** (публичный id автора) — это меняет доменную модель и хранение сессии, не только провод. Блокирует протокол.
2. **Решить §2.6** (непрочитанное на устройстве или на сервере) — определяет, есть ли `chat.markRead` вообще.
3. **Решить Q1a** из [реестра](../research/open-questions.md) — где заканчивается E2EE. Полезную нагрузку сообщения можно спроектировать как непрозрачный блоб и оставить это одним явным швом, но решение всё равно нужно.
4. После этого — черновик протокола: конверт, корреляция, коды ошибок, жизненный цикл соединения.
5. Параллельно и независимо от протокола можно делать клиентскую подготовку: транспортный интерфейс с loopback-реализацией, состояние сессии в домене и UI, очередь команд в data-слое, спаривание и хранение адреса с пиннутым ключом.
